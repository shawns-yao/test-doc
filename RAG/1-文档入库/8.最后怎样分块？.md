**最后分块，是把已经恢复结构、清洗完成的文档，组织成适合检索的内容片段。核心不是“每块多少字”，而是“哪些内容必须放在一起，拆开后怎样找回上下文”。**

前面如果已经丢失图片、读错表格或弄乱阅读顺序，分块不能自动修复。

**1.正文怎样分块**  
优先按照章节、段落、句子边界划分，长度只是约束，不应该成为唯一依据。

例如：

> 产品支持退款。仅限购买后七天内、尚未激活的产品。

不能把“支持退款”单独分成一块，把限制条件放到一个没有关联的块中。否则后面只检索到前半句，就可能回答错误。

正文分块需要注意：

- 短小且完整的段落可以直接成为一块。
- 连续解释同一个问题的段落，可以合并。
- 过长段落再按照句子拆分。
- 不同章节不能仅仅为了凑足长度而拼在一起。
- 标题路径应该随内容保留，例如“售后政策 → 退款条件”。

**2.表格、图片、公式怎样分块**  
这些内容不能完全沿用普通正文的切分方式。

|内容|合理的处理方式|
|---|---|
|短表格|尽量整体保留，带上表格标题、表头、单位和必要注释|
|长表格|按完整行或逻辑行组拆分，每块继承对应表头；合并单元格涉及的关系不能丢失|
|图片、截图|保留原图引用，将 OCR、图片说明和相关正文建立关联；内容过长时可以拆成多个关联块|
|公式|尽量保持公式完整，同时保留变量定义、单位和适用条件|
|脚注、例外条件|与它限制或解释的正文、表格关联，不能成为没有指向的孤立块|

比如，一张参数表拆成三块，后两块只有“型号、数字”，没有表头和单位，虽然文字没有丢失，但已经不容易正确理解。

图片也不是必须把“原图、全部 OCR、前后正文”硬塞进一个巨大块。**可以分别存储，但必须知道它们属于同一张图、解释哪段正文。**

**3.块大小、重叠、父子分块**  
块太小容易缺少条件和解释；块太大容易把无关内容混在一起，降低检索精度。

因此应该先确定结构边界，再检查长度。最终要符合实际嵌入模型的输入限制，字符数不能直接当作 Token 数。

**重叠**用于保留边界附近的上下文，例如前一块末尾的完整句子。但不能靠大量重叠补救错误的结构拆分，也不能把这种有意保留的重复当成清洗噪声删除。

**父子分块**则是：

- 父块保存较完整的章节或内容范围。
- 子块保存较小、便于匹配的内容。
- 子块命中后，可以通过关联关系补充父块上下文。

它解决的是“小块方便检索、大块方便理解”的矛盾，不会自动识别所有条件、图片关系或复杂表格。

**4.两个项目实际怎样做**  
以下是已读取的代码行为和源码默认值，不代表当前知识库正在使用这些配置。

**MimirQ：**

- 默认采用递归字符分块，默认大小 **1000 个字符**，重叠 **200 个字符**，优先寻找段落、换行和句子边界。
- 这个默认实现会把整个 HTML 表格保留为一块，因此长表格可能超过目标大小。
- 另有 PDF 位置块、Markdown 表格和父子分块策略，需要实际选择才会使用。
- Markdown 表格专用策略按照整行拆分，但后续块的表头保存在元数据中；不能据此认定它已经进入嵌入文本。

**WeKnora：**

- 分块器源码默认大小为 **512 个字符**，重叠 **80 个字符**。
- 提供标题、启发式和自动选择等策略，但当前代码中，策略为空走的是旧分块器，并不自动等于 `auto`。
- 对 Markdown 表格、图片引用、代码块和 `$$…$$` 公式有结构保护，并有延续表格补表头的处理。
- 保护存在长度限制，不能保证所有长表格、复杂表格和公式都不会被拆坏；也提供父子分块和可选的近似 Token 长度约束。

**两者还有一个共同注意点：**所检查的图片 OCR 子块生成路径，都没有把识别文字重新交给主文档分块器。因此正文分块配置，并不天然约束这些图片派生块。

**5.最终应该怎么使用**  
比较合理的原则是：**结构优先，长度受控，上下文可补，来源可追溯。**

每个块保留文档及版本、标题路径、页码、原文位置，以及必要的父子、图片、表格关联。标题、表头、单位和适用条件不能仅仅“存进元数据就算完成”，还要确保它们能够进入检索文本或可靠地补入问答上下文。

最终链路是：

**结构化内容 → 确定内容单元 → 拆分过长单元 → 补齐必要上下文 → 保留来源和关联 → 校验输入长度 → 建立索引。**

没有通用的最佳块大小，需要结合你的 PDF 和实际问题验证。
