# 1.1 网站访问量升高后，如何保证网站不挂掉？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>核心思路是"分层削峰、逐级保护"——让流量尽量在离用户最近、成本最低的层级被消化，不直接压到数据库。同时先做容量评估（压测摸清各层上限），再按层部署防护。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">分层治理手段：</b>① <b>CDN/静态化</b>：静态资源、图片走 CDN，动态页面部分缓存；② <b>缓存</b>：Redis 缓存热点数据，扛住大部分读；③ <b>异步削峰</b>：写请求进 MQ，后端按能力消费；④ <b>限流熔断</b>：网关限流（令牌桶）、熔断保护下游；⑤ <b>水平扩容</b>：无状态服务多实例 + 负载均衡；⑥ <b>降级兜底</b>：非核心功能（推荐、详情）降级返回默认，保核心链路。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>先找瓶颈再扩容——瓶颈可能在数据库连接、单点组件（如单 Redis）、带宽；扩容前先确认服务无状态化（Session 外置到 Redis）；缓存要防穿透/击穿/雪崩，否则流量照样打崩 DB。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>无限扩容成本高，要有容量上限和过载保护（限流拒绝比挂掉好）；降级影响用户体验，要提前定义降级策略；监控告警要能在大促前发现容量缺口。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>压测定容量基线 → 核心链路梳理（哪些必须保）→ 网关限流 + 缓存 + 异步化 → 大促预案（扩容、降级开关、监控大盘）→ 复盘调参。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>限流算法有哪些（令牌桶/漏桶/滑动窗口）区别；怎么定位瓶颈（监控 + 链路追踪 + 压测）；缓存和数据库一致性怎么处理（Cache Aside）；为什么无状态化才能水平扩容（Session 不落本机）。</div>

# 1.2 接口处理很多且很慢，如何定位与优化？数据库已经没有可优化空间后，还有哪些可能原因？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>定位慢接口要"先分层、再下钻"：从链路耗时分布找最慢的段，而不是瞎猜。定位工具：链路追踪（Trace 各 span 耗时）、APM、慢日志、火焰图。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">排查流程（步骤）：</b>① <b>看链路</b>：Trace 里接口耗时分解——网络/网关/服务内/DB/RPC/外部调用各占多少；② <b>看应用</b>：CPU 高（计算密集/死循环）、GC 频繁（内存问题）、线程池耗尽（任务堆积）、锁等待（竞争/死锁）；③ <b>看数据库</b>：慢 SQL、连接池打满、锁等待、主从延迟；④ <b>看下游</b>：RPC/MQ/第三方 API 延迟；⑤ <b>压测复现</b>：隔离变量确认根因。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">数据库没空间后还有哪些原因：</b>① <b>跨服务调用</b>：下游 RPC 慢/超时重试放大；② <b>GC 停顿</b>：Full GC 导致长暂停；③ <b>线程池/连接池耗尽</b>：任务排队而非执行慢；④ <b>锁竞争</b>：分布式锁、JVM 锁、数据库锁；⑤ <b>序列化/带宽</b>：大对象序列化、网络传输慢；⑥ <b>外部依赖</b>：第三方 API、DNS、证书；⑦ <b>磁盘/网络 I/O</b>：日志刷盘、磁盘满；⑧ <b>热点数据</b>：CPU 缓存失效、单 key 热点。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>"慢"要先分是<b>执行慢</b>还是<b>排队慢</b>（线程池/连接池指标）；P99 和平均值要一起看（平均好看但 P99 爆炸说明有尾部延迟）；优化后必须压测验证。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>没有链路追踪时定位靠猜，效率极低；盲目加缓存/加线程掩盖真实瓶颈；超时和重试设置不当会造成雪崩（重试风暴）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>全链路 Trace + 关键指标大盘（P99、线程池活跃、GC、连接池）；慢接口拆解耗时画像；优化后对比压测报告；外部调用设超时 + 熔断防雪崩。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>怎么区分是应用慢还是数据库慢（链路耗时 + 数据库监控）；线程池打满为什么接口慢（排队）；Full GC 怎么定位（GC 日志 + 内存 dump）；重试风暴是什么（下游超时后大量重试叠加）。</div>

# 1.3 如何设计高并发访问下的库存校验？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>高并发库存校验的核心矛盾：校验（读）和扣减（写）必须原子，且不能把全部流量压到数据库。经典分层：本地预检 → Redis 原子扣减 → MySQL 条件更新兜底。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程（分层方案）：</b>① <b>本地预检</b>：进程内缓存库存快照，先过滤明显无货请求（秒级粗筛）；② <b>Redis 原子扣减</b>：Lua 脚本一次完成"库存 > 0 判断 + 扣减 + 记录用户"，避免先读后写竞态；③ <b>MySQL 兜底</b>：<code>UPDATE stock SET stock = stock - 1 WHERE id = ? AND stock &gt; 0</code> 条件更新，影响行数 0 即库存不足；④ 扣减成功才允许下单，失败回补。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>Redis 与 MySQL 库存要<b>对账</b>（定期比较差异，差异来自回补失败/超时重试）；库存扣减要<b>幂等</b>（同用户同单不能扣两次）；预扣（下单冻结）与实扣（支付成功）分离，超时自动释放。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>分布式锁粒度过大会串行化所有请求（不要全局锁，用 Lua/条件更新替代）；Redis 挂了要降级到数据库直扣（限流保护）；本地缓存可能短暂超卖（靠 DB 兜底拦截）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>秒杀/抢购场景：本地预检 + Redis Lua + DB 条件更新 + 对账任务；普通商品：Redis 缓存读 + DB 扣减；监控库存差异、扣减失败率和回补任务执行情况。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>为什么 Lua 脚本能保证原子（单线程执行整段脚本）；条件更新为什么能防超卖（行锁 + 条件判断原子）；预扣和实扣为什么分离（防恶意占用库存）。</div>
  </div>
</div>

# 1.4 如何保证抽奖的一致性，避免奖品扣减成功但抽奖失败？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>"奖品扣减成功但抽奖失败"的本质是<b>两个操作不在一个事务边界</b>——扣库存（写）和抽奖结果（写）分离导致部分成功。解决思路：要么同事务，要么用状态机 + 补偿保证最终一致。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">方案一（同事务强一致）：</b>抽奖动作和奖品扣减放<b>同一个数据库事务</b>：<code>BEGIN → 扣减奖品库存（条件更新）→ 写入中奖记录 → COMMIT</code>，任一步失败整体回滚，天然一致。适合单库、低频（如非秒杀抽奖）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">方案二（异步最终一致）：</b>抽奖结果先落库（状态=进行中），MQ 异步扣减奖品库存，消费者幂等处理；失败重试进死信，补偿任务扫描"已中奖但库存未扣"的记录重试或回滚。适合 Redis 扣减 + 异步落库的高并发场景。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>奖品库存扣减必须<b>幂等</b>（抽奖单号做唯一键）；用<b>状态机</b>管理抽奖单状态（待处理/已中奖/已发货/已回滚）；对账任务定期扫描状态不一致的单据；Redis 扣减成功但 DB 落库失败时，补偿要么补落库要么回补 Redis。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>强一致方案在高并发下锁竞争大；最终一致方案有延迟窗口（用户看到中奖但奖品未扣完）；补偿任务本身可能失败——要设计重试上限和人工介入通道。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>抽奖单号贯穿全链路；中奖结果先行 + MQ 扣库存 + 死信告警 + 对账补偿；监控"中奖未扣减"和"扣减未中奖"两类差异单；发货状态机推进。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>为什么不用分布式事务（2PC 性能差、可用性低）；最终一致怎么保证不丢（消息可靠投递 + 幂等消费 + 对账兜底）；回滚时 Redis 和 DB 的顺序（先恢复 DB 权威，再刷缓存）。</div>
  </div>
</div>

# 1.6 RPC 调用过程中内存已满，但网络缓冲区收到数据包时，程序还能正常收到吗？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>能。关键是区分两套内存：<b>内核网络缓冲区（socket 接收队列）</b>和<b>进程用户态堆内存</b>。数据包先由网卡/内核收进 socket 缓冲区，这一步不依赖进程堆内存；进程堆内存满（OOM 边缘）只影响"从内核缓冲区读出来放进堆"这一步。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程（数据到达路径）：</b>① 网卡中断 → 数据进内核接收队列（sk_buff）；② 进程调用 <code>recv</code>/read 把数据从内核缓冲拷贝到用户态缓冲区（堆上）；③ 应用解析、处理。内存满发生在第②步——内核缓冲区有数据，但堆上分配目标缓冲区失败或 OOM。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>① "内存满"要区分：JVM 堆满（可 GC 后继续）vs 系统内存耗尽（内核可能触发 OOM killer 杀进程）；② 内核缓冲区有独立内存池（不算进程堆）；③ 若进程完全不读，内核缓冲区会满 → 触发 TCP 窗口收缩/零窗口，对端停止发送（背压），最终可能丢包或连接卡死。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>应用读得慢 + 内核缓冲满 → 对端发送阻塞（TCP 流控生效）；系统内存真的耗尽时 OOM killer 可能直接杀进程，比"收不到数据"更严重；要监控堆使用率和 GC，而不是等 OOM。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>RPC 框架设置接收缓冲区上限 + 背压处理；Netty 的 <code>autoRead</code> 暂停读取形成反压；堆内存监控预警 + GC 调优；OOM 前 dump 保留现场。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>TCP 窗口和背压的关系（接收方窗口为 0 对端停止发送）；OOM killer 怎么选进程（内存占用评分）；内核缓冲区和用户缓冲区的区别（谁负责拷贝）。</div>

# 1.7 什么是领域驱动设计（DDD）？项目中的 DDD 如何分层？

  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>DDD（领域驱动设计）以<b>业务领域为核心</b>建模：业务专家与开发用统一语言（Ubiquitous Language）描述领域，识别<b>限界上下文</b>（业务边界）、<b>实体/值对象/聚合</b>（领域模型），让代码结构对齐业务结构，而不是被技术框架牵着走。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程（四层分层）：</b>① <b>接口层（Controller）</b>：HTTP/RPC 入参出参转换，不含业务逻辑；② <b>应用层（Application）</b>：用例编排（调仓储、领域服务、事务边界），不写业务规则；③ <b>领域层（Domain）</b>：核心——实体、值对象、聚合根、领域服务、领域事件，业务规则在这里；④ <b>基础设施层（Infrastructure）</b>：数据库、MQ、缓存实现，仓储接口的实现。依赖方向：外层依赖内层（依赖倒置，领域层不依赖基础设施）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>仓储（Repository）接口定义在领域层、实现在基础设施层——领域层不 import MyBatis/JPA；聚合根是事务一致性的边界；贫血模型（只有 getter 的"数据类"）vs 充血模型（行为在实体里）是 DDD 落地程度的标志。</div>

    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>告警/诊断域建模：告警聚合（实体+值对象+领域事件）；状态机放领域层（业务规则），Controller 薄层、仓储换实现不影响领域；新业务先画限界上下文再写代码。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>DDD 和传统三层（Controller/Service/DAO）的区别（业务规则位置、依赖方向）；聚合根是什么（一致性边界的入口）；贫血模型和充血模型；什么时候不适合 DDD（简单 CRUD/报表）。</div>

    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>秒杀的本质是"海量请求抢少量资源"，设计原则：<b>流量尽量在入口被拦截，核心写操作原子化，数据库只承担最终落账</b>。全链路：前端 → 网关 → 应用 → Redis → MQ → MySQL，每层都削峰。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程（全链路设计）：</b>① <b>前端/接入层</b>：按钮置灰、验证码、静态页面 CDN，拦截无效点击；② <b>网关层</b>：限流（令牌桶按用户/IP）、黑白名单、防脚本；③ <b>应用层</b>：本地库存预检（进程内缓存粗筛）+ 用户资格校验（已购/黑名单/频控）；④ <b>Redis 层</b>：Lua 脚本原子完成"库存 > 0 判断 + 扣减 + 记录用户"，<code>SETNX</code> 防重复抢购；⑤ <b>MQ 层</b>：发送秒杀成功事件，异步落单；⑥ <b>MySQL 层</b>：消费者幂等创建订单、条件更新扣库存兜底（<code>stock &gt; 0</code>），对账回补。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">Redis 和 MySQL 的职责边界：</b><b>Redis</b>：扛高频读写——库存预扣、资格判断、频控计数、结果缓存；<b>MySQL</b>：最终事实——订单、扣减流水、用户中奖记录；Redis 结果必须能由 MySQL 重建（Redis 挂了可以预热重建）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节（问题处理）：</b>① <b>限流</b>：网关令牌桶 + 用户维度频控 + 接口级配额，超限直接拒绝；② <b>缓存一致性</b>：Redis 预扣 → 异步落 DB → 对账；不一致时以 DB 为准回滚/回补 Redis；扣减事件幂等；③ <b>缓存雪崩</b>：库存 key 不过期（活动期永续）+ Redis 高可用（主从/哨兵/集群）+ 预热 + 降级开关（Redis 挂 → DB 直扣限流）；④ <b>缓存击穿</b>：库存 key 是热点，用 Lua 原子扣减天然避免"失效瞬间打爆 DB"。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>超卖风险：Redis 扣减与 DB 兜底之间的窗口（用 DB 条件更新兜底 + 对账）；恶意刷单：接口幂等 + 频控 + 风控；MQ 积压：消费者水平扩展 + 监控；Redis 故障：降级预案 + 容量冗余。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>活动前：压测定容量、预热库存、灰度开关；活动中：监控 Redis 扣减 QPS、MQ 积压、订单成功率、超卖差异；活动后：对账、回补、复盘调参；发奖异步化 + 状态机管理订单生命周期。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>秒杀为什么不直接扣数据库（行锁串行化，QPS 上不去）；Redis 扣了 MySQL 没扣怎么办（对账 + 回补）；怎么防止一个人抢多个（Redis 用户维度标记 + 幂等）；库存预热失败怎么办（降级直连 DB + 限流）。</div>
  </div>
</div>

# 1.13 异步任务如何降级？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3F8C12;">① 任务分级：</b>把异步任务分成三类——<b>核心必需</b>（失败影响主流程）、<b>重要可降级</b>（失败可用默认值）、<b>非核心可丢弃</b>（埋点、推荐补充信息）。没有分级就谈不了降级策略。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">② 每个分支必须有超时：</b>异步不等于无限等待——给每个分支设置独立超时（如 100ms/300ms），超时立刻返回 fallback，避免拖慢主链路（<code>completeOnTimeout</code> 或 <code>orTimeout</code>）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">③ 线程池隔离：</b>不同异步任务用不同线程池，防止一个慢依赖把全局异步池占满；配置有界队列和拒绝策略（常用 CallerRuns 或快速失败），把压力显式化。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">④ 熔断 + 限流：</b>下游错误率/超时率升高时快速熔断，短时间直接走降级结果；对高并发流量限流，避免雪崩放大。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">⑤ 监控与演练：</b>必须监控线程池队列长度、拒绝次数、熔断状态；降级不是事故才开，平时就可灰度演练。</div>
  </div>
  <div style="margin:10px 0 0;padding:8px 12px;border-left:3px solid #3F8C12;background:rgba(82,196,26,.08);border-radius:8px;font-size:13.5px;line-height:1.7;"><b style="color:#3F8C12;">口述重点：</b>异步降级的本质是把失败隔离在分支内，不让非核心能力反向拖垮主流程；关键手段是超时、隔离、熔断、限流和可用兜底。</div>
</div>

# 1.14 异步任务（视频生成类）如何排队、取消、重试、回调？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答（状态机 + 消息队列 + 回调投递器）：</b>
    <div style="margin:6px 0 0;"><b style="color:#3F8C12;">状态流转：</b>前端提交视频生成请求后先落任务表，状态从 CREATED 进入 QUEUED，投递进 MQ；Worker 消费执行进入 RUNNING，最终收敛到 SUCCEEDED / FAILED / CANCELED / TIMEOUT。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">排队：</b>入队时按<b>幂等键去重</b>，按优先级 + create_time 排序，再按租户做配额限制，避免大客户把全局资源打满。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">取消：</b>分两类——任务在排队中直接出队并置 CANCELED；已在运行中走 CANCEL_REQUESTED，Worker 在阶段边界轮询取消标记，安全释放 GPU 和临时文件。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">重试：</b>只针对可重试错误（超时、网络抖动），采用<b>指数退避加抖动</b>并限制最大次数，超过阈值进死信队列；不可重试错误（参数非法、内容违规）直接失败。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">回调：</b>采用「至少一次」投递，带签名和时间戳做鉴权，失败重试并入回调死信队列；回调接收方按 <code>task_id/event_id</code> 幂等消费。</div>

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答（拆、缓存、削峰、分治、兜底）：</b>
    <div style="margin:6px 0 0;">① <b>系统拆分</b>——大系统拆多个子系统，单机单库变分布式，每个子系统只承接一部分压力；② <b>缓存</b>——高并发大多是读多写少，热点数据放缓存让大部分请求不落数据库；③ <b>MQ 削峰</b>——大量写请求先灌 MQ 排队，后端按承载能力消费；④ <b>分库分表</b>——单库单表瓶颈时水平拆分摊平写入和存储压力；⑤ <b>读写分离</b>——主库写从库读，读流量大继续扩从库；⑥ <b>ES/检索引擎承接查询</b>——全文检索、复杂搜索、统计查询迁到 ES；⑦ <b>工程兜底</b>——限流、防刷、CDN、静态化、异步化、小事务、锁粒度优化、JVM/SQL 优化、灰度扩容。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">秒杀/大促场景补充：</b>不暴露真实秒杀地址、前端静态化、网关和 Redis 防刷限流、库存预热到 Redis 用 Lua 原子扣减、能异步的都异步（短信/积分/优惠券）、事务尽量小、并发控制细节（乐观锁/悲观锁/间隙锁/快照读/当前读/MVCC）必须清楚。</div>

# 1.16 分布式服务接口请求的顺序性如何保证？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">前提：</b>尽量从业务设计上<b>避免强顺序依赖</b>——引入严格顺序保证会带来系统复杂度上升、吞吐下降、热点 key 压力变大、排障恢复更麻烦。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">三类解法：</b>① <b>Hash 分发到同一机器</b>——按业务 ID 一致性 hash 路由到同一台机器，机器内部同一 key 请求进内存队列串行处理（同一 key 有序、不同 key 并行）；② <b>MQ/内存队列串行化</b>——生产端按业务 key 发到同一 partition/队列，消费端对 key 做 hash 落到固定线程顺序消费；③ <b>锁与序列号控制</b>——分布式锁、数据库行锁或请求带版本号/序列号控制乱序更新（更重、吞吐和热点问题更明显）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">更新型请求加幂等：</b>执行前检查 Redis 幂等 key → 执行中异常回滚恢复 → 成功后改状态位，避免重复执行。</div>
  </div>
  <div style="margin:10px 0 0;padding:8px 12px;border-left:3px solid #3F8C12;background:rgba(82,196,26,.08);border-radius:8px;font-size:13.5px;line-height:1.7;"><b style="color:#3F8C12;">口述重点：</b>顺序性不是白拿的，核心思路是「同一 key 聚合到同一路径上串行处理」，常见手段是 hash 路由 + 队列串行 + 幂等兜底。</div>
</div>

# 1.17 Sentinel 限流体系怎么做？分布式限流一致性？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">本质：</b>「控制面下发规则，数据面本地快速判定」。<b>控制面</b>——控制台配置限流/熔断/系统保护规则，存到配置中心（Nacos）动态推送各实例；<b>数据面</b>——业务代码在资源点埋点，请求走 slot chain（统计、限流、熔断），本地内存计数 + 滑动时间窗判断 QPS/RT/异常率是否超阈值，超阈值执行快速拒绝、排队等待、预热放量。</div>

# 2.1 CAP 在后端怎么落地理解？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">关键点一：</b>CAP 只在<b>发生网络分区（P）时</b>才要求取舍——平时网络正常时，很多系统既能高可用也能强一致。一旦分区发生必须选：要 <code>C</code>：宁可拒绝部分请求，也不返回旧数据；要 <code>A</code>：宁可先返回，后续再收敛一致。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键点二：</b>后端落地不是「系统级二选一」，而是<b>业务分级</b>——同一个公司里通常同时有 CP 和 AP 服务：<b>交易/资金/库存扣减</b>偏 CP（错一笔代价太高）；<b>内容流/推荐/点赞计数</b>偏 AP（允许短暂不一致）；<b>用户资料展示</b>常做折中（读 AP、关键写 CP）。</div>

# 2.2 最终一致性常见模式？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3F8C12;">① Outbox 事件模式：</b>本地业务数据和「待发送事件」写在<b>同一个数据库事务</b>里——例如订单服务创建订单时同时写一条 <code>order_created</code> 到 outbox 表，事务提交后后台任务把事件投递到 MQ。解决「订单写成功了但消息没发出去」的问题，关键价值是把「数据库写入」和「事件产生」绑在一个本地事务里。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">② 可靠重试：</b>消费者处理失败按规则重试——固定重试、指数退避、延迟队列、最大重试次数、失败进死信队列；适合临时性故障（网络抖动、下游超时、锁冲突）。前提是消费逻辑必须<b>幂等</b>，否则重试会把业务做重。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">③ 补偿事务：</b>某一步已成功、后续失败时执行「反向操作」纠偏——订单已创建但库存扣减失败，把订单状态改成取消；支付成功发券失败，补发券或退款。补偿不是回滚数据库，而是用<b>业务语义纠偏</b>。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">④ 定时对账/巡检修复：</b>最终兜底——即使 MQ 丢了、重试漏了、补偿没跑到，定时任务扫描异常状态把脏数据补回来（每天扫「已支付但订单未完成」重新触发履约；扫 outbox 未投递事件重发）。保证系统不是「出错就永远错下去」。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">选型：</b>积分、通知、履约这类链路优先用最终一致；资金扣减这类强一致要求高的场景更谨慎，尽量缩小异步范围。</div>
  </div>
</div>

# 2.3 为什么幂等是刚需？接口幂等怎么设计？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">为什么是刚需：</b>网络抖动、超时重试、消息重复投递在分布式系统里是<b>常态不是异常</b>。没有幂等就会出现重复扣款、重复发券等严重事故，所以必须在业务层做幂等保护。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">插入型请求：</b>最直接的方法是<b>数据库唯一键</b>（订单号、业务流水号、用户+业务主键），重复插入被数据库挡住；也可在 Redis 用「接口 + 请求参数」拼唯一 key，先判断是否处理过。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">更新型请求：</b>拆成多个阶段配<b>状态位</b>——执行前检查 Redis 幂等 key：值为 <code>1</code> 说明已成功执行直接返回；值为 <code>0</code> 说明同请求执行中，等待或快速失败；执行中异常不修改成功标记；执行成功后再改完成态。强一致更新可配合数据库独占锁（<code>select ... for update nowait</code>）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">工程化：</b>幂等键有明确生成规则；幂等状态设合理 TTL 避免永久脏状态；日志里区分「首次执行、重复命中、处理中重试」；高风险写操作把幂等设计成<b>平台能力</b>而不是每个接口各自手写。</div>
  </div>
  <div style="margin:10px 0 0;padding:8px 12px;border-left:3px solid #3F8C12;background:rgba(82,196,26,.08);border-radius:8px;font-size:13.5px;line-height:1.7;"><b style="color:#3F8C12;">口述重点：</b>幂等不是简单「查一下有没有」，而是要区分「未执行、执行中、已完成」三种状态，并根据插入型、更新型请求分别设计。</div>
</div>

# 2.4 2PC、3PC、TCC、Saga 怎么选？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="display:flex;flex-wrap:wrap;gap:8px;margin:8px 0 0;">
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">2PC / XA</b>
        <div style="margin:4px 0 0;">事务管理器先询问每个参与方能否执行；第一阶段预留资源，第二阶段统一提交或回滚。一致性强，但<b>严重依赖数据库锁和协调</b>，不适合高并发。</div>
      </div>
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">3PC</b>
        <div style="margin:4px 0 0;">改进阻塞问题，但实现复杂。</div>
      </div>
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">TCC</b>
        <div style="margin:4px 0 0;">Try 检测资源并预留；Confirm 真正执行；Cancel 失败补偿回滚。可实现较强一致，但<b>业务侵入大、补偿逻辑复杂</b>——适合资金类、强一致、每环节执行时间短的场景。</div>
      </div>
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">Saga</b>
        <div style="margin:4px 0 0;">适合长流程<b>最终一致</b>，各步骤带补偿动作。</div>
      </div>
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">本地消息表</b>
        <div style="margin:4px 0 0;">A 系统本地事务同时写业务数据和消息表，后台线程轮询再调 B 系统，B 必须幂等；缺点：高并发下消息表成为数据库压力点。</div>
      </div>
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">可靠消息最终一致</b>
        <div style="margin:4px 0 0;">A 先发 half message，本地事务成功再发 confirm/commit；confirm 丢了 MQ 通过<b>回查</b>确认本地事务状态；B 消费需幂等、失败重试补偿。适合订单、库存、履约这类允许最终一致的链路。</div>
      </div>
    </div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">Seata 框架理解：</b><code>TC</code> 协调器维护全局事务状态；<code>TM</code> 事务发起者，负责开始/提交/回滚全局事务；<code>RM</code> 资源管理器管理各分支事务并向 TC 汇报。流程：TM 向 TC 申请全局事务 ID → 各分支注册 → 成功统一提交，失败由 TC 驱动各分支回滚。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">选型：</b>强一致核心链路更适合 TCC；大部分互联网业务更常用「可靠消息 + 幂等 + 补偿 + 对账」这套最终一致方案。</div>
  </div>
  <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>为什么很多互联网业务最终选 Saga/Outbox 而不是 2PC？</div>
</div>

# 2.5 限流该放哪一层？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">核心原则：</b>限流应当分层设置。越靠近流量入口，越能以较低成本挡住无效流量；越靠近具体资源，越能按照真实容量精确保护。生产系统通常不是只在某一层限流，而是形成“边缘层粗筛、网关层统一控制、服务层精细保护、资源层兜底”的多级防线。</div>
    <div style="display:grid;grid-template-columns:86px minmax(0,1fr);column-gap:12px;row-gap:8px;margin:10px 0 0;">
      <div style="color:#3F8C12;font-weight:600;">边缘层</div><div>CDN、WAF 或负载均衡器按 IP、地域和连接数做粗粒度限制，优先阻断攻击流量和异常爬虫，避免请求进入内部网络。</div>
      <div style="color:#3F8C12;font-weight:600;">网关层</div><div>按用户、租户、应用、接口或令牌维度做全局限流，适合控制开放接口配额和系统总入口流量。网关知道身份与路由，但通常不了解服务内部线程池、数据库连接池等真实压力。</div>
      <div style="color:#3F8C12;font-weight:600;">服务层</div><div>针对热点方法、核心业务和特定下游设置独立阈值。例如订单服务调用库存服务时，根据库存服务的承载能力限制并发，防止一个依赖变慢拖垮整个调用链。</div>
      <div style="color:#3F8C12;font-weight:600;">资源层</div><div>线程池有界队列、数据库连接池、消息队列消费速率和信号量属于最后一道容量保护。即使上游规则失效，也不能允许请求无限堆积。</div>
    </div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">算法选择：</b>固定窗口实现简单但存在窗口边界突刺；滑动窗口统计更准确但存储和计算成本较高；漏桶按固定速率流出，适合严格整形；令牌桶允许一定突发流量，是业务接口最常见的选择。单机限流可用 Guava RateLimiter、Sentinel 等，本地实例扩容后总阈值会随实例数变化；需要严格全局配额时，可用 Redis + Lua 或网关集中限流，但要考虑网络开销和 Redis 故障降级。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">被限流后的处理：</b>不是简单丢弃。可以返回 <code>429 Too Many Requests</code> 和 <code>Retry-After</code>，也可以根据业务选择排队、降级结果、异步受理或关闭非核心功能。写请求重试必须具备幂等性，并加入指数退避和随机抖动，防止客户端立即重试形成二次流量峰值。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与治理：</b>阈值过低会误伤正常用户，过高则无法保护下游；仅按 IP 限流可能误伤 NAT 后的大量用户，仅按用户限流又挡不住匿名攻击。阈值应结合容量压测、历史峰值和下游 SLA 制定，并持续监控通过量、拒绝量、排队时间、P95/P99 延迟以及资源利用率。</div>
  </div>
  <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>令牌桶与漏桶有什么区别；集群扩容后本地限流阈值如何调整；Redis 限流不可用时应该放行还是拒绝；为什么限流必须和降级、熔断一起设计？</div>
</div>

# 2.6 熔断的价值是什么？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>熔断器用于处理“下游已经明显异常，继续调用只会浪费资源”的场景。它持续统计一段时间窗口内的请求数量、失败率、慢调用比例或连续失败次数；达到阈值后暂时停止真实调用并快速返回降级结果，从而避免调用方线程、连接池和重试预算被耗尽，把局部故障隔离在依赖边界内。</div>
    <div style="position:relative;padding-left:36px;margin:10px 0 0;">
      <div style="position:absolute;left:11px;top:10px;bottom:10px;width:2px;background:var(--border);"></div>
      <div style="position:relative;margin:0 0 8px;"><div style="position:absolute;left:-29px;top:3px;width:20px;height:20px;border-radius:50%;background:#9BBBF4;color:#fff;font-size:12px;font-weight:600;display:flex;align-items:center;justify-content:center;">1</div><div style="background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:9px 12px;font-size:13.5px;line-height:1.7;"><b style="color:#3A5FBF;">关闭（Closed）：</b>请求正常访问下游，熔断器在滑动窗口中记录成功、失败和耗时。只有达到最小请求数后才计算失败率，避免少量偶发错误触发熔断。</div></div>
      <div style="position:relative;margin:0 0 8px;"><div style="position:absolute;left:-29px;top:3px;width:20px;height:20px;border-radius:50%;background:#FAAD14;color:#fff;font-size:12px;font-weight:600;display:flex;align-items:center;justify-content:center;">2</div><div style="background:var(--card);border:1px solid var(--border);border-left:3px solid #B26E00;border-radius:12px;padding:9px 12px;font-size:13.5px;line-height:1.7;"><b style="color:#B26E00;">打开（Open）：</b>达到失败率或慢调用阈值后拒绝请求，不再访问下游；经过设定的等待时间后进入半开状态。</div></div>
      <div style="position:relative;margin:0;"><div style="position:absolute;left:-29px;top:3px;width:20px;height:20px;border-radius:50%;background:#52C41A;color:#fff;font-size:12px;font-weight:600;display:flex;align-items:center;justify-content:center;">3</div><div style="background:var(--card);border:1px solid var(--border);border-left:3px solid #3F8C12;border-radius:12px;padding:9px 12px;font-size:13.5px;line-height:1.7;"><b style="color:#3F8C12;">半开（Half-Open）：</b>只放少量探测请求。探测成功则恢复关闭状态，仍失败则重新打开，避免下游刚恢复就被全量流量再次压垮。</div></div>
    </div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">组合关系：</b>超时负责限制单次调用等待时间；重试处理短暂抖动；熔断处理持续性故障；隔离限制故障最多占用多少资源；降级决定熔断后返回什么。常见顺序是“超时控制 → 有限重试 → 统计失败并熔断 → 返回缓存、默认值或友好错误”。非幂等写请求不应盲目重试。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与配置：</b>阈值过敏会因短暂抖动频繁打开，阈值过松又无法及时止损；降级结果必须明确是否允许旧数据；半开探测数量过多可能造成恢复风暴。需要监控熔断次数、状态持续时间、慢调用比例、失败率和降级命中量，并对核心依赖与非核心依赖使用不同规则。</div>
  </div>
  <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>熔断、限流和降级分别解决什么问题；为什么必须设置最小请求数；半开状态如何避免大量请求同时探测；熔断后返回缓存数据会有什么一致性风险？</div>
</div>

# 2.7 隔离舱模式有什么用？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>隔离舱模式借鉴船舶把船体划分为多个水密舱的思路，把系统资源切成相互独立的配额。某个业务、租户或下游发生阻塞时，只能耗尽自己的资源池，不能占满全局线程、连接和内存，从而把故障半径限制在一个可控区域。</div>
    <div style="display:grid;grid-template-columns:96px minmax(0,1fr);column-gap:12px;row-gap:8px;margin:10px 0 0;">
      <div style="color:#3F8C12;font-weight:600;">线程池隔离</div><div>为不同依赖分配独立线程池和有界队列，隔离最彻底，也能分别设置超时、拒绝策略和监控；代价是线程数量、上下文切换和调参成本较高。</div>
      <div style="color:#3F8C12;font-weight:600;">信号量隔离</div><div>请求仍在原线程执行，只限制同时访问某个依赖的并发数，开销更小；但下游阻塞时仍会占用调用方线程，因此更适合延迟稳定、调用时间短的依赖。</div>
      <div style="color:#3F8C12;font-weight:600;">资源池隔离</div><div>数据库连接池、HTTP 连接池、消息队列、缓存实例和对象存储客户端分别设置容量，防止某类慢请求占尽共享连接。</div>
      <div style="color:#3F8C12;font-weight:600;">部署级隔离</div><div>通过独立进程、容器、节点、可用区或租户配额进一步隔离 CPU、内存和故障域，适合核心链路与非核心链路、在线业务与离线任务。</div>
    </div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">落地步骤：</b>先识别共享资源和关键依赖，再按业务重要性与调用特征划分资源池；为每个池配置容量、队列、超时和拒绝策略；核心业务预留独立配额，非核心业务达到上限时快速失败或降级；最后监控活跃线程、排队长度、连接使用率、拒绝量和任务耗时，根据压测和线上峰值调整容量。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>隔离过细会造成资源碎片和运维复杂度上升，某个池空闲时资源也不能被其他池利用；隔离过粗则仍可能相互拖垮。资源池不是越大越好，过大的队列只会把过载转换成更高延迟。通常要配合限流、超时、熔断和降级共同使用。</div>
  </div>
  <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>线程池隔离和信号量隔离怎么选；为什么有界队列也是隔离的一部分；隔离舱与熔断器的职责有什么区别；资源划分后如何避免大量闲置？</div>
</div>

# 2.8 最小可观测性集合是什么？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3F8C12;">三件套 + 统一请求 ID：</b><b>Metrics（指标）</b>回答「系统现在健不健康」——QPS、RT、错误率、CPU、线程池、MQ 堆积；<b>Logs（日志）</b>回答「某次请求到底发生了什么」——关键业务字段、错误堆栈、上下文；<b>Traces（链路追踪）</b>回答「这次请求经过了哪些服务、卡在哪一跳」。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">工程落地：</b>Prometheus/Grafana 做 Metrics，ELK 或 Loki 做 Logs，Jaeger/SkyWalking/Zipkin 做 Traces——核心不是工具名，而是三者通过<b>同一个 requestId</b> 串起来。</div>
  </div>

# 2.9 高峰故障时如何做限流、降级、回滚？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">处理目标：</b>高峰故障时首先控制故障扩散，优先保证核心链路和数据正确；其次恢复服务能力；最后才处理积压和完整功能。不能在原因尚未确认时无限重启或持续重试，否则可能进一步耗尽线程池、数据库连接和下游容量。</div>
    <div style="position:relative;padding-left:36px;margin:10px 0 0;">
      <div style="position:absolute;left:11px;top:10px;bottom:10px;width:2px;background:var(--border);"></div>
      <div style="position:relative;margin:0 0 8px;"><div style="position:absolute;left:-29px;top:3px;width:20px;height:20px;border-radius:50%;background:#9BBBF4;color:#fff;font-size:12px;font-weight:600;display:flex;align-items:center;justify-content:center;">1</div><div style="background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:9px 12px;font-size:13.5px;line-height:1.7;"><b style="color:#3A5FBF;">确认影响：</b>从错误率、P99、QPS、资源水位和业务成功率判断影响范围，按服务、接口、租户和版本切分；冻结非必要发布，统一故障指挥和时间线。</div></div>

      <div style="position:relative;margin:0 0 8px;"><div style="position:absolute;left:-29px;top:3px;width:20px;height:20px;border-radius:50%;background:#9BBBF4;color:#fff;font-size:12px;font-weight:600;display:flex;align-items:center;justify-content:center;">4</div><div style="background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:9px 12px;font-size:13.5px;line-height:1.7;"><b style="color:#3A5FBF;">定位并回滚：</b>若故障与新版本、配置或流量切换高度相关，优先回滚应用和配置。数据库结构变更必须保证向前、向后兼容，已产生的数据不能简单依赖代码回滚恢复，需要补偿脚本或双版本兼容。</div></div>

      <div style="position:relative;margin:0;"><div style="position:absolute;left:-29px;top:3px;width:20px;height:20px;border-radius:50%;background:#52C41A;color:#fff;font-size:12px;font-weight:600;display:flex;align-items:center;justify-content:center;">6</div><div style="background:var(--card);border:1px solid var(--border);border-left:3px solid #3F8C12;border-radius:12px;padding:9px 12px;font-size:13.5px;line-height:1.7;"><b style="color:#3F8C12;">复盘治理：</b>补齐容量基线、自动门禁、故障开关、回滚演练和告警分级；记录发现时间、止损时间和恢复时间，验证同类故障能否更早发现、更小影响、更快恢复。</div></div>
    </div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">关键风险：</b>回滚后仍可能持续报错，因为数据库或缓存已经写入不兼容数据、旧实例未全部摘除、消息队列仍在回放错误消息、下游尚未恢复，或者客户端正在集中重试。因此回滚只是一个止损动作，必须继续核对版本分布、配置、数据状态、积压队列和依赖健康度。</div>
  </div>
  <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>为什么恢复流量必须逐步放量；数据库变更为什么可能无法直接回滚；消息积压如何避免压垮刚恢复的下游；限流和降级的解除顺序如何决定？</div>

# 3.2 RPC 一次调用的完整链路是什么？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">完整链路：</b>调用方先通过<b>代理拦截</b>本地接口，序列化请求并做<b>服务发现、负载均衡</b>，再经网络传输到服务端；服务端反序列化后执行业务逻辑并返回结果，客户端再做反序列化、超时控制和重试决策。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">Dubbo 调用底层（五层）：</b>① <b>动态代理</b>——面向接口编程，底层代理对象拦截方法调用；② <b>负载均衡</b>——random、consistent hash 等选一台机器；③ <b>协议层</b>——dubbo/rmi/hessian/http 等；④ <b>网络通信</b>——常基于 Netty/Mina 做 NIO 异步通信；⑤ <b>序列化</b>——把请求编码成二进制发出。服务端做反序列化、协议解析、网络收包，再经代理调到真正的本地服务。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">Dubbo 集群容错策略：</b><code>failover</code> 失败自动切换重试（读操作）；<code>failfast</code> 失败立刻返回（非幂等写）；<code>failsafe</code> 失败忽略（日志类）；<code>failback</code> 失败后台重发（消息通知）；<code>forking</code> 并行调用多个 provider 一个成功即返回（换时延耗资源）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">如何设计一个 RPC 框架（最小闭环）：</b>动态代理（本地接口代理成远程调用）+ 注册中心（服务注册与发现）+ 负载均衡（从多个 provider 选路）+ 协议与序列化（请求格式与编解码）+ 网络通信框架（Netty 高并发连接）。</div>
  </div>
  <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>链路里最常见的性能瓶颈在哪三处，如何快速定位？</div>

# 3.3 服务注册中心的核心职责是什么？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;">核心是「<b>服务实例元数据维护 + 健康检查 + 发现路由</b>」——提供者注册并周期上报心跳，消费者订阅实例变更并更新本地路由表。注册中心本身要保障<b>高可用、弱依赖</b>，故障时可降级读本地缓存。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">ZooKeeper vs Eureka：</b>ZK 偏 <b>CP</b>（一致性更强、变更感知快，通过 watcher 通知，但服务实例多时推送压力大）；Eureka 偏 <b>AP</b>（可用性优先，节点 peer 同步、消费者周期性拉取，默认变更感知慢，可缩短缓存同步/心跳/拉取周期优化到秒级）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">大规模注册中心优化：</b>注册表<b>分片存储</b>（不让每台机器存全集）；每分片主从备份；消费者经代理层<b>按需拉取</b>局部注册信息；避免每次变更在全集上广播同步。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">Redis 当注册中心（折中方案）：</b>Provider 写 Redis Hash 并设 TTL，周期性刷新过期时间作心跳；Consumer 周期性扫描服务前缀拉取列表。适合轻量级、内部可控场景；强一致注册发现用 ZooKeeper/etcd 更标准。</div>
  </div>
  <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>注册中心短时不可用时，消费者如何避免全链路雪崩？</div>

# 3.4 RPC 的超时、重试、熔断怎么配？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">超时：</b>先从端到端总预算倒推，为 DNS、建连、排队、服务处理和响应读取分别留出时间；基于下游 P99/P999 和业务可接受时延设置，而不是简单写一个很大的固定值。客户端、网关、服务端和数据库的超时要有层次，避免下游已经放弃而上游仍长期占用线程。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">重试：</b>只对连接失败、限时超时等暂态错误重试，设置有限次数、指数退避和随机抖动；读请求或带幂等键的写请求才适合自动重试，扣款、创建订单等非幂等写默认不重试，或先查询业务状态再决定补偿。重试预算应计入总超时，不能每一层都重复重试。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">熔断：</b>按错误率、慢调用比例、连续失败数或并发占满触发，状态通常为 closed、open、half-open。open 状态快速失败或返回降级值，经过冷却窗口放少量探测请求；探测成功逐步恢复，失败则继续熔断。熔断要按接口和下游实例隔离，不能一个热点接口拖住整个服务。</div>
    <div style="margin:8px 0 0;"><b style="color:#9B5C00;">配套措施：</b>结合舱壁隔离、限流、备用实例和降级缓存，记录重试放大倍数、熔断次数、半开成功率和超时原因。高峰止损时优先停止无意义重试、降低非核心流量，再根据下游恢复情况逐步放量。</div>
  </div>
  <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>为什么“重试次数越多越危险”，在高峰时如何止损？超时和熔断的触发顺序如何避免误杀？</div>
</div>

# 3.5 序列化协议取舍看什么？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">评估维度：</b>看<b>编码解码性能、消息体大小、跨语言能力、Schema 演进、可调试性、安全边界</b>和生态支持。协议选型要结合网络带宽、CPU、延迟目标和灰度发布方式，不能只比较单次 benchmark。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">常见协议：</b>Protobuf 采用字段编号和二进制编码，体积小、性能高、跨语言强，适合稳定的内部 RPC；JSON 可读性和调试体验好，适合开放 API，但体积和解析成本更高；Hessian 或 Java 原生序列化接入简单，却要重点治理版本兼容、反序列化类型白名单和不可信输入风险。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">兼容演进：</b>新增字段使用新编号并提供默认值，旧客户端忽略未知字段；不要复用已删除的字段编号，必要时标记 reserved。枚举新增值、字段类型变化和必填语义都要评估旧客户端行为，灰度期间保证新旧版本可以互相读写。</div>
    <div style="margin:8px 0 0;"><b style="color:#9B5C00;">取舍：</b>可读性优先的管理接口可以使用 JSON，高吞吐内网链路更适合 Protobuf；涉及外部合作方时要提供版本、文档和兼容测试。无论选择何种协议，都要限制消息大小、解析深度和超时，避免恶意或异常消息耗尽资源。</div>
  </div>
  <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>线上灰度升级时，如何做字段向前/向后兼容？为什么不能随意复用删除过的字段编号？</div>
</div>

# 3.6 RPC 调用失败的排查顺序是什么？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">第一步看现象：</b>按调用方、被调用方、接口、实例、版本和时间窗口拆分 QPS、P95/P99、超时率、错误码、重试率和熔断次数，先判断是全量故障、单实例故障还是特定参数触发。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">第二步分层：</b>检查服务发现是否返回过期或空实例，DNS 和连接建立是否正常，连接池是否耗尽，客户端线程池和队列是否打满；再看服务端线程池、GC、CPU、锁等待、数据库连接和下游依赖。网络层可用 TCP 重传、RTT 和丢包指标区分传输问题。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">第三步还原链路：</b>用 TraceId 对齐调用方、网关、RPC 客户端和服务端日志，确认请求到底有没有到达、卡在哪个阶段、是否重复执行。结合发布记录和流量变化，把根因归为配置/代码回归、流量突增、下游抖动或基础设施异常。</div>
    <div style="margin:8px 0 0;"><b style="color:#9B5C00;">止损与复盘：</b>先对非核心调用降级、停止无效重试或摘除异常实例，再修复根因；恢复后核对积压、重复请求和数据一致性。补齐超时、错误码、实例、版本和请求量维度的监控，避免下次只能依赖人工翻日志。</div>
  </div>
  <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>同样是超时，如何快速判断是网络抖动还是线程池打满？如果服务端已经返回成功但客户端超时，重试会带来什么风险？</div>

# 3.7 ZooKeeper 与 ZAB 协议？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">角色与数据模型：</b>集群角色三种——<b>Leader</b>（负责写）、<b>Follower</b>（同步数据并提供读）、<b>Observer</b>（只读、不参与选举）。数据模型是 znode 树：<b>持久节点</b>适合放元数据；<b>临时节点</b>连接断开即消失，适合分布式锁、服务在线状态。客户端与 ZK 建 TCP 长连接（session），sessionTimeout 内重连可延续原 session。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">Watcher：</b>对 znode 注册监听，节点变化时收到回调通知——分布式锁的羊群效应规避就靠监听前驱节点。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">ZAB 协议：</b>「带顺序保证的主从同步协议」——Leader 收到事务请求先写本地日志，把 proposal 按顺序同步给 follower；follower 先写磁盘再返回 ack；Leader 收到过半 ack 后发出 commit；follower 收到 commit 后才让新数据可见。关键点：proposal 带全局递增的 <code>zxid</code> 保证顺序；过半写机制；Leader 崩溃后只要超半数节点存活就能重新选主恢复。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">一致性定位：</b>ZK 不是「严格强一致」，更准确是<b>顺序一致性优先、最终收敛</b>——业务强依赖强一致读可主动调用 <code>sync()</code>。</div>
  </div>
</div>

# 5.1 为什么需要 Service Mesh？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">

# 6.1 如何设计一个高可用 KV 存储系统？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3F8C12;">① 分片（一致性哈希）：</b>哈希空间看成一个环（0 到 2^32-1），节点和 key 都映射到环上，key 顺时针找到第一个节点作为归属；扩缩容只迁移受影响区间数据。用<b>虚拟节点</b>（每台物理机映射多个点到环上）让数据更均匀、热点更少；可加<b>加权虚拟节点</b>（高配机器分配更多 vnode）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">② 数据模型与复制：</b>key → value + version + timestamp；每个 key 写到 N 个副本（主副本 + 后续副本）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">③ 读写路径：</b>写——客户端到协调节点，并行写 N 副本，达到 <b>W 个成功即返回</b>；读——协调节点读 N 副本中的 <b>R 个</b>，做版本合并后返回最新值。条件 <b>R + W > N</b> 提高读写一致性概率。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">④ 故障处理：</b>副本宕机时先写可用副本（<b>hinted handoff</b>），恢复后补数据；后台修复用 <b>anti-entropy</b>（如 Merkle tree）+ <b>read repair</b>。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">⑤ 可用性与一致性取舍：</b>追求强一致（偏 CP）——写入多数派确认，网络分区时宁可拒写不读脏数据；追求高可用（偏 AP）——优先接受读写、允许短暂不一致后续异步收敛。场景决策：交易、余额、库存扣减优先一致性；缓存、Feed、推荐、计数优先可用性和低延迟。</div>
  </div>
  <div style="margin:10px 0 0;padding:8px 12px;border-left:3px solid #3F8C12;background:rgba(82,196,26,.08);border-radius:8px;font-size:13.5px;line-height:1.7;"><b style="color:#3F8C12;">口述重点：</b>一致性哈希分片 + N 副本复制（写 W 确认、读 R 合并）+ read repair 收敛；一致性与可用性按业务分级——核心是把取舍显式化，并用监控和修复机制兜底。</div>
</div>

# 6.3 如何设计一个爬虫系统？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">本质：</b>爬虫系统是带<b>调度能力的数据采集系统</b>。核心链路：Seed URL 进入 Frontier 调度队列 → Downloader 拉取页面 → Parser 解析内容和新链接 → URL/内容去重过滤 → 回到 Frontier。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">URL Frontier（最关键）：</b>不是简单 FIFO，而是调度中心，要同时解决三件事——<b>优先级</b>（按页面重要性和更新频率安排抓取顺序）、<b>礼貌性</b>（按 host 维度拆队列，同一 host 串行抓取加间隔）、<b>新鲜度</b>（更新频繁的重要页面提高重抓频率）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">去重：</b>URL 去重（防重复 URL 进 Frontier，用 Bloom Filter/HashSet/Redis Set）+ 内容去重（防不同 URL 相同内容，用哈希值/checksum）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">其他重点：</b>DNS 缓存、robots.txt、失败恢复、spider trap。</div>
  </div>
  <div style="margin:10px 0 0;padding:8px 12px;border-left:3px solid #3F8C12;background:rgba(82,196,26,.08);border-radius:8px;font-size:13.5px;line-height:1.7;"><b style="color:#3F8C12;">口述重点：</b>爬虫系统最核心的不是「抓得快」，而是「调度得稳、过滤得准、恢复得动」。</div>

# 6.4 如何设计搜索系统？自动补全怎么做？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答（召回、粗排、精排、展现）：</b>
    <div style="margin:6px 0 0;"><b style="color:#3F8C12;">写入链路（离线/准实时）：</b>文档采集 → 解析清洗分词抽字段 → 建倒排索引 → 生成排序特征 → 索引写入搜索引擎——「把数据变成可搜索」。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">查询链路（在线）：</b>Query 理解（分词、纠错、同义词扩展）→ <b>召回</b>（从倒排索引快速拿候选）→ <b>排序</b>（BM25/相关性模型/点击率综合）→ 过滤、去重、高亮、分页——「把 query 变成结果页」。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">召回理解：</b>目标是「别漏掉可能相关的候选」而非最精准——倒排索引召回、同义词扩召回、拼写纠错召回、向量召回（语义检索）；召回更看<b>覆盖率和延迟</b>。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">排序理解：</b>决定「谁排前面」——文本相关性、热度、点击率/转化率、时效性、个性化；分<b>粗排</b>（快速筛一遍）+ <b>精排</b>（更贵的模型细算）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">自动补全：</b>强调<b>前缀匹配 + 高频词优先 + 低延迟</b>——Trie/前缀树、倒排 + 前缀索引、Redis ZSet 存热点 query；排序结合前缀命中、历史频次、时效性、个性化。</div>
  </div>
</div>

# 6.5 如何设计信息流/朋友圈系统？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3F8C12;">目标：</b>用户发动态后粉丝较快看到、首页打开快、高峰期不崩、允许几秒内慢慢同步但不能乱。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">发帖流程（写扩散）：</b>发帖先落帖子库 → 生成分发任务入 MQ → 推送工人查粉丝列表 → 把帖子编号写进粉丝首页列表 → 粉丝打开首页直接看到。「首页列表只存编号」省内存速度快。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">读扩散与混合：</b>大 V 发一条要写几百万粉丝首页、写入压力太大——大 V 用读扩散（发帖不全量分发，粉丝打开首页时临时拉取合并）。最终<b>普通用户写扩散（读快）、大 V 读扩散（写稳）</b>混合模式。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">稳定性：</b>幂等（同一条分发任务重复执行只写一次）、重试、死信队列（多次失败先隔离）、监控（队列堆积、首页延迟、分发成功率）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">权限控制：</b>「发布时控制可分发范围，读取时再做一次权限校验」双层控制——关系 + 可见范围 + 用户配置联合判断，客户端缓存权限数据做本地快速判断，刷新时最终判定。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">点赞链路：</b>独立存储、缓存优先——Redis Set 存点赞用户 ID（SCARD 计数、SMEMBERS 列表）；好友可见用好友集合与点赞集合做交集判断；幂等（DB 用 (user_id, post_id) 联合唯一键，Redis Set 天然去重）。</div>
  </div>
  <div style="margin:10px 0 0;padding:8px 12px;border-left:3px solid #3F8C12;background:rgba(82,196,26,.08);border-radius:8px;font-size:13.5px;line-height:1.7;"><b style="color:#3F8C12;">口述重点：</b>朋友圈主链路是「发帖异步分发到时间线」，点赞链路是「独立存储、缓存优先、关系裁剪可见性、幂等防重」。</div>

# 6.7 如何设计一个支付系统？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3F8C12;">边界：</b>电商支付后端，不存信用卡信息，接入第三方 PSP（Stripe 类）；支持买家付款（pay-in）和卖家结算（pay-out）；高可靠、可审计、可对账。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">核心模块：</b><b>Payment Service</b>（接收支付请求、维护支付状态机、协调流程）、<b>PSP Adapter</b>（对接外部渠道）、<b>Ledger</b>（账务记账）、<b>Wallet</b>（卖家余额）、<b>Webhook Handler</b>（PSP 异步回调）、<b>Reconciliation Service</b>（每日对账）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">核心流程：</b>前端调 Payment Service → 创建 payment event 和 payment order → 调 PSP 注册支付（带全局唯一 payment_order_id 作幂等键）→ PSP 返回 token → 前端拉起 hosted payment page → 支付完成后 PSP redirect + webhook 异步通知 → 后端更新 order 状态 → 成功则更新 wallet 和 ledger。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">三大关键难点：</b>① <b>幂等性</b>——防重复扣款：同一 order 带同一 idempotency key，服务端唯一约束/幂等表只处理一次，调 PSP 时也传幂等键；② <b>一致性和失败恢复</b>——不假设天然强一致：支付状态设计成明确状态机（pending/success/failed/unknown）+ retry queue + dead letter queue，最终不一致靠 reconciliation（拿 PSP/银行结算结果与内部 ledger 逐笔对账）；③ <b>账务正确性</b>——用 <b>double-entry ledger 复式记账</b>：钱包余额是业务视图，ledger 才是财务真相来源，每笔资金流转有借贷对应关系。</div>
  </div>
  <div style="margin:10px 0 0;padding:8px 12px;border-left:3px solid #3F8C12;background:rgba(82,196,26,.08);border-radius:8px;font-size:13.5px;line-height:1.7;"><b style="color:#3F8C12;">口述重点：</b>支付系统最关注的不是单纯高并发，而是 correctness——不能重复扣款、不能丢单、账必须对得上。回答结构：先需求边界 → 再高层架构和核心流程 → 重点展开幂等、失败恢复、对账和账务系统。</div>
</div>

# 6.8 如何设计附近地点检索服务？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3F8C12;">需求与量级：</b>输入经纬度 + 搜索半径，低延迟返回附近商家；附近搜索、商家详情、商家增删改（写入不要求实时，次日生效）。假设 1 亿 DAU、每人每天 5 次搜索，QPS 约 5000——典型读多写少，优化重点放读路径。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">架构：</b>两个无状态服务——<b>LBS 检索服务</b>（按位置找候选商家）+ <b>Business 商家服务</b>（详情和低频写）；数据层是商家主表 + 地理索引表，主从架构读写分离。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">关键难点（地理检索）：</b>不能用全表扫距离，也不能只靠经纬度普通索引（二维范围检索效率差）。选 <b>Geohash</b> 做空间索引——把地图切成网格编码成字符串前缀；查询时按半径选 geohash 精度（500 米用更细精度）→ 计算用户所在网格 + <b>8 个邻居网格</b>批量拿候选商家 ID → 最后精确距离计算排序。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">边界问题：</b>只查当前网格会漏掉边缘商家，必须查邻居网格；网格是方形而半径是圆形，最后要做<b>精确距离过滤</b>；结果不足时逐步扩圈逐级放大搜索范围。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">缓存与扩展：</b>两层缓存——「geohash → 商家 ID 列表」+「business_id → 商家详情」；缓存键用 geohash 而非精确经纬度，避免用户轻微移动导致缓存碎片。商家主表按 business_id 分片；geo 索引表优先用读副本扩吞吐；部署多 Region 多 AZ。</div>
  </div>
  <div style="margin:10px 0 0;padding:8px 12px;border-left:3px solid #3F8C12;background:rgba(82,196,26,.08);border-radius:8px;font-size:13.5px;line-height:1.7;"><b style="color:#3F8C12;">口述重点：</b>附近搜索 = 地图切格子（Geohash）做快速候选 + 精确距离做最终过滤。</div>
</div>

# 6.9 分布式 ID：UUID、号段、Snowflake 怎么选？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="display:flex;flex-wrap:wrap;gap:8px;margin:8px 0 0;">
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">UUID</b>
        <div style="margin:4px 0 0;">无中心、生成简单、全局唯一性好；但字符串长、无序，做 DB 主键导致索引离散、页分裂多。适用：不追求有序、量不大或离线场景。</div>
      </div>
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">号段模式（Segment/Leaf）</b>
        <div style="margin:4px 0 0;">从 DB 一次批量申请一段 ID（如 10000 个），本地内存递增发放——趋势递增、性能高、实现简单；依赖号段服务和 DB，要处理预取和高可用。适用：业务主键、订单号等「希望有序且高性能」场景。</div>
      </div>
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">Snowflake</b>
        <div style="margin:4px 0 0;">时间戳 + 机器 ID + 序列号（常见 41+10+12）——本地生成、趋势递增、吞吐高、长度固定；难点是时钟回拨、机器 ID 分配、跨机房部署。解法：持久化 lastTimestamp 服务重启时先校验，或把时间上报 ZK 校验管理。适用：高并发在线系统主流方案。</div>
      </div>
    </div>
  </div>
  <div style="margin:10px 0 0;padding:8px 12px;border-left:3px solid #3F8C12;background:rgba(82,196,26,.08);border-radius:8px;font-size:13.5px;line-height:1.7;"><b style="color:#3F8C12;">口述重点：</b>要无依赖选 UUID；要数据库友好选号段；要高并发低延迟通常选 Snowflake，但要重点治理时钟回拨和机器号冲突。</div>
</div>

# 6.10 短链系统怎么设计？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答（ID 系统 + 短链系统 + 热点治理三段）：</b>
    <div style="margin:6px 0 0;"><b style="color:#3F8C12;">生成方案：</b>自增 ID（号段/雪花）转 62 进制（<code>id → base62 short code</code>）最常见——短、稳定、可控；插入 DB 依赖唯一索引兜底防短码冲突，写入冲突时重试（重新生成或加盐）；写 Redis 缓存。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">跳转链路（读路径）：</b>客户端 → CDN/网关 → 短链服务 → Redis 查短码映射（code → long_url）→ 命中返回 301/302；未命中查 DB 回填缓存（设 TTL）；点击埋点异步化（入 MQ 不阻塞跳转主链路）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">301 vs 302：</b>301 长期不变利于 SEO 和缓存；302 可控性高便于后续改目标链接——很多业务默认 302，营销活动常用。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">热点治理：</b>热点 key——本地缓存 + Redis、多副本读、热点预热、限流熔断、热点隔离；缓存穿透——参数校验、Bloom Filter 预判、空值缓存（短 TTL）；击穿——互斥重建；雪崩——TTL 抖动 + 限流降级。</div>
  </div>
</div>

# 6.11 邀请码系统怎么设计？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答（增长中台五段）：</b>
    <div style="margin:6px 0 0;">当成<b>增长中台能力</b>而非单次活动接口（可能服务注册拉新、交易返佣、活动裂变）。核心链路五段：<b>邀请码生成 → 下发 → 验证 → 绑定 → 发奖</b>。原则：<b>绑定关系必须强一致，奖励发放可以最终一致</b>。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">① 生成：</b>保证唯一、可读、可控——批量预生成（大活动，减高峰压力）+ 实时生成（长尾，省库存）两种模式；雪花生成自增 ID + Base62 编码成 8 位短码；先落权威存储，热点数据同步 Redis。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">② 验证（第一道关键校验）：</b>API Gateway 鉴权、限流、黑名单、参数合法性；优先查 Redis（是否存在/过期/禁用/次数上限），缓存未命中回源 DB；风控前置（设备/IP/账号异常、高频尝试命中风险规则不进绑定）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">③ 绑定（最核心，强一致）：</b>幂等校验（每次请求带 request_id 防重复绑定）；写绑定关系依赖<b>数据库事务和唯一约束</b>保证「同一被邀请人同一场景只能绑定一次」。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">④ 发奖（异步）：</b>绑定成功只发一条「绑定成功事件」到 MQ，下游奖励服务异步消费（现金/积分/优惠券/返佣）；消费方幂等，防 MQ 重复投递导致重复生效。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">扛高并发的关键：</b>前三段靠缓存、限流和风控削峰；绑定靠幂等、事务和唯一约束保证正确性；发奖靠 MQ 异步解耦压力——<b>前链路做短，后链路做异步</b>。</div>
  </div>
</div>
