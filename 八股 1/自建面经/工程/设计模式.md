## 一、设计原则

# 1.1 什么是开闭原则？在项目中如何体现？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>开闭原则（OCP）——对扩展开放、对修改关闭：新增功能时优先通过<b>扩展新代码</b>实现，而不是修改已有代码。核心是抽象 + 多态：依赖抽象接口，具体实现可替换、可新增。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程：</b>① 定义稳定抽象（接口/抽象类）封装变化点；② 实现类遵循接口；③ 新增能力 = 新增实现类并注册，不触碰既有实现；④ 通过配置、工厂、策略表等做运行时选择。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>不是"完全不改代码"——接口本身、注册表、调用方少量扩展点改动是允许的；典型载体：策略模式、模板方法、观察者、SPI/插件机制、依赖注入。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>过度抽象会引入不必要的接口层级，代码难读；抽象错了变化点比不抽象更糟——要等变化出现两次再抽象（Rule of Three）；分层要符合业务演进方向。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>告警通知多通道（飞书/邮件/短信）定义 Notifier 接口按需注册；规则引擎用策略表驱动；支付渠道、消息队列实现做 SPI 抽象；新增渠道只加类不改核心流程。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>开闭原则和里氏替换的关系（子类可替换父类不破坏契约，是实现 OCP 的前提）；工厂/策略/模板如何体现 OCP；"对修改关闭"是否意味着禁止改任何代码（不是，改的是扩展点而不是核心逻辑）。</div>
  </div>
</div>

# 2.1 单例模式有哪些实现方式？如何保证线程安全？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>单例保证一个类全局只有一个实例，提供全局访问点，适合配置中心、连接池、线程池、日志器等无状态或共享状态组件。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现方式（线程安全对比）：</b>① <b>饿汉式</b>：类加载即创建，天然线程安全，但可能浪费（不用也创建）；② <b>懒汉式 + synchronized</b>：方法级加锁，线程安全但性能差；③ <b>双重检查锁（DCL）</b>：先判空再进锁再判空，需 <code>volatile</code> 防止指令重排暴露半初始化对象；④ <b>静态内部类</b>：<code>Holder</code> 延迟加载 + 类加载机制保证线程安全，推荐；⑤ <b>枚举</b>：JVM 保证唯一实例，天然防反射和序列化破坏，最推荐。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>DCL 的 <code>volatile</code> 必须加（new 的三步：分配内存→初始化→赋值，重排后其他线程可能拿到未初始化对象）；反射 <code>setAccessible</code> 可破坏普通单例；序列化会生成新实例（加 <code>readResolve</code> 修复）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>全局状态难测试（单例持有可变状态时测试间互相污染）；多类加载器/分布式场景"单例"不成立；滥用单例 = 隐式全局变量，增加耦合。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>Spring 容器默认单例 Bean（IoC 管理生命周期，替代手写单例）；连接池、配置对象用单例；需要懒加载 + 线程安全时用静态内部类或枚举；Spring 中用 <code>@Component</code> 默认单例 + 注入，不用手写 DCL。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>DCL 为什么要 volatile（指令重排）；枚举为什么能防反射破坏（JVM 层面限制）；Spring 单例和设计模式单例的区别（容器管理生命周期）；懒汉和饿汉的取舍（启动时间 vs 内存占用）。</div>
  </div>
</div>

# 2.2 为什么选择责任链模式？它有什么优点？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>责任链把多个处理器串成链，请求沿链传递，每个处理器决定自己处理、传给下一个或终止。适合"一个请求可能被多个候选处理器按顺序处理/拦截"的场景：审批流、过滤器、拦截器、校验链。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程：</b>① 定义处理器接口（<code>handle(request)</code> + 下一个节点引用）；② 每个处理器实现"能否处理 + 处理 + 是否继续"；③ 链装配：按顺序串联（构造注入/链表/列表）；④ 请求从链头进入，逐节点传递。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">优点：</b>① <b>解耦</b>：请求方不知道具体谁来处理，只认识链头；② <b>开闭原则</b>：新增处理器不改已有代码，只改装配；③ <b>灵活编排</b>：顺序、增删节点动态调整；④ <b>职责单一</b>：每个处理器只做一件事。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>两种变体——<b>纯责任链</b>（每个节点要么处理要么下传，不能既处理又下传）和<b>不纯责任链</b>（可处理后再下传，如过滤器链）；注意节点顺序敏感，顺序错了语义就变。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>链过长时调试困难（请求到底被谁处理了）；节点顺序耦合业务语义；性能上逐节点传递有少量开销，但通常可忽略；要提供断点/日志跟踪请求在链中的路径。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>Web 过滤器链（Servlet Filter/Spring Interceptor）；告警处理链（去重→分级→限频→多渠道通知）；请求校验链（参数→权限→风控→业务）；MyBatis 插件/Netty ChannelHandler 都是责任链思想。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>责任链和装饰器的区别（链式传递 vs 层层增强）；责任链和策略的区别（多个候选顺序执行 vs 运行时选一个）；如何动态调整链顺序（配置装配）。</div>
  </div>
</div>

# 2.3 责任链模式如何结合工厂模式？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>责任链负责"按顺序处理"，工厂负责"创建对象"——结合点：工厂负责<b>创建和装配整条链</b>，调用方只依赖工厂拿到的链头，不知道链内部结构和节点个数。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程（典型组合）：</b>① 定义处理器接口和若干实现类（Spring 中 <code>@Component</code> 注册）；② 工厂/配置类收集所有处理器（按 <code>@Order</code> 或配置顺序排序）；③ 工厂把处理器串成链返回链头；④ 调用方 <code>chainFactory.create()</code> 获得链并传入请求。Spring 场景：注入 <code>List&lt;Handler&gt;</code> 自动收集所有实现，排序后串联——零手工装配。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>工厂隐藏了"有哪些节点、什么顺序"的细节；新增节点 = 新增一个 <code>@Component</code> 实现 + 排序注解，链路自动更新（开闭原则的完整体现）；也可以由工厂按配置（数据库/配置文件）动态决定链成员。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>隐式装配让新人难以一眼看清链结构（需要日志/文档说明）；工厂 + 反射/依赖注入的魔法要控制范围；排序冲突（两个节点同 Order）要定义稳定策略。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>Spring Boot 过滤器/拦截器链注册；告警链：注入 <code>List&lt;AlertHandler&gt;</code> + <code>@Order</code>，新增处理阶段只加类；参数校验链用工厂按场景（创建/更新/查询）装配不同链。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>Spring 如何自动收集所有实现（<code>List&lt;Interface&gt;</code> 注入）；工厂创建链和手动 new 链的区别（解耦 + 可配置）；为什么顺序注解用 <code>@Order</code>（值小的先执行）。</div>
  </div>
</div>

# 2.4 有一个门票计算场景：全票 100 元，学生半价，老人和军人免费，儿童按身高半价或免费，适合使用什么设计模式？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>这是典型的"价格策略随人群类型变化"场景——同一种操作（算票价），不同对象（人群）有不同算法，且策略会不断新增（教师、医护优惠等）。最合适的是<b>策略模式</b>：把每种人群的计价规则封装成独立策略类，运行时按人群类型选择。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程：</b>① 定义策略接口 <code>PriceStrategy.calc(visitor)</code>；② 实现类：<code>StudentStrategy</code>（半价）、<code>SeniorStrategy</code>（免费）、<code>SoldierStrategy</code>（免费）、<code>ChildStrategy</code>（按身高判断半价/免费）、<code>NormalStrategy</code>（100 元）；③ 工厂/Map 按人群类型取策略：<code>Map&lt;Type, PriceStrategy&gt;</code>；④ 计算票价时查表调用。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>也可以用<b>责任链</b>（依次判断是否命中优惠并叠加）但策略更贴合"一人一种规则"；儿童按身高再分支属于策略内部逻辑；新增人群 = 新增策略类 + 注册，不动计价主流程（开闭原则）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>策略类膨胀（人群多则类多）——可合并相似策略或表格驱动；策略选择逻辑（if-else 判人群）要收敛到工厂/注册表，否则违背模式初衷；优惠可叠加场景要组合策略或单独处理。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>电商优惠计价（满减/折扣/券）策略表驱动；计费系统（按量/包月/阶梯）策略模式；会员等级权益计算；配置中心下发策略参数。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>策略模式和 if-else 的区别（可扩展性、可测试性）；策略模式与状态模式的区别（外部选择 vs 内部状态转移）；为什么不用责任链（一人一种规则，无顺序传递需求）。</div>
  </div>
</div>

# 2.5 天气预报变化时，不同用户收到不同通知并推荐不同行程，适合使用什么设计模式？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>这是典型的<b>观察者模式（发布-订阅）</b>：天气是<b>主题（被观察者）</b>，不同用户/行程推荐器是<b>观察者</b>。天气变化时主题广播事件，所有观察者收到通知各自处理——"一对多、状态变化时自动通知"。也适合用<b>事件驱动/消息队列</b>实现（松耦合的发布订阅）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程：</b>① 定义主题接口（<code>subscribe/unsubscribe/notify</code>）与观察者接口（<code>update(weather)</code>）；② 天气服务作为主题维护观察者列表；③ 天气变化时遍历通知所有观察者；④ 各观察者（通勤用户、户外用户、学生）按自己的规则发通知、推行程。Spring 场景：<code>ApplicationEvent</code> + <code>@EventListener</code> 天然实现；分布式场景：MQ 广播（fanout 交换机 / 广播 topic）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>观察者只依赖主题接口，互不感知（解耦）；推送内容差异（不同用户不同通知）由各观察者自行决定；通知失败不能拖垮主题（异步化、隔离）；"不同行程推荐"也可叠加策略模式选择推荐算法。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>观察者过多时通知变慢（可异步）；观察者异常影响其他观察者（try-catch 隔离）；强引用可能内存泄漏（未注销）；事件风暴（事件链式触发）难排查，需要链路追踪。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>订单状态变化通知多系统（Spring 事件 + <code>@Async</code>）；告警分发（按订阅者路由）；Redis 发布订阅/MQ 广播做跨服务事件；前端事件总线（EventBus）解耦组件。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>观察者和发布订阅的区别（观察者模式主题直接持有观察者 vs 发布订阅经事件总线解耦）；观察者模式如何防止内存泄漏（弱引用/显式注销）；和监听器的关系（监听器是观察者的一种实现）。</div>
  </div>
</div>

# 2.6 浏览器事件通常可以看作什么设计模式？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>浏览器事件体系（<code>addEventListener</code>、事件冒泡/捕获、DOM 事件流）本质是<b>观察者模式</b>：DOM 元素是主题，事件监听器是观察者，事件触发时浏览器通知所有注册的监听器。JS 的 EventTarget 接口就是标准的观察者实现。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程（事件传播三阶段）：</b>① <b>捕获阶段</b>：事件从 window 沿 DOM 树向下传播到目标元素；② <b>目标阶段</b>：到达事件目标；③ <b>冒泡阶段</b>：从目标沿 DOM 树向上传播回 window。监听器可选择在捕获或冒泡阶段触发（<code>addEventListener(type, fn, useCapture)</code>）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b><b>事件委托</b>（事件冒泡的应用）：把监听器挂到父元素，子元素事件冒泡统一处理，适合动态列表——本质是利用观察者 + 冒泡减少监听器数量；<code>stopPropagation</code> 阻断传播，<code>preventDefault</code> 阻止默认行为（两者区别常考）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>监听器不注销会造成内存泄漏（SPA 页面切换后旧监听仍持有 DOM 引用）；冒泡链上事件处理过多影响性能；stopPropagation 滥用会破坏事件委托和其他监听者。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>前端列表/表格用事件委托挂一个监听处理所有行点击；组件销毁时移除监听（<code>removeEventListener</code> / Vue <code>onUnmounted</code>）；自定义组件事件（Vue <code>emit</code>/React 回调）也是观察者思想；EventBus 跨组件通信。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>捕获和冒泡的区别（自上而下 vs 自下而上）；事件委托的原理和好处（冒泡 + 少监听 + 动态元素）；stopPropagation 和 preventDefault 的区别；事件监听器为什么可能内存泄漏（闭包持有引用未注销）。</div>
  </div>
</div>

# 2.7 设计模式了解哪些？请结合项目说明。

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>设计模式是解决特定场景问题的可复用方案，分三类：<b>创建型</b>（单例、工厂、建造者——对象怎么创建）、<b>结构型</b>（代理、装饰器、适配器——对象怎么组合）、<b>行为型</b>（策略、模板方法、观察者、责任链——对象怎么协作）。面试重点不是背模式，而是讲清"场景 → 为什么用 → 怎么落地"。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地（结合项目讲 3-4 个）：</b>① <b>策略模式</b>：告警分级处理（P0 立即电话、P1 飞书、P2 邮件）——策略表驱动，新增级别只加策略类；② <b>责任链 + 工厂</b>：请求校验链（参数 → 权限 → 风控 → 幂等），Spring 注入 <code>List&lt;Handler&gt;</code> 自动装配；③ <b>观察者</b>：订单/故障状态变化通过 Spring 事件通知下游（通知、指标、对账）异步解耦；④ <b>模板方法</b>：多数据源同步流程（抽取 → 转换 → 加载）共用骨架，子类实现差异步骤；⑤ <b>代理模式</b>：Spring AOP 事务/日志拦截本质是动态代理。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>模式选择看<b>变化点</b>：行为变化选策略、协作变化选观察者、职责链选责任链、组合变化选装饰器；不要为模式而模式——先有重复和变化，再有抽象。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>模式是"重构的终点"不是起点；过早抽象增加复杂度；面试中把模式对应到 Spring/Netty/MyBatis 等框架源码里的实例（单例 Bean、AOP 代理、ChannelHandler 责任链、MyBatis 插件）比背定义更有说服力。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>策略和模板方法的区别（委托 vs 继承）；代理和装饰器的区别（控制访问 vs 增强功能）；工厂方法和抽象工厂的区别（一个产品族 vs 多个产品族）；哪些框架源码用了什么模式。</div>
  </div>
</div>
