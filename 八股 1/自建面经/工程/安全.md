# 1.1 什么是 SQL 注入？如何防止？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>SQL 注入是应用把用户可控输入直接拼接进 SQL，导致输入被数据库解析为额外的语法或条件。攻击者可能绕过登录、读取不应访问的数据、修改数据，严重时还可能利用数据库能力影响文件或系统。根因不是“输入里出现了某个特殊字符”，而是代码把数据和 SQL 结构混在了一起。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程（攻击链）：</b>① 应用把参数直接拼进 SQL 字符串；② 输入中的特殊字符（引号、注释符）闭合原语句结构；③ 注入片段被当作 SQL 执行；④ 数据泄露或篡改。注入点常见于登录、搜索、排序、分页和批量接口。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">防止手段：</b>首选参数化查询或 ORM 的绑定参数，让 SQL 模板和参数分开，由驱动负责正确编码；动态表名、排序字段和列名不能直接接收任意输入，应使用白名单映射。还要对输入做长度、类型和业务范围校验，但不能把黑名单过滤当成主要防线。数据库账号遵循最小权限，读写分离，禁止应用账号拥有不必要的管理权限，并通过日志、告警和审计发现异常查询。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>测试时覆盖登录、搜索、排序、分页、批量接口和二次拼接路径，检查是否仍存在字符串拼接；错误响应不要暴露 SQL、表结构和堆栈；上线前配合代码扫描、依赖升级和定向安全测试验证。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>必须用 <code>${}</code> 的动态表名/排序字段是天然高风险点，只能白名单映射；黑名单转义可被编码变体绕过，只能当辅助；安全方案不能只依赖单一手段。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>DAO 层强制 <code>PreparedStatement</code>/MyBatis <code>#{}</code>；排序字段走枚举白名单；错误统一脱敏返回；数据库账号按服务隔离最小权限；上线前 sqlmap 扫描 + 代码审计。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>为什么预编译能防注入（结构解析先于参数绑定，数据不再参与语法解析）；MyBatis <code>#{}</code> 和 <code>${}</code> 的区别；哪些场景必须用 <code>${}</code> 如何保证安全（白名单）；盲注和报错注入是什么。</div>
  </div>
</div>

# 1.2 什么是 XSS 和 CSRF？分别如何防护？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理（XSS）：</b>跨站脚本攻击，攻击者把脚本或可执行内容注入页面，在受害者浏览器中执行。三种类型：<b>反射型</b>（请求参数即时回显）、<b>存储型</b>（恶意内容存数据库后展示）、<b>DOM 型</b>（前端脚本不安全地操作 DOM）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">XSS 防护：</b>按输出上下文做编码——HTML、属性、URL、JavaScript 和 CSS 上下文不能使用同一种转义；富文本必须使用可信的白名单清洗器，避免直接使用 <code>innerHTML</code> 拼接不可信内容；配置 CSP 限制脚本来源；Cookie 设置 <code>HttpOnly</code>、<code>Secure</code> 和合适的 <code>SameSite</code>；避免把 Token 放在可被脚本读取的位置。前端框架的默认转义有帮助，但危险 API、模板拼接和第三方组件仍需人工审查。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">概念原理（CSRF）：</b>攻击者诱导已登录浏览器向目标站点发起跨站请求，浏览器会自动携带 Cookie，使服务端误以为请求来自用户本人。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">CSRF 防护：</b>CSRF Token、校验 <code>Origin/Referer</code>、Cookie 的 <code>SameSite</code>、关键操作二次确认、避免用 GET 修改数据。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>CORS 只控制浏览器读取响应，不能单独替代 CSRF 防护；XSS 与 CSRF 维度不同——XSS 是"信任了不可信输入"，CSRF 是"信任了浏览器自动携带的凭证"；XSS 窃取 Token 会使 CSRF 防护失效，所以先防 XSS。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>富文本场景必须放行 HTML 时过滤最难（标签黑名单易绕过，用白名单清洗器）；全局 CSP 可能影响第三方脚本；<code>SameSite=Strict</code> 可能影响正常跨站跳转场景。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>前端框架默认转义 + 富文本白名单清洗；登录 Cookie 全开 <code>HttpOnly; Secure; SameSite=Lax</code>；写操作接口统一 CSRF Token 校验；安全头（CSP、X-Frame-Options）网关统一配置；敏感操作加二次验证。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>存储型和反射型 XSS 的区别（持久化 vs 一次性）；HttpOnly 防什么（XSS 读 Cookie）；CSRF 为什么第三方站点也能发请求（浏览器自动带 Cookie）；JWT 放 Header 为什么不怕 CSRF（凭证不在 Cookie 里，不会自动携带）。</div>
  </div>
</div>

# 1.3 什么是 DoS 攻击？常见的网络攻防手段有哪些？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>DoS（Denial of Service）是通过消耗 CPU、内存、连接、带宽、线程池或业务配额，使正常用户无法获得服务。单个来源发起的是 DoS，多个来源协同发起的是 DDoS。除了网络洪泛，还可能是 HTTP 慢请求、恶意大包、昂贵查询、登录撞库或接口被高频调用等应用层攻击。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">分层防护（实现流程）：</b>① <b>边缘</b>：CDN、云清洗、Anycast 或高防服务吸收流量；② <b>网关</b>：按 IP、用户、设备、接口和成本做限流、连接数限制和验证码；③ <b>应用</b>：设置请求体大小、超时、并发、队列和熔断；④ <b>数据库</b>：参数化查询、查询成本限制和连接池隔离；⑤ 高耗时任务异步化，非核心功能在压力下限流或降级。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>慢速攻击（Slowloris 占连接不释放）要用请求超时和头部超时；大包攻击用请求体大小限制；应用层攻击（撞库、昂贵查询）靠限流和配额；攻击识别靠流量基线对比。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>防护不能只依赖封 IP，因为攻击可能使用代理、NAT 或分布式来源，且误封会影响正常用户；限流阈值过低会误伤正常流量；清洗和扩容有成本，需要按业务价值分层投入。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>运营上建立基线和告警，关注 QPS、连接数、错误率、P95/P99、CPU、内存、带宽和下游资源；准备应急 Runbook、黑白名单、扩容和回滚方案，并保留取证日志。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>DDoS 和 DoS 的区别（多源 vs 单源）；慢速攻击怎么防（超时 + 连接数限制）；应用层 DoS 和网络层 DoS 的区别；限流有哪些算法（令牌桶/漏桶/滑动窗口）各自特点。</div>
  </div>
</div>

# 1.4 Web 应用中如何保护密码、密钥和敏感数据？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理（密码）：</b>密码不能明文保存，也不能使用普通 MD5 或 SHA-1 直接哈希。应使用带随机盐和成本参数的专用密码哈希算法，如 Argon2id、bcrypt 或 scrypt；登录时用同算法校验，并设置失败次数限制、验证码、风险控制和多因素认证。密码重置 Token 要随机、短时有效、一次性使用，并避免在日志和 URL 中泄露。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程（密钥管理）：</b>密钥和 Token 不应硬编码在代码、镜像或仓库中，运行时从密钥管理系统或受控环境注入，按服务和环境隔离，遵循最小权限和定期轮换。密钥生命周期：生成、分发、访问、轮换、吊销、审计和应急替换都要有记录。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程（敏感数据）：</b>传输使用 TLS；数据库和备份中的敏感字段根据风险进行加密或脱敏，密钥与密文分离保存；日志、Trace、错误信息和监控标签要过滤身份证号、手机号、Token、密码和连接字符串。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>bcrypt/Argon2 自带盐和成本因子，相同密码产生不同哈希；加密 ≠ 哈希——密码用单向哈希，可逆数据（手机号）用加密 + 密钥管理；前端不要把高权限密钥放入可见代码。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>加盐哈希无法防止弱密码被离线爆破（配合强度策略）；密钥轮换要处理存量数据解密兼容；脱敏与可用性冲突（测试环境需要真实数据时用合成数据）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>服务端接口做鉴权、授权、重放防护和审计；日志脱敏组件统一过滤敏感字段；配置中心/环境变量注入密钥，不落代码仓库；数据删除、导出和备份符合组织的保留与合规要求。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>为什么不能用 MD5 存密码（无盐可查彩虹表 + 算力可爆破）；bcrypt 和 MD5 的区别（盐 + 成本因子 + 慢哈希）；加密和哈希的区别（可逆 vs 不可逆）；密钥轮换怎么做（双密钥灰度 + 存量解密）。</div>
  </div>
</div>

# 2.1 什么是对称加密和非对称加密？常见算法有哪些？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="display:flex;flex-wrap:wrap;gap:8px;margin:8px 0 0;">
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">对称加密</b>
        <div style="margin:4px 0 0;">同一个密钥完成加密和解密，速度快、适合大量数据，例如 AES-GCM、ChaCha20-Poly1305。</div>
        <div style="margin:4px 0 0;"><b style="color:#B26E00;">难点：</b>密钥分发和管理——不能把密钥直接随密文传输；关注随机数、Nonce 不复用、认证标签和密钥轮换。</div>
        <div style="margin:4px 0 0;"><b style="color:#B26E00;">注意：</b>只使用 AES-CBC 等不带完整性校验的模式时还需要额外 MAC，优先选择 AEAD 模式。</div>
      </div>
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">非对称加密</b>
        <div style="margin:4px 0 0;">公钥 + 私钥：公钥可公开，私钥必须保护。RSA-OAEP、椭圆曲线用于密钥交换或加密少量数据；RSA-PSS、ECDSA、Ed25519 用于数字签名。</div>
        <div style="margin:4px 0 0;"><b style="color:#B26E00;">代价：</b>计算开销较大，通常不直接加密大文件——用它安全交换一次性对称密钥，再用对称算法加密业务数据（混合加密）。</div>
      </div>
    </div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地（HTTPS 混合加密）：</b>通过证书和密钥交换验证服务端身份并协商会话密钥，后续 HTTP 报文使用对称 AEAD 加密。加密解决机密性和完整性，数字签名或证书链解决身份认证；算法、密钥长度和协议版本应使用经过审计的标准库，不能自行设计密码算法。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>TLS 1.3 用 ECDHE 前向保密密钥交换 + AES-GCM/ChaCha20 对称加密；JWT 的 HS256 是 HMAC 对称签名（共享密钥），RS256/ES256 是非对称签名（公钥验证）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>为什么非对称不用来加密大数据（性能差）；混合加密流程是什么（非对称换对称密钥）；RSA 和 ECC 区别（密钥长度与安全性）；前向保密是什么（每次会话独立密钥，长期私钥泄露不影响历史会话）。</div>
  </div>
</div>
