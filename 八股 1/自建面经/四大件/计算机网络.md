## 一、HTTP

# 1.1 HTTP 请求报文由哪些部分组成？请说明请求行、请求头、空行和请求体的作用。

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：蔚来</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">整体结构：</b>HTTP/1.x 请求报文由请求行、请求头、空行和请求体四部分组成；HTTP/2、HTTP/3 在传输层采用二进制帧，但语义上仍对应方法、目标、头字段和数据。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">请求行：</b>包含方法、请求目标和协议版本，例如 <code>GET /users?page=1 HTTP/1.1</code>。方法表达意图，目标包含路径和查询参数，版本决定协议能力；<code>Host</code> 在 HTTP/1.1 中通常必须出现，用于虚拟主机路由。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">请求头：</b>描述报文元数据和协商信息，如 <code>Content-Type</code>、<code>Content-Length</code>、<code>Authorization</code>、<code>Cookie</code>、<code>Accept</code>、缓存和连接控制字段。头字段不等于业务参数，业务参数应按约定放在路径、查询参数或请求体中。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">空行与请求体：</b>空行（<code>CRLF CRLF</code>）标记请求头结束；请求体承载 JSON、表单、文件等数据，长度由 <code>Content-Length</code> 或分块传输编码确定。<code>GET</code> 通常没有请求体，但协议并非绝对禁止，服务端是否处理要看接口约定。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">常见误区：</b>查询参数属于请求目标，不是请求头；HTTPS 只保护传输过程，服务端解密后仍要做鉴权、参数校验和重放防护；请求体可为空，不能据此判断请求是否成功。</div>
  </div>
</div>

# 1.2 HTTPS 使用 TLS/SSL 加密时，具体加密 HTTP 报文的哪些内容？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：蔚来</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">保护范围：</b>HTTPS 是 HTTP 运行在 TLS 之上。握手完成后，请求行、请求头、请求体，以及响应状态行、响应头、响应体都会作为 TLS 应用数据加密并校验完整性，窃听者不能直接读取 URL 路径、Cookie、Authorization 或业务内容。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">握手概要：</b>客户端发送支持的 TLS 版本、随机数和密码套件；服务端返回证书、随机数并证明私钥持有权；双方通过 ECDHE 等密钥交换协商会话密钥，随后用 AES-GCM 或 ChaCha20-Poly1305 等对称算法保护数据。证书主要解决“我连的是谁”，不直接用于加密全部业务报文。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">仍可见的信息：</b>TCP 头、IP 头和路由所需的网络元数据仍可能可见，包括通信双方 IP、端口、连接时间和流量大小；域名通常还可能通过 DNS、SNI 或证书信息暴露，具体取决于 DNS 加密和 TLS 版本。TLS 不能隐藏所有流量特征。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">边界与误区：</b>HTTPS 只能保护客户端到 TLS 终止点之间的链路；在反向代理或网关处解密后，内部链路仍需重新启用 TLS 或采用可信网络控制。证书校验关闭、信任任意证书或混用 HTTP 会破坏安全性。</div>
  </div>
</div>

# 2.1 TCP 和 UDP 有什么区别？请从连接方式、可靠性和传输速度等方面比较。

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：蔚来、BIGO、腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">连接与语义：</b>TCP 是面向连接的可靠字节流，建立连接后不保留应用消息边界；UDP 是无连接的数据报，每次发送保留独立报文边界，接收端可以知道一份数据报的范围。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">可靠性机制：</b>TCP 通过三次握手、序列号、确认应答、超时重传、滑动窗口、流量控制和拥塞控制，保证尽可能有序、无重复地交付；UDP 不保证到达、顺序和去重，也不负责重传与拥塞控制，可靠性需要应用层补足。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">性能差异：</b>TCP 有握手、状态维护、确认和重传开销，队头阻塞可能放大丢包影响；UDP 首包快、头部小、可广播/多播，应用可以自行选择重传、纠错、拥塞策略，但“UDP 更快”不是无条件结论，网络拥塞时仍会丢包。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">场景选择：</b>文件传输、网页、数据库连接、支付等需要完整一致的数据优先 TCP；实时音视频、在线游戏、DNS、物联网遥测等更关注时延或可容忍少量丢包的场景常用 UDP。QUIC 在 UDP 之上实现可靠传输、多路复用和 TLS，兼顾两者特性。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>TCP 为什么是字节流（协议不理解业务消息）；UDP 是否任何场景都不好（不是，低时延和自定义可靠性是优势）；TCP 如何避免拥塞（慢启动、拥塞避免、快速重传和恢复等机制）。</div>
  </div>
</div>

# 2.2 UDP 是否在任何场景下都不如 TCP？请说明实时音视频、DNS 查询等 UDP 更有优势的场景。

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：蔚来</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;">不是。UDP 没有连接建立、重传和拥塞控制，能够减少等待和协议开销。实时音视频通常宁可丢失少量过期数据，也不希望因为重传导致画面或声音卡顿；DNS 查询报文通常很小，使用 UDP 可以快速完成一次请求，必要时再切换 TCP；在线游戏也常使用 UDP 传输实时状态，再由应用层根据业务需要补充序号、校验或可靠重传。</div>
    <div style="margin:8px 0 0;">选择协议要看业务目标：如果必须保证数据完整、有序且可靠，优先 TCP；如果更看重实时性，且应用可以容忍丢包或自行实现控制，UDP 可能更合适。</div>

# 3.2 TCP 三次握手为什么是三次，而不是两次或四次？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>三次握手的目的：<b>双方确认各自的发送和接收能力都正常</b>，并同步初始序列号（ISN）。SYN = 请求建立连接，ACK = 确认收到。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程：</b>① 客户端发 <code>SYN(seq=x)</code>；② 服务端回 <code>SYN+ACK(seq=y, ack=x+1)</code>；③ 客户端回 <code>ACK(ack=y+1)</code>，连接建立。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节（为什么是三次）：</b>① <b>两次不够</b>：服务端无法确认客户端收到了自己的 SYN——若客户端没收到，客户端会认为连接失败而服务端已在等待，浪费资源；且旧的失效 SYN 可能让服务端误建连接；② <b>三次已够</b>：第三次 ACK 让服务端确认"客户端能收能发"，双方能力互证完成；③ <b>四次多余</b>：第三次 ACK 可以同时捎带任何后续信息，无需单独第四次。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>三次握手引入 1 RTT 建连延迟（HTTP 频繁建连慢）——HTTP/1.1 keep-alive、HTTP/2 连接复用、TLS 1.3 0-RTT 都为此优化；SYN Flood 攻击：服务端半连接队列被打满（syncookie 缓解）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>服务端连接池/keep-alive 减少握手次数；抓包验证 <code>tcpdump -S</code> 看三次握手时序；SYN Flood 防护（syncookies、半连接队列调优）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>两次握手为什么不行（无法确认对方接收能力 + 旧 SYN 误建）；三次握手的序列号同步意义（双方 ISN 独立）；SYN Flood 原理与防护（半连接占满 → syncookie/队列限制）；为什么挥手是四次（全双工独立关闭）。</div>
  </div>
</div>

        <div style="background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:9px 12px;font-size:13.5px;line-height:1.7;">B 回 <code>ACK</code> → A 进入 FIN_WAIT_2，B 进入 CLOSE_WAIT——此时 B 可能还有数据要发。</div>
      </div>
      <div style="position:relative;margin:0 0 8px;">
        <div style="position:absolute;left:-29px;top:3px;width:20px;height:20px;border-radius:50%;background:#9BBBF4;color:#fff;font-size:12px;font-weight:600;display:flex;align-items:center;justify-content:center;">3</div>
        <div style="background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:9px 12px;font-size:13.5px;line-height:1.7;">B 数据发完后发 <code>FIN</code>（B→A 方向关闭）→ B 进入 LAST_ACK。</div>
      </div>
      <div style="position:relative;margin:0;">
        <div style="position:absolute;left:-29px;top:3px;width:20px;height:20px;border-radius:50%;background:#FAAD14;color:#fff;font-size:12px;font-weight:600;display:flex;align-items:center;justify-content:center;">4</div>
        <div style="background:var(--card);border:1px solid var(--border);border-left:3px solid #FAAD14;border-radius:12px;padding:9px 12px;font-size:13.5px;line-height:1.7;">A 回 <code>ACK</code> → B 关闭，A 进入 TIME_WAIT（2MSL 后彻底关闭）。</div>
      </div>
    </div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节（为什么不能简化成三次）：</b>② 和 ③ 不能合并——B 收到 FIN 后<b>不一定立刻没数据要发</b>，需要先 ACK 表示"收到你的关闭请求"，等自己的数据发完再单独发 FIN。如果强制合并（B 收到 FIN 立刻回 FIN），B 没发完的数据就丢了。四次挥手是两个半关闭组合，本质是"ACK 和 FIN 分离"。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>CLOSE_WAIT 堆积 = 应用收到关闭请求但没关 fd（泄漏）；FIN_WAIT_2 长时间停留说明对端 FIN 没到（超时兜底）；TIME_WAIT 大量出现占端口（主动关闭方）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>排查 <code>ss -tan</code>：CLOSE_WAIT 多查应用未释放连接、TIME_WAIT 多查短连接场景；连接池复用减少挥手；服务端优雅停机（先停止接收新请求再等存量处理完再 FIN）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>为什么 B 的 ACK 和 FIN 要分开（B 还有数据要发）；谁进入 TIME_WAIT（主动关闭方）；CLOSE_WAIT 是什么状态（被动方收到 FIN 等应用关闭）；半关闭是什么（shutdown 只关一个方向）。</div>

# 3.4 TCP 四次挥手中的 `2MSL` 有什么意义？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>MSL（Maximum Segment Lifetime）是报文在网络中的最大生存时间（通常 30s~2min，Linux 常见 30s/60s）。TIME_WAIT 持续 <b>2MSL</b>（通常 1~4 分钟），是主动关闭方在发完最后一个 ACK 后必须等待的时间。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">两个意义：</b>① <b>保证最后一个 ACK 可达</b>：若最后的 ACK 丢失，对端会重发 FIN，2MSL 内还能重发 ACK；② <b>让旧报文消亡</b>：2MSL 足以让本连接的所有残留报文（1 个 MSL 从 A 到 B + 1 个 MSL 从 B 到 A）在网络中消失，防止旧连接报文串扰到四元组相同的新连接。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>只有<b>主动关闭方</b>进入 TIME_WAIT；2MSL 期间该四元组不能复用（端口被占）；TIME_WAIT 数量多 = 主动关闭多 = 短连接多。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>高并发短连接场景 TIME_WAIT 堆积占端口（可能到 6 万上限）；缓解：<code>tcp_tw_reuse</code>（仅出向安全）、<code>tcp_tw_recycle</code>（已废弃，有 NAT 问题）、长连接复用、调小 MSL——但缩短 2MSL 有旧报文串扰风险，慎用。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>服务端作为被动方通常没有 TIME_WAIT 问题；客户端/代理频繁主动断开时监控 TIME_WAIT 数量；用连接池/keep-alive 降低建连断连频率；必要时调 <code>tcp_fin_timeout</code> 和 tw_reuse。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>为什么是 2MSL 不是 1MSL（往返双向各一程）；TIME_WAIT 能缩短吗（能但有风险）；tw_reuse 和 tw_recycle 的区别（安全出向复用 vs 废弃全局复用）；服务端会有 TIME_WAIT 吗（主动关闭时也有）。</div>
  </div>
</div>

# 3.5 抓包时为什么可能只看到三个包？ACK 丢失和延迟确认会产生什么影响？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>握手/挥手"只见三个包"是 <b>TCP 延迟确认（Delayed ACK）</b> 的典型现象：接收方不立刻回 ACK，而是等 40ms（或攒到两个报文/有数据捎带）再回——把两个 ACK 合并成一个，或让 ACK 与数据同包捎带。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">三种"只见三包"场景：</b>① <b>三次握手只见 3 个包</b>：正常就是 3 个（SYN/SYN+ACK/ACK），若抓包只看到 SYN、SYN+ACK 而没有最后的 ACK，说明客户端 ACK 未发出或抓包点/过滤问题；② <b>挥手只见 3 个包</b>：被动方把 ACK 和 FIN 合并发出（数据发完时延迟确认触发的 FIN 捎带 ACK）；③ <b>数据传输只见 3 个包</b>：数据 + ACK 捎带（piggyback），实际是 2 个数据段 1 个确认段。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节（ACK 丢失/延迟的影响）：</b>① ACK 丢失：发送方靠<b>快重传</b>（3 个重复 ACK）或<b>超时重传</b>兜底，TCP 不因单个 ACK 丢失而失败（累计确认机制，后续 ACK 覆盖）；② 延迟确认：正常机制，但配合 <b>Nagle 算法</b>可能产生"延迟确认 + 等待小包"的交互死锁（发送方攒小包、接收方攒 ACK）——这就是 <b>糊涂窗口综合征</b>，严重时吞吐骤降，需要用 <code>TCP_NODELAY</code>（禁用 Nagle）解决。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>延迟确认省流量但增加小包 RTT；Nagle 减少小包但和延迟确认叠加会卡顿；网络库默认建议 <code>TCP_NODELAY</code> 关 Nagle（换来低延迟，牺牲小包合并）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>Netty/RPC 客户端开 <code>TCP_NODELAY</code> 降低小请求延迟；抓包判断"缺包"时先排除抓包点位置（中间链路 vs 端点）；性能问题排查看 RTT 和重传统计（<code>netstat -s</code>）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>累计确认是什么（ACK n 表示 n 之前全收到）；Nagle 算法是什么（攒小包到 MSS 或等 ACK 再发）；为什么抓包看到的包数和理论不一样（捎带/延迟确认/合并）；TCP_NODELAY 解决什么问题（Nagle 交互死锁）。</div>
  </div>
</div>

# 3.6 TCP 粘包和半包是什么？如何解决？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>TCP 是<b>字节流</b>协议，没有消息边界——应用层 send 的"消息"只是往流里写字节，接收方可能一次读到多条消息拼在一起（<b>粘包</b>），也可能一条消息分多次到达（<b>半包</b>）。这是 TCP 流特性，不是协议 bug。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">粘包半包产生原因：</b>① 发送方：Nagle 合并小包、批量发送；② 接收方：recv 缓冲区一次取多、应用读得不及时；③ 网络：分段（MSS）和重组。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">解决方案（消息定界四种）：</b>① <b>固定长度</b>：每条消息定长，不足补位（简单但浪费）；② <b>分隔符</b>：以 <code>\n</code> 或特殊字符结尾（适合文本协议，如 Redis RESP、HTTP 头）；③ <b>长度前缀</b>：包头 4 字节长度 + 消息体（最通用，Netty <code>LengthFieldBasedFrameDecoder</code>）；④ <b>自定义协议头</b>：魔数 + 版本 + 长度 + 业务字段（RPC 框架标配）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>解包流程 = 缓冲累积 → 按协议判断是否凑齐一条 → 拆出完整消息 → 剩余留待下次；半包要"攒够再处理"，粘包要"切分处理"；<code>TCP_NODELAY</code> 减少发送侧粘包但不能根治（接收侧仍可能合并）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>分隔符要防内容冲突（转义）；长度前缀要防恶意超大长度（校验上限）；固定长度浪费带宽；协议设计要兼容拆包缓冲（内存上限防攻击）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>Netty 用 <code>LengthFieldBasedFrameDecoder</code>（长度前缀）处理粘包半包；自研 RPC 协议带魔数 + 长度；HTTP/Redis 协议天然带定界（\r\n / 长度）；压测覆盖大数据包和小包混合场景。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>UDP 会粘包吗（不会，数据报有边界，但可能丢包乱序）；粘包和半包谁更常见（都常见，取决于发送频率和大小）；为什么 TCP 不保留消息边界（字节流设计，交给应用层定界）。</div>
  </div>
</div>

# 3.7 UDP 接收缓冲区只有 10 KB，但数据包有 100 KB，能否正常接收？TCP 的情况有什么不同？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>分两层回答：① <b>UDP 单包上限</b>：IP 包最大 65535 字节，UDP 载荷上限约 65507 字节（64KB 级）——100KB 的"数据包"本身就超过单包上限，应用层必须分片或分包；② <b>接收缓冲区 10KB</b>：UDP 是数据报语义，一个完整报文必须一次性放进缓冲区——10KB 缓冲区装不下单个大报文时，<b>整个报文被丢弃</b>（不是截断保留），这就是"UDP 丢大包"的常见原因。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现细节（UDP 侧）：</b>① 100KB 数据发 UDP：要么应用层拆成多个 ≤MTU 的数据报（自己处理序号/重组/丢包），要么用 >MTU 的 IP 分片（不推荐：分片丢失率高）；② 接收：单次 <code>recvfrom</code> 必须给足缓冲区（>= 报文大小），缓冲区不够则报文丢弃；③ 调大 <code>SO_RCVBUF</code> 只影响"能缓存多少个完整报文"，不影响单个大报文放不下。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">TCP 侧对比：</b>TCP 是字节流，没有"报文必须一次读完"的限制——10KB 缓冲区 + 100KB 数据：<code>recv</code> 分多次读完即可，内核窗口和流控保证不丢（缓冲区满则发送方停发，数据留在网络/对端）；TCP 也支持大数据（不分包语义，MSS 分段重组由内核完成）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>UDP 应用层设计规范：报文 < MTU（约 1472 字节，避免 IP 分片）、缓冲区按最大报文定、丢包重传自行实现；TCP 无需关心这些（内核负责）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>UDP 大包在公网几乎必丢（分片 + 无重传）；调大 UDP 缓冲区解决"缓存报文数"而非"单包大小"；100KB 用 UDP 传输本身就是设计错误，要么拆包要么换 TCP/QUIC。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>音视频数据按帧拆包（每包 1KB 级）+ 序号重组；DNS 用 UDP 小报文（<512B 无扩展时）；大文件/大消息传输走 TCP 或 QUIC；网络库设置 <code>SO_RCVBUF</code> 并监控丢包统计。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>UDP 报文最大多少（65507 字节）；为什么 UDP 大报文会被丢弃而不是截断（数据报原子性）；MTU 和 MSS 的区别；怎么安全传大文件用 UDP（应用层分片 + 序号 + 重传 = 自研可靠 UDP）。</div>
  </div>
</div>

# 4.1 HTTP 和 HTTPS 有什么区别？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：BIGO、腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="display:flex;flex-wrap:wrap;gap:8px;margin:8px 0 0;">
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">HTTP</b>
        <div style="margin:4px 0 0;">明文传输，数据可被窃听、篡改，无法验证服务器身份（可能被中间人冒充）。</div>
        <div style="margin:4px 0 0;"><b style="color:#B26E00;">代价：</b>无加密开销，性能略快（少 TLS 握手）；仅适合无敏感数据的场景。</div>
      </div>
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">HTTPS</b>
        <div style="margin:4px 0 0;">HTTP + TLS：加密（防窃听）、完整性校验（防篡改）、证书认证（防冒充）。</div>
        <div style="margin:4px 0 0;"><b style="color:#B26E00;">代价：</b>多 1~2 次 RTT 握手（TLS 1.3 已优化为 1-RTT/0-RTT）；CPU 加解密开销（现代硬件可忽略）；证书成本与运维。</div>
      </div>
    </div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程（HTTPS 核心）：</b>① 客户端验证服务器证书（证书链 → CA 信任）；② 密钥交换（ECDHE/RSA）协商对称会话密钥；③ 后续 HTTP 报文用对称加密（AES-GCM）传输；④ 每次传输带认证标签防篡改。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>HTTPS 加密的是 HTTP 内容（URL 路径和参数在 TLS 内），但域名（SNI）和 IP 可见；默认端口 80 vs 443；证书有效期和续期（Let's Encrypt 自动化）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>全站 HTTPS 是标配（浏览器标记不安全）；混合内容（HTTPS 页面引 HTTP 资源）会被拦截；TLS 握手优化（会话复用、0-RTT）降低性能损失；自签证书仅限内网。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>Nginx/网关终结 TLS（证书集中管理）；HTTP 跳转 HTTPS（301 + HSTS）；内网服务间也可用 mTLS；证书监控告警防过期。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>HTTPS 握手具体几轮（TLS 1.2 2-RTT、1.3 1-RTT）；对称和非对称在 HTTPS 里各干什么（密钥交换 vs 数据加密）；中间人攻击怎么防（证书链验证）；HSTS 是什么（强制 HTTPS）。</div>
  </div>
</div>

# 4.2 HTTP/1.0、HTTP/1.1、HTTP/2.0 和 HTTP/3.0 有什么区别？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="display:flex;flex-wrap:wrap;gap:8px;margin:8px 0 0;">
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">HTTP/1.0</b>
        <div style="margin:4px 0 0;">每个请求单独建立 TCP 连接，用完即断——连接开销大，慢。</div>
      </div>
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">HTTP/1.1</b>
        <div style="margin:4px 0 0;"><b>持久连接（keep-alive）</b>复用 TCP；管线化（基本失败）；Host 头、分块传输、断点续传。<b>队头阻塞</b>：一个请求响应慢，后续排队。</div>
      </div>
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">HTTP/2</b>
        <div style="margin:4px 0 0;"><b>多路复用</b>（二进制分帧，一个 TCP 并发多个流）解决应用层队头阻塞；头部压缩（HPACK）；服务端推送。仍有 <b>TCP 层队头阻塞</b>（丢包时整条连接阻塞）。</div>
      </div>
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">HTTP/3</b>
        <div style="margin:4px 0 0;">基于 <b>UDP 的 QUIC</b>：连接迁移、0-RTT 握手、独立流（丢包只阻塞该流）——彻底解决队头阻塞；内核态拥塞控制。</div>
      </div>
    </div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>演进主线 = 减少连接开销（1.0→1.1）+ 消除队头阻塞（1.1→2→3）+ 减少握手（TLS 1.3 + QUIC 0-RTT）；HTTP/2 的二进制分帧和流优先级是核心机制；HTTP/3 需要 QUIC 支持（UDP 端口 443）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>HTTP/2 在弱网（高丢包）下反而比 1.1 慢（TCP 队头阻塞放大）；HTTP/3 新协议生态和中间设备兼容性仍在完善；升级收益要实测（多路复用对图片多的小资源页面收益大）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>Web 服务开启 HTTP/2（Nginx 一行配置）；资源合并/雪碧图在 HTTP/2 下不再必要；长连接 + 连接池是 1.1 下的标配优化；CDN/网关支持 HTTP/3 后按需开启。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>HTTP/2 队头阻塞和 HTTP/1.1 的区别（流内 vs 请求级）；QUIC 为什么能解决队头阻塞（独立流 + UDP）；0-RTT 是什么（首次握手后复用会话票据）；服务端推送为什么用得少（缓存命中率问题）。</div>
  </div>
</div>

# 4.3 HTTPS 的完整握手和加密过程是怎样的？密钥如何交换？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>HTTPS 用<b>混合加密</b>：非对称（RSA/ECDHE）只用于身份认证和密钥协商，协商出的对称密钥（AES-GCM）用于实际数据加密——兼顾安全与性能。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">TLS 1.2 完整握手（2-RTT）：</b>① ClientHello（支持的版本/加密套件/随机数）→ ② ServerHello + 证书 + ServerKeyExchange（ECDHE 参数）→ ③ 客户端<b>验证证书链</b>（CA 信任 + 域名匹配），用 ECDHE 计算会话密钥 premaster；④ 双方交换 Finished（用协商密钥加密），握手完成。TLS 1.3 精简为 <b>1-RTT</b>（证书和密钥交换参数合并），会话恢复时 <b>0-RTT</b>。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">密钥交换两种方式：</b>① <b>RSA 密钥交换</b>：客户端用服务器公钥加密 premaster 发给服务器——私钥泄露则历史流量全解密（无前向保密），已弃用；② <b>ECDHE</b>：双方用椭圆曲线 Diffie-Hellman 各自计算同一会话密钥，<b>私钥不传输</b>——即使长期私钥泄露，历史会话仍安全（前向保密），TLS 1.3 只允许这种方式。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>证书的作用是<b>把公钥绑定到域名</b>（防中间人替换公钥）；会话密钥每次握手随机生成；握手中的 Finished 消息互相验证对方持有同一密钥。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>2-RTT 握手延迟（用会话复用/0-RTT 优化）；0-RTT 有重放风险（只用于幂等请求）；证书私钥泄露是灾难（轮换 + 吊销）；中间设备（防火墙）可能干扰 TLS 1.3。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>网关终结 TLS（客户端少一次握手）；会话缓存（session ticket）减少重复握手；证书自动化续期；安全扫描验证 TLS 版本和套件。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>前向保密是什么（ECDHE 保证历史流量不被长期私钥解密）；证书链验证过程（根 CA → 中间 CA → 叶子证书）；1-RTT 和 0-RTT 的区别；为什么不用非对称直接加密数据（性能差）。</div>
  </div>
</div>

# 4.4 HTTP/3 为什么使用基于 UDP 的 QUIC？QUIC 解决了什么问题？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>QUIC 是基于 UDP 实现的"类 TCP"传输协议，HTTP/3 跑在 QUIC 上。选 UDP 的原因：<b>TCP 在操作系统内核里，无法按需改造</b>（升级 TCP 要改内核和全网设备），UDP 只是信封，可靠性全部由 QUIC 在用户态实现——协议演进不再受制于内核和中间设备。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">QUIC 解决的问题：</b>① <b>队头阻塞</b>：HTTP/2 多条流共享一个 TCP，一条流丢包会阻塞所有流；QUIC 每个流独立（独立序列号），丢包只影响该流；② <b>握手延迟</b>：TLS 1.3 集成在 QUIC 内，首次 1-RTT、复用 0-RTT（TCP+TLS 需要 2-3 RTT）；③ <b>连接迁移</b>：连接 ID 不依赖四元组，WiFi↔4G 切换不断连（TCP 换 IP 就断）；④ <b>前向纠错/更细拥塞控制</b>：用户态可灵活实现。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>QUIC 自实现拥塞控制、重传、乱序重组（用户态，可平滑升级算法）；0-RTT 有重放风险需应用层幂等；UDP 可能被中间网络 QoS 限速（运营商对 UDP 不友好）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>UDP 流量被部分网络设备限制/丢包；QUIC 生态（代理、防火墙识别）不如 TCP 成熟；弱网下 QUIC 的优势最明显，好网络下与 HTTP/2 差距不大。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>视频/直播/弱网场景优先开启 HTTP/3（CDN 支持）；服务端（Nginx/Envoy）配置 QUIC 监听；客户端库（Cronet/OkHttp）支持自动升级；内网场景收益有限可不启用。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>QUIC 和 TCP 的区别（内核 vs 用户态、独立流）；为什么说 QUIC 解决了队头阻塞（流独立 + 独立序列号）；连接迁移怎么实现（连接 ID 代替四元组）；0-RTT 的风险（重放）。</div>
  </div>
</div>

# 5.1 网络七层模型是什么？HTTP 和 TCP 分别位于哪一层？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">

  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>OSI 七层模型自下而上：<b>物理层</b>（比特流/网线信号）→ <b>数据链路层</b>（MAC 帧/交换机）→ <b>网络层</b>（IP 路由/路由器）→ <b>传输层</b>（TCP/UDP 端口）→ <b>会话层</b>（建立会话）→ <b>表示层</b>（编码加密）→ <b>应用层</b>（HTTP/FTP/DNS）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">HTTP 和 TCP 的位置：</b><b>HTTP 在应用层</b>（第 7 层）；<b>TCP 在传输层</b>（第 4 层）。实际使用的是四层 TCP/IP 模型：应用层（HTTP/DNS）→ 传输层（TCP/UDP）→ 网络层（IP）→ 网络接口层。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>每层只和相邻层交互，上层数据封装进下层（HTTP 报文 → TCP 段 → IP 包 → 帧）；分层的好处是各层独立演进（换传输层协议不用改应用）；面试常结合问题考：DNS 用 UDP 但也在应用层、负载均衡"四层/七层"就是指传输层/应用层。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>严格七层是理论模型，实际 TCP/IP 四层更贴近实现；分层过细增加开销和复杂度——实际工程按需合并。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>排障按层下钻：应用层看 HTTP 状态码 → 传输层看端口/TCP 状态 → 网络层看连通性（ping/traceroute）；四层 LB 转发 TCP、七层 LB 解析 HTTP。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>TCP/IP 四层和 OSI 七层的对应关系；DNS 在哪层（应用层，但用 UDP/53）；路由器/交换机分别工作在哪层（网络层/数据链路层）；负载均衡四层七层的区别（是否解析应用内容）。</div>

# 5.3 路由器和交换机有什么区别？路由器的基本原理是什么？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">

  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="display:flex;flex-wrap:wrap;gap:8px;margin:8px 0 0;">
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">交换机（二层）</b>
        <div style="margin:4px 0 0;">工作在<b>数据链路层</b>，按 <b>MAC 地址</b>转发帧，连接同一子网内的设备（局域网）。</div>
        <div style="margin:4px 0 0;">维护 MAC 地址表（学习源 MAC），未知 MAC 广播，目标明确则单播转发。</div>
      </div>
      <div style="flex:1 1 300px;min-width:0;background:var(--card);border:1px solid var(--border);border-left:3px solid #3A5FBF;border-radius:12px;padding:10px 12px;font-size:13.5px;line-height:1.7;">
        <b style="color:#3A5FBF;">路由器（三层）</b>
        <div style="margin:4px 0 0;">工作在<b>网络层</b>，按 <b>IP 地址</b>转发包，连接不同子网/网络（跨网段），是互联网的枢纽。</div>
        <div style="margin:4px 0 0;">维护路由表（直连/静态/动态学习），逐跳转发（下一跳），NAT 转换、选路。</div>
      </div>
    </div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">路由基本原理（转发流程）：</b>① 收到 IP 包，提取目的 IP；② 查<b>路由表</b>（最长前缀匹配：匹配到最具体的路由条目）；③ 确定下一跳地址和出接口；④ 重写 MAC 头（源/目的 MAC 换为下一跳的）后转发——这就是"路由是逐跳的，IP 不变、MAC 每跳换"；⑤ 无匹配路由则丢弃（回 ICMP 不可达）。路由表来源：直连路由、静态配置、动态协议（OSPF/BGP）学习。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>家庭"路由器"实际是路由器 + 交换机 + NAT + DHCP + 无线 AP 的合体；三层交换机 = 交换机 + 路由能力（VLAN 间路由）；路由环路靠 TTL 递减防死循环。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>路由表错误/环路导致网络中断；动态路由收敛需要时间（故障切换秒级）；NAT 影响端到端（P2P 需要打洞）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>数据中心：交换机组内网 + 路由器/网关出公网；排查跨网段不通：ping（三层）通而应用不通查端口；<code>traceroute</code> 定位丢包跳点。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>交换机怎么学习 MAC（泛洪 + 源地址学习）；路由器怎么防环路（TTL、水平分割）；NAT 原理（内网 IP ↔ 公网端口映射）；三层交换机和路由器区别（硬件转发的路由）。</div>

# 5.4 腾讯会议可能使用什么协议？为什么可能采用基于 UDP 的自研可靠协议？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>腾讯会议是实时音视频场景，媒体流（音视频）走 <b>UDP/RTP</b>（或基于 UDP 的自研可靠协议），控制信令（入会、发言权、布局）走 TCP/HTTPS。核心矛盾：实时性优先——TCP 的重传和队头阻塞会把延迟拖到不可用。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">媒体链路（UDP 方案）：</b>① 音视频编码（OPUS 音频 / VP8/AV1 视频）→ ② RTP 打包（带序号和时间戳）→ ③ UDP 传输（低延迟）；④ RTCP 反馈丢包率/RTT → ⑤ 自适应码率 + FEC + 选择性重传；⑥ 弱网时降分辨率/帧率保通话。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">为什么用自研可靠协议：</b>① <b>延迟可控</b>：TCP 重传导致延迟不可控（RTO 秒级），RTP 选择性重传只救关键帧；② <b>无队头阻塞</b>：一帧丢包不影响后续帧处理（TCP 会阻塞后续所有数据）；③ <b>FEC 能力</b>：冗余包恢复丢包，无需往返；④ <b>码率自适应</b>：按反馈实时调整；⑤ <b>抗抖动</b>：接收端 Jitter Buffer 吸收抖动。控制信令仍走 TCP/HTTPS（可靠性优先）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>NAT 穿越用 STUN/TURN（打洞失败走 TURN 中继）；音视频 QoS 优先级高于屏幕共享；多端接入（网页 WebRTC、客户端自研）需要协议互通层。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>UDP 公网穿越成功率依赖打洞（TURN 中继增加延迟和带宽成本）；运营商可能限制 UDP；弱网极端情况降级为语音/文字。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>会议系统：信令 TCP + 媒体 UDP + TURN 兜底；监控丢包率、RTT、卡顿率、码率自适应次数；弱网模拟（丢包/抖动注入）压测。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>为什么信令不用 UDP（丢一条指令就是事故）；WebRTC 的传输层是什么（UDP + SRTP）；TURN 中继什么时候需要（对称 NAT 打洞失败）；音视频为什么不用 HTTP（延迟 + 双向实时）。</div>
  </div>

    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>输入 URL 到页面展示 = 一次完整的"解析 → 寻址 → 连接 → 传输 → 渲染"链路，几乎覆盖全部网络知识点，面试常从这条链路展开追问。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">完整流程（九步）：</b>① <b>URL 解析</b>：拆出协议、域名、端口、路径、参数；② <b>DNS 解析</b>：查浏览器缓存 → 系统缓存 →  hosts → 本地 DNS → 递归/迭代解析得到 IP（DNS over UDP/53）；③ <b>TCP 连接</b>：三次握手（HTTPS 加 TLS 握手）；④ <b>HTTP 请求</b>：组装请求行/头/体，可能先查缓存（强缓存/协商缓存）；⑤ <b>服务端处理</b>：网关/负载均衡 → 应用 → 数据库，返回响应；⑥ <b>响应接收</b>：状态码判断、解压（gzip）、按 Content-Type 处理；⑦ <b>解析 HTML</b>：构建 DOM 树（边解析边加载）；⑧ <b>加载子资源</b>：CSS/JS/图片（并发连接，HTTP/2 多路复用），CSSOM 构建，JS 执行（可能阻塞渲染）；⑨ <b>渲染</b>：DOM + CSSOM → 渲染树 → 布局 → 绘制 → 合成显示。</div>

    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>每一环都可能失败——DNS 解析失败（缓存/换 DNS）、连接超时（重试/降级）、响应慢（超时/熔断）、渲染慢（懒加载/骨架屏）；优化按链路逐环排查（Chrome DevTools 的 Network/Performance 面板就是这条链路的可视化）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>性能优化对应链路各环：CDN（就近 + 缓存）、DNS 预解析（dns-prefetch）、连接复用、静态资源缓存（强缓存 + 版本号）、JS 异步加载、图片懒加载、首屏 SSR/骨架屏；监控首屏时间、TTFB、FCP/LCP。</div>

# 5.6 Protocol Buffers 是什么？为什么适合服务间通信？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>Protobuf 是 Google 的二进制序列化协议：用 .proto 文件定义消息结构，生成各语言代码，序列化为紧凑二进制。对比 JSON/XML：体积小、解析快、有强类型 Schema。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">为什么适合服务间通信：</b>① <b>体积小</b>：二进制 + varint 变长编码 + 字段号代替字段名，比 JSON 小 3-10 倍——省带宽省序列化时间；② <b>解析快</b>：无需字符串解析，直接按字段号定位；③ <b>强类型契约</b>：.proto 即接口文档，前后端/多语言按同一 Schema 生成代码，类型错误编译期发现；④ <b>兼容演进</b>：字段有唯一编号，新增字段向后兼容（旧客户端忽略未知字段），删除字段保留编号即可——服务间升级互不阻塞；⑤ <b>多语言</b>：官方支持 Java/Go/C++/Python 等，RPC（gRPC）默认用它。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>字段编号 1-15 用 1 字节（省空间），高频字段用小编号；<code>repeated</code> 对应数组；<code>optional</code>/<code>oneof</code> 表达可选语义；升级规则：只加字段、不删不改已有编号和类型。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>二进制不可读（调试要工具转 JSON）；.proto 变更需要版本管理（破坏性变更要评估）；对浏览器直连不友好（网页端用 gRPC-Web 或 JSON 映射）；小数据量场景收益不明显（仍有 Schema 维护成本）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>RPC 框架（gRPC/Dubbo）消息体用 Protobuf；服务间高 QPS 接口序列化从 JSON 换 Protobuf 可显著降延迟；Schema 仓库统一管理 .proto 版本；压测对比序列化耗时和包体大小。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>Protobuf 为什么比 JSON 小（二进制 + varint + 字段号）；向后兼容怎么保证（字段编号机制）；varint 编码是什么（小整数 1 字节）；gRPC 为什么选 Protobuf（契约 + 性能 + 流式支持）。</div>

# 5.7 零拷贝是什么？用户态协议栈能解决什么问题？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>零拷贝 = 减少数据在<b>磁盘/内核缓冲/用户空间</b>之间的拷贝次数。传统读文件再发送要 4 次拷贝 + 4 次上下文切换；零拷贝技术把拷贝降到 1-2 次，主要在<b>内核内完成</b>。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现方式（三种）：</b>① <b>mmap + write</b>：文件映射到用户地址空间，省去内核→用户的一次拷贝（仍有一次 CPU 拷贝）；② <b>sendfile</b>：<code>sendfile(fd, socket)</code> 直接内核内"磁盘 → socket"（配合 <code>DMA gather</code> 真正零 CPU 拷贝），Linux 下文件→网络传输的标准答案；③ <b>splice/io_uring</b>：管道式零拷贝；<b>Kafka 用 sendfile</b> 发日志文件，<b>Netty 的 FileRegion</b> 即封装 sendfile。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">用户态协议栈（DPDK 等）：</b>把 TCP/IP 协议栈从内核搬到用户态，用 DPDK 直接操作网卡（轮询 + 大页 + 无锁队列），解决：① <b>内核协议栈开销</b>（中断、锁、上下文切换、拷贝）；② <b>单机连接数/吞吐瓶颈</b>；③ <b>协议定制能力</b>（自研可靠 UDP、新拥塞算法）。典型场景：LB/网关（LVS 的 DPDK 版）、高频交易、CDN 边缘。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>零拷贝适用"<b>数据不经用户处理</b>"（文件→网络、网络→文件）；数据要加工（编解码）就省不了；用户态协议栈放弃内核协议栈的通用性（要自己管 TCP 状态、ARP、路由）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>零拷贝省 CPU 但牺牲灵活性（不能修改数据）；用户态协议栈复杂度高（网络栈细节自理）、绑定特定网卡驱动、排障困难——只在高吞吐刚需场景用；io_uring 是内核态的新答案（异步 + 减少系统调用）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>Kafka 日志发送、静态文件服务（Nginx sendfile）、大文件下载用零拷贝；RPC 框架大响应体考虑 FileRegion；网关压测发现内核协议栈瓶颈时评估 DPDK/用户态栈。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>传统 4 次拷贝在哪（磁盘→内核→用户→内核→网卡）；sendfile 为什么快（内核内完成 + DMA）；零拷贝能处理需要改数据的场景吗（不能）；DPDK 为什么快（用户态轮询 + 免中断 + 大页）。</div>
  </div>
</div>

# 5.8 `epoll` 的工作过程和底层原理是什么？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>epoll 是 Linux 的 I/O 多路复用机制：<b>一个线程同时监听成千上万个 fd</b>，内核通知哪些 fd 就绪（可读/可写），应用只处理就绪的 fd——解决"每连接一线程"的资源瓶颈。相比 select/poll：O(1) 复杂度、无上限、不重复拷贝 fd 集合。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">工作过程（三个系统调用）：</b>① <code>epoll_create</code>：内核创建 eventpoll 对象（红黑树 + 就绪链表）；② <code>epoll_ctl</code>：把要监听的 fd 注册进红黑树，并挂回调；③ <code>epoll_wait</code>：阻塞等待，就绪事件由回调放入就绪链表，用户取走处理。fd 就绪时（数据到达触发软中断）回调把 fd 加入就绪链表并唤醒等待线程。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">两种触发模式：</b>① <b>LT（水平触发，默认）</b>：只要缓冲区还有数据就持续通知——不易漏事件、编码简单（Java NIO 默认）；② <b>ET（边缘触发）</b>：只在状态变化（空→有数据）时通知一次——必须一次读完否则漏数据，性能更高（Netty 默认 ET + 循环读到 EAGAIN）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>就绪事件通过回调驱动（不是轮询）；红黑树支持动态增删 fd；epoll_wait 只返回就绪列表（O(就绪数)）；惊群问题用 EPOLLEXCLUSIVE/多线程各建 epoll 缓解。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>ET 模式读不干净就丢数据（必须循环读）；epoll 只对网络 fd 友好（普通文件不生效，磁盘 I/O 用 io_uring/AIO）；线程模型仍要设计好（单线程事件循环 vs 多线程）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>Netty/Redis/Nginx 都是 epoll 驱动；Java NIO（Selector）底层即 epoll（Linux）；高连接场景（网关、IM）用事件驱动而非线程池；连接数和 QPS 压测验证。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>epoll 和 select/poll 的区别（复杂度、上限、回调 vs 轮询）；LT 和 ET 的区别及各自坑（漏事件 vs 漏数据）；epoll 为什么快（红黑树 + 回调 + 就绪链表）；惊群问题（多线程同时 wait 同一 epoll）。</div>
  </div>
</div>

# 5.9 如何让 UDP 实现类似 TCP 的可靠传输效果？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>UDP 只提供"尽力交付"，可靠传输需要在<b>应用层补齐 TCP 的能力</b>：序号（排序/去重）、确认（ACK）、重传（超时/NACK）、流量控制、拥塞控制。这就是"可靠 UDP"（RUDP），KCP/QUIC/自研协议都是这条路。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程（核心机制）：</b>① <b>序号</b>：每个包带递增序号，接收方按序重组、去重；② <b>确认</b>：接收方回 ACK（可累计/批量/捎带），发送方维护已确认水位；③ <b>重传</b>：超时未确认 → 重传；或接收方发现空洞 → 回 NACK 快速要求重传（比等超时快，RTP/RTX 思路）；④ <b>流控</b>：滑动窗口限制在途包数；⑤ <b>拥塞控制</b>：按丢包率/RTT 动态调整发送速率（借鉴 TCP 或 BBR 思路）；⑥ 可选 <b>FEC</b>：冗余包提前恢复部分丢包。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">成熟方案：</b><b>KCP</b>（游戏场景可靠 UDP，ARQ 模型，快重传 + 非退让流控）、<b>QUIC</b>（完整可靠传输 + 加密 + 多路复用）、<b>SRT</b>（音视频可靠 UDP，FEC + 重传混合）；自己实现时按场景裁剪：游戏要低延迟（快速重传）、文件传输要高吞吐（窗口大）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>可靠 UDP ≠ 照搬 TCP——TCP 的重传策略（超时指数退避）不适合实时场景；按业务选机制：允许丢的加 FEC、不能丢的加重传、乱序容忍的省排序；序号要防回绕。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>自研可靠 UDP 复杂度高（状态机、窗口、拥塞都要自己维护和测试）；能直接用 TCP/QUIC 时别重复造轮子；可靠 UDP 的价值在"保留 UDP 的低延迟和可定制性"。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>游戏同步：KCP；视频传输：SRT/QUIC；弱网文件传输：自研 RUDP（序号 + NACK + 窗口）；优先评估 QUIC 现成库（成熟、加密、多路复用）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>NACK 和超时重传哪个快（NACK 快，接收方主动报缺）；可靠 UDP 和 TCP 性能差异（TCP 内核优化成熟，RUDP 场景定制）；KCP 为什么适合游戏（低延迟优先于公平性）；FEC 和重传怎么搭配（按丢包率）。</div>
  </div>
</div>

# 5.10 即时通讯软件使用 UDP 时，如何保证消息有序？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>UDP 不保证顺序、不保证到达，IM 要自己实现<b>应用层可靠传输</b>：序号 + 确认 + 重传 + 乱序缓冲。核心思路是"TCP 的能力在用户态重造，但只做业务需要的那部分"。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程（四要素）：</b>① <b>序号</b>：每条消息带单调递增的 seq（发送方维度），接收方按 seq 排序；② <b>乱序缓冲</b>：接收方维护滑动窗口，seq 不连续的消息先缓存，补齐后再按序上抛——解决乱序；③ <b>确认与重传</b>：接收方回 ACK（可批量），发送方超时未确认则重传——解决丢失；④ <b>去重</b>：重传可能导致重复，按 seq 去重（已经上抛的 seq 直接丢弃）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">IM 场景的特殊设计：</b>① 消息有<b>全局唯一 ID</b>（服务端分配）+ 会话内 seq 双轨；② 多端同步靠服务端下发（消息序号由服务端保证单调）；③ 客户端收到乱序消息先进本地缓存，按序展示（聊天界面不能乱）；④ 拉取补漏：客户端发现 seq 空洞时向服务端拉取缺失消息（比重传更可靠）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>UDP 方案适合"高频小消息 + 丢得起少量"的场景（语音、游戏状态）；IM 文本消息要求不丢，所以很多 IM 实际是"UDP 通道 + 服务端兜底（TCP/HTTP 拉取）"双通道；心跳检测连接状态。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>自研可靠传输复杂度高（序号管理、窗口、重传策略、流量控制都要自己做）；完全可靠场景直接用 TCP/QUIC 更省事；UDP + 自研的收益是低延迟和可定制。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>IM 消息：TCP 长连接为主 + UDP 心跳；语音/实时状态：UDP + 序号丢弃旧包；游戏帧同步：UDP 带序号 + 插值预测；消息补漏接口（拉缺失 seq 区间）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>乱序缓冲怎么实现（窗口 + 缓存 + 排序上抛）；序号溢出怎么办（回绕处理）；UDP 丢包率高了怎么办（降级 TCP/重传策略）；为什么聊天界面必须按序（会话上下文）。</div>
  </div>
</div>

# 5.11 视频聊天网络质量不好时，如何从协议层优化通话质量？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>实时音视频优先<b>实时性</b>而非可靠性——宁可丢旧帧也不等重传（等重传 = 卡顿）。所以走 UDP/RTP 而非 TCP，协议层优化围绕"抗丢包、控延迟、自适应码率"三条线。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">协议层优化手段：</b>① <b>传输协议</b>：RTP（实时传输）+ RTCP（反馈）；弱网可换 SRT/QUIC（带前向纠错）；② <b>前向纠错（FEC）</b>：发送冗余包，丢包无需重传即可恢复（用带宽换延迟）；③ <b>丢包重传（NACK/RTX）</b>：对关键帧（I 帧）选择性重传，P 帧丢失直接跳过；④ <b>自适应码率（ABR）</b>：根据 RTCP 反馈的丢包率/RTT 动态降码率、降分辨率/帧率，保住通话不中断；⑤ <b>Jitter Buffer</b>：接收端抖动缓冲吸收网络抖动（过大增延迟，过小易卡顿，动态调整）；⑥ <b>关键帧请求</b>：画面花屏时向对端请求 I 帧（PLI/FIR）快速恢复。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>QoS 优先级：语音 > 视频 > 数据；RTCP 反馈周期要快（丢包率统计粒度）；拥塞时先降视频再降音频（保语音）；带宽极差时降级为语音通话（音频码率远低于视频）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>FEC 冗余占带宽（好网络下是浪费）；Jitter Buffer 大则延迟高（说话对不上口型）；重传关键帧在大丢包时仍可能失败——需要多级降级策略；公网穿越（NAT）需要 STUN/TURN（TURN 中继增加延迟）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>WebRTC 自带 ABR + FEC + NACK + Jitter Buffer 全套（业务直接用）；自研音视频按上述链路实现；监控丢包率、RTT、卡顿率、码率自适应次数。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>为什么音视频不用 TCP（重传导致延迟不可控）；FEC 和重传怎么选（丢包率低用重传、高用 FEC）；PLI/FIR 是什么（请求关键帧恢复花屏）；WebRTC 为什么选 UDP（实时性）。</div>

# 5.12 《英雄联盟》游戏中的网络通信过程是怎样的？会用到哪些协议，数据如何传输？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">

    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>游戏通信分两类流量：<b>对局实时数据</b>（位置、技能、状态，频率高、延迟敏感）和<b>非对局数据</b>（登录、商城、匹配、战绩，可靠性优先）。两类流量用不同协议。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">对局实时链路（UDP/KCP 类）：</b>① 客户端以固定频率（如 30Hz）上传操作（移动/技能释放），服务端统一模拟（权威服务器，防作弊）后广播状态；② 数据用 <b>UDP</b>（或 KCP/自研 RUDP）传输——低延迟优先，丢失的旧状态帧直接丢弃（插值/预测补偿）；③ 客户端<b>本地预测 + 插值</b>：自己操作即时响应（不等服务器），对他人位置插值平滑，掩盖网络延迟和丢包；④ 关键事件（伤害结算、击杀判定）由服务端权威裁决，必要时可靠重传；⑤ 延迟补偿：服务端按客户端 RTT 回溯判定（回滚时间窗）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">非对局链路（TCP/HTTPS）：</b>登录认证（HTTPS）、匹配队列、商城交易、战绩查询走 TCP/HTTP——这些必须可靠，延迟要求低；语音通话走 UDP + 音频协议（如 WebRTC 类）；大厅内开黑组队用 TCP 长连接。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>帧同步 vs 状态同步：LOL 用<b>状态同步</b>（服务端模拟、客户端只表现）；帧同步（RTS 类）要求所有客户端同一输入序列（网络要求更高）；丢包率/延迟/RTT 是核心指标（东南亚/跨服玩家延迟高 → 分区 + 就近服务器）；NAT 打洞直连（自定义房间）失败走中继。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>UDP 被限速/丢包严重时游戏体验崩（重连/降频）；权威服务器 + 状态同步的带宽成本高（每玩家广播）；外挂防护（服务端裁决）与延迟（本地预测）矛盾——取舍靠预测 + 校验。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>游戏服务：状态同步 + UDP 实时通道 + TCP 业务通道 + 分区就近部署；监控延迟、丢包率、同步频率、预测回滚率；弱网模拟测试（丢包/抖动/带宽限制）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>为什么对局不用 TCP（重传导致延迟抖动和卡顿）；状态同步和帧同步的区别（服务端模拟 vs 输入同步）；本地预测怎么保证一致性（服务端权威 + 回滚校正）；延迟补偿是什么（按 RTT 回溯判定）。</div>
  </div>
</div>

# 5.13 BIO、NIO、AIO 的核心区别是什么？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>BIO 是<b>同步阻塞</b>，调用线程等待 I/O 完成，传统模型是一连接一线程；NIO 是<b>同步非阻塞</b>，线程通过 channel 和 selector 轮询多个连接的就绪事件；AIO 是<b>异步非阻塞</b>，提交 I/O 后立即返回，由系统在完成后通过回调或 completion handler 通知。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">维度对比：</b>BIO 编程直观但线程数随连接数增长，容易受线程栈和上下文切换限制；NIO 通过少量事件循环线程支撑大量连接，但状态管理和半包拆包更复杂；AIO 理论上把等待交给系统，实际效果取决于操作系统、JDK 实现和底层文件/网络支持。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">选型与误区：</b>高并发网络服务通常采用 NIO/Netty，平衡性能与工程复杂度；阻塞数据库调用即使放在 NIO 服务里仍会阻塞业务线程，因此还要配合独立线程池。非阻塞不等于异步，NIO 的 selector 线程仍然同步地处理就绪事件。</div>
  </div>
  <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>Java 生态里为什么 AIO 在业务系统里不如 NIO 常见？NIO 服务如何处理粘包、半包和慢客户端？</div>
</div>

# 5.14 I/O 多路复用原理怎么讲？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>多路复用通过<b>一个线程监听多个连接的就绪事件</b>（读、写、异常），只有事件到达时才分发处理，避免每个连接长期占用一个阻塞线程。它解决的是“等待多个 I/O”的线程利用率问题，不会自动提升业务处理速度。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现差异：</b><code>select</code> 每次调用都要传递并遍历 fd 集合，存在数量上限；<code>poll</code> 去掉固定数量限制，但仍需线性扫描；Linux <code>epoll</code> 通过内核事件表注册 fd，并把就绪事件放入 ready list，应用只处理就绪项，连接数很大时更高效。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">水平与边沿触发：</b>LT 只要 fd 仍可读就会重复通知，编程简单；ET 只在状态变化时通知，必须循环读到 <code>EAGAIN</code>，否则可能丢失后续处理机会。非阻塞 fd、读写缓冲区、半包协议解析和连接关闭检测需要一起设计。</div>
    <div style="margin:8px 0 0;"><b style="color:#9B5C00;">风险与边界：</b>单个事件循环中不能执行长时间计算或阻塞调用，否则会拖住所有连接；写事件不能永久监听，否则发送缓冲区可写时会产生忙轮询。生产环境要限制单次事件处理预算、监控 event loop 延迟和活跃连接数。</div>
  </div>
  <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>epoll 相比 select 的核心优化点是什么？LT 和 ET 如何选择？为什么 ET 模式必须使用非阻塞读取？</div>
</div>

# 5.15 Netty 如何体现 Reactor 模型？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">模型映射：</b>Reactor 的核心是<b>事件驱动分发</b>：Reactor 线程监听就绪事件，Handler 负责处理读写和协议状态。Netty 常用主从 Reactor，Boss <code>EventLoopGroup</code> 负责 accept，新连接注册到 Worker <code>EventLoop</code>，Worker 负责 read、decode、业务事件传播和 write。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">Pipeline 处理：</b>数据进入 <code>ChannelPipeline</code> 后依次经过入站和出站 <code>ChannelHandler</code>；解码器负责半包/粘包和协议帧，业务 handler 处理请求，编码器把响应写回 channel。每个 channel 通常绑定一个 EventLoop，减少并发访问同一连接状态的锁竞争。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">线程边界：</b>非 I/O 的重计算、阻塞数据库和远程调用应下沉到独立业务线程池，再通过事件回到 EventLoop；线程池要有界、可监控，并避免在 I/O 线程里调用 <code>sync</code>、<code>await</code> 或长时间 <code>join</code>。</div>
    <div style="margin:8px 0 0;"><b style="color:#9B5C00;">常见风险：</b>EventLoop 被阻塞会让同一线程上的多个连接一起超时；业务线程池过小会造成任务排队，过大又会争抢 CPU。需要关注 event loop pending tasks、单次 handler 耗时、写缓冲区水位和连接关闭后的资源释放。</div>
  </div>
  <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>如果在 I/O 线程里做重计算，会出现什么线上表现？一个连接为什么通常固定到同一个 EventLoop？如何处理写缓冲区高水位和背压？</div>
</div>
