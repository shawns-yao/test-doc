# 2.1 RabbitMQ 做了什么？为什么要使用它？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>RabbitMQ 是基于 AMQP 协议的消息中间件（Erlang 实现），核心模型：Producer → Exchange →（Binding/RoutingKey）→ Queue → Consumer。与 Kafka/RocketMQ 最大的区别是<b>Exchange 路由模型</b>——消息不直接进队列，由交换机按路由规则分发，路由灵活。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程（四种交换机）：</b>① <b>Direct</b>：RoutingKey 精确匹配单队列；② <b>Fanout</b>：广播给所有绑定队列（发布订阅）；③ <b>Topic</b>：通配符匹配（<code>order.*</code>、<code>#</code>），最灵活；④ <b>Headers</b>：按消息头匹配。消费者消费后手动/自动 ack，失败可重回队列或进死信。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">为什么使用：</b>① 复杂路由需求（按业务类型/优先级分发）；② 多语言生态好（AMQP 协议客户端全）；③ 功能开箱即用：延迟队列（插件）、死信队列、TTL、优先级、消息确认；④ 部署轻量，中小规模足够。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>吞吐量天花板低于 Kafka（万级）；集群镜像/仲裁队列有同步开销；Erlang 生态排障学习成本；高吞吐日志/流场景不适合。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>业务通知分发（订单状态按类型路由到不同队列）；多系统集成（不同团队不同语言用 Topic 交换机订阅）；配合死信队列做延迟重试（消息过期 → DLX → 重试队列）。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>Exchange 和 Queue 的关系（路由层 vs 存储层）；Direct/Topic/Fanout 区别；消息确认机制（ack 手动/自动）；死信队列怎么实现（DLX + 路由 key）。</div>
  </div>
</div>

# 2.2 如何设计高可用的 RabbitMQ？镜像队列有什么作用？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>RabbitMQ 高可用靠集群：普通集群（节点间只复制元数据，队列数据在单节点）+ <b>镜像队列/仲裁队列</b>（消息在多个节点冗余）。镜像队列把队列复制到集群内多个节点，主节点故障时从副本提升，消息不丢。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">实现流程：</b>① 部署多节点集群（节点互联 + 统一 Erlang cookie）；② 队列声明为镜像（policy：<code>ha-mode=all</code> 全部节点或 <code>exactly</code> 指定副本数）；③ 生产者写入主副本，主副本同步/异步复制到从副本；④ 主节点宕机，从副本选主继续服务。新版本推荐<b>仲裁队列（Quorum）</b>：Raft 共识、数据多副本、替代镜像队列。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>镜像队列同步模式（同步 = 全副本 ack 后返回，可靠但慢；异步 = 快但可能丢）；仲裁队列基于 Raft，多数派写入，可靠性更强；客户端要配置<b>重连和确认</b>，故障切换期间消息由重试保证。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>全镜像写放大（每节点都存）；脑裂风险（分区时可能双主，靠网络分区策略）；高可用不等于不丢消息——生产端确认 + 队列持久化 + 消费端 ack 三层都要配置。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>生产环境 3 节点集群 + 仲裁队列；队列和消息都声明持久化；生产者确认（publisher confirm）；消费者手动 ack；监控队列副本同步状态和节点健康。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>镜像队列和仲裁队列的区别（异步复制 vs Raft 共识）；普通集群为什么不复制消息（只有元数据）；脑裂怎么处理（网络分区策略/最小节点数）。</div>
  </div>
</div>

# 3.1 Kafka 怎么使用？如何保证消息可靠投递和消费？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>Kafka 是分布式日志型消息系统：Topic 分 Partition，Partition 内有序、多副本（Leader/Follower），消费组内分区分配消费。使用：建 Topic → Producer 按 key 路由写分区 → Consumer 从分区拉取并提交 offset。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">生产端可靠性（投递不丢）：</b>① <code>acks=all</code>：Leader 等所有 ISR 副本确认才返回；② <code>retries</code> 重试 + <code>enable.idempotence=true</code> 幂等（防止重试重复写）；③ 发送失败落本地/死信补偿。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">存储可靠性：</b>副本因子 ≥2（生产建议 3），ISR 同步；<code>min.insync.replicas</code> 控制最少同步副本数；broker 宕机由 Controller 重新选举 Leader。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">消费端可靠性：</b>① <b>先处理后提交</b> offset（业务成功再 commit），处理失败不提交可重新消费；② 至少一次语义下消费必须<b>幂等</b>（重复消费不可避免）；③ 提交时机权衡：处理前提交（快但丢消息）vs 处理后提交（不丢但可能重复）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键细节：</b>Kafka 保证分区内有序，跨分区不保证——需要全局有序就单分区或按 key 路由；消费组 rebalance 会触发停顿（max.poll.interval 控制）；offset 提交用 <code>commitSync</code> 保证不丢。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>acks=all + 同步副本降低吞吐（高可靠 vs 高吞吐权衡）；重复消费是常态，幂等是刚需；消息积压用增加分区和消费者横向扩展。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>日志/埋点管道（高吞吐场景）；消费端幂等表 + 处理后提交；监控 lag（消费积压）、ISR 状态和 broker 磁盘；关键业务事件用 acks=all + 幂等 Producer。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>acks=0/1/all 的区别；ISR 是什么（同步副本集合，落后则剔除）；为什么 Kafka 吞吐高（顺序写 + 页缓存 + 零拷贝）；rebalance 是什么（分区重新分配，会短暂停消费）。</div>
  </div>
</div>

# 3.2 如何设计一个消息队列系统？以 Kafka 为例说明核心组件和链路。

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <span style="display:inline-block;padding:2px 10px;border-radius:999px;background:rgba(58,95,191,.10);border:1px solid rgba(58,95,191,.22);color:#3A5FBF;font-size:12.5px;font-weight:600;">公司：腾讯</span>
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">概念原理：</b>消息队列系统 = 存储 + 网络 + 协议 + 协调的集合。Kafka 核心组件：<b>Producer</b>（发送端）、<b>Broker</b>（存储节点）、<b>Topic/Partition</b>（逻辑队列/物理分片）、<b>ConsumerGroup</b>（消费组）、<b>ZooKeeper/KRaft</b>（元数据与选主）、<b>Controller</b>（分区领导选举）。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">核心链路（生产到消费）：</b></div>
    <div style="position:relative;padding-left:36px;margin:10px 0 0;">

      </div>
      <div style="position:relative;margin:0 0 8px;">
        <div style="position:absolute;left:-29px;top:3px;width:20px;height:20px;border-radius:50%;background:#9BBBF4;color:#fff;font-size:12px;font-weight:600;display:flex;align-items:center;justify-content:center;">2</div>
        <div style="background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:9px 12px;font-size:13.5px;line-height:1.7;">Leader 写入本地日志（顺序追加），ISR 副本同步，达到 <code>acks</code> 要求后返回。</div>

        <div style="background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:9px 12px;font-size:13.5px;line-height:1.7;">消息落盘为 segment 文件（顺序写 + 页缓存 + 零拷贝 <code>sendfile</code>）。</div>
      </div>
      <div style="position:relative;margin:0 0 8px;">

        <div style="background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:9px 12px;font-size:13.5px;line-height:1.7;">Consumer 从分区<b>拉取（pull）</b>并推进 offset。</div>
      </div>
      <div style="position:relative;margin:0 0 8px;">
        <div style="position:absolute;left:-29px;top:3px;width:20px;height:20px;border-radius:50%;background:#9BBBF4;color:#fff;font-size:12px;font-weight:600;display:flex;align-items:center;justify-content:center;">5</div>
        <div style="background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:9px 12px;font-size:13.5px;line-height:1.7;">消费组内分区分配，rebalance 协调。</div>
      </div>
      <div style="position:relative;margin:0;">
        <div style="position:absolute;left:-29px;top:3px;width:20px;height:20px;border-radius:50%;background:#FAAD14;color:#fff;font-size:12px;font-weight:600;display:flex;align-items:center;justify-content:center;">6</div>
        <div style="background:var(--card);border:1px solid var(--border);border-left:3px solid #FAAD14;border-radius:12px;padding:9px 12px;font-size:13.5px;line-height:1.7;"><b style="color:#B26E00;">元数据变更</b>（建 Topic、宕机选主）由 Controller/KRaft 处理。</div>
      </div>
    </div>
    <div style="margin:8px 0 0;"><b style="color:#3A5FBF;">关键设计点：</b>① <b>顺序写</b>：日志追加保证高吞吐；② <b>分区并行</b>：吞吐随分区数扩展，代价是跨分区无序；③ <b>offset 机制</b>：消费者进度持久化，支持重放；④ <b>副本 + ISR</b>：可靠性靠副本冗余而非刷盘（Kafka 刷盘宽松，靠副本防丢）；⑤ <b>零拷贝</b>：消费路径避免用户态拷贝。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">风险与取舍：</b>分区数过高增加元数据和文件句柄开销；消费组重平衡导致短暂停摆；堆积时磁盘和 lag 压力；强顺序需求牺牲并行度。设计取舍本质：吞吐 vs 有序 vs 可靠 vs 运维复杂度。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">项目落地：</b>监控 lag、ISR、磁盘使用和 rebalance 频率；分区数按目标吞吐规划（单分区约 10MB/s 级，预留扩展）；key 设计保证同业务实体同分区有序；消费处理用批量 + 幂等表。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>为什么 Kafka 不用推而用拉（消费者自己控制速率、批量）；分区和消费者的对应关系（一个分区同一时刻只被组内一个消费者消费）；消息在 Kafka 中删除吗（按保留策略删除 segment，不是删单条）；Controller 挂了会怎样（重新选举）。</div>
  </div>
</div>

# 3.3 至少一次与恰好一次怎么选？消费幂等如何做？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">怎么选：</b><b>恰好一次</b>语义实现复杂、成本高，跨系统链路很难端到端保证。多数业务采用<b>"至少一次投递 + 消费端幂等"</b>——在可控复杂度下获得足够的可靠性。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">消费幂等三层：</b>核心是为每条业务事件定义<b>唯一幂等键</b>（订单号、业务流水号等），消费前先查重。① <b>Redis SETNX</b>：高性能幂等，降低重复消费压力（线上首选）；② <b>数据库唯一键</b>：资金/发券等关键链路的<b>最终兜底</b>，避免 Redis 异常导致重复执行；③ 去重表 + 唯一索引。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">追问：</b>为什么恰好一次难（分布式事务 + 多系统）；SETNX 幂等键过期了怎么办（DB 兜底）；幂等键怎么生成（业务 ID + 操作类型）。</div>
  </div>
</div>

# 3.7 死信队列的价值是什么？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3F8C12;">核心价值：</b>隔离多次重试仍失败的<b>"毒消息"</b>（数据格式错、字段脏、下游永久失败、代码 bug），防止主队列被反复阻塞。死信队列还<b>保留问题现场</b>（原始消息 + 失败原因），便于人工修复、补偿重放和规则迭代。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">流转路径：</b>消费失败 → 重试队列/延迟重试（指数退避）→ 超过阈值 → <b>DLQ</b>；主链路继续消费新消息，不受毒消息拖累。运维定期扫 DLQ 分类处理：可修复的补偿重放，代码 bug 修后重放，确认废弃的归档。</div>
    <div style="margin:8px 0 0;"><b style="color:#B26E00;">追问：</b>死信和重试队列的区别（有限重试 vs 最终隔离）；死信消息怎么处理（人工 + 工具重放）；DLQ 本身满了怎么办（监控告警 + 容量治理）。</div>
  </div>
</div>

# 3.8 削峰填谷为什么离不开 MQ？

<div style="--primary:#3A5FBF;--card:var(--background-primary);--border:var(--background-modifier-border);--text:var(--text-normal);--muted:var(--text-muted);max-width:780px;font:14px/1.65 Roboto,'PingFang SC','Segoe UI',Arial,sans-serif;color:var(--text);margin:12px 0;box-sizing:border-box;">
  <div style="margin:8px 0 0;background:var(--card);border:1px solid var(--border);border-left:3px solid var(--primary);border-radius:12px;padding:12px 14px;">
    <b>回答：</b>
    <div style="margin:6px 0 0;"><b style="color:#3A5FBF;">核心价值：</b>MQ 把<b>突发请求转成可控消费速率</b>，隔离前台高峰和后台处理能力差异。生产端快速写入，消费者按照数据库、下游接口和自身线程池的实际能力平滑处理，从而把瞬时峰值变成一段可观测的积压。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">完整链路：</b>入口限流后校验请求并写入消息 → Broker 持久化和副本确认 → 消费者按分区/队列顺序拉取 → 本地批量处理和提交 offset → 成功消息确认，失败消息进入重试或死信。削峰的前提是消息能够持久化，不能把压力简单推迟到内存队列。</div>
    <div style="margin:8px 0 0;"><b style="color:#3F8C12;">配套治理：</b>设置有界堆积容量、消费者并发上限和优先级队列；通过扩容消费者、批量拉取、批量写入和按业务降级追赶积压。核心指标包括生产速率、消费速率、堆积量、最老消息年龄、处理耗时和失败重试次数。</div>
    <div style="margin:8px 0 0;"><b style="color:#9B5C00;">边界与风险：</b>MQ 不能无限吸收流量，堆积过久会造成消息过期、顺序破坏和用户体验延迟；下游必须具备幂等，消费者扩容要受数据库连接数和锁竞争约束。对支付、库存等强实时链路，不能只依赖异步消息，要保留同步确认或状态查询。</div>
  </div>
  <div style="margin:8px 0 0;"><b style="color:#B26E00;">面试追问：</b>积压严重时，优先扩消费者还是先降级，判断依据是什么？为什么扩容消费者可能让数据库雪崩？如何保证削峰后仍然满足业务时效？</div>
</div>
