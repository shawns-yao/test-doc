# 12.主 Agent 在什么情况下会调用 `delegate_task`？

当一个子任务可以被相对独立地完成，而且委派能明显降低主 Agent 的上下文压力或提高并行效率时，主 Agent 才调用它。
- **需要深入探索某个局部问题**，比如去分析一个模块、追一条调用链、查一组日志。
- **可以和主任务并行进行**，比如一个 Agent 查后端，一个 Agent 查前端。
- **子任务会产生大量中间信息**，但主 Agent 最终只需要结论和证据，不需要把全部过程塞进自己的上下文。
- **需要不同能力或角色**，比如主 Agent 做整体规划，把代码审查、测试分析、日志诊断交给专门的子 Agent。
- **任务边界比较清楚**，可以明确告诉子 Agent“你只负责什么、输出什么”。

# 13.如何判断一个任务值得委派，而不是主 Agent 直接完成？

我一开始是这么做的。后面发现不太好

核心不是看“任务难不难”，而是看：

> **委派带来的收益，是否大于委派本身的成本。**也就是值不值得委派

其次：把大量探索过程隔离在子 Agent 上下文里，主 Agent 只保留压缩后的结果。

小而连续的任务，主 Agent 自己做；大而独立、可并行、上下文重的任务，才委派。

并行，后一步强依赖前一步结果，就没必要拆成三个子 Agent。


最后判断，因为子 Agent 拿不到父 Agent 的全部上下文，所以委派前必须把任务说明白。
	如果主 agent说不清楚，不是“不太值得委派”，而是“根本没法可靠委派”。
然后真正让委派产生收益的，不是“这个任务很复杂”，而是：

> **这个子任务能不能和主任务、其他子任务彼此隔离。**


## 另外，还有第二种想法，

因为 devcli 问的是“这个任务值不值得委派？”，本质上算一种受益，或者成本判断

另外一个做法是**程序不去判断“值不值得委派”，而只判断“能不能委派”
	不是主 agent 自己凭借感觉判断，而是让每一个子 agent 自己声明，什么情况下应该调用我。
不是让主 Agent 凭一个统一的、模糊的“感觉”去判断要不要委派，而是把每一种子 Agent 当成一个有明确能力边界的工具，**由子 Agent 自己在 description 里声明“什么任务适合调用我、什么任务不要调用我”**。主 Agent 做的事情，是拿当前任务去和这些声明做匹配。

# 14.如何避免简单任务被过度委派，导致协调成本超过收益？


- **简单操作禁止委派**：读一个文件、搜一个关键词、跑一次测试、改一个小函数，主 Agent 直接做。
- **只有满足明显收益才委派**：比如子任务相对独立、需要大量探索、可以并行，或者会明显占用主 Agent 上下文。
- **设置最小任务规模**：如果预计只需要 1～2 次 Tool Call 就能完成，就不允许委派。
- **限制委派数量和层级**：例如一轮最多创建几个子 Agent，子 Agent 不允许无限继续委派，防止“Agent 套 Agent”。
- **考虑协调成本**：创建子 Agent 还要传上下文、等结果、校验结果、合并结果。如果这些成本比直接执行还高，就不委派。

# 17.为什么子 Agent 不能继续调用 `delegate_task`？

- **控制复杂度**  
    主 Agent 本来还能知道“我派了谁、谁负责什么”。如果子 Agent 再派孙 Agent，任务关系会越来越深，最后很难判断某个结果到底来自哪里、谁应该负责收口。
- **防止预算失控**  
    一个子 Agent 再开 3 个，3 个再各开 3 个，很容易变成指数增长。模型调用、上下文、工具执行都会迅速放大。
- **避免权限和安全边界被间接绕过**  
    主 Agent 的委派可能经过审批和能力检查。如果子 Agent 能继续委派，就等于它又获得了“创建新执行主体”的能力，权限传播会变得很难控制。
- **保持责任链清晰**  
    子 Agent 的职责应该是：
    
    > 接受一个明确任务 → 完成 → 返回结果。
