# 6.结构化 Tool Calling 和普通文本中解析工具指令有什么区别？


**结构化**：参数有 schema 约束——类型、必填项、枚举值、未知字段。有些接口甚至在生成时就被限制成只能吐合法值。校验失败是明确的失败。
并且**结构化**可以带有编号，你回结果时带上同一个编号，配对是确定的。
工具调用可以增量到达，参数一点点拼出来。你能提前知道「它要调什么」，甚至能在模型还没说完时就开始准备。比如，模型在回答用户的时候，其实工具调用就以及发起了，可以把工具调用放到执行队列中进行

代价
- **工具清单本身要占上下文**。工具越多，发给模型的 schema 越大。这就是为什么工具超过一定数量要先做筛选，只挑相关的几个发过去。
	- 比如首先先按「域」筛，比如文件读取，文件修改，git 工具等
	- **再按 Agent 权限过滤**：当前 Agent 没有写文件权限，那么写文件、删文件这类工具连候选集都不应该进入。
	- 第三层是，不能固定死，比如第一轮给搜索工具，模型发现要改代码，第二轮换成读写工具，第三轮换成测试工具。每轮重算，不是开局选死。
- **描述质量决定选对率**。schema 写得含糊，模型照样选错工具——只是错得「格式合法」而已。

# 7.工具参数如何通过 JSON Schema 校验？

首先判断这段参数是不是合法 JSON、是不是一个对象、必填项在不在、类型对不对、有没有多余字段、枚举值合不合法。
	**标准 JSON Schema 校验库**
	**再叠一层自己写的轻量校验兜底**
为什么必须有兜底？因为外部接进来的工具，它的 schema 可能用了校验库不支持的方言——这时候库直接抛异常。**不能因为这个就把工具废掉**，所以库跑失败时静默降级，用自己的那套继续查必填项、类型、多余字段。

**失败长什么样**：回一句「工具参数校验失败: 〈具体哪里不对〉。请根据工具 JSON Schema 修正参数后重试。」

然后，如果 Schema 通过，需要查的是 schema 根本表达不了的东西
- **参数之间的组合关系**：起止行不能倒过来，比如 startTime 应该小于 endTime
- **项目真实状态**：要改的文件必须真的存在；要列的目录必须真的是目录，比如不能修改项目外的内容，防止目录漂移
- **路径安全**：解析后必须落在项目根内
- **语法合法性**：正则能不能编译、URL 是不是 http/https 且带主机名
- **策略语义**：命令黑名单，比如 sudo，rm rf 这些肯定不行

# 8.为什么模型看到的工具定义和实际执行工具必须来自同一份快照？

**因为模型是「按它看到的 schema」写参数的。执行端要是拿另一份 schema 来判，就等于用甲的标准出题、用乙的标准判卷**

# 9.如果模型返回重复的 `tool_call_id`，或者工具结果乱序返回，怎么处理？

**核心动作叫「对账」——先把结果的顺序彻底扔掉，改按 id 建索引；然后以模型的调用列表为唯一权威，逐条取结果。缺的补、多的丢、重的去、身份错的纠正。**

同一轮内 ID 必须唯一；第二次出现**直接拒绝该调用**，不执行，也不猜它对应哪条结果。
结果靠 ID 和调用绑定，ID 一重复就无法可靠关联。

如果工具返回的是乱序的，
	并行执行，但结果**按提交顺序收集**。所以从执行层出来时顺序已经还原了
	即使顺序真乱了也不怕——每个结果都携带自己的 `tool_call_id`，根据 ID 找回原始调用。

# 10.工具调用失败后，是由程序重试，还是交给模型纠正？两者如何区分？

问题翻译：模型发出了 N 个工具调用，后面就需要有 N 个工具结果
如果模型一次性发起了 3 个调用，比如 A 读文件，B 跑测试，查 Git，如果执行到了 B，用户点击了取消。那么这个时候变成了 A 有结果，B 被取消，C 没有执行，如果历史记录中记录了 ABC 三个 Tool Call，却只有 A 的 Tool Result，那么协议就断了，那么应该中断 → 把剩余任务都标记取消 → **继续把 A、B、C 的结果收完整。**

最后做一次对账，假如模型声明了 ABC，但是收集器中最终的结果只有 AB，那么强行补 C：执行器未返回结果。

1.工具调用失败，发生在用户点击取消这个地方，已经取消了就直接结束，那批工具调用**根本不进历史**。
没有调用，就没有孤立结果这回事。

2.工具还没来得及执行就发现取消了——不返回空列表，而是**为这批里每一个调用各生成一条「已取消」回执**，一条不少。

一批并行工具，每个调用拿到的是从上游派生出来的**独立令牌**。所以「某一个调用被取消」不会牵连同批的其他调用，也不会让整批变成「没有结果」。

取消是父子级联的，但级联的每一级都能单独收口。
