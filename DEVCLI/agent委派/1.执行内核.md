# 1.你说“统一执行内核”，具体统一了哪些逻辑？

因为之前不同的入口各写了一遍循环体，所以为了复用，现在的循环只有一份
也就是**取消检查 → 调用方自己的轮数上限 → 预算检查（八种退出原因，固定优先级）→ 才允许推进轮次。**

1.其中**检查与推进必须是原子的**，比如说，设置了子 agent 工作 ，如果不检测，否则会出现「是否取消检查通过之后、推进之前，额度被并行的子任务吃掉」这种状态撕裂

2.第二个是**轮数上限有两级**，调用方自己的上限（子任务默认 32 轮）和全局硬上限（默认 100 轮）分开判定。前者命中报「达到轮数上限」，后者命中报「硬轮数上限」——两种失败在最终报告里是不同状态，不是一个笼统的「超时了」。

3.-**准备阶段之后要再查一次**。每轮前的钩子（压缩历史、注入待处理诊断）本身会消耗 Token，所以准备完成后要复查一次；但**已经预留的轮次不重复检查**，否则会把自己刚拿到的额度又判掉。
比如提示压缩失败等。


## 1.模型调用

- **采样请求身份**。每次请求生成唯一标识，同一标识重复发起会取消前一个。这让并行子任务的请求能独立取消，不会互相踩。
- **响应后记账**。输入、输出、缓存输入三种 Token 统一记录，并发出成本估算事件——四个入口的用量口径一致。

## 2.横切关注点

- **状态机事件统一**：思考中、工具执行中、结果已对账、完成、失败、取消、预算超限、轮数超限、陈旧上下文、刷新中、刷新失败可重试。所有入口发同一套状态，前端和日志才不用写四份适配。
- **钩子生命周期包裹**：代理开始/结束、每轮开始、助手消息完成、工具执行开始、工具结果收到

# 2.ReAct、Plan task 和 SubAgent 的执行流程有什么相同点和不同点？

相同点
**循环体与闸门顺序**。取消检查 → 调用方轮数上限 → 预算判定 → 才推进轮次

**中断挽救行为**。取消或模型调用异常时，只把已流出的文本补回历史，不补工具调用。

**事件状态机**。思考中、工具执行中、结果已对账、完成、失败、取消、预算超限、轮数超限、陈旧上下文、刷新中——三者发同一套状态。

不同点
React 是会话级别，跨轮积累，工具是全量，工具多的时候做路由筛选，单会话不并行
SubAgent 每次执行新建，各个 agent 之后不共享

# 3.一轮 ReAct 从模型返回到工具结果再次进入上下文，完整链路是什么？

## 第 1 件：先看有没有人喊停

模型刚回话，系统第一眼先看：用户是不是刚按了取消？

- 是 → 把模型**已经说出口的那半段话**记进对话（不然用户会觉得「刚才明明说了一半，怎么没了」），然后收工。
- 不是 → 继续。

这里有个讲究：只记它说的话，**不记它要调的工具**。因为工具不打算跑了——如果记了「我要调工具」却没有对应结果，对话格式就断了。比如 llm 刚说了思路，打算调用工具，然后用户停止，那么工具不执行

## 第 2 件：算账

这一轮模型说了多少字、花了多少钱，记下来。

为什么要记？因为要设上限。不记账就没法判断「是不是该停了」，模型可以一直说、一直调工具。


## 第 4 件：干活之前先看额度够不够

模型要调 3 个工具，系统先看账上还剩几个额度：

- **不够 → 一个都不跑**，直接告诉模型「额度不够」；
- 够 → 扣掉 3 个，开始干。

为什么不够就一个都不跑？因为跑一半最麻烦。设想「读甲、读乙、改丙」里，改丙执行完了、别的没执行——文件已经被改了，但模型不知道后面的情况，工作区就停在半成品状态。**要么全干，要么全不干。**


## 第 5 件：真的去干

- 最多同时干 4 件，多了排队；
- **只读的活**（读甲、读乙）可以同时干；
- **会改东西的活**（改丙）必须排队，一个一个来——万一两个工具要改同一个文件，同时改就乱套了；
- 每件事都有时间上限，超时就停，不会一直挂着。

## 第 6 件：把结果对齐

模型说要干 3 件，系统就必须拿回 **3 个结果**，顺序也要对上。

为什么这么严？因为对话格式要求「我说要调三个工具」后面必须跟三个结果，少一个接口就报错。

现实里经常出岔子：某个工具根本没返回、模型不小心用了重复编号、返回的结果标错了是哪个工具的。这些情况系统都要**补一个占位结果**（内容是「这次调用失败了」），不能留缺口。

## 第 7 件：结果太长就压缩

模型读了两个大文件，全塞回对话会把上下文撑爆。所以系统先算「还剩多少空间」，再压缩。

- 多个结果**平均分**剩余空间，不是谁先来谁占满；
- 单条实在太长，就把完整内容存到别处，对话里只放一小段，加一句「完整内容在这个位置」；
- 图片另外限制：最多 4 张。


还有一些提示，

比如工具回「你没权限」，系统会补一句：**不要重试，也不要换个工具绕过去**。
为什么要加？因为模型容易犯傻——被拒绝之后会一直重试同一个操作，或者换个小号工具接着试。提前把话说死，能省好几轮。

还有提醒一句「你是不是卡住了」，模型连续几轮用**完全一样的参数**干同样的事，系统插一句提醒。

注意：只是提醒，不强行打断。给它一次自己反应过来的机会。提醒了还重复，才会真的掐断。

子 Agent 花的钱要记在主 Agent 账上，不然「总预算」就是摆设。两套循环各记一套账，早晚对不上。

**3. 取消必须一起停**

你按 Ctrl+C，子 Agent 里正在跑的命令也得停。两套循环就得各写一遍「怎么把取消传下去」。

**4. 「是不是在原地打转」的判定标准会漂**

主循环判一次、子循环判一次。一开始一样，改着改着就不一样了——同一个任务，主 Agent 觉得正常，子 Agent 觉得是死循环。

# 5.如果模型同时返回 reasoning、content 和多个 tool call，系统如何处理？
## 多个工具调用——按固定顺序整批处理

这里顺序不能换：

**a. 先算账，再动手。**​ 一次性把这批要花的额度扣掉。不够就**整批拒绝**，不做「前两个跑了、第三个没跑」。半执行的批次会让对话变成「部分成功」，模型很难判断到底哪些生效了。

**b. 裁剪。**​ 可见工具太多时，先挑出这一批相关的几个。

**c. 逐个校验参数。**​ 参数非法的**不进入真实执行**，直接回一条可读的校验错误。注意——**错误也是「结果」，配对不能破**。

**d. 执行。**​ 只读的并行跑；有副作用的排队串行（同一个工作区不能让两个写入同时进行）。

**e. 结果对账。**​ 这一步专门保证「模型要了几条，就回几条，顺序不变」。四种情况都得处理：某条没结果（补一条）、回了个不存在的编号（丢掉）、同一个编号回了两条（去重）、编号对不上（按原始调用顺序纠正）。

**f. 体积治理。**​ 太长的结果截断或落盘，回一个引用加预览。

**g. 整批一次性放回上下文**，进入下一轮。
