# 1.**主 Agent 在执行过程中，自己判断哪一段工作可以切出去独立完成，然后切出去。**​ 它不是一条预设流水线，也不提前排布任务图——切不切、切几段，都是运行时决定的。


什么时候切出去，下面是三道硬性门槛
第一，需要多轮工具操作的任务。单次操作（读一个文件、跑一条命令）切出去只会增加开销。
第二，如果需要边做边看主 Agent 的中间结论，切出去就变成来回同步，反而更慢。
第三，完成的条件可以独立描述，比如能说清「输入是什么、范围到哪里、什么算做完、交付什么

## 子任务看得见什么
**子任务不继承父会话历史。**冻结的系统规则与技能快照，以及主 Agent 显式写下的任务交代和必要背景
父任务的对话过程、长期记忆、其他兄弟任务的进展，它一概看不见。
切出去的意义就是**用一个干净、聚焦的上下文去做一件事**。如果把父会话整段复制过去，子任务既会背上无关负担，也会和父任务产生耦合，失去隔离的价值。

## 子任务能做什么,并且**子任务不能再往下委派**
- **只读角色**（探查、规划、复核）：只能读，不能改。
- **执行角色**：可以在隔离的工作区里改动，但改动范围必须提前声明。
越权尝试会被直接挡回——不能靠猜工具名绕过，也不能因为任务描述里写了某个路径就获得额外的系统权限。任务描述里的范围声明，不等于真实的访问隔离。


子任务做完不等于改动能落地，执行过程中有改动类的操作失败且没被修复，整个子任务的产出作废，不应用。
当改动面较大、或触碰了关键资源（数据库迁移、权限、安全配置一类），系统会自动再起一个只读的复核者去核对真实产物，而不是相信子任务自己的汇报。复核不通过，改动就不落地。通过后才做版本校验式的原子提交
子任务回报的是**结构化的结论**：做了什么、证据是什么、哪些路走不通、还有什么没解决。正文有长度上限，且主任务全程最多保留最近若干份，不会无限堆积。

## 2.假设子 Agent 在隔离工作区修改了两个文件，主 Agent 期间又修改了其中一个文件：**系统怎样发现这个修改冲突？最终是拒绝合并、重新让子 Agent 处理，还是有其他策略？请按你项目里的实际流程说明输入、检查和结果。**

答案不是简单的“发现文件变了就报冲突”：能安全合并就自动合并；不能证明安全，就整批拒绝。

比如项目最开始是文件 A 和文件 B，子 agent 看到的是快照，如果同时主项目的 Agent 也进行了这两个文件的修改，




合并，选中的是 Java AST 来根据三方进行合并
也就是，子 agent 最开始看到的版本，子 agent 修改完成之后的版本，主 agent 现在的版本

1.首先判断有没有可能证明双方修改互不干扰？如果可以，就自动合并。
2.如果不能自动合并，那么子 Agent 所依赖的上下文是不是已经过期？如果过期，就拒绝。

如果冲突，直接拒绝，并将信息发送给主 agent，让主 agent 思考在进行下一轮的行动

第二个问题就是上下文新鲜度，主 agent 在派遣子 agent 的时候，子 agent 那到的是一份冻结的项目快照
那么问题在于，假设子 agent 修改了文件 A，但是修改这个文件 A 的同时依赖了文件 B，也就是读取文件 B 的内容，根据文件 B 的内容来修改文件 A
但是在子 agent 工作的期间，主 agent 修改了文件 B（子 agent 没有修改文件 B），那么之前的普通的文件写冲突没有办法检测，
因为这个时候子 agent 改了 A，主 agent 改了 B，看起来是没有冲突的，但是实际上是可能存在问题的，子 Agent 的修改可能已经不正确了。

所以总结一句话，也就是做决定看过的内容，有么有被后面的人改掉


解决方式可以考虑**观察记录 + 版本校验 + 刷新/重算”** 三件事一起解决。理解成数据库里的 **乐观锁**，只不过锁的不是一行数据，而是 Agent 的“推理依据。

第一种：子 agent 还活着，可以让主 agent 告知子 agent，B 发生了变化，之前的上下文失效了，需要重新读取相关资源
我的做法是在 子 agent 写入的时候，做一次显式跨越隔离工作区的刷新动作，在真正的 write 之前，先检测 a 还是 a 吗，b 还是 b 吗

追问：不是冻结了快照吗。那么再让它刷新的话，那么看到的不还是快照的内容吗。
	需要有一个显式跨越隔离工作区的刷新动作，冻结快照的目的，正常执行过程中，不允许主项目的变化偷偷渗进子 agent 中，但是如果系统明确决定，worker 的上下文已经过期，需要刷新。那么可以执行一个显式跨越隔离工作区的刷新动作

第二种：子 agent 结束了，就不能简单的刷新，应该拒绝这次，重启子 agent 或者让主 agent 进行修改
