# 3.Schema 校验和语义校验有什么区别？

Schema 校验检查“这个 Tool Call 长得对不对”；语义校验检查“这个 Tool Call 做的事情对不对”

因为 Schema 校验：只看结构，它关心的是字段是不是正确，类型对不对，格式对不对，枚举等对不对，
	但是 Schema 并不知道这个语义对不对，因为 Schema 校验并不是安全校验

语义校验是看参数的真实含义，处理的是参数虽然合法，但它所表达的操作是否合法、合理、符合上下文。
	比如对于一个路径，语句校验会问
		这个路径是不是允许访问的？ 
		是不是超出了项目目录？ 
		用户真的要求删除吗？ 
		这个操作和当前任务有关吗？ 
		是否违反当前权限？ 
		是否属于高风险动作？


举一个例子。比如 execute_command，执行命令，schema 校验只能看到 command 是存在的，并且是 String，
但是里面的字符串比如是 rm -rf   这种就是结构正确，但是不允许执行的


再举一个例子，比如用户说帮我看看为什么这个测试会失败
但是模型却生成了一个寄邮件的工具调用，邮件内容是 ssh 的内容，这种 Schema 可能完全合法，但语义上有巨大问题。


其中语义校验分成两类，
	第一种是确定性语义校验，能确定性判断的安全问题，就不要让模型猜。
		比如路径是否越界 
		域名是否在 allowlist 
		命令是否命中危险规则 
		文件数量是否过大 
		是否访问 secret 路径 
		HTTP 是否访问内网地址
	第二种是，上下文语义校验有些问题程序很难纯规则判断，比如这个操作到底是不是用户想要的？
		比如用户只是要求“分析测试失败”，但是模型突然准备调用 `send_email`。单靠参数结构和路径规则并不能判断它为什么要发邮件，这时就需要结合原始用户意图、当前任务和已有上下文做语义判断。


接下来就是所谓的 Policy Engine，也就是这个操作在当前规则下，允许、拒绝，还是需要人工审批

# 4.如果工具参数格式合法，但业务语义不合法，系统如何处理？

结合第三题

- Schema 校验通过，只说明参数结构合法；
- 然后进入语义校验；
- 确定性问题用规则判断，比如路径越界、危险命令、Secret 访问；
- 上下文问题结合用户意图和当前任务判断；
- 最后由 Policy Engine 给出 `ALLOW / DENY / REQUIRE_APPROVAL`。

# 5.为什么工具执行结果必须结构化，而不能只返回一段文本？

如果工具只返回一段自然语言，Agent 就只能“猜”这次调用到底是成功、失败、被拒绝还是可以重试。
比如工具返回了自由文本，如工具权限被拒绝，那么模型可能需要自己理解，是用户权限不够？还是是文件系统拒绝？要不要重试，要不要换工具？

工具结果必须结构化，因为 Agent 后续决策不能依赖自然语言错误文本。
系统需要明确区分成功、失败、拒绝和取消，并提供错误码、是否可重试、结果数据和必要的审计信息，让模型能够基于机器可读状态决定下一步，而不是通过关键词猜测。
