# 自动审批策略是怎么设计的（重点）

程序负责决定“绝对不能做什么”，自动审批模型负责判断“这件事用户是不是已经明确想让我做”。

因为 Coding Agent 很容易遇到这种情况
用户提出了一个需要，这个需求需要修改多个地方的代码，那么每修改一个文件，都需要问用户是否同意，一次两次还好，如果真的每次都询问
用户一定会出现，审批疲劳的问题，

所以，能不能让系统自己判断，这是不是用户是已经授权范围内的正常操作，比如用户说，修改问题，并测试运行，那么这里就隐性的包含了几个授权，修改代码，测试运行

但是不能简单的让模型决定所有的问题，否则如果 Coding Agent 很容易遇到这种情况：安全系统就没意义了。

所以项目的设计是，先经过确定性边界，以及有的授权，必须人工确定的特殊操作，剩下的模糊的情况


自动审批做了什么？

一开始，模型不确定，是问用户，现在模型不确定，问审批层，

首先是硬安全边界，比如 rm -rf，这个根本不需要问，直接拒绝就可以，因为它属于程序确定能判断的东西。 （比如命令黑名单，非法协议，修改安全配置等）

其次是用户自己的规则，额外可以让用户显示的配置自定义的规则，假如用户配置，不要修改 xxx.json，或者修改测试文件可以自动放行
	硬阻止：用户说不要修改 xxx，命中直接拒绝
	

然后用户的意图优先，比如用户再配置文件中说测试文件可以直接修改，但是这次对话，用户又说，这次不要改测试，那么以当前的用户明确意图优先

# 12.HITL 审批和策略拒绝的优先级如何确定？

策略拒绝优先于 HITL；人工审批只能决定“系统允许交给人决定”的操作，不能突破机器硬红线

比如假设 Agent 生成：rm -rf ，那么这个时候应该拒绝，而不是弹：是否允许执行 `rm -rf /`？

HITL 处理的是，系统系统认为这件事不是绝对禁止，但风险高到不能自动决定。
所以链路是策略审批有三种，允许，拒绝，HITL 审批，

# 13.用户审批通过后，能否执行原本被策略拒绝的操作？

人工审批只能处理 **Policy Engine 认为“可以交给人决定”的操作**，不能覆盖已经被硬策略拒绝的操作。
对于明确违反系统安全边界的内容，不能再弹出：是否允许？否则所谓的硬策略实际上就失去了意义。
人工审批不是最高权限。Policy 定义系统绝对不能突破的安全边界，HITL 只负责处理边界内需要人判断的操作。

# 15.如果审批过程中参数被修改，系统是否允许继续执行？

不能直接继续执行。因为目标资源变化了，风险变化了，业务含义也就变化了

所以参数一旦发生修改，就应该认为：
	原 Tool Call 已经失效，产生了一个新的 Tool Call。

否则攻击者可以先提交一个低风险参数，获得批准，审批后偷偷换成高风险参数
	本质上是TOCTOU，检查时和执行时不是同一个对象。

审批必须绑定具体参数和资源，而不能只绑定 Tool 名称。审批后只要参数发生变化，就必须重新做 Schema、语义和 Policy 校验；如果风险等级变化，还要重新进入 HITL。

# 16.为什么关闭 HITL 后，某些高风险操作仍然应该失败关闭？


关闭 HITL 只代表“不要询问用户”，不代表“所有原本需要审批的操作自动批准”。
比如不是用户只要关掉弹窗，就获得了更高权限。
