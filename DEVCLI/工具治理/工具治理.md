# 1.以“读取文件”和“修改文件”这两类工具为例，你的系统是怎么做权限和参数校验的？请具体说一下：工具调用进入程序后依次检查什么，校验失败时返回什么，为什么不能只依赖模型自己遵守规则？

**核心原则是：模型只能提出工具调用，权限和参数是否合法，由程序判断。读取和修改共用一条检查管线，但修改文件会增加写入范围、受保护路径和并发检查。**

**一、工具调用进入后，依次检查什么**  
以 `read_file`、`write_file` 和 `edit_file` 为例，主要顺序是：

**取消检查 → 工具存在性 → 能力权限 → Skill 权限 → Schema 校验 → 审批判断 → 审计包装 → 语义与策略检查 → 文件操作 → 结果治理。**

注意：**当前实现中，正式语义校验在普通 HITL 审批之后。不能讲成“所有参数和路径都检查完才弹窗”。但即使用户批准，后续硬检查仍然可以拒绝执行。**

**1. 取消检查和工具存在性**

先判断任务是否已经取消，再确认工具确实注册过。

模型编造一个工具名称，不会凭空获得新能力；不存在就返回 `UNKNOWN_TOOL`，不会继续执行。

**2. 能力权限与 Skill 权限**

这里回答的是：**这个执行者有没有资格使用这个工具？**

程序根据工具声明的副作用类型、当前执行范围和工具白名单判断。例如：

- 只读 Agent 可以读取文件，不能调用修改文件的工具。
- 委派 Worker 还受到自己的写入路径范围限制。
- 当前 Skill 限定了可用工具时，也必须符合该限制。

权限来自程序维护的上下文，不来自模型说的“我已经得到授权”。

**3. Schema 校验**

这里回答的是：**参数结构对不对？**

- 读取文件：`path` 必须提供，类型是字符串；分页参数必须符合声明的类型。
- 写入文件：需要 `path` 和 `content`。
- 精确修改：需要 `path`、`old_string`、`new_string`；其中替换内容允许为空，表示删除匹配文本。

缺少字段、类型错误等情况，返回错误

**但路径是合法字符串，不代表这个路径允许访问。**后面还要检查参数实际含义。

**4. 审批判断**

普通文件读取通常不需要操作审批；修改文件在启用 HITL 时，根据任务授权和审批规则决定是否询问用户。

这里要区分两个概念：**能力权限决定“能不能做”，任务授权主要决定“需不需要再问”。**授权不能突破只读限制，也不能让受保护配置变成可写。

**二、读取与修改分别还检查什么**  
**读取文件：检查访问目标，再控制内容释放。**

路径需要规范化并解析实际位置，防止通过绝对路径、`..` 或符号链接读到项目根之外；同时检查目标是否符合文件读取要求、分页参数是否有效。

目前还会对有大小上限的完整文件快照进行敏感内容检查，**先检查，再分页返回**，避免只请求密钥中间几行来绕过检测。

命中敏感内容时，要求单次允许、拒绝或适用的脱敏处理。这里拦的是“把原文提供给模型”，不是说程序完全不读取文件字节。检测本身也不能保证识别所有秘密。

成功后返回文件内容、分页信息，并按当前执行上下文登记读取基线。

**修改文件：检查目标范围，再检查修改是否成立。**

除了项目根围栏，还会检查：

- **受保护路径：凭据、私钥、版本库元数据及 Agent 自身关键配置不能通过文件工具修改。
- **委派范围：Worker 只能修改分配给自己的路径。
- **修改规则：精确编辑要求文件存在，旧文本非空且唯一匹配；匹配不到或出现多次就拒绝，不猜测修改位置。
- **大小限制：检查待编辑文件或最终写入内容是否超过上限。
- **并发与版本：参与相应步骤治理时，检查写租约及读取基线，避免覆盖其他步骤的新修改。这不是所有普通调用都具有完整的并发事务保护。

通过后才写入，并记录实际修改；内容没有变化时，返回“无需写入”，不冒充一次新修改。

## 三、校验失败时返回什么

统一返回结构化结果：**状态 + 错误码 + 消息 + 是否可重试**。关键在最后一项，它决定了模型下一步能不能自己救回来：

|错误码|含义|可重试|
|---|---|---|
| `POLICY_DENIED` |策略硬边界拒绝|**否**|
| `CAPABILITY_DENIED` |超出能力范围 / 委派写白名单|**否**|
| `SEMANTIC_VALIDATION_FAILED` |参数组合或资源状态不合法|是|
| `INVALID_ARGUMENTS` |参数类型或格式错误|是|
| `UNKNOWN_TOOL` |工具不存在，附搜索引导|是|

这个二分法是有意的：**权限问题重试没有意义，参数问题重试才有意义**。能力范围拒绝的消息里还会附上当前允许的工具示例，并明确写一句「不得换工具绕过限制」。

## 四、为什么不能只依赖模型自己遵守规则

四条理由，从弱到强：

1. **模型输出是不可信输入。**​ 系统提示词、工具描述、仓库文件都可能被注入。程序把「模型声称自己守规矩」当作事实，等于把边界交给最容易被操纵的那一环。
    
2. **模型无法自证。**​ 它只能声明意图，不能证明自己解析到的路径就是它以为的那个路径。符号链接、目录联接、`..` 穿越都会让它的判断与实际落点不一致——而它不会知道自己判断错了。
    
3. **能力范围不是对话能改的东西。**​ 它由任务创建时确定，通过线程上下文传递。模型再怎么被说服，也改不了自己的权限。**这正是注入防御的架构性依据：让注入成功也没有用。**​
    
4. **审计与追责需要程序侧的事实。**​ 审计记录的是程序实际放行或拒绝了什么，不是模型声称做了什么。这一条决定了事后能不能复盘。
    

项目自己的设计原则把这件事说得很直白：**模型负责理解和生成，程序负责权限、状态、证据和一致性。**
