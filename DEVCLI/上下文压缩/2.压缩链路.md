# 6.Microcompact 和语义摘要有什么区别？

Microcompact 当前只处理可以确定证明的内容：
- 内容指纹完全相同的重复工具结果。
- 同一路径先 `read_file`，后来已经被 `write_file` 或 `edit_file` 覆盖的旧读取结果。

也就是先用低成本的处理冗余无作用的内容

# 8.为什么压缩边界必须落在 `user` 消息边界？

1. **配对的天然完整单位是一轮用户请求**。一条用户消息之后的助手消息与工具批次都属于同一轮，切在中间就切断了配对。
2. **摘要要有明确的「这一段在讲什么」**。切在用户边界，被压掉的才是整轮请求；切在中间，摘要描述的对象是残缺的。
3. **重建后的历史形状要求它**。压缩后的历史固定是「系统提示 + 摘要（占一条用户消息的位置）+ 助手确认 + 保留的尾部」。摘要必须能合法地占住一个用户位置——切点在助手或工具中间，摘要就插不进去，会出现工具结果找不到它的调用。
4. **兜底场景也有对应退化**。单条用户轮次里可能塞进无界的助手/工具批次，没有更晚的用户边界时，退化为「只在完整工具批次之后切分」，好让投影能把被删掉的请求替换成摘要那一轮。


---
# 9.如何避免拆开 `tool_call/tool_result` 配对？


1. **主切分**：从尾部往前累计 token，命中第一个满足保留预算的**用户边界**。
2. **尾部超预算时**：只移动安全的用户边界，规则层不得截断用户、助手或最近的工具结果。
3. **没有更晚用户边界时**：退化为「完整工具批次之后」切分。
4. **工具结果淘汰那一层干脆不删消息**：只处理带调用标识的工具结果，替换内容、保留消息本身，配对结构原地不动。
5. **最后的兜底截断**：也是按用户边界整段对齐着删，至少保留最近三条；而且保护事实补不回来时，宁可放弃这次截断。

还有一道独立的校验：一致性检查器会核对摘要有没有把「未解决」的事实错误地写成「已解决」，并且状态冲突**只在同一事实子句或同一条结构化条目内判定**，不用全文关键词互相推断。

# 10.为什么首次摘要和后续增量摘要采用不同策略？

**首次没有基准可增补，只能从头建。

**​策略是：完整摘要请求能放进模型输入预算就一次调用；确实超出才分片做 Map-Reduce。分片上限按完整提示词的 token 估算动态定，优先在消息文本边界切，不切断 Unicode 代理对。


**后续已有结构化摘要，按「已有摘要 + 增量提示词 + 新增消息」的完整请求预算逐批处理**，让模型提出六种操作：新增、更新、解决、取代、过期、删除，程序校验后更新滚动摘要，再处理下一批。

为什么不统一？两头都不划算：

- 每次都重做全部：贵，而且已经稳定的结论每次都要重新表述一遍，容易漂移。
- 首次就做增量：没有基准，没有对象。

还有一条更关键的设计取向：**不「先各自生成一堆独立摘要再无界拼接」**——那正是摘要套摘要的来源。所以每一批都以「已有摘要」为输入做更新，而不是并排堆叠。


---
# 11.如何避免多轮摘要出现“摘要套摘要”？

问题：每次压缩历史时，怎么避免把“旧摘要”再次当普通聊天内容去总结，最后变成“摘要的摘要的摘要”？


旧摘要不是历史材料，而是一个持续更新的“状态表”。下一次压缩时，直接修改这张状态表，而不是重新总结它。

假设第一次压缩，得到摘要 v 1，后面又聊了很多内容，如果再第二次压缩中，把历史编程旧摘要 v 1+后续聊天一起交给模型，那么摘要 v 2 会吧 v 1 再压缩一遍，但是其实 v 1 中的很多内容已经没有用了

# 12.为什么摘要采用固定六段结构，而不是完全自由生成？


六段是：主要请求与意图、关键技术概念、文件和代码、踩过的坑和修复、问题解决过程、逐条用户消息。

并且摘要并不是单纯给用户看的文字，而是 agent 后续运行中所依赖的结构化状态


如果完全的自由生成，会存在几个问题
- 每个模型的摘要格式不同，程序无法稳定解析。
- 文件、错误、用户约束可能混在叙述中，难以校验是否丢失。
- 摘要过长时，程序不知道哪些内容可以优先清理。
- 模型可能自行添加“待办、当前状态、下一步”，与 `SessionMemory` 形成两套状态来源。

固定六段式
**1. 主要请求与意图**  
放用户到底要什么——最初的诉求，以及中途被修正后的**最终**意图。默认生命周期是「稳定」，重要性最高（90），而且是六段里**唯一完全不参与裁剪**的一段。

为什么给它这个地位：意图是整个摘要的解释框架。意图一旦在裁剪里被削掉，后面五段就失去了"为什么记这些"的依据，模型会开始自己补一个任务目标出来。

**2. 关键技术概念**  
放这次任务涉及的技术名词、方案名、口径约定、版本前提。默认「稳定」，重要性 70，裁剪顺序里排**最后**（最不容易被裁）。

为什么：它是理解上下文的前提，但不像意图那样不可替代；标成稳定是因为概念本身不会因为任务推进而失效。

**3. 文件和代码**  
放具体文件路径、符号名、改动位置。默认「已解决」，重要性 70，裁剪顺序排第三。

为什么单独给它一段：路径和符号名属于**精确实体**，在自然语言改写里最容易被模糊成"相关文件""某个方法"。单独成段，才好把"必须以原文出现"这条硬规则落下去。

**4. 踩过的坑和修复**  
放走过的弯路、失败的尝试、错误码，以及最后怎么绕过去的。默认「已解决」，重要性 70，裁剪顺序排第二。

为什么保留：防止模型把同一个坑再踩一遍。但坑修好之后过程细节的价值就掉了，所以它的优先级低于路径和概念。

**5. 问题解决过程**  
放推理脉络、方案权衡的经过。默认「已解决」，重要性 50，**裁剪顺序第一位**——预算不够时最先被裁。

为什么最先裁：它是六段里最"过程性"、最不承载最终结论的一段，但往往占的空间最大。裁它等于用最少的结论损失换最多的空间。

**6. 逐条用户消息**  
放用户逐条的原话要点。默认生命周期是「进行中」（六段里唯一），重要性 50。

它的裁剪规则和别的段**故意相反**：别的段截断是"保头部"，这一段是**保尾部**——最多保留最近 20 条，更早的折成一行计数。理由是最新的用户消息最可能改变当前意图，而用户明确纠正过的信息优先级最高，要能覆盖旧事实。
