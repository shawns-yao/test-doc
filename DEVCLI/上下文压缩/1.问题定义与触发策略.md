# 1.长上下文任务中最主要的问题是什么？

Agent 的上下文不只是有聊天内容，还有包括系统提示词，工具定义，用户和模型的消息，工具的执行结果，图片，以及下一轮模型的输出空间

其中工具结果，代码命令等增加的非常快，如果缩短他们容易丢掉，用户的原始要求和限制，修改的文件和当前的状态，已经失败的文件和失败的原因，tool call 和 tool result 的对应关系等

所以项目解决的是：

> 在 Token 预算内，将早期过程压缩成结构化状态，同时保留最近原始上下文，使 Agent 能连续执行而不是“失忆”。


---
# 2.为什么不能简单删除最早的消息？

因为消息的新旧不等于重要程度。

如果从中间截断，可能只剩 Tool Result，没有对应的 Tool Call，Provider 会拒绝整次请求。

因此项目不会按消息数量机械删除，而是：

1. 保留 System Prompt。
2. 从尾部按照 Token 预算保留最近原文。
3. 将切分点落在 `user` 边界或完整工具调用批次之后。
4. 把早期内容转换为结构化摘要。
5. 使用事实账本和语义校验检查约束、决策及任务状态。
6. 摘要缺少阻塞性事实时，拒绝本次压缩，保留原历史。

# 5.为什么模型已经返回最终答案时，不一定立即触发摘要？

因为正式压缩发生在**下一次调用模型之前**，不是每条消息写入以后立即执行。
	模型给出最终答案、没有后续工具调用，循环就结束了——这一轮不会再有下一次调用，摘要自然不发生。

这样设计的原因是：

- 当前已经不需要再次调用模型，立即压缩没有窗口收益。
- 同步生成摘要会增加一次模型调用、延迟和成本。
- 摘要失败不应该影响已经生成的最终答案。
- 最终答案通常是高价值信息，不应为了暂时没有用途的空间立即改写。
