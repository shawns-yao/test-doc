# 1.“懒压缩 + 结构化滚动摘要”，请具体讲一次压缩是怎么触发的：压缩前拿哪些内容作为输入，压缩后产出什么结构，哪些信息会保留或被丢弃？另外，怎么避免模型生成的错误摘要污染后续上下文？

**可以把它理解成：历史快装不下时，把较早的对话整理成一份“带校验的交接记录”，最近的对话继续保留。不是让模型随便总结一下，就直接替换原文。**

下面用“分析仓库并修复一个 bug”串起来讲。

**一、什么时候触发：懒压缩是什么意思？**

“懒”指的是：**不在每次新增消息后，都立刻压缩正式对话历史；达到上下文预算阈值才处理。**

Agent 在执行循环中估算历史消息占用的 Token，并根据当前模型的上下文配置、工具定义占用等计算历史预算。达到阈值，就触发压缩，而不是固定聊满多少轮才压缩。

例如，前面已经读取很多文件、执行多次测试，工具输出把上下文撑大了，这时就需要压缩。

这里有个细节：项目还支持在轮次结束后异步准备“预摘要”。**提前准备摘要，与提前替换历史，是两回事。** 正式历史仍在触发压缩、通过检查后才替换。


所谓的微压缩，并不是总结上下文，而是确定性地回收已经能证明冗余的工具输出。更像一个垃圾回收的机制。
真正的核心不是旧，而是可以证明冗余，不是说超过了 10 轮删除，或者超过了多少 token 删除，而是把重复或者能被后续事实证明过期的进行回收。
整体的思路是，确定性的便宜操作优先，概率性的昂贵操作后置。

具体的操作，只处理 Tool Result，因为用户问答或者 ai 的消息中可能包含真实的对话语义。但是工具结果往往特别大，比如工具返回几百行等，这些才是上下文膨胀的大户。

并且也不是什么都删除，对于内容完全重复，例如 Agent 连续两次读取同一个文件，相当于同样的东西存了两份。第二种情况是，旧的 read_file 的内容失效了，
比如之前 int age=10，后面修改代码，将改成 int age=20 改，那么第一份的工具结果就不需要再进行存储了。只保留第二个就可以了。
然后回收的内容也不是删除，而是从模型上下文保留到硬盘，

微压缩的目的是，比如 120 k，微压缩之后发现 100 k，还没有到达需要压缩的地步，用于节省。

**二、压缩前：拿什么作为输入？**

---

上下文压缩中，文本，内容，图片，。文件等需要分开压缩

---

先把历史分成三部分：

|部分|怎么处理|
|---|---|
|开头的系统规则|保留，不交给模型重新解释|
|较早的对话|作为摘要来源|
|最近一段对话|按 Token 预算保留，继续提供细节|

切分时会寻找安全的用户消息边界或完整工具批次边界，避免把“工具调用”和“工具返回结果”拆开。

摘要来源包括早期用户要求、助手回复、工具调用和工具结果。**第一次压缩主要处理旧消息；后续通常用“上一版摘要＋这次新增的旧消息”做增量更新。** 输入过长时可以分块汇总。

在摘要前，程序还会：

- 保存原始消息快照，避免先清理内容、再丢失摘要依据。
- 折叠重复或可判定已被后续结果替代的工具输出。

**三、怎么压缩的以及压缩后：产出什么结构？**

发起一次特殊的 llm 调用，明确要求这个压缩调用不能唤起任何工具，也就是这是一个受限的 agent 模型调用，不参与正常的 Tool Loop，
要求摘要包括六段信息

|分段|修复 bug 场景下的内容示例|
|---|---|
|主要请求与意图|修复问题，但不能改变公开接口|
|关键技术概念|与问题有关的缓存机制、调用关系|
|文件和代码|相关位置、关键逻辑和修改内容|
|踩过的坑和修复|哪种尝试失败，原因是什么|
|问题解决过程|如何定位问题、采用了什么处理方式|
|逐条用户消息|用户提出的要求和补充，不保证逐字保留|

它不只是六段自由文本。摘要条目还可以带有标识、主题、修订号、生命周期、重要性和证据引用，用于更新、替代和清理旧内容。

最终上下文大致变成：

**系统规则 → 滚动摘要 → 恢复的受保护事实及运行上下文 → 最近对话。**

特别注意：**“待办、当前工作、下一步”不再由滚动摘要维护。** 当前任务状态由运行时任务记忆维护，避免摘要模型自己宣布任务完成。

**四、哪些保留，哪些丢弃？**

优先保留用户约束、关键决策、有关文件和错误、未解决问题，以及最近对话。

重复输出、已被替代的信息、较低优先级的历史细节会被折叠或裁剪；已失效、已被替代的摘要条目，不再把旧正文注入上下文。

例如，同一份错误日志出现五次，不需要五份原文；但“测试仍然失败，错误是什么”不能随手删掉。

**压缩是有损的。** “保留关键事实”不等于“所有历史细节都能完整恢复”。



# 2.怎么防止一次错误摘要，把后面整个 Agent 的上下文都带偏？

核心不是“让摘要模型尽量不犯错”，而是：

> **永远不要把摘要当成新的事实源。摘要只能是可回溯、可验证、可丢弃的派生缓存。**

假设 Agent 前面已经聊了很多轮：上下文越来越长，于是系统决定压缩。
但如果模型摘要时犯错，后面的模型看到的就只剩下这个**错误摘要**。


所以再摘要压缩之前，先做一步事实提取，也就是压缩前先列一个“考试答案”。然后模型再生成摘要。
