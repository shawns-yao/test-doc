
# Service：Pod 的 IP 一直变，调用方到底怎么找到它

## 一、问题：Pod 的 IP 从来都不固定

Deployment 一旦重建、滚动更新或扩缩容，**那批 Pod 的 IP 就全变了**。如果调用方把 Pod 地址写死，那么每次发布、重启、扩容都得改代码，这显然不可行。

解法是给这组 Pod 一个**固定的门牌**：**Service**。

## 二、Service 是什么：固定门牌 + 一份自动名单

Service 提供三样「不会变 / 自动维护」的东西：

- **一个固定的虚拟 IP（ClusterIP）**：只在集群内部可达，默认类型就是它。
- **一个固定的名字**：会被集群 DNS 解析成上面的虚拟 IP。
- **一份自动维护的后端名单**：记录当前有哪些健康的 Pod。

需要特别澄清：**Service 自己并不转发流量，它本质是一组规则。** 真正干活的是每个节点上的 **kube-proxy**——它持续盯着 Service 和后端名单，在节点上写出 iptables / IPVS 规则，把发往虚拟 IP 的请求**负载均衡**到某一个后端 Pod。所以「Service」更像写在墙上的分工规则，而不是一台站在中间的机器。

## 三、Service 怎么知道流量该给谁：靠标签，不靠 IP

每个 Pod 出生时都带着几张「便签」，叫**标签（Label）**，比如「我是订单服务」「我是 v2」。Service 不记 IP，只写一条**选择器（Selector）**规则：

> 凡是贴着「app = 订单服务」这张便签、并且已经就绪的 Pod，都是我的成员。

于是后端名单（存在 EndpointSlice 里）自动维护：新 Pod 起来、标签匹配且就绪，自动进名单；旧 Pod 被杀、或标签不符、或还没就绪，自动被排除。**自始至终，Service 自己的地址都没动过。**

## 四、调用方怎么写地址：写名字就行

集群内部自带一个「通讯录」——DNS 组件（CoreDNS）。**你完全不需要知道任何 IP**：Service 的名字会自动变成一个域名，代码里直接写服务名即可，例如 `http://order-service`。这件事的正式名字叫**服务发现（Service Discovery）**。

## 五、一个必须记住的区分：Service 不是 Pod 的上级

- **Deployment** 管「Pod 有几个、是哪个版本」。
- **Service** 管「流量怎么找到这些 Pod」。

这两者**互不知道对方存在，只靠标签对上号**，这就是松耦合。好处很实在：你换版本、加副本、改配置，Service 一行都不用动。反过来，一旦把 Service 当成「Pod 的上级」，就会开始问「Service 重启了 Pod 会不会重启」这类从根上跑偏的问题。
