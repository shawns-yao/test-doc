
# Deployment：谁来保证永远有 N 个 Pod 在跑

## 一、裸 Pod 最大的毛病：没人管

裸 Pod 一旦挂了，就真的挂了——没人知道，更没人补上。手动一个个重启既不可靠也不现实。

于是需要一个「管家」，它的全部工作就是**不断核对两件事**：

- **期望状态**：你声明「这个服务要一直保持 3 个副本」。
- **实际状态**：现在真正活着的有几个。

一旦发现少了（挂掉、被误删、节点宕机），它就立刻补到 3 个。这个管家就是 **Deployment**。这种「只描述想要什么、由系统持续对齐」的方式叫**声明式**，背后是一个不停循环的对账（reconcile）过程。

## 二、Deployment 内部其实是三层

打开 Deployment，里面是三个层级，各管一件事：

- **Deployment —— 管版本**：「当前要跑的是 v2」。
- **ReplicaSet —— 管数量**：「v2 这个版本，要 3 个」。
- **Pod —— 具体实体**：真正干活的实例。

打个比方：Deployment 是店长定的**编制表**（「这个岗位永远 3 个人」），ReplicaSet 是某个版本的**当班考勤表**，Pod 是**具体上班的人**。换版本不是把旧人改造一遍，而是新开一张 v2 的考勤表，让 v1 的人逐渐下班——所以每换一次版本，就会多出一张 ReplicaSet。

## 三、滚动更新：为什么用户感觉不到

换版本时，Deployment 不会「把旧的全部杀掉，再把新的全部起来」，那样服务会中断。它做的是**一进一出、平滑交替**：

**先起一个新的 → 等它通过就绪检查（真正「就绪」、能接活了）→ 才撤掉一个旧的 → 再起下一个，如此循环。** 整个过程始终保持「有足够的容器在接活」。

更新的节奏由两个参数控制（默认都约为 25%）：

- **maxSurge（峰值）**：更新期间，最多允许比期望副本数**多出**几个 Pod（用来先把新的顶上来）。
- **maxUnavailable（不可用）**：更新期间，最多允许比期望副本数**少**几个 Pod（即同时能撤掉几个旧的）。

## 四、新版本起不来，怎么回滚

Deployment 每次变更都会留下一份历史版本（即旧的 ReplicaSet），所以可以一键退回上一版。但**回滚不是「把新容器改回旧代码」，而是把旧的那张考勤表重新拿出来，按它重建一批旧版本的 Pod**。

- **前提**：旧镜像还在仓库里，并且你知道要退到哪一版。
- **K8s 默认不会自动回滚**：新版本一直起不来时，它会卡在中间状态（旧的还留着、不敢全杀），超过期限（默认约 10 分钟）报一个「进度超时（ProgressDeadlineExceeded）」就不再推进——它只是告诉你「我卡住了」，并不会自己退回去。**决定退不退的是人，或者你那条流水线。**
