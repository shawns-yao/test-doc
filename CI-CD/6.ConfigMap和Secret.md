
# ConfigMap 和 Secret：配置和密码不该打进镜像

## 一、为什么配置和密码要放在镜像外面

1. **同一个镜像要跑在多个环境**（开发、测试、预发、生产），数据库地址、功能开关各不相同。打进去就得为每个环境各构建一次镜像，「一次构建、到处运行」的好处直接归零。
2. **密码会跟着镜像到处流转**——镜像仓库里、别人的机器上、构建日志里，全是它；改一次密码还得重新构建镜像。
3. **镜像构建完就是只读的**（这正是它的优点），所以配置只能在**运行时从外部注入**。

一句话：**镜像里放不变的东西，配置和密码从外面给。**

## 二、ConfigMap 与 Secret 的分工

- **ConfigMap**：放普通配置——数据库地址、功能开关、超时时间，**明文**保存。
- **Secret**：放敏感信息——密码、令牌、密钥、证书。常见类型有：
  - **Opaque**：通用键值（最常用）；
  - **kubernetes.io/dockerconfigjson**：私有镜像仓库的拉取凭据；
  - **kubernetes.io/tls**：HTTPS 证书与私钥（Ingress 常用）；
  - **kubernetes.io/service-account-token**：服务账号令牌。

## 三、Secret 默认不是加密，只是编码

这是几乎所有新手都会搞错的一点：**Secret 默认并没有加密，它只是把值做了一次 Base64 编码。** 任何能读到它的人，随手一解码就能还原明文。它和 ConfigMap 的真正差别，是「**有意愿被保护**」：单独存放、权限可以收得更紧、默认不轻易打印到日志、可以开启静态加密。

要让 Secret 真正安全，靠的是这几件事，而不是「它叫 Secret」：

- **开启 etcd 静态加密**：让 Secret 落盘到 etcd 时是密文存储（配置 EncryptionConfiguration），否则有权限读到 etcd 备份的人能直接拿到明文。
- **收紧 RBAC 权限**：限制谁能 get / list Secret；默认状态下能读 ConfigMap 的人往往也能读 Secret。
- **绝不把 Secret 提交进代码仓库**；CI 里可接入密钥扫描。

## 四、怎么把配置交给容器：两种方式

- **注入为环境变量**：用 `env` 指定单个键，或用 **`envFrom`** 把整个 ConfigMap / Secret 的所有键一次性批量注入为环境变量。
- **挂载为文件**：把 ConfigMap / Secret 挂成容器里的一个目录，每个键变成一个文件（适合配置文件、证书）。

## 五、核心结论：配置改了，不等于应用知道了

- **环境变量**是启动那一刻的快照，之后集群里怎么改，容器里都不会变。
- **挂载成文件**会更新，但有延迟，而且**应用必须自己重新读**——启动时读一次就缓存住的应用照样不生效。

所以最稳的做法是**把配置改动当成一次发布**：改配置 → 触发一次滚动更新 → 新容器带着新配置起来 → 旧容器被换掉。这样「配置版本」和「镜像版本」始终对得上，出问题也能一起回滚。

再往前推一步：**配置改动应该跟代码一样走 Git**（GitOps）。在生产上直接敲命令改配置等于绕过所有流程，下次同步或回滚时这份手改值会被覆盖——然后你会得到一个「我明明改过啊」的深夜故事。
