
# 健康检测（探针）：集群怎么知道一个容器还能不能干活

## 一、光看「进程在不在」远远不够

如果只判断「进程是否存在」，会漏掉两种最常见的「假活」状态：

- **进程还在，但已经废了**：死锁、连接池耗尽、依赖的下游挂了。进程活着，请求进去却全报错。
- **进程刚起来，但还不能接活**：正在加载缓存、预热数据、初始化连接。进程在，但此刻还干不了活。

把这两种容器当成健康的、继续往里打流量，用户就会看到一片 500。所以需要一套更细的**健康检查（探针，Probe）**。

## 二、三种探针，各问一个问题

- **存活探针 livenessProbe**：问「你还活着吗？」失败 → **杀掉并重启容器**（相当于重试，赌它重起一次能好）。
- **就绪探针 readinessProbe**：问「你现在能接活吗？」失败 → **把容器从 Service 后端名单里摘掉、不派流量**，但**不重启**，人还在；恢复后自动加回。
- **启动探针 startupProbe**：问「你启动完了吗？」在它通过之前，存活 / 就绪探针**一律先不生效**。

## 三、为什么还需要 startupProbe

有些老应用（尤其大型 Java 服务）启动很慢，要加载几分钟。如果只配存活探针，它会在应用还没启动完时就反复判定失败、不断重启容器——结果应用**永远也启动不完**，陷入「启动 → 被判死 → 重启」的死循环。

启动探针就是给慢启动应用一段「宽限期」：

- 它通过之前，存活 / 就绪探针都不介入，不会被误杀；
- 它一旦通过（确认启动完成），就把健康判断交还给存活 / 就绪探针，自己不再起作用。

## 四、探针具体怎么探：三种方式

- **HTTP 请求（httpGet）**：探一个 HTTP 路径，返回 **2xx / 3xx** 算成功。**最常用**，适合有 Web 服务的应用。
- **TCP 端口（tcpSocket）**：探端口能不能建立连接。**最弱**——端口通只说明进程在监听，不代表业务正常。
- **执行命令（exec）**：在容器里跑一条命令，**退出码为 0** 算成功。适合没有 Web 接口的服务。

## 五、探针的节奏参数

同一条探针，靠这几个参数控制「多久探一次、几次失败才算数」：

- **initialDelaySeconds**：容器启动后，等多少秒再开始第一次探测（给初始化留时间）。
- **periodSeconds**：探测间隔，默认 10 秒。
- **timeoutSeconds**：单次探测的超时时间，默认 1 秒，超时算一次失败。
- **failureThreshold**：连续失败几次才判定为失败，默认 3 次。
- **successThreshold**：需要连续成功几次才算恢复（就绪探针默认 1）。

## 六、设计原则：要探业务，但别探太重

- **就绪探针要真实**：它决定能不能接活，应反映关键依赖（如必要的连接、缓存是否就绪），但**不要依赖会抖动的下游**，否则别人一抖你就被摘流量。
- **存活探针要保守**：它一失败就重启，误判会造成无意义的反复重启；通常只用来从「彻底卡死」中自救。
- **探测要轻**：别每次都查数据库、调重接口，探针本身可能把服务拖垮。
