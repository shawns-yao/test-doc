
# 资源和调度：为什么容器会被 OOMKill、为什么有空机器却调度不上

## 一、requests 和 limits：两个数字管两件事

- **requests（申请量）**：「我保证要这么多」。**调度器按这个数字决定把 Pod 放到哪台机器**，它是「预留」——不管你实际用不用，这块资源都算被占住。
- **limits（上限）**：「最多给我这么多」，超了就会被处理。

打个比方：requests 是**订座**，limits 是**限购**。订了座别人就不能坐，哪怕你一直没来；超过限购就会被拦下。

## 二、最关键的一点：CPU 和内存超限后果完全不同

这是本讲最值得记住的一句话：

- **CPU 超限 → 限速（throttle）**：不杀你，只是让你慢下来。服务还活着，但响应变慢、吞吐下降。
- **内存超限 → 直接杀（OOMKilled）**：内存没法「限速」——它已经被占住，只能把整个容器干掉，再由上层重启。**退出码 137 就是这么来的（137 = 128 + 9，即被 SIGKILL 强制终止）。**

所以「接口变慢」和「容器反复重启」是两个方向完全不同的故障，别用同一套思路去查。

## 三、为什么「明明有空机器，Pod 却调度不上」

因为调度器是按 **requests 求和**来判断的，**不看实际用量**。一台 4 核的机器上跑了两个 Pod、每个申请 2 核——哪怕它们实际各只用 0.1 核，这台机器在调度器眼里也已经「满了」，第三个申请 1 核的 Pod 只能一直排队。

- **requests 设太大**：大量资源被白白预留，钱花了没用上。
- **requests 设太小**：机器被超卖，多个容器真跑起来互相抢、一起变慢。

这本质是**容量规划问题**，不是单纯的配置问题。

## 四、内存不够时杀谁：由 QoS 等级决定，不是随机

节点内存真的不够时，kubelet 会按 Pod 的 **QoS（服务质量等级）** 决定先牺牲谁。QoS 由你怎么设 requests / limits 自动划定，共三档（保护力度从弱到强）：

- **BestEffort（尽力而为）**：完全没设 requests / limits。节点一紧张**最先被杀**。
- **Burstable（可突发）**：设了 requests / limits，但不满足 Guaranteed。当实际用量**超出自己的 requests** 时，会排在 BestEffort 之后被杀。
- **Guaranteed（有保障）**：每个容器的 CPU、内存都设了、且 **requests = limits**。**最受保护、最后才轮到**，通常只在极端情况下才被波及。

所以「为什么被杀的是我不是别人」不是运气，而是你的 QoS 档位和超出 requests 的程度决定的——**想保命，就把 requests / limits 设清楚。**
