
# 镜像、容器、Pod 与 CI/CD：从「在我机器上能跑」到自动上线

## 一、镜像：把程序和它依赖的环境一起打包

### 1.1 「在我机器上能跑」是怎么回事

你写的程序在自己电脑上正常，发给别人却跑不起来：缺了某个库、依赖版本不一致、操作系统不同。问题往往不在代码，而在于——**一个程序能跑，靠的不只是代码，还有它身后的一整套环境。**

### 1.2 解法：连同环境一起打包

与其只交代码、让对方自己凑环境，不如把代码连同依赖、运行时、系统配置一起打成一个自包含的包。这个包就是**镜像（Image）**。

- 镜像里装的是「让程序能跑起来所需的一切」，构建完成后**只读**、不能被修改。
- 同一个镜像，在任何机器上解开都是一致的环境，这就是「一次构建，到处运行」。

### 1.3 镜像是「一层一层」叠出来的

镜像不是一个大文件，而是由多个**只读层（Layer）**堆叠、联合挂载而成：基础系统层、运行时层、依赖层、代码层……每一层对应构建脚本（Dockerfile）里的一步。

- **层可以复用**：多个镜像能共享相同的底层，只在有差异的地方新增层，构建和传输都更快。
- **改代码很省**：通常只有最上面的代码层需要重建，下面的层直接走缓存。

## 二、容器：镜像跑起来的实例

### 2.1 镜像和容器：模板与实例

镜像是**静态的、只读的模板**；把它运行起来，得到的那个**正在运行的进程**就是**容器（Container）**。

- 类比：镜像是模具 / 菜谱，容器是用模具做出的成品 / 按菜谱炒出的菜。也像集装箱——规格统一，里面装什么不影响运输和吊装。

### 2.2 一个镜像，可以同时跑任意多个容器

同一个镜像，可以启动一份、两份、十份彼此独立的容器。每个容器都建立在镜像的只读层之上，并在最上面加了一层**自己的可读写层**——运行中产生的临时文件、改动都在这一层，容器一删就丢弃。

- 容器是「用完即可丢弃」的：坏了、卡住了，删掉重新起一个就行，底下的镜像不受影响。
- 容器之间靠 namespace 隔离各自的视图、靠 cgroups 限制能用多少资源，彼此互不干扰。

## 三、Pod：编排的最小单位

### 3.1 容器多了，需要「编排」

单机跑几个容器没问题；规模一上来就有新麻烦：一台机器装不下、机器会故障、流量高峰要临时加实例。需要一个「管家」自动决定**容器放到哪台机器、挂了怎么补、流量涨了怎么扩**——这叫**编排（Orchestration）**，Kubernetes（简称 K8s）就是这样的编排系统。

### 3.2 为什么最小单位是 Pod，而不是容器

有些容器天生要绑在一起：比如主程序 + 一个专门收集它日志的助手，必须同进同退。K8s 不直接调度单个容器，而是把这组**紧密耦合的容器**打包成一个 **Pod**，作为最小调度单位——要搬一起搬，要死一起死。

### 3.3 Pod 里，什么是共享的、什么是隔离的

- **共享网络**：Pod 内的容器看到同一个 network namespace——同一个 IP、同一张网卡、同一套端口，彼此直接用 <code>localhost</code> 通信。
- **共享存储卷**：挂载同一个 Volume（卷），容器之间就能互相递文件。
- **文件系统 / 进程相互隔离**：每个容器有独立的 rootfs 和进程视图，默认互不相通，这是最容易想当然搞错的一点。
- **Pod IP 是临时的**：Pod 一重建 IP 就变，所以绝不能靠 Pod IP 做服务发现——这正是后面需要 Service 的原因。

## 四、CI/CD：代码怎么自动跑到线上

### 4.1 流水线：把一长串手动操作交给机器

从代码到线上，要经过编译、测试、打包镜像、推送仓库、修改配置、重启等一连串动作，纯手工操作十次能漏八次。把这些步骤写成一条自动执行的流程，就是**流水线（Pipeline）**。

### 4.2 CI 管「检查」，CD 管「上线」

- **CI（持续集成，Continuous Integration）**：每次提交代码，自动触发编译、测试、安全扫描，尽早把坏代码挡在主干之外。
- **CD（持续交付 / 持续部署，Continuous Delivery / Deployment）**：检查通过后，自动把新版本发布到目标环境。在 K8s 上通常是**滚动更新**——先起新 Pod、等它就绪，再逐步撤掉旧 Pod，整个过程用户无感知。
