# 01 亿级流量场景下，需要和 30 万个黑名单 ID 做匹配，并要求秒级响应，如何高效实现黑名单过滤？

## 01 核心回答


**概念原理（两级方案）：**黑名单完整数据存储在 Redis `SET` 中作为**精确判断依据**，同时在每个应用实例本地维护 **Bloom Filter（布隆过滤器）** 做预筛。请求到达后先查本地 Bloom：版本已确认新鲜时，判断“不存在”可直接放行；判断“可能存在”再通过 Redis `SISMEMBER` 精确确认——绝大多数非黑名单请求在应用内存完成判断，避免每个请求都访问 Redis，在负查询占比高且版本维护可控时降低网络 IO 和 Redis QPS。

**请求处理流程：**

1. 请求 → 查本地 Bloom Filter

2. 版本已确认追平且不存在 → **放行**；版本落后 → 精确回源

3. 可能存在 → Redis `SISMEMBER` 精确确认 → 命中才拦截。Bloom 允许假阳性，最多导致一次额外 Redis 查询，**不会直接误拦截**。

**同步顺序（关键细节）：**必须避免数据同步延迟产生**“假阴性”**（Bloom 判不存在但实际是黑名单）。**新增黑名单**：先确保所有可使用阴性快速路径的实例已包含该新增项，再发布权威黑名单新版本；未确认实例必须回源或暂停服务，不能只更新一个 Bloom 就写 Redis；**删除黑名单**：先从 Redis 删除，普通 Bloom 不立即删除对应元素，允许暂时保留假阳性，后续通过**周期性全量重建**清理。

**分布式最终一致：****MQ/CDC 增量同步 + 版本号校验 + 周期性全量重建**。每个变更事件支持幂等消费；实例发现版本号断层则放弃增量，重新加载完整快照并**原子替换**本地 Bloom Filter。

**性能扩展路径：**先通过本地 Bloom、大批量查询和连接池降低 Redis 压力；只有单个 Redis 实例的 CPU、网络吞吐或 QPS 确实达到瓶颈时，再考虑 Redis Cluster 分片。

**监控指标：**Bloom 误判率、Bloom 命中率、Redis `SISMEMBER` QPS / P99 延迟、数据版本差异、同步失败率。

**口述重点：**Bloom 只负责快速排除“不可能命中”的请求，最终是否命中黑名单必须由精确存储确认；同步顺序的核心是“新增先 Bloom、删除先 Redis”，在所有服务实例均已纳入变更的前提下避免同步漏判，版本落后必须回源。

## 02 理解机制与追问

先澄清“亿级”是日请求总量还是峰值每秒请求，以及允许多长的黑名单生效延迟。30 万个 64 位 ID 的裸数据约 2.4 MB，本地精确哈希集合也可能足够，不能默认一定需要 Bloom + Redis。只有内存或网络访问成本确有压力时，才用概率预筛减少负查询。

## 03 易错点与适用边界

关键修正：数学上的无假阴性只针对已经完整加入当前过滤器的集合，不包括同步遗漏。先更新某个 Bloom 再写 Redis，不能证明所有服务实例已更新。新实例、离线实例、重建期间必须校验版本；版本落后时回退权威精确查询或按业务拒绝服务。Bloom 阳性需精确确认，阴性直接放行需以版本新鲜度成立为前提。

## 04 面试口述

先用本地精确集合评估容量，再决定是否用 Bloom。若采用两级方案，我不仅解释误判，还会保证所有可服务实例的过滤器包含当前生效黑名单，否则阴性必须回源。
