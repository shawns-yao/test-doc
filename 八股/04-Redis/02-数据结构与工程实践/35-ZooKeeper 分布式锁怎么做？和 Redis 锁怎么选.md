# 35 ZooKeeper 分布式锁怎么做？和 Redis 锁怎么选？

## 01 核心回答

**概念原理：**ZooKeeper 锁思路和 Redis 不同，常见做法基于**临时顺序节点**：

1. 客户端在锁目录下创建临时顺序节点

2. 如果自己是最小节点，说明拿到锁

3. 如果不是最小节点，就**监听排在自己前面的那个节点**

4. 前驱节点删除后，再尝试拿锁。

**优点：**客户端会话过期后临时节点删除、锁释放，短暂断连不等于立即释放；监听前驱节点而非锁根节点，减少**羊群效应**；更容易实现公平锁语义。

**Redis 锁**

性能高、实现轻，适合高频短锁；但底层复制一致性要格外注意（主从异步复制下可能双持锁）。

**ZooKeeper 锁**

一致性更强、自动释放更自然，但性能和复杂度成本更高。

**选型：**高并发热点资源竞争时，更好的方向不是「把锁做得更重」，而是先从业务上拆分资源、降低热点。

---

## 02 理解机制与追问

临时节点绑定 ZooKeeper 会话，而不是客户端 TCP 一断就立即消失；短暂断连和会话过期要区分。创建顺序节点后若响应丢失，客户端应以唯一请求标识查找已创建节点，避免盲目重试造成多节点。监听前驱时要处理“前驱在注册监听前已删除”的竞争，重新检查并进入循环。

---

## 03 易错点与适用边界

ZooKeeper 解决锁授予的协调，不会自动停止已失去会话的旧进程访问外部资源。仍需让资源端验证 fencing token 或用业务条件更新。顺序节点可辅助生成顺序标识，但还要考虑锁目录重建、计数范围等边界。公平性是按成功排队顺序近似实现，不保证调度延迟相同。

---

## 04 面试口述

用临时顺序节点排队，只监听前驱减少通知风暴；会话过期释放锁。选 ZooKeeper 仍要处理失效持有者的外部写，锁协调与业务执行是两回事。
