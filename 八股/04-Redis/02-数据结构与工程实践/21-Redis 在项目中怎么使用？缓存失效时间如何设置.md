# 21 Redis 在项目中怎么使用？缓存失效时间如何设置？

## 01 核心回答


**缓存**
用户、配置和热点查询结果，采用 Cache Aside。

**临时状态**
会话、验证码、幂等键和分布式锁，用带 TTL 的 String 或 Hash。

**高并发原子操作**
计数、排行榜、集合去重和在线状态，分别用自增、Sorted Set、Set、Bitmap。

**TTL 策略：**不能一刀切。短期验证码和幂等键按业务有效期设置；热点缓存设置较长 TTL 并使用随机抖动，避免大量 key 同时过期；必须及时失效的数据用主动删除、版本号或消息通知。缓存重建要防止击穿，删除失败要有重试和对账，不能把 TTL 当作一致性方案的唯一保障。

**关注：**缓存穿透、热 key、大 key、内存淘汰、主从延迟、持久化和故障降级。上线前通过命中率、回源 QPS、P99 延迟、内存使用和过期分布判断 TTL 是否合理，而不是只看缓存是否命中。

---

## 02 理解机制与追问

TTL 从数据允许多旧、重建代价、访问频率和内存预算反推。热点缓存可提前异步刷新；长尾缓存更适合自然过期。幂等键有效期必须覆盖客户端重试和消息重投窗口，而验证码、安全令牌不能为分散过期随意超过安全有效期。

---

## 03 易错点与适用边界

随机抖动应加在业务允许范围，不能改变必须准时失效的语义。Redis 到期通常结合访问时检查与主动清理，不能依赖过期事件精确调度业务任务。SET 等覆盖操作可能影响原 TTL，按命令语义验证；TTL 不是数据备份也不是强一致协议。

---

## 04 面试口述

我不会给所有 key 一个固定时间，而是按业务新鲜度、重建成本和容量设 TTL，再用命中、回源和尾延迟验证；关键有效期单独严格处理。
