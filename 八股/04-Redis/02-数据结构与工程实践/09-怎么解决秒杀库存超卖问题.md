# 09 怎么解决秒杀库存超卖问题？

## 01 核心回答


1. **入口控制：**验证码、用户和设备限流、黑名单、重复购买校验以及队列削峰控制请求量。

2. **Redis 原子扣减：**库存预热到 Redis，用 Lua 脚本一次完成“库存大于零、扣减库存、记录用户是否购买”，避免先读后写超卖。脚本成功只代表获得下单资格，不等于订单和库存已最终完成。

3. **异步落库兜底：**消息队列异步创建订单或扣减 MySQL 库存，消费者用订单号/请求号幂等；MySQL 用 `UPDATE stock SET stock = stock - 1 WHERE id = ? AND stock > 0` 条件更新兜底；库存预扣、支付超时、取消订单和回补用明确状态机管理，避免多扣或多补。

还要处理 Redis 故障、缓存预热失败、消息积压、数据库主从延迟和热点 key。监控覆盖入口 QPS、限流拒绝、Redis 脚本耗时、库存差异、订单成功率、队列堆积和补偿失败率。秒杀不是简单加一把分布式锁，锁粒度过大反而会把大量请求串行化。

---

## 02 理解机制与追问

Redis 预扣与发 MQ 若是两步，进程在中间崩溃会出现库存已预占却没有订单任务。可把预占状态和待发送事件一起写入同一受控原子域，再由可恢复投递器发送并幂等确认，或以数据库事务/outbox 作为事实入口；具体方案须权衡吞吐与故障恢复。

---

## 03 易错点与适用边界

“库存不超卖”不等于“Redis 预扣一定不丢、用户一定下单成功”。MySQL 条件扣减的受影响行数决定最终是否成功，用户唯一购买约束还要独立执行。取消回补须以订单状态迁移为前提且只补一次；消息乱序、重复以及 Redis 故障后重新预热都需要版本/流水对账。

---

## 04 面试口述

先限流削峰，预扣只授资格，最终订单与库存由权威事务约束。难点是预扣到落单之间的可靠事件、重复消费和取消回补，而不是单条扣库存命令。
