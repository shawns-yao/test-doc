# 19 Redis 中的双写一致性有哪些常见实现方式？先写 MySQL 再删 Redis 可能出现什么问题？

## 01 核心回答


常见模式：

**Cache Aside**
读未命中查库回填，写时更新库再删缓存。

**先 DB 后删缓存**
生产最常用，MySQL 为事实来源，写成功删 Redis。

**先删缓存后更新**
更新期间读请求可能回填旧值，常配合延迟双删。

**binlog 异步刷新**
订阅 binlog 或变更消息异步更新缓存，需可靠事件、重试和对账。

**“先写 MySQL 再删 Redis”的竞态：**两个窗口——线程 A 更新数据库但尚未删缓存时，线程 B 读到旧缓存；A 删缓存后，线程 C 因读取旧数据库副本或事务快照，又把旧值回填到 Redis。短 TTL、延迟双删、版本号、读主库、分布式锁和缓存写入版本比较可降低概率，但不能无条件宣称强一致。

**强一致建议：**关键读写走数据库事务或同一协调机制，牺牲部分性能换取确定性。方案必须覆盖删除失败、重复消息、主从延迟、缓存故障、回填旧值和补偿任务自身失败等场景。

---

## 02 理解机制与追问

典型旧回填时序：读请求查到数据库旧版本并暂停；写请求提交新版本、删除缓存；旧读恢复把旧值填回。即使所有读都走主库也可能出现，所以“读主就解决一致性”不成立。延迟双删只是再删一次，无法证明一定晚于所有暂停的旧读。

---

## 03 易错点与适用边界

版本 CAS 必须原子比较并写入；若删除整个键连版本一起消失，旧回填可能被当成首次写入而放行。可保留版本栅栏/失效代数或采用事务性事件驱动视图，但每种方案都有内存、可用性与复杂度代价。TTL 仅给特定故障路径设收敛窗口，还取决于失败恢复和回填源是否正确。

---

## 04 面试口述

先库后删是常见最终一致起点，难点是提交后漏删和并发旧值回填。我会用可靠事件保证失效可重试，版本协议解决乱序，关键强一致读仍走权威路径。
