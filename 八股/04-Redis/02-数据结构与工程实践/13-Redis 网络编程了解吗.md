# 13 Redis 网络编程了解吗？

## 01 核心回答


**通信模型：**TCP + RESP 协议。客户端把命令编码为 RESP，服务端解析、执行并返回响应；事件驱动模型处理连接建立、可读事件、命令执行、写回和定时任务。单条命令在同一实例内不被其他客户端命令插入，因此 `INCR`、`SETNX` 等单命令具有原子性。

**客户端优化：**连接池复用 TCP 连接；pipeline 一次发送多条命令减少网络往返，但 pipeline 不等于事务；需要条件判断和多步原子操作时用 `MULTI/EXEC` 或 Lua。长耗时命令和大 key 操作会拖长事件循环；慢客户端会积压缓冲，BLPOP 等通常只阻塞调用客户端，通过拆分、分页、异步处理和超时控制降低影响。

**排查：**区分客户端排队、网络往返、服务端命令执行、持久化和复制延迟；关注连接数、输入输出缓冲区、慢查询、热点 key 和集群重定向，不能只看平均耗时。

## 02 理解机制与追问

RESP 是消息编码协议，TCP 是字节流：客户端必须按协议长度和类型解析，不能假设一次 read 就是一条完整回复。pipeline 把多次等待 RTT 变成批量发送，但仍需匹配每条回复；批次过大增加服务端输出缓冲和尾延迟。多路复用不等于每个连接都有独立执行线程。

## 03 易错点与适用边界

修正“阻塞命令占用事件循环”：BLPOP 这类等待数据的命令通常阻塞的是调用客户端，服务器仍服务其他客户端；长时间执行的 Lua、大集合操作才可能占住命令执行路径。Redis 6 起引入可配置 I/O 线程，后台持久化、回收等也并非全由单一线程完成，细节按版本看。

## 04 面试口述

我会从协议解析、长连接、多路复用、命令执行和批量往返解释性能，区分客户端等待与服务器计算阻塞，再用慢日志和网络指标定位延迟。
