# 38 Redis 热 key 如何发现与治理？

## 01 先区分热 key、大 key 和热分片

热 key 是单位时间内被大量访问的键，大 key 是值体积或集合规模很大的键；一个小计数器也可能极热，两者也可能重叠。热分片还可能由很多普通键共同造成。排查先把节点 CPU、网络字节、P99、命令耗时和访问分布对应起来，确认瓶颈是读请求数、返回字节、写竞争还是长命令，不能看见某节点忙就直接拆所有键。

Redis Cluster 把一个 key 路由到一个槽、一个负责的主节点；单纯加节点或迁槽可以隔离它与其他负载，却不会把这个 key 的写入自动并行到多台主节点。虚拟节点或更多槽也不能消除单键热点。依据：[Redis Cluster 槽位与路由](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)。

---

## 02 热点怎样发现才不会把生产拖慢

1. 优先在应用或代理统计每个时间窗口的访问频次、读写比例和响应字节，采用采样或有界 Top-K 汇总，关联活动、租户与命令类型；避免把所有原始 key 永久变成高基数监控标签
2. 支持时使用 redis-cli 的 `--hotkeys` 辅助扫描。它依赖 LFU 淘汰策略下的访问频率计数，结果是带衰减的近似频度，不是精确实时 QPS 排名；不要为了排障直接修改生产淘汰策略。按节点覆盖并限速，也要理解短促热点可能在扫描前后消失。`--bigkeys`/内存统计找的是规模，不能代替热度统计。依据：[Redis CLI 扫描模式](https://redis.io/docs/latest/develop/tools/cli/)、[Redis LFU 淘汰与近似计数](https://redis.io/docs/latest/develop/reference/eviction/)
3. 慢日志用于找高执行成本命令，不代表能发现大量很快但总量极高的 GET。`MONITOR` 会输出实时命令流，处理与传输都增加负载，也可能暴露业务参数；只在受控范围、短时窗口使用，不把它当常驻全量热键采集器。依据：[Redis SLOWLOG](https://redis.io/docs/latest/commands/slowlog/)、[MONITOR 的性能代价](https://redis.io/docs/latest/commands/monitor/)

## 03 读热点如何分担

优先减少抵达 Redis 的重复读取：对读多写少且允许短暂旧值的数据使用有界本地缓存、客户端缓存或适合的边缘缓存；同 key 并发 miss 做请求合并，热门活动前分批预热。缓存键必须包含租户、权限和影响结果的条件，不能把个性化结果缓存成所有人共用。

缓存收益必须和失效协议一起设计。Redis 客户端缓存可跟踪读取并接收失效通知，需核对客户端版本、断线清理和重连语义；不能漏掉失效消息后继续永久使用旧值。变更极频繁时，失效通知成本可能超过缓存收益。依据：[Redis 客户端缓存机制与适用边界](https://redis.io/docs/latest/develop/clients/client-side-caching/)。

若业务允许副本延迟，可把部分只读流量交给副本并监控复制延迟；写后读、权限撤销和库存决策不能默认读到旧值也正确。只读快照可以复制成多个物理 key 分散读取，但需要版本化发布、统一失效与额外内存，不能套用到可变计数器。依据：[Redis 复制与读副本一致性](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)。

## 04 写热点为什么不能直接复制几份

同一计数器复制为多个可写副本，会改变“一个权威值”的语义。只有业务允许可合并统计时，才按固定维度分桶累加后汇总，并接受读取聚合、延迟与重复事件去重的代价。余额、库存和全局配额不能让各桶都持有一份完整额度，否则会超发；需预分配且总和守恒的额度、唯一业务流水和安全的调拨/回收规则。

另一条路径是按业务键排队、合并批量或异步处理，降低重复工作，但队列必须有上限、持久化和幂等，用户要知道收到的是受理还是完成。Lua/INCR 能缩短原子临界区，却仍在对应执行节点串行处理；长 Lua 还会阻塞其他请求。跨槽拆键后不能继续声称单个 Lua 能保证整组原子性。这些是按业务不变量推导的方案，需用真实负载验证，不能把分桶当作无代价扩容。

## 05 失效与恢复时怎样保护回源

热点过期、缓存节点故障、本地缓存批量清空都会把压力推回数据库。应给回源独立的并发上限、总超时、有限队列和降级策略；同键只让一个受控任务重建，其他请求有界等待，或在业务允许时读旧值。TTL 抖动能分散许多键的到期，却不能独自解决一个超级热 key 的瞬时失效。

恢复时先预热少量关键键，再逐步解除限制；避免所有实例同时回填、刷新或建立连接。验收同时看热点节点的 CPU/带宽/P99、Redis 请求下降比例、缓存新鲜度、数据库回源峰值、拒绝率，以及库存/计数对账。至少演练热点突然出现、缓存失效、副本延迟和实例断线，不能只验稳态命中率。
