# 27 从海量 key 里查出某一固定前缀的 key？

## 01 核心回答

**低频排查/运维：SCAN**

`SCAN 0 MATCH prefix:* COUNT 1000`——**不要用 KEYS**（海量 key 可能长时间占用 Redis 命令执行线程）。

**特点：**分批渐进遍历；不是强一致快照，可重复返回，变化中元素结果不确定，稳定存在元素有完整遍历保证。

**高频业务查询：二级索引**

给 key 前缀单独建 Set/ZSet 二级索引——写入业务 key 时同时写索引集合，查询走索引不扫全库。

**注意：**配合 Lua 原子更新、脏索引清理。

**追问：**KEYS 为什么危险（O(N) 阻塞单线程）；SCAN 游标是什么（每次返回新游标继续迭代）；重复与变动中元素怎么处理（去重/幂等；一致快照另行设计）。

## 02 理解机制与追问

SCAN 从 0 游标开始，反复把返回游标传入，直到返回 0 才结束；某批为空不代表结束。COUNT 是工作量提示，不保证每批恰好返回相应数量。MATCH 通常是遍历后的匹配过滤，不是前缀索引，因此前缀再窄也不能假设只扫描匹配键。

## 03 易错点与适用边界

修正“非阻塞/任意漏读”：SCAN 是把完整遍历拆成短命令，每次仍占用执行时间；完整遍历保证返回从开始到结束一直存在的元素，可重复返回，期间新增/删除元素是否返回不确定。Cluster 需遍历相关主节点，并处理迁移导致的变化。高频业务检索应维护索引且处理键过期后的索引残留。

## 04 面试口述

运维用有界批次 SCAN，按游标完成遍历并去重；业务高频查询建二级结构。SCAN 缓解长时间阻塞，但不是强一致快照或高效前缀索引。
