# 17 如何设计一个结构来存储 QQ 号和在线状态？

## 01 核心回答


**Bitmap**
只判断是否在线且 ID 紧凑时：`SETBIT online user_id 1` / 离线清零 / `GETBIT` 查询。

**Set**
用户 ID 稀疏时，Bitmap 浪费空间，改用 Set 存在线用户。

**Hash / 集合**
需要保存设备、登录时间、地域和连接节点时，按用户维度存详细状态。

**状态维护：**在线状态不能只靠一次登录写入。客户端定期发送心跳并刷新 TTL，连接断开或超时后由连接服务清理；多端登录时记录设备集合或连接计数，只有最后一个连接退出才变为离线。更新事件携带连接版本或时间戳，避免网络抖动和乱序消息让旧连接覆盖新状态。

**边界：**Redis 只保存实时状态，登录历史和审计信息异步写入持久化存储。还要考虑热 key、集群分片、批量心跳、Redis 故障和短暂不可用时的降级，不能简单把“缓存读不到”判定为用户离线。

---

## 02 理解机制与追问

在线状态本质是带租约的连接集合。为每个用户设备连接保存唯一 session/version 和最后心跳时间；清理离线时只删除匹配的旧连接版本，避免上一连接的迟到断开事件把新登录踢掉。用户只要还有任一有效连接就在线，需显式定义多设备聚合规则。

---

## 03 易错点与适用边界

Bitmap 和普通 Set 成员没有逐 bit/逐 member TTL，不能对一个全局 online key 续期来表达所有用户各自心跳。可用每连接独立 TTL 键，或按最后活跃时间维护 ZSet 并按超时裁剪，再维护派生在线索引。通知只作加速，定期清扫处理漏事件。缺失缓存与确认离线也应区分。

---

## 04 面试口述

我会把在线定义成有效会话租约，选择能按连接过期的结构，再派生用户在线集合。版本校验和多端规则比单纯选 Bitmap 或 Set 更重要。
