# 07 Redis 唯一 ID 怎么设计？

## 01 核心回答


唯一 ID 通常需要全局唯一、趋势递增、可排序、低延迟生成、无中心单点以及适当长度。常见方案：

**数据库自增**
简单，但跨库扩展困难。

**UUID**
冲突概率低且通常较长；是否有序取决于 UUID 版本。

**Redis `INCR`**
方便、中心化序列，需考虑持久化和故障切换。

**号段模式**
数据库一次分配一段区间，应用本地递增，减少数据库访问。

**雪花算法：**ID 划分为时间戳、机器或数据中心标识和序列号，同一毫秒内由序列号区分并发请求。实现时要处理时钟回拨、机器 ID 分配、序列号耗尽和服务重启；机器标识冲突会产生重复 ID。时间戳位数决定可用年限，序列位数决定单毫秒峰值，按真实 QPS 和部署规模计算。

选型要结合是否需要按创建时间排序、长度限制、跨地域部署、隐私和迁移需求。数据库仍应设置唯一约束，消息和接口还要带业务幂等键，避免客户端重试导致同一个业务被重复创建。

## 02 理解机制与追问

INCR 在当前主节点执行序列中原子，但若最新计数未复制或未持久化就发生切换，计数可能回退并再次发出旧 ID。唯一性不能仅靠“自增命令原子”证明。号段方案把分配的高水位可靠提交后再发号，允许空洞通常比冒险重复更容易接受。

## 03 易错点与适用边界

“唯一”“全局严格递增”“按时间大致有序”“业务幂等”是不同目标。UUID 也有多种版本，不能一概说全部无序。雪花算法要持久化/协调机器标识和重启状态，处理时钟回拨及序列耗尽；数据库唯一约束是防线，不是使失败自动消失的魔法。

## 04 面试口述

Redis INCR 适合简单序列，但我会说明主从切换和恢复回退风险。高要求全局 ID 应比较持久号段、时间有序 ID 等方案，业务重试则另用幂等键。
