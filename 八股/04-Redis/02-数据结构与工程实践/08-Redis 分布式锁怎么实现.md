# 08 Redis 分布式锁怎么实现？

## 01 核心回答


**加锁：**`SET lock_key token NX PX ttl`——只有 key 不存在时设置成功，同时写入过期时间；`token` 必须是随机且唯一的持有者标识。

**释放：**不能直接 `DEL`，要用 Lua 脚本比较 value 与自己的 token，匹配后再删除，避免锁过期后被新线程获得、旧线程误删新锁。

**续期：**TTL 要覆盖正常临界区但不能无限延长；任务可能超过 TTL 时由持有者定期续期，续期前确认 token 仍属于自己。客户端长时间暂停、网络分区、主从切换都可能让锁与业务状态短暂不一致，关键业务需幂等、状态校验或数据库条件更新兜底。

**工程注意：**处理获取超时、退避重试、异常释放、锁粒度、监控和故障恢复。Redis 锁适合短任务互斥，不天然提供跨库事务语义；涉及库存、余额和支付时，优先使用数据库唯一约束、条件更新或可靠协调服务，并明确故障模型和一致性边界。

## 02 理解机制与追问

租约过期后旧持有者未必停止：线程长时间暂停，恢复后可能继续写外部数据库。比较 token 解锁只防误删新锁，不阻止这个陈旧写。需要时让受保护存储验证单调递增的 fencing token，拒绝更旧持有者的写入；随机 token 本身不具备这种顺序。

## 03 易错点与适用边界

主从异步复制下，锁写入丢失后新主可再次授锁。Redlock 依赖多个独立主实例和时间假设，不能泛称解决全部故障一致性。续期失败要停用租约并中止可取消操作，已发出的外部操作仍需业务约束兜底。8.4 起可用带条件的 DELEX 安全释放，旧版本 Lua 比较删除仍适用。

## 04 面试口述

基本锁用原子 SET NX 加租期、唯一持有者、安全释放，但租约不是让旧线程自动消失。对不可重复的外部写，要靠 fencing、幂等或权威条件更新守住不变量。
