# 32 为什么不把所有查询都塞到 Redis？

## 01 核心回答

**内存成本**
全量数据进内存成本极高（对比磁盘存储）。

**一致性复杂**
全量缓存要维护与数据库的一致性，更新/失效链路变长。

**失效治理难**
全量 key 的过期、淘汰、重建策略复杂，运维成本高。

**冷数据浪费**
低频数据占内存，命中率低，性价比差。

**原则：**Redis 适合**高频热点和低延迟读**；冷热分层 + 按访问特征选型（MySQL 存全量事实，Redis 存热点，ES 存检索）更可持续。

**追问：**什么数据适合放 Redis（热点/短 TTL/计数类）；冷数据怎么处理（归档/淘汰/降级存储）。

## 02 理解机制与追问

缓存收益可粗略看读取复用度与重建成本：反复读取、计算昂贵且允许短暂旧值的数据更值得缓存；只读一次的大结果可能成本大于收益。复杂组合筛选若把每种条件都缓存，键空间和失效依赖会迅速膨胀，变成难维护的派生视图系统。

## 03 易错点与适用边界

Redis 也能承载持久数据或通过扩展实现检索，但必须按产品和数据模型评估，不能因此把所有查询机械搬过去。缓存命中率高也未必节省关键成本，应看数据库负载、回源峰值、端到端尾延迟和错误恢复。压测还需覆盖冷启动和全缓存失效。

## 04 面试口述

我缓存高复用、可重建、时效允许的数据，并对失效成本做预算；复杂关系事实留在合适的数据系统，避免把查询优化变成缓存一致性难题。
