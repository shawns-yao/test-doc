# 33 Redis Hash 的渐进式扩容？

## 01 核心回答

**扩容触发：**底层 dict 根据负载与扩容策略触发扩容——按容量需要申请**更大的**新数组，把键值对重新分配（rehash）。如果 hash 很大（上百万键值对），一次完整 rehash 耗时很长，对单线程 Redis 压力大。

**渐进式 rehash：**同时保留**新旧两个 hash 结构**，在定时任务和读写指令中**逐步迁移**旧结构元素到新结构——减小一次集中迁移导致的长停顿。新增键写新表，查找等操作检查迁移中的两张表（7.2 dictFind 先旧后新）；迁移完成后释放旧表。

**缩容：**Redis 的 hash 还有缩容（与 Java HashMap 的容量策略不同）——原理同扩容，新数组根据所需容量缩小，不保证始终恰好减半。

**追问：**渐进式 rehash 期间数据在哪个表（未迁移键在旧表，新写入和迁移键在新表；查找两边）；为什么不能一次完成（阻塞单线程事件循环）；和 Java HashMap 扩容区别（Java 一次性扩容 vs Redis 渐进）。

## 02 理解机制与追问

这里主要讲底层 dict，不是所有 Redis Hash 对象：小 Hash 可能仍用 listpack，不发生同样的哈希表扩容。迁移期间旧表与新表并存，rehash 索引记录已迁移位置，新插入进入新表；查找、更新、删除按实现检查可能含数据的表，普通访问和周期任务分摊迁移工作。

## 03 易错点与适用边界

源码修正：Redis 7.2 dictFind 按旧表 0 再新表 1 查找，原“新表优先”错误。扩容/缩容依据负载因子、所需容量及当前重哈希策略，不是永远严格两倍/一半；fork 期间还要控制 COW 成本。渐进迁移降低单次停顿，但不是零成本，暂时双表也增加内存峰值。

## 04 面试口述

核心是用两张表和迁移游标把一次大重哈希摊到多次操作，新键入新表，查询兼顾未迁移部分；表访问顺序与阈值必须按版本源码描述。
