# 20 Redis 集群中的 16384 个槽位是怎么分配和迁移的？

## 01 核心回答


**槽位映射：**key 映射到 `0`~`16383` 哈希槽，通常计算 `CRC16(key) mod 16384`；使用 `{tag}` 时只对大括号内内容计算哈希，使相关 key 落到同一槽位并支持多 key 操作。每个主节点负责一部分槽位，副本复制主节点数据并在故障时参与转移。

**MOVED / ASK：**客户端缓存槽位到节点的映射；请求发到错误节点返回 `MOVED`，客户端更新映射后重试；迁移过程中可能返回 `ASK`，客户端只把当前请求临时转发到目标节点，不立即永久修改映射。

**迁移流程：**扩容时按批次迁移槽位和 key，等待目标节点接收并校验后再切换槽位归属，期间控制带宽、批量大小和业务影响。

**约束与关注：**多 key 命令、事务和 Lua 通常要求 key 位于同一槽位，key 设计要合理使用 hash tag。扩容缩容还要关注复制追平、热点槽位、迁移失败重试、槽位覆盖率、MOVED/ASK 次数和故障恢复。

## 02 理解机制与追问

经典迁移时源槽处于 MIGRATING，目标处于 IMPORTING：源节点已存在的 key 仍可处理，缺失且可能迁出的 key 可返回 ASK；客户端先对目标发送 ASKING，再执行当前请求。完成后更新槽归属，MOVED 才提示长期路由应刷新。槽是路由单位，key 才是逐步搬迁的数据单位。

## 03 易错点与适用边界

hash tag 需符合非空花括号片段规则，并非任意出现大括号都一样。同槽支持原子多 key，不同槽通常 CROSSSLOT；迁移中的多 key 操作还可能临时不可执行。把所有 key 都用同一 tag 会失去分片收益，一个大 key 也不会自动分散到多个槽。

## 04 节点如何发现彼此并传播槽位状态

客户端命令端口之外，节点通过独立的 Cluster Bus 建立节点间 TCP 连接。PING/PONG 心跳携带发送者身份、槽位位图、配置纪元等信息，并用 Gossip 部分交换对其他节点的观察，用于节点发现和故障判定；管理员通过 CLUSTER MEET 建立信任关系后，节点信息可进一步传播。客户端仍直接访问槽位负责节点，Gossip 不是转发业务命令的中央代理。

一个节点判定对端超时仅形成 PFAIL 本地怀疑；升级为 FAIL 需要满足主节点故障报告规则，副本提升还需选举授权等条件。配置纪元帮助处理槽归属的新旧配置，不能把 Gossip 最终传播误解成用户数据强一致复制。Cluster 使用固定槽而非一致性哈希环，异步复制故障窗口仍可能丢已确认写。依据：[Redis Cluster 总线、Gossip 与故障检测](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)。

## 05 面试口述

Cluster 把 key 映射到固定槽，再把槽映射到节点。扩容主要迁移槽的所有权与数据，客户端必须正确处理 ASK 临时跳转和 MOVED 路由更新。
