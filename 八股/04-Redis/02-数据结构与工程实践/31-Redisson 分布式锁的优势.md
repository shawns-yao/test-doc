# 31 Redisson 分布式锁的优势？

## 01 核心回答

Java 场景可优先评估成熟 **Redisson** 封装（比手写 `SET NX PX` 更完整，底层仍是 Redis 锁语义）：

**可重入**
同一线程重复加锁不会自己锁死（计数）。

**看门狗续期**
业务没执行完自动延长过期时间，降低正常长任务租约到期风险，但不能保证暂停或分区时续期成功。

**安全解锁**
内部 Lua 校验锁持有者，避免误删别人的锁。

**高效等待**
Pub/Sub 通知唤醒，减少无脑轮询。

**API 完整：**公平锁、读写锁、MultiLock 等能力需按所用版本核实；不能把某种 API 的存在当成跨故障安全证明。手写方案的细节（Lua 释放/token）见 2.8。

**追问：**看门狗原理（默认 watchdog 超时常为 30s，续期周期按版本实现；固定 leaseTime 路径另看语义）；主从切换时锁会丢吗（可能丢锁；Redlock 依赖额外假设，不能无条件视为解决方案）；锁续期失败怎么办（业务幂等兜底）。

---

## 02 理解机制与追问

Redisson 把可重入计数、持有线程身份、续期、超时等待和通知封装起来，降低手写协议遗漏。watchdog 常用于未指定固定 leaseTime 的锁；指定 leaseTime 的语义是到期释放，不能假设两种路径都有无限续期。实例活着也可能暂停过久导致租约已失效。

---

## 03 易错点与适用边界

修正原“RedLock 解决主从丢锁”：Redlock 有独立主节点和时间模型假设，不能承诺对任何暂停、分区、外部写都安全。官方新版能力和弃用项随版本变化，选择具体锁前查当前文档；默认 30 秒、周期按实现调整，不宜把每 10 秒写成永恒 API 保证。关键外部操作仍需 fencing 或业务约束。

---

## 04 面试口述

Redisson 的价值是完整的客户端锁工程封装，而不是改变分布式租约的物理限制。我会确认 leaseTime、续期和故障策略，再决定业务是否能容忍双执行。
