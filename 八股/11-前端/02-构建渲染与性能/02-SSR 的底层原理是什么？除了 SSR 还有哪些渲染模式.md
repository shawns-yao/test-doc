# 02 SSR 的底层原理是什么？除了 SSR 还有哪些渲染模式？

## 01 核心回答


**概念原理（SSR）：**服务端把组件渲染成 HTML 字符串返回，浏览器直接展示首屏；随后加载 JS 完成**水合（hydration）**——绑定事件、接管交互。常见实现是在服务端执行组件并输出 HTML，可生成字符串或流式响应，随后按需水合。

**渲染模式对比：**① **CSR（客户端渲染）**：主要由 JS 构建页面，首屏和可抓取性取决于资源、实现与搜索引擎能力；② **SSR**：服务端出 HTML，有利于较早展示内容和抓取，但服务端开销与客户端水合成本仍需衡量；③ **SSG（静态生成）**：构建时生成 HTML，可结合 CDN 提供低运行成本，适合文档、博客等可预生成且允许重建更新的内容；④ **ISR（增量静态再生）**：SSG + 定时/按需重建；⑤ **混合渲染**：按路由选模式（Nuxt/Next 支持）。

**关键细节：**SSR 环境没有 window/document（服务端执行要注意副作用）；水合不一致（服务端 HTML 与客户端渲染结果不同）会告警；首屏所需数据可在服务端预取并安全序列化注入，后续交互仍可客户端取数。

**追问：**SSR 为什么可能先显示内容却还不能交互（HTML 先到，相关 JS 和水合尚未完成）；什么场景用 SSG（内容可预生成，并接受构建或按约定失效更新）；Next.js 的 SSR 和 SSG 怎么选（数据变化频率）。

## 02 SSR 与水合的成本边界

订正补充：SSR 不限于先生成完整字符串，也可流式返回 HTML；现代框架能按边界逐步水合，不能概括成整页在完成所有水合前都不可交互。SSR、SSG 也不保证一定更快，服务端取数、缓存命中、网络与客户端 JavaScript 成本都会影响结果。

水合要求服务端输出与客户端首次渲染在结构和初始数据上匹配。时间、随机数、地区格式和只在浏览器存在的数据都可能造成不一致；应设计一致的初始状态，而非滥用忽略警告。SSR 每个请求的用户状态应隔离，避免模块级共享对象串用户。

## 03 选择渲染模式的依据

按内容更新频率、个性化程度、搜索抓取需求、部署能力和交互复杂度选择。SSG 可以通过重建更新内容，ISR 的失效和缓存语义依框架而异；SSR 输出敏感个性化内容时不能不分用户地公共缓存。首屏数据可由服务端获取，后续交互请求仍可在客户端完成。
