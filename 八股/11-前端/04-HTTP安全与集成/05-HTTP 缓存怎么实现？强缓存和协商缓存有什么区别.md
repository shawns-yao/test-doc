# 05 HTTP 缓存怎么实现？强缓存和协商缓存有什么区别？

## 01 核心回答


**强缓存**

**不发请求**，直接读本地缓存。

**字段：**`Cache-Control: max-age=3600`（相对时间，优先）或 `Expires`（绝对时间，HTTP/1.0）。

**命中条件：**缓存未过期 → 200 (from disk/memory cache)。

**协商缓存**

**发请求**，服务端判断是否用缓存。

**字段：**请求带 `If-None-Match`（对比 `ETag`，不透明验证器而非必然的内容哈希）或 `If-Modified-Since`（对比 `Last-Modified`）。

**结果：**未变 → `304` 用缓存；变了 → 200 新响应。

**配合策略：**强缓存 + 版本号（文件名 hash）是静态资源标配——hash 变了 URL 变，天然绕过旧缓存；协商缓存用于 HTML 等需及时更新的资源；`no-cache` = 复用前验证，`no-store` = 不存储该请求或响应。

**追问：**max-age 和 Expires 谁优先（Cache-Control）；ETag 和 Last-Modified 的精度及强弱验证器差异；强制刷新时浏览器如何处理缓存（行为依浏览器与操作而异）。

---

## 02 验证器与缓存指令订正

ETag 是服务器提供的不透明验证器，不保证是内容哈希；既可能是强验证器也可能是弱验证器。客户端同时发送 If-None-Match 和 If-Modified-Since 时，前者有优先规则，不能认为需要两者都独立通过。

no-cache 允许存储，但复用前必须成功验证；没有可用验证器时可能得到完整响应，并不保证一定是 304。no-store 禁止按指令存储该请求或响应，但不是清除既有缓存的万能指令，也不保证浏览器历史等机制完全不保留信息。

---

## 03 发布与用户隔离

带内容哈希的静态资源可采用长有效期，HTML 常用重新验证以发现新资源 URL。旧 HTML 或已打开页面仍可能引用旧 chunk，发布时应保留一段旧资源可用期。含用户数据的响应要考虑 private、授权及缓存键，动态 CORS 响应还可能需要 Vary: Origin，避免共享缓存串用户或串来源。
