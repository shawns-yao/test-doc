# 08 为什么选择 JWT？登录鉴权流程是什么？JWT 的 JSON 中一般包含哪些属性？

## 01 核心回答


**为什么选 JWT：**① 自包含验证——可减少共享 Session 查询，适合需要独立验签的服务边界；② **自包含**——用户信息在令牌内，减少查库；③ 跨域友好（放 Header 不依赖 Cookie）；④ 缺点：主动撤销通常需要额外状态或查询机制、体积大。

**登录鉴权流程：**① 用户提交账号密码 → ② 服务端校验 → ③ 签发 JWT（Header + Payload + 签名，Base64url 编码 + HMAC/RSA 等签名或 MAC）→ ④ 返回给前端（存 HttpOnly Cookie 或内存）→ ⑤ 内存访问令牌可带 `Authorization: Bearer <token>`，HttpOnly Cookie 则由浏览器按 Cookie 规则发送 → ⑥ 服务端验签 + 校验过期 → 放行。

**Payload 常见属性：**`sub`（用户 ID）、`iat`（签发时间）、`exp`（过期时间，登录策略通常要求，RFC 并非一律必填）、`iss`（签发方）、`aud`（受众）、`role`/`permissions`（权限，按需）。

**追问：**JWT 怎么防篡改（签名验证，密钥服务端持有）；怎么实现登出（前端删 token + 短过期 + 黑名单/refresh token）；refresh token 机制（短 access + 长 refresh 轮换）。

---

## 02 JWT 结构和声明订正

常见三段式令牌是 JWS 紧凑序列化形式，使用 Base64url 而非加密，拿到令牌的人通常可读取 Payload，不应放秘密或不必要的个人数据。JWT 也可以使用 JWE 加密表示，不能把所有 JWT 永久等同于三段签名串。

RFC 7519 的注册声明并非全部强制必填，exp 也不是该规范对所有 JWT 的必选字段；登录令牌的应用策略通常应要求过期时间，并验证签发者、受众和必要声明。验签必须限制允许算法、使用可信密钥，并处理 nbf、时钟偏差等条件，不能信任令牌自带的 alg 就接受任意算法。

---

## 03 两条凭据链路不可混写

若令牌在 HttpOnly Cookie 中，浏览器脚本不能读取后再拼进 Authorization；应由浏览器按 Cookie 规则发送，并防 CSRF。若用内存中的访问令牌，则可由脚本设置 Bearer 头，并考虑跨源预检。两种方案可以组合，但要清楚各令牌用途。

JWT 不是无法主动失效：可用撤销列表、令牌版本或账户状态检查实现，但会引入状态与查询成本。只删除客户端令牌不撤销已泄露副本；权限声明也可能过时，高风险操作仍需实时授权。选择 JWT 应有独立验签或跨服务边界等实际理由，不能仅说“比 Session 更安全”。
