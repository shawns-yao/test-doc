# 04 HTTP/3 为什么使用基于 UDP 的 QUIC？QUIC 解决了什么问题？

## 01 核心回答


**概念原理：**QUIC 是基于 UDP 实现的"类 TCP"传输协议，HTTP/3 跑在 QUIC 上。选 UDP 的原因：**广泛部署的 TCP 实现多位于内核，端到端特性还受中间设备约束**（并非每次升级都要改全网设备，也存在用户态 TCP 栈），UDP 只是信封，可靠性全部由 QUIC 在用户态实现——协议逻辑可随应用更新，但仍需处理网络对 UDP 的限制。

**QUIC 解决的问题：**① **队头阻塞**：HTTP/2 多条流共享一个 TCP，一条流丢包会阻塞所有流；QUIC 每个流有独立字节偏移与交付顺序，包号用于包级确认，丢包只影响该流；② **握手延迟**：TLS 1.3 集成在 QUIC 内，首次 1-RTT、复用 0-RTT（TCP+TLS 需要 2-3 RTT）；③ **连接迁移**：连接 ID 不依赖四元组，WiFi↔4G 切换不断连（TCP 换 IP 就断）；④ **用户态可演进的丢包恢复与拥塞控制**：用户态便于迭代实现。

**关键细节：**QUIC 自实现拥塞控制、重传、乱序重组（用户态，可平滑升级算法）；0-RTT 有重放风险需应用层幂等；UDP 可能被中间网络 QoS 限速（运营商对 UDP 不友好）。

**风险与取舍：**UDP 流量被部分网络设备限制/丢包；QUIC 生态（代理、防火墙识别）不如 TCP 成熟；弱网下 QUIC 的优势最明显，好网络下与 HTTP/2 差距不大。

**项目落地：**视频/直播/弱网场景优先开启 HTTP/3（CDN 支持）；服务端（Nginx/Envoy）配置 QUIC 监听；客户端需核对所用库与版本的 HTTP/3 支持，例如支持 QUIC 的 Cronet 配置；内网场景收益有限可不启用。

**面试追问：**QUIC 和 TCP 的区别（内核 vs 用户态、独立流）；为什么说 QUIC 解决了队头阻塞（流独立 + 独立序列号）；连接迁移怎么实现（连接 ID 代替四元组）；0-RTT 的风险（重放）。

---

## 02 理解补充与边界校订

QUIC 用包号识别与确认包，用流偏移表达每条流的字节顺序，不能把二者统称为每流独立包序号。连接 ID 为迁移提供标识，实际迁移仍要路径验证与策略允许。RFC 9000 的基础 QUIC 不内置通用 FEC，FEC 属于额外扩展/应用设计；不能把所有 QUIC 客户端库都说成现成启用了它。
