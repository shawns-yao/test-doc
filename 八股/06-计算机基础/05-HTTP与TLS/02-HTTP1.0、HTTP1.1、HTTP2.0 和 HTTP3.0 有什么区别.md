# 02 HTTP/1.0、HTTP/1.1、HTTP/2.0 和 HTTP/3.0 有什么区别？

## 01 核心回答


**HTTP/1.0**

默认非持久连接，常用每请求建连；也存在 keep-alive 扩展——连接开销大，慢。

**HTTP/1.1**

**持久连接（keep-alive）**复用 TCP；管线化（基本失败）；Host 头、分块传输、断点续传。**队头阻塞**：一个请求响应慢，后续排队。

**HTTP/2**

**多路复用**（二进制分帧，一个 TCP 并发多个流）解决应用层队头阻塞；头部压缩（HPACK）；服务端推送。仍有 **TCP 层队头阻塞**（丢包时整条连接阻塞）。

**HTTP/3**

基于 **UDP 的 QUIC**：连接迁移、0-RTT 握手、独立流（丢包只阻塞该流）——减少跨流传输队头阻塞；QUIC 常在用户态实现拥塞控制。

**关键细节：**演进主线 = 减少连接开销（1.0→1.1）+ 消除队头阻塞（1.1→2→3）+ 减少握手（TLS 1.3 + QUIC 0-RTT）；HTTP/2 的二进制分帧和流优先级是核心机制；HTTP/3 需要 QUIC 支持（UDP 端口 443）。

**风险与取舍：**HTTP/2 在弱网（高丢包）下反而比 1.1 慢（TCP 队头阻塞放大）；HTTP/3 新协议生态和中间设备兼容性仍在完善；升级收益要实测（多路复用对图片多的小资源页面收益大）。

**项目落地：**Web 服务开启 HTTP/2（Nginx 一行配置）；资源合并/雪碧图在 HTTP/2 下不再必要；长连接 + 连接池是 1.1 下的标配优化；CDN/网关支持 HTTP/3 后按需开启。

**面试追问：**HTTP/2 队头阻塞和 HTTP/1.1 的区别（HTTP/1.1 管线化响应按请求顺序交付；HTTP/2 消除这一应用层串行约束，但 TCP 丢包仍可能阻塞同连接的多个流）；QUIC 为什么能解决队头阻塞（独立流 + UDP）；0-RTT 是什么（首次握手后复用会话票据）；服务端推送为什么用得少（缓存命中率问题）。

---

## 02 理解补充与边界校订

旧文「HTTP/3 彻底消除队头阻塞、内核态拥塞控制」需要订正：它减少跨 QUIC 流的有序交付阻塞，同一流仍需按序，流间还共享拥塞预算；QUIC 常在用户态实现。HTTP/1.0 也存在 keep-alive 扩展，HTTP/1.1 默认持久连接。HTTP/2 server push 是协议能力，不代表当前浏览器均支持或建议依赖。
