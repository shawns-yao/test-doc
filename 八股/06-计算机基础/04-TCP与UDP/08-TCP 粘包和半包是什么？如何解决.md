# 08 TCP 粘包和半包是什么？如何解决？

## 01 核心回答


**概念原理：**TCP 是**字节流**协议，没有消息边界——应用层 send 的"消息"只是往流里写字节，接收方可能一次读到多条消息拼在一起（**粘包**），也可能一条消息分多次到达（**半包**）。这是 TCP 流特性，不是协议 bug。

**粘包半包产生原因：**① 发送方：Nagle 合并小包、批量发送；② 接收方：recv 缓冲区一次取多、应用读得不及时；③ 网络：分段（MSS）和重组。

**解决方案（消息定界四种）：**① **固定长度**：每条消息定长，不足补位（简单但浪费）；② **分隔符**：以 `\n` 或特殊字符结尾（适合文本协议，如 Redis RESP、HTTP 头）；③ **长度前缀**：包头 4 字节长度 + 消息体（最通用，Netty `LengthFieldBasedFrameDecoder`）；④ **自定义协议头**：魔数 + 版本 + 长度 + 业务字段（RPC 框架标配）。

**关键细节：**解包流程 = 缓冲累积 → 按协议判断是否凑齐一条 → 拆出完整消息 → 剩余留待下次；半包要"攒够再处理"，粘包要"切分处理"；`TCP_NODELAY` 减少发送侧粘包但不能根治（接收侧仍可能合并）。

**风险与取舍：**分隔符要防内容冲突（转义）；长度前缀要防恶意超大长度（校验上限）；固定长度浪费带宽；协议设计要兼容拆包缓冲（内存上限防攻击）。

**项目落地：**Netty 用 `LengthFieldBasedFrameDecoder`（长度前缀）处理粘包半包；自研 RPC 协议带魔数 + 长度；HTTP/Redis 协议天然带定界（\r\n / 长度）；压测覆盖大数据包和小包混合场景。

**面试追问：**UDP 会粘包吗（不会，数据报有边界，但可能丢包乱序）；粘包和半包谁更常见（都常见，取决于发送频率和大小）；为什么 TCP 不保留消息边界（字节流设计，交给应用层定界）。

## 02 理解补充与边界校订

把 TCP 当作不断增长的字节序列，应用自己的解析器负责决定何时凑成一帧；无论禁用 Nagle、一次 send 多大，仍需完整拆帧逻辑。长度字段必须校验上限、负数/溢出和超时，防止攻击者声明超大帧后慢速占住内存。读到半帧只表示暂时不完整，EOF 时仍不完整则是截断错误。
