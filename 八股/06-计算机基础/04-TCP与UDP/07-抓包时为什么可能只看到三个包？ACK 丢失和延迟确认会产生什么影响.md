# 07 抓包时为什么可能只看到三个包？ACK 丢失和延迟确认会产生什么影响？

## 01 核心回答


**概念原理：**三次握手本来通常为三段，挥手三段可能来自 ACK 与 FIN 合并，不能只按包数归因为 **TCP 延迟确认（Delayed ACK）**。延迟确认的含义是：接收方不立刻回 ACK，而是等待一个实现相关的短暂延迟（不是协议统一固定 40ms）（或攒到两个报文/有数据捎带）再回——把两个 ACK 合并成一个，或让 ACK 与数据同包捎带。三段挥手来自 ACK 与 FIN 合并，不必然由延迟 ACK 导致。

**三种"只见三包"场景：**① **三次握手只见 3 个包**：正常就是 3 个（SYN/SYN+ACK/ACK），若抓包只看到 SYN、SYN+ACK 而没有最后的 ACK，说明客户端 ACK 未发出或抓包点/过滤问题；② **挥手只见 3 个包**：被动方把 ACK 和 FIN 合并发出（数据发完时延迟确认触发的 FIN 捎带 ACK）；③ **数据传输只见 3 个包**：数据 + ACK 捎带（piggyback），实际是 2 个数据段 1 个确认段。

**关键细节（ACK 丢失/延迟的影响）：**① ACK 丢失：发送方靠**快重传**（3 个重复 ACK）或**超时重传**兜底，TCP 不因单个 ACK 丢失而失败（累计确认机制，后续 ACK 覆盖）；单个 ACK 丢失可能被后续累计确认覆盖，也不必然触发重传；② 延迟确认：正常机制，但配合 **Nagle 算法**可能产生"延迟确认 + 等待小包"的延迟叠加（发送方攒小包、接收方攒 ACK）——这通常是受定时器限制的额外延迟，不等同于糊涂窗口综合征，后者另指小窗口更新和小段交互；严重时吞吐骤降，可评估 `TCP_NODELAY`（禁用 Nagle）或应用层合并发送来降低额外等待。

**风险与取舍：**延迟确认省流量但增加小包 RTT；Nagle 减少小包但和延迟确认叠加会卡顿；延迟敏感小消息场景可评估 `TCP_NODELAY` 禁用 Nagle（换来低延迟，牺牲小包合并）。

**项目落地：**Netty/RPC 客户端开 `TCP_NODELAY` 降低小请求延迟；抓包判断"缺包"时先排除抓包点位置（中间链路 vs 端点）；性能问题排查看 RTT 和重传统计（`netstat -s`）。

**面试追问：**累计确认是什么（ACK n 表示 n 之前全收到）；Nagle 算法是什么（攒小包到 MSS 或等 ACK 再发）；为什么抓包看到的包数和理论不一样（捎带/延迟确认/合并）；TCP_NODELAY 解决什么问题（Nagle 延迟叠加）。
