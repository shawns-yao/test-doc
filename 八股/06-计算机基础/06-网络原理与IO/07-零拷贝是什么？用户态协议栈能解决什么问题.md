# 07 零拷贝是什么？用户态协议栈能解决什么问题？

## 01 核心回答


**概念原理：**零拷贝 = 减少数据在**磁盘/内核缓冲/用户空间**之间的拷贝次数。传统读文件再发送要 4 次拷贝 + 4 次上下文切换；零拷贝技术把拷贝降到 1-2 次，主要在**内核内完成**。

**实现方式（三种）：**① **mmap + write**：文件映射到用户地址空间，省去内核→用户的一次拷贝（仍有一次 CPU 拷贝）；② **sendfile**：`sendfile(out_fd, in_fd, ...)` 直接内核内"磁盘 → socket"（配合 `DMA gather` 真正零 CPU 拷贝），Linux 下文件→网络传输的标准答案；③ **splice**：经管道转移数据；**io_uring** 提供异步提交，其中部分操作可减少复制；**Kafka 用 sendfile** 发日志文件，**Netty 的 FileRegion** 即封装 sendfile。

**用户态协议栈（DPDK 等）：**自建用户态 TCP/IP 协议栈可配合 DPDK；DPDK 本身不是完整协议栈，常用它 直接操作网卡（轮询 + 大页 + 无锁队列），解决：① **内核协议栈开销**（中断、锁、上下文切换、拷贝）；② **单机连接数/吞吐瓶颈**；③ **协议定制能力**（自研可靠 UDP、新拥塞算法）。典型场景：LB/网关（LVS 的 DPDK 版）、高频交易、CDN 边缘。

**关键细节：**零拷贝适用"**数据不经用户处理**"（文件→网络、网络→文件）；数据要加工（编解码）就省不了；用户态协议栈放弃内核协议栈的通用性（要自己管 TCP 状态、ARP、路由）。

**风险与取舍：**零拷贝省 CPU 但牺牲灵活性（不能修改数据）；用户态协议栈复杂度高（网络栈细节自理）、绑定特定网卡驱动、排障困难——只在高吞吐刚需场景用；io_uring 是内核态的新答案（异步 + 减少系统调用）。

**项目落地：**Kafka 日志发送、静态文件服务（Nginx sendfile）、大文件下载用零拷贝；RPC 框架大响应体考虑 FileRegion；网关压测发现内核协议栈瓶颈时评估 DPDK/用户态栈。

**面试追问：**传统 4 次拷贝在哪（磁盘→内核→用户→内核→网卡）；sendfile 为什么快（内核内完成 + DMA）；零拷贝能处理需要改数据的场景吗（不能）；DPDK 为什么快（用户态轮询 + 免中断 + 大页）。

## 02 理解补充与边界校订

「零拷贝」必须注明省掉哪一次 CPU 拷贝，不代表硬件完全不搬运数据。io_uring 本身是异步提交/完成接口，不保证每种操作都零拷贝；DPDK 是数据面框架，也不等于完整 TCP/IP 协议栈。TLS、压缩或内容改写可能改变 sendfile 路径的收益，结合协议栈和硬件能力测量。

## 03 零拷贝为什么仍占 CPU 和内存

“零”通常指省掉某些数据复制，不是 CPU 完全退出。CPU 仍执行系统调用、管理页表/缓冲与协议状态，处理缺页、发送完成和错误；DMA 负责搬运字节，也需要软件组织传输。`sendfile` 可能只传出部分数据，非阻塞输出还可能返回 `EAGAIN`，调用方仍须维护偏移、等待可写并重试，不能把一次调用返回当成整个文件已被业务接收。依据：[Linux sendfile](https://man7.org/linux/man-pages/man2/sendfile.2.html)。

文件映射和常规文件发送仍会利用页缓存。`mmap` 建立的是虚拟地址映射，不等于已把所有页读入物理内存；首次访问或缓存被回收后可能缺页，冷文件读取、回收与磁盘 I/O 会放大尾延迟。大文件扫描也可能挤占其他热点缓存，应同时观察缺页、磁盘延迟、RSS、页缓存和容器总内存；cgroup 内存核算包含文件缓存，不能只用 Java 堆占用判断安全余量。分别压测冷热缓存与受限内存场景，限制并发/在途缓冲，避免把少复制误认为零内存成本。依据：[Linux mmap](https://man7.org/linux/man-pages/man2/mmap.2.html)、[cgroup v2 内存控制](https://docs.kernel.org/admin-guide/cgroup-v2.html#memory)。
