# 06 Protocol Buffers 是什么？为什么适合服务间通信？

## 01 核心回答


**概念原理：**Protobuf 是 Google 的二进制序列化协议：用 .proto 文件定义消息结构，生成各语言代码，序列化为紧凑二进制。对比 JSON/XML：体积小、解析快、有强类型 Schema。

**为什么适合服务间通信：**① **体积小**：二进制 + varint 变长编码 + 字段号代替字段名，通常比冗长 JSON 更紧凑，但具体比例需要对真实消息测量——省带宽省序列化时间；② **解析快**：无需字符串解析，直接按字段号定位；③ **强类型契约**：.proto 即接口文档，前后端/多语言按同一 Schema 生成代码，类型错误编译期发现；④ **兼容演进**：字段有唯一编号，新增字段向后兼容（旧客户端忽略未知字段），删除字段保留编号即可——服务间升级互不阻塞；⑤ **多语言**：官方支持 Java/Go/C++/Python 等，RPC（gRPC）默认用它。

**关键细节：**字段编号 1-15 用 1 字节（省空间），高频字段用小编号；`repeated` 对应数组；`optional`/`oneof` 表达可选语义；升级规则：只加字段、不删不改已有编号和类型。

**风险与取舍：**二进制不可读（调试要工具转 JSON）；.proto 变更需要版本管理（破坏性变更要评估）；对浏览器直连不友好（网页端用 gRPC-Web 或 JSON 映射）；小数据量场景收益不明显（仍有 Schema 维护成本）。

**项目落地：**RPC 框架（gRPC/Dubbo）消息体用 Protobuf；服务间高 QPS 接口序列化从 JSON 换 Protobuf 可显著降延迟；Schema 仓库统一管理 .proto 版本；压测对比序列化耗时和包体大小。

**面试追问：**Protobuf 为什么比 JSON 小（二进制 + varint + 字段号）；向后兼容怎么保证（字段编号机制）；varint 编码是什么（小整数 1 字节）；gRPC 为什么选 Protobuf（契约 + 性能 + 流式支持）。

---

## 02 理解补充与边界校订

原文「小 3–10 倍」不是格式保证；体积取决于字段名、数值分布、压缩与消息结构。删除字段后应把编号和必要的名字设为 reserved，禁止复用；unknown field 的保留还取决于转换路径，转 JSON 等过程可能改变信息。线协议兼容也不等于业务语义兼容，枚举新增值和默认值都要测试。
