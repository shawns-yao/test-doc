# 08 `epoll` 的工作过程和底层原理是什么？

## 01 核心回答


**概念原理：**epoll 是 Linux 的 I/O 多路复用机制：**一个线程同时监听成千上万个 fd**，内核通知哪些 fd 就绪（可读/可写），应用只处理就绪的 fd——解决"每连接一线程"的资源瓶颈。相比 select/poll：避免每次扫描完整 fd 集合；规模受资源上限与就绪事件处理成本约束。

**工作过程（三个系统调用）：**① `epoll_create`：内核创建 eventpoll 对象（红黑树 + 就绪链表）；② `epoll_ctl`：把要监听的 fd 注册进红黑树，并挂回调；③ `epoll_wait`：阻塞等待，就绪事件由回调放入就绪链表，用户取走处理。fd 就绪时（数据到达触发软中断）回调把 fd 加入就绪链表并唤醒等待线程。

**两种触发模式：**① **LT（水平触发，默认）**：只要缓冲区还有数据就持续通知——不易漏事件、编码简单（Java NIO 默认）；② **ET（边缘触发）**：只在状态变化（空→有数据）时通知一次——必须一次读完否则漏数据，性能更高（Netty native epoll 可配置 ET；具体默认值需看所用 transport/版本）。

**关键细节：**就绪事件通过回调驱动（不是轮询）；红黑树支持动态增删 fd；epoll_wait 只返回就绪列表（O(就绪数)）；惊群问题用 EPOLLEXCLUSIVE/多线程各建 epoll 缓解。

**风险与取舍：**ET 模式未正确耗尽可读数据可能漏掉继续处理的时机（必须循环读）；epoll 只对网络 fd 友好（普通文件不生效，磁盘 I/O 用 io_uring/AIO）；线程模型仍要设计好（单线程事件循环 vs 多线程）。

**项目落地：**Netty/Redis/Nginx 都是 epoll 驱动；Java NIO（Selector）底层即 epoll（Linux）；高连接场景（网关、IM）用事件驱动而非线程池；连接数和 QPS 压测验证。

**面试追问：**epoll 和 select/poll 的区别（复杂度、上限、回调 vs 轮询）；LT 和 ET 的区别及各自坑（漏事件 vs 漏数据）；epoll 为什么快（红黑树 + 回调 + 就绪链表）；惊群问题（多线程同时 wait 同一 epoll）。

## 02 理解补充与边界校订

旧文的「O(1)、无上限」需删除绝对化：epoll 避免每次扫描全量 fd，但注册维护、就绪数量、内存与 fd 上限仍有成本。ET 未读到 EAGAIN 的风险是已有数据仍留着却可能不再获得预期通知，不是内核自动丢数据。Netty 的触发模式取决于 NIO 或 native epoll transport 与配置，不能一概称默认 ET。
