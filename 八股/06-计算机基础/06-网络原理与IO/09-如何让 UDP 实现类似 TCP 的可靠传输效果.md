# 09 如何让 UDP 实现类似 TCP 的可靠传输效果？

## 01 核心回答


**概念原理：**UDP 只提供"尽力交付"，可靠传输需要在**应用层补齐 TCP 的能力**：序号（排序/去重）、确认（ACK）、重传（超时/NACK）、流量控制、拥塞控制。这就是"可靠 UDP"（RUDP），KCP/QUIC/自研协议都是这条路。

**实现流程（核心机制）：**① **序号**：每个包带递增序号，接收方按序重组、去重；② **确认**：接收方回 ACK（可累计/批量/捎带），发送方维护已确认水位；③ **重传**：超时未确认 → 重传；或接收方发现空洞 → 回 NACK 快速要求重传（比等超时快，RTP/RTX 思路）；④ **流控**：滑动窗口限制在途包数；⑤ **拥塞控制**：按丢包率/RTT 动态调整发送速率（借鉴 TCP 或 BBR 思路）；⑥ 可选 **FEC**：冗余包提前恢复部分丢包。

**成熟方案：****KCP**（游戏场景可靠 UDP，ARQ 模型，快重传 + 非退让流控）、**QUIC**（完整可靠传输 + 加密 + 多路复用）、**SRT**（音视频可靠 UDP，FEC + 重传混合）；自己实现时按场景裁剪：游戏要低延迟（快速重传）、文件传输要高吞吐（窗口大）。

**关键细节：**可靠 UDP ≠ 照搬 TCP——TCP 的重传策略（超时指数退避）不适合实时场景；按业务选机制：允许丢的加 FEC、不能丢的加重传、乱序容忍的省排序；序号要防回绕。

**风险与取舍：**自研可靠 UDP 复杂度高（状态机、窗口、拥塞都要自己维护和测试）；能直接用 TCP/QUIC 时别重复造轮子；可靠 UDP 的价值在"保留 UDP 的低延迟和可定制性"。

**项目落地：**游戏同步：KCP；视频传输：SRT/QUIC；弱网文件传输：自研 RUDP（序号 + NACK + 窗口）；优先评估 QUIC 现成库（成熟、加密、多路复用）。

**面试追问：**NACK 和超时重传哪个快（NACK 快，接收方主动报缺）；可靠 UDP 和 TCP 性能差异（TCP 内核优化成熟，RUDP 场景定制）；KCP 为什么适合游戏（低延迟优先于公平性）；FEC 和重传怎么搭配（按丢包率）。

## 02 理解补充与边界校订

可靠性设计还需要连接标识、包认证、防重放、路径 MTU 与重组内存上限。ACK 只证明传输对端收到，业务提交仍需应用级确认和幂等。不要把「低时延」归因于不退让：公网方案必须公平地响应拥塞；QUIC 的基础规范不内置 FEC，按场景选择成熟实现通常比自研状态机更可靠。
