# 09 配置治理的最佳实践？

## 01 核心回答

配置应按**环境分层**（开发/测试/生产隔离），**敏感信息外置**到密钥系统，避免硬编码进仓库；再通过**配置中心**做版本管理和灰度发布，并明确优先级与回滚策略，减少误配事故。

**要点：**① 配置与代码分离（ConfigMap/环境变量，不同环境不同配置）；② 密钥不进仓库（密钥管理系统注入）；③ 版本化 + 灰度 + 回滚预案；④ 优先级按目标 Spring Boot 版本及 PropertySource 顺序确认，不能使用“本地 > 环境 > 配置中心”的通用口诀。

---

## 02 如何解释配置覆盖顺序

常见运行场景下，命令行参数可以覆盖系统属性和环境变量，系统属性/环境变量可以覆盖普通配置文件；配置文件内部还受 profile、jar 内外位置和 import 顺序影响。测试属性源又有专门优先级，配置中心接入方式可能插入自己的 PropertySource。排错要定位最终值来自哪个源，而不是只看仓库中的 application.yml。

---

## 03 让误配置尽早暴露

使用 ConfigurationProperties 将相关配置绑定成结构化对象，并用校验约束范围、必填项和组合条件。超时统一标明单位；生产危险开关有安全默认值；变更记录版本、负责人和生效范围，先小流量验证再推广。

动态更新并不自动意味着已有连接池/线程池实例会重建；应确认每个配置的生效时点。多字段配置应以一致快照发布，避免读到半新半旧组合。密钥来源可外置，但日志、诊断端点和错误信息同样要防泄露。

---

## 04 配置更新为什么不能只依赖 Redis Pub/Sub

Redis Pub/Sub 是至多一次投递：订阅者断线或未能处理时，通知不会保存到待消费队列中等待重放。因此把“发布成功”当成“所有实例已更新”并不成立，Pub/Sub 适合作为变化提示，配置事实应保存在可按版本重新读取的权威存储。依据：[Redis Pub/Sub 投递语义](https://redis.io/docs/latest/develop/pubsub/#delivery-semantics)。

一种可恢复流程是：先持久化不可变配置版本，再通知版本变化；实例收到通知、长轮询返回、定期校验或重连时，比较已生效版本与权威版本。缺版本或不能可靠补齐增量时重新拉完整快照，完成格式、权限、组合约束及依赖资源验证后，本地原子替换整个配置对象；单次请求使用同一快照。并发拉取的旧响应不能覆盖新版本，回滚也应作为新的发布版本明确指向旧内容，保留审计。

验证失败保留最后有效配置并告警，不能把坏配置半应用后再补救。最后有效配置也不能无限沿用：密钥撤销、权限收紧等场景要有最大陈旧时间和安全失败策略。上报各实例“已下载/已验证/已生效”版本，发布控制面按确认结果放量；若要求严格同一版本服务，需额外的准入或版本路由屏障，长轮询和本地原子替换本身不保证全集群瞬间一致。
