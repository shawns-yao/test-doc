# 04 事务失效有哪些场景？同类内部调用为什么失效？

## 01 核心回答


**概念原理：**Spring 事务基于 AOP 代理：调用 `@Transactional` 方法时，实际调用的是**代理对象**，代理在方法前后开启/提交/回滚事务。绕过代理会使该方法上的事务拦截规则不执行；若外层已有事务，内部调用仍可能在外层事务中运行。

**失效场景清单：**① **同类内部调用（最常见）**：类内部 `this.methodB()` 调 `@Transactional` 方法——this 调用绕过代理，该方法的事务配置不被重新应用，但可能仍处于外层事务；② **方法可见性不匹配**：接口代理要求 public 接口方法；Spring 6.0+ 类代理默认也支持 protected/包可见事务方法，private 不能靠子类代理拦截；③ **异常被吞**：方法内 try-catch 捕获异常不抛出，拦截器可能看不到异常；若事务已被标记 rollback-only 仍会回滚；④ **异常类型不对**：默认只回滚 RuntimeException/Error，checked 异常默认不据此回滚，除非显式规则或 Spring 6.2+ 全局回滚配置改变该行为；⑤ **自建代理未生效**：类没有被 Spring 管理（new 出来的）、或 `@Transactional` 加在接口/类但代理配置问题；⑥ **传播行为配置**：`REQUIRES_NEW` 内层独立事务、`NOT_SUPPORTED` 挂起事务；⑦ **数据库不支持事务**：MyISAM 表；⑧ 多线程调用（新线程不在原事务上下文）。

**同类内部调用怎么解决：**① 优先把事务边界拆到另一个 Bean；② 获取代理再调用需明确代理和循环依赖约束，不把自注入当通用解法；③ 用 `TransactionTemplate` 编程式事务（代码内包事务逻辑，不依赖代理）。

**面试追问：**为什么 Spring 不处理内部调用（代理基于外部调用拦截）；编程式事务和声明式事务的区别；rollbackFor=Exception.class 什么时候必须写（方法抛 checked 异常也要回滚时）。

## 02 排查顺序是边界、资源、规则

先确认调用确实经过代理、事务基础设施已启用；再确认选中的 TransactionManager 管的是实际执行 SQL 的 DataSource/资源；最后检查传播、回滚规则、异常是否越过拦截器以及提交时有没有 rollback-only。多数据源选错管理器，即使打印“开启事务”也可能没有保护目标连接。

“方法抛过异常”不等于一定回滚。异常若在目标方法内被捕获且未标记 rollback-only，拦截器可能只看到正常返回；反过来，内层 REQUIRED 已把共享事务标记回滚，外层捕获异常后仍可能在提交时得到 UnexpectedRollbackException。

## 03 版本与异步边界

默认回滚通常是 RuntimeException/Error；Spring 6.2 起可以全局配置 rollbackOn=ALL_EXCEPTIONS，具体项目还可能用 rollbackFor/noRollbackFor 覆盖。不要不看配置就断言 checked exception 必然提交。传统命令式事务绑定线程，普通新线程不会继承；响应式事务使用 Reactor context，应按对应管理器和管线说明。
