# 10 高并发下库存校验有哪些优化点？规则引擎热更新如何设计？

## 01 核心回答


**概念原理：**库存校验优化的本质是减少无效流量和热点竞争，同时保留可证明的权威扣减：读走本地/Redis 缓存，写用原子操作（Lua/条件更新）替代锁。规则引擎热更新则是"规则与代码分离 + 配置下发不重启"。

**库存校验优化点：**① **本地预检**：进程内缓存库存（秒级同步），过滤大部分无货请求；② **Redis 分层**：热库存走 Lua 原子扣减，冷数据按需加载；③ **异步扣减**：资格预扣 + MQ 异步实扣，缩短锁持有时间；④ **读写分离**：库存查询走从库/缓存，扣减走主库；⑤ **分片**：超热点商品按 ID 分段（stock_1..N）分散写压力；⑥ **监控**：扣减失败率、超卖差异、回补成功率。

**规则引擎热更新设计：**① **规则外置**：规则存数据库/配置中心，不写死在代码（Drools/QLExpress/自研表达式）；② **版本管理**：每次变更生成版本号，新旧规则并存；③ **缓存双写**：规则变更 → 更新 DB → 发布消息 → 各节点刷新本地规则缓存（版本号对比）；④ **灰度验证**：按流量百分比或调用方灰度新规则，异常一键回滚到旧版本；⑤ **生效保障**：本地缓存 + 定时兜底拉取，防止消息丢失导致规则不一致。

**关键细节：**规则热更新最重要的是**回滚能力**（版本化 + 双写 + 灰度）；规则执行要超时和异常兜底（按规则风险选择拒绝、旧规则或降级，风控/资格规则不能默认放行）；库存优化每一项都要有量化目标（QPS、超卖数）。

**风险与取舍：**本地库存快照可能误放或误拒，最终库存不变量由权威扣减保证；规则引擎引入额外复杂度（表达式性能、安全沙箱）；热更新失败要能快速回滚，否则规则漂移比不更新更糟。

**项目落地：**限流规则/风控规则用配置中心 + 版本号 + 灰度开关；库存预检缓存秒级刷新 + DB 兜底；规则引擎执行日志和耗时监控；变更走审批 + 自动回滚。

**面试追问：**热更新和灰度发布的区别（配置 vs 代码，但思路相同）；规则引擎为什么比 if-else 好（可运营、可灰度）；如何保证各节点规则一致（版本号 + 消息 + 兜底拉取）。

## 02 热点优化不能破坏总库存约束

单商品库存拆成多个桶，可以降低同一写点竞争，但每桶必须分配明确额度，总额度不超过可售库存。用户去重、桶库存和预留记录若由同一个 Redis Lua 操作，在 Cluster 中仍须满足同槽约束；把用户 Set 随意拆到不同槽不再能与一个总库存键原子更新。

读从库或缓存只适合展示/预检，不能用可能滞后的余额决定最终承诺。库存预留之后可靠发事件的故障窗口见抽奖链路题，异步化不能删除这个责任。

## 03 规则热更新要保证单次请求用同一版本

新规则先下载、验签/校验、编译和测试，成功后原子替换不可变规则快照；请求开始时拿到版本引用，整个请求使用同一版本，避免前半段按旧规则、后半段按新规则。节点记录加载版本、发布时间与错误，推送只作通知，定期对账版本补漏。

配置原子替换不等于全集群瞬间一致。若规则影响奖品概率、价格、授权等结果，应把版本写进业务流水；严格切换可用分批启用、版本路由或活动冻结窗口。表达式执行需限制资源和可调用能力，回退策略根据规则风险确定。

口述：“库存分桶先分配额度，规则热更新先构建完整新快照再切换，单请求固定版本；灰度、失败回退和版本可追溯比单纯不重启更重要。”
