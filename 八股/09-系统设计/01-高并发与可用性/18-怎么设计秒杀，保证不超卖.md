# 18 怎么设计秒杀，保证不超卖？

## 01 原有理解

问题：一个高并发秒杀系统，怎么做到请求扛得住，库存扣不错，Redis 挂了还能恢复的

核心：
用户请求->网关限流/防刷->Redis->Lua(检查是否重复购买+判断库存+预占库存)->成功后写入 MQ->立刻返回排队中->订单服务异步消费 MQ，数据库条件扣库存+创建订单->成功/失败补偿

Redis 是第一道高性能库存闸门，数据库是最终防超卖底线，MQ 用来削峰。

---
## 02 怎么设计秒杀，保证不超卖

所谓的超卖是指，库存只有一件，两个线程同时查询，认为都可以买，然后两个人都执行扣减，最终卖出去两件，但是实际上只有一件
问题就是-->检查库存和扣减库存不是一个原子操作。

---

## 03 Redis+Lua 原子预扣库存

秒杀之前，先将库存放到 Redis 中，进行预热，这样用户过来之后，不直接访问 MySQL，而是先访问 Redis。

Lua 脚本一次性完成三件事，这三件事情必须是一个原子操作，如果不是原子操作，那么中间其他的线程可能插入进来
判断是否已经买过
库存是否  >0
然后库存  -1

---

## 04 Redis 已经控制库存了，为什么数据库还需要再防止一次

不能说，有了 Redis Lua，所以绝对不会超卖

因为 Redis 可能宕机，故障切换，数据丢失，等等原因，所以数据库是最后一道防线

并且订单消费者再最终操作数据库时，不能先 select，再 update，而是应该让数据库自己做条件扣减

---

## 05 解决一人重复下单

除了库存不超卖之外，假如每一个人只能买一件
如果用户疯狂的点击，发送了很多次请求，所以 Lua 中还需要同时判断这个用户是不是已经参加过
所以 Lua 实际负责的是
检查用户
检查库存
记录用户
扣除库存

然后数据库应该再建立唯一的约束，例如活动 ID+商品 ID+用户 ID，必须唯一
这样即使 MQ 重复消费，Redis 判断失效，程序重复执行，那么数据库依然不能生成两笔秒杀订单

---
## 06 秒杀怎么兼顾性能和防止超卖

如果除了考虑不超卖，但是秒杀场景可能有 10 万库存，100 万人同时抢

如果 100 万次请求全部打到数据库，那么数据库直接就挂了，所以秒杀的设计关键不仅仅是怎么加锁，还有怎么让绝大多数的请求根本到不了数据库

---

## 07 网关限流

再最外层拦截，比如前端展示当前请求繁忙，请稍后再试

---

## 08 Redis 快速判断库存

比如 Redis 最多只放 1000 个有效请求，后面的请求再 Redis 中就可以告诉他们，当前已经售空，根本不用访问 Mysql

---

## 09 为什么还需要 MQ（比如 Kafka）

比如 Redis 放入了 1000 个请求进入 Mysql，那么数据库还是会产生瞬时压力，

于是可以 Redis Lua 成功后，发送 MQ，给用户返回排队中，让订单服务再慢慢的消费，于是 MQ 起到了削峰填谷。

---

## 10 MQ 怎么防止重复消费

比如消费者成功处理，但是还没有来得及 ACK，消费者挂了，那么 MQ 重新投递，于是同一条秒杀消息可能执行两次

所以订单服务必须幂等

所以秒杀系统防止超卖不是一个 Lua 脚本，而是一整套

Redis Lua 原子扣减
数据库条件扣减
数据库唯一约束
MQ 消费幂等
失败补偿

---
## 11 Lua 脚本中的 Key 怎么设计

按照业务前缀 : {活动 ID +  商品 ID }：其他维度

比如活动 ID 为 1001，商品 ID 为 2001，那么 key 设计成

库存 Key 可以设计成：

```
seckill:stock:{1001:2001}
```

用户购买标记：

```
seckill:buyer:{1001:2001}:user:8888
```

订单结果：

```
seckill:result:{1001:2001}:user:8888
```

其中{1001：2001}并不是随意的设计，因为 Redis Cluster（集群）可能会把 key 分散到不同的节点，
但是如果 Lua 脚本一次性操作两个 key，并且两个 key 还再不同的 Redis 节点中，那么 Redis Cluster 不能简单的让一个 Lua 脚本跨节点原子执行。
于是会遇到 crossslot 的问题，也就是 Redis Cluster 的 "跨槽" 错误-->命令里的多个 key，经过计算不属于同一个 hash slot（哈希槽），Redis Cluster 拒绝执行。

因此要让 Lua 用到的 key 落到同一个 Hash Slot 中，也就是使用{1001：2001}

---

## 12 购买用户怎么存

方式 1；每一个用户一个 Key，有这个 key 说明买过，
优点：简单
缺点：如果用户特别多，Key 的数量会很多
方式 2：可以用 Set，比如 Redis Lua 中检查用户是不是还再 Set 中，不在加入 Set，再得
但是这样大型得活动可能会产生一个巨大得热点 Set
优化需有边界：只把用户 Set 分桶可减小单个集合，但若桶号进入不同 hash tag，就不能再与同一个总库存键由单个 Lua 原子处理。跨槽扩展需把库存额度也分配到各桶，并设计全局购买去重与额度迁移，不能只改 key 就同时得到原子性和跨节点分散。

---

## 13 Key 的 TTL

秒杀活动的 Key 不应该永久留着。
可以设计成活动结束+一段业务缓存时间，然后过期。

---
## 14 Redis 挂了，系统有自愈能力吗？自愈怎么做

Redis 挂了通常宁愿暂时停止秒杀，也不能直接把流量打到数据库。

---

## 15 自愈应该怎么做？

自愈按“暂停或严限流入口 → 核实权威事实和未决预留 → 重建缓存与消费状态 → 校验差异 → 小流量恢复”推进，每一步记录活动版本与恢复水位。只有库存守恒、订单唯一性和旧任务隔离通过检查，才扩大流量；不能只看 Redis 进程重新上线。

---

## 16 库存怎么恢复？

不能 Redis 挂了，就重新从最初的库存加载。因为库存可能已经发生了变化
应该从权威数据库中恢复，并且需要考虑 MQ 中未完成的预占库存，并且恢复需要状态重建+对账

---
## 17 如何保证 Redis 的高可用

1. 主节点+从节点+自动故障切换，比如 Redis 集群

2. Redis 集群

3. Redis 持久化 混合存储 RDB+AOF

4. 客户端容错
1. 合理超时
2. 重试次数限制
3. 退避+熔断

5. 监控 Redis，需要关注，内存使用率，命中率，QPS，慢查询，热点 Key，Big Key，P 99 延迟等

---

## 18 纠错与可靠性空隙

本题的整体分层思路成立，但“Lua 成功后发送 MQ”之间仍可能宕机，必须有可恢复的预留/事件记录。活动中 Redis 发生主从切换也可能丢掉已返回的预留，所以用户应先得到受理状态，数据库事务成功才形成最终订单。原子执行只解决并发穿插，不等于跨系统原子提交或同步持久化。

同槽 hash tag 保证相关键能在一个脚本里操作，同时也意味着该活动热点仍集中到一个槽。把用户桶分散到不同槽会破坏这个前提；要跨节点扩展必须设计额度分片、订单唯一约束与安全调拨，而不是只给 Set 加桶号。

---

## 19 用故障时序检验防超卖

1. Redis 已预留、MQ 发布结果不明：按 reservationId 查证并重发，不能重新减库存
2. 数据库已建单、消费位点未提交：唯一购买约束与业务流水识别重复，扣减与建单在同一事务
3. 用户取消和支付成功并发：仅合法状态迁移可释放或确认，迟到补偿不能释放已售库存
4. Redis 重建：暂停或切换入口版本，结合数据库事实及未决预留重算额度，对账并确认旧执行者不能重复生效后再开放

口述：“防超卖的底线是权威数据库条件扣减与订单唯一约束；Redis 和 MQ 降低压力但各有故障窗口。单槽 Lua 保局部原子，可靠预留账本保恢复，取消和补偿都按状态幂等执行。”
