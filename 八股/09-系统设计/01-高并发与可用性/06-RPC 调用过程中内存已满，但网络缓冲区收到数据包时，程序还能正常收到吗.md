# 06 RPC 调用过程中内存已满，但网络缓冲区收到数据包时，程序还能正常收到吗？

## 01 核心回答


**概念原理：**不一定，必须区分“内核收到字节”和“RPC 业务正常收到并处理”。关键是区分两套内存：**内核网络缓冲区（socket 接收队列）**和**进程用户态堆内存**。数据包先由网卡/内核收进 socket 缓冲区，这一步不直接依赖 JVM 堆，但仍依赖系统或容器可用内存；进程堆内存满（OOM 边缘）只影响"从内核缓冲区读出来放进堆"这一步。

**实现流程（数据到达路径）：**① 网卡中断 → 数据进内核接收队列（sk_buff）；② 进程调用 `recv`/read 把数据从内核缓冲拷贝到用户态缓冲区（可为预分配堆缓冲或堆外直接缓冲）；③ 应用解析、处理。若是应用分配失败，问题可能发生在第②步或解析处理阶段——内核缓冲区有数据，但堆上分配目标缓冲区失败或 OOM。

**关键细节：**① "内存满"要区分：JVM 堆满（可 GC 后继续）vs 系统内存耗尽（内核可能触发 OOM killer 杀进程）；② 内核 socket 内存不计入 JVM 堆，但可能被容器 cgroup 内存控制计入；③ 若进程完全不读，内核缓冲区会满 → 触发 TCP 窗口收缩/零窗口，对端受流控限制（仍可发送窗口探测）；应用可能持续等待或超时，不能等同于 TCP 静默丢失业务数据。

**风险与取舍：**应用读得慢 + 内核缓冲满 → 对端发送阻塞（TCP 流控生效）；系统内存真的耗尽时 OOM killer 可能直接杀进程，比"收不到数据"更严重；要监控堆使用率和 GC，而不是等 OOM。

**项目落地：**RPC 框架设置接收缓冲区上限 + 背压处理；Netty 的 `autoRead` 暂停读取形成反压；堆内存监控预警 + GC 调优；OOM 前 dump 保留现场。

**面试追问：**TCP 窗口和背压的关系（接收方窗口为 0 对端停止发送）；OOM killer 怎么选进程（内存占用评分）；内核缓冲区和用户缓冲区的区别（谁负责拷贝）。

## 02 按三种内存情况回答

1. JVM 堆达到上限但已有可复用接收缓冲：读取字节可能仍成功，随后反序列化或构建对象可能失败
2. 堆外直接内存耗尽：即使堆看起来正常，Netty 等框架也可能无法分配网络 buffer，读链路不能正常前进
3. 主机或容器整体内存受压：内核分配、socket 缓冲与进程生存都可能受影响，cgroup 还可能先触发容器 OOM

TCP ACK 证明传输层接收到了相应字节，不证明应用已 read，更不证明 RPC 业务已执行。网络缓冲有数据也不能推出调用者最终能拿到成功结果。

## 03 诊断与保护

同时看 JVM 堆/GC、直接内存、RSS、cgroup memory.events、socket 队列和应用消费速率。暂停 autoRead 是施加背压的一种方式，不能让上游无限缓存；还需帧大小限制、有界队列、连接数和在途请求上限。OOM 时临时生成巨大 dump 可能再耗尽磁盘，应预设采集与存储策略。

口述：“可能收到了 TCP 字节，但不一定能完成 RPC。要看是堆、堆外还是系统内存耗尽，以及有没有可复用缓冲；流控只能减慢发送，不能保证业务继续执行。”
