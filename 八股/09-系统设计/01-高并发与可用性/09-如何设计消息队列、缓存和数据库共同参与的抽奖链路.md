# 09 如何设计消息队列、缓存和数据库共同参与的抽奖链路？

## 01 核心回答


**概念原理：**抽奖链路天然适合"缓存扛读、MQ 削峰、数据库落事实"的分工：Redis 处理高频扣减和资格判断，MQ 异步化下游写操作，MySQL 保存最终结果，三者通过幂等和补偿保证最终一致。

**核心链路（时序）：**① 请求进网关限流 → ② 校验资格（Redis 查用户抽奖次数/黑名单）→ ③ **Redis Lua 原子扣减**奖品库存 + 记录中奖结果（临时态）→ ④ 发送抽奖事件到 MQ → ⑤ 消费者幂等落 MySQL（抽奖记录 + 奖品扣减 + 发货单）→ ⑥ 成功回执 / 失败补偿（重试 → 死信 → 对账回滚 Redis）。

**关键细节：**① 每个角色职责单一：Redis 管"能不能抽"（资格+库存预扣），MQ 管可靠传递与缓冲，需配置确认、保留和消费恢复，MySQL 管"最终事实"；② 事件带**抽奖单号**做幂等键；③ Redis 扣了但 DB 失败 → 补偿任务按单号回补 Redis 或重试落库；④ 中奖名单查询走 Redis 缓存，DB 为准。

**风险与取舍：**缓存与 DB 状态短暂不一致（最终一致窗口）；MQ 积压导致发奖延迟；Redis 故障时先停止或严限流；仅在状态重建和数据库容量验证后切换直扣；对账是最后防线，必须跑。

**项目落地：**抽奖单号贯穿全链路；Redis Lua 扣库存 + MQ 异步落库 + 对账任务 + 死信告警；监控：Redis 扣减成功率、MQ 积压、差异单数量（Redis 有 DB 无/DB 有 Redis 无）。

**面试追问：**为什么扣减放 Redis 不放 DB（QPS 与行锁）；最终一致靠什么闭环（幂等 + 重试 + 对账）；Redis 和 DB 不一致怎么修（以 DB 为准回补/回滚 Redis）。

---

## 02 三个系统之间的空隙必须能恢复

Redis Lua 成功后进程在发 MQ 前退出，是原链路最大的双写窗口；“消费者幂等”解决不了这条消息从未发出的情况。可以选择数据库事务内受理记录加 outbox，Redis 只作流量闸门；也可在 Redis 同槽脚本内记录可恢复事件/预留，再由转发器可靠投递，但此方案仍必须面对 Redis 持久化与复制丢失边界。选择取决于是否已向用户作出成功承诺。

应至少持久化 drawId、规则版本、候选结果、预留状态、终态及事件 ID。返回“处理中”和返回“中奖成功”是两个不同业务承诺，不能把临时 Redis 结果直接当已履约事实。

---

## 03 三种故障逐一推演

- Redis 已预留而 MQ 未确认：按预留记录重试或查询发送结果，不能凭一次超时取消
- MySQL 事务已提交但消费确认丢失：重投命中唯一 drawId，复用成功结果，不再扣奖品
- 超时取消与迟到消费并发：通过状态条件和版本只允许一个终态获胜；取消已生效的旧任务不能重新发奖

对账应比较业务流水与状态，不只是两个库存数字；差额可能来自仍在途的合法预留。口述：“缓存挡高频请求，数据库保存可审计结果，MQ 负责传递；关键是可靠记录每次预留与事件，覆盖发消息前宕机和重复确认窗口，再用有条件补偿收敛。”
