# 17 Sentinel 限流体系怎么做？分布式限流一致性？

## 01 核心回答

**本质：**「控制面下发规则，数据面本地快速判定」。**控制面**——控制台配置限流/熔断/系统保护规则，存到配置中心（Nacos）动态推送各实例；**数据面**——业务代码在资源点埋点，请求走 slot chain（统计、限流、熔断），本地内存计数 + 滑动时间窗判断 QPS/RT/异常率是否超阈值，超阈值执行快速拒绝、排队等待、预热放量。

**为什么快：**判定在本机完成不走远程 RPC；规则热更新生效快；指标异步上报控制台可视化和告警。

**分布式限流一致性（集群流控）：**Sentinel 用 **Token Server + Token Client**——Client 收到请求先向 Token Server 申请令牌，Server 按目标版本支持的集群规则统一判定，不能假设所有单机流控模式都支持集群，把多实例流量收敛到全局配额视角，一致性明显优于本地模式。

**口述重点：**Sentinel 默认单机限流；全局配额可用集群流控 Token Server，但需说明失败回退和统计窗口语义——在性能和一致性之间做工程折中。

---

## 02 集中发令牌不等于强一致配额永不超发

单机每实例 100 QPS，10 个实例的总量可能达到约 1000 QPS，而且流量偏斜会导致一边拒绝、一边空闲。集群规则应明确阈值是全局总量还是单机均摊，并保证资源 flowId 和命名空间一致。

Token Server 通信失败时，官方配置可回退本地限流；这提高可用性，但会改变全局配额保证。对成本预算或稀缺资源，可能要失败关闭或预分配有界额度；普通保护规则可接受短时偏差。Token Server 自身需要容量、分片、故障切换和观测，切换后的计数语义也要验证。

---

## 03 控制面与数据面分别验收

控制台展示的规则不一定已持久化或已被所有实例应用，生产要核对配置源、版本、订阅状态和兜底拉取。数据面记录通过、拒绝、等待、回退、本地/集群模式和 Token Server 延迟，才能发现“规则存在但未生效”。

口述：“默认本地限流用于低成本保护；要总配额则使用集群 Token Server，并明确阈值类型与失败策略。规则一致、计数一致和故障期间是否放行是三件事，不能只说用了集群模式就严格全局一致。”
