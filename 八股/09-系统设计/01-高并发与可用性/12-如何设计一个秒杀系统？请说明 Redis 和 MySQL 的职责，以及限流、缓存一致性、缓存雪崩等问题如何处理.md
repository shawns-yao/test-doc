# 12 如何设计一个秒杀系统？请说明 Redis 和 MySQL 的职责，以及限流、缓存一致性、缓存雪崩等问题如何处理。

## 01 核心回答


**概念原理：**秒杀的本质是"海量请求抢少量资源"，设计原则：**流量尽量在入口被拦截，核心写操作原子化，数据库只承担最终落账**。全链路：前端 → 网关 → 应用 → Redis → MQ → MySQL，每层都削峰。

**实现流程（全链路设计）：**① **前端/接入层**：按钮置灰、验证码、静态页面 CDN，拦截无效点击；② **网关层**：限流（令牌桶按用户/IP）、黑白名单、防脚本；③ **应用层**：本地库存预检（进程内缓存粗筛）+ 用户资格校验（已购/黑名单/频控）；④ **Redis 层**：Lua 脚本原子完成"库存 > 0 判断 + 扣减 + 记录用户"，`SETNX` 防重复抢购；⑤ **MQ 层**：可靠发送预留/受理事件，异步落单，最终成功需数据库确认；⑥ **MySQL 层**：消费者幂等创建订单、条件更新扣库存兜底（`stock > 0`），对账回补。

**Redis 和 MySQL 的职责边界：****Redis**：扛高频读写——库存预扣、资格判断、频控计数、结果缓存；**MySQL**：最终事实——订单、扣减流水、用户中奖记录；Redis 可售状态重建需结合 MySQL 事实和未决预留流水，不能只复制数据库剩余数。

**关键细节（问题处理）：**① **限流**：网关令牌桶 + 用户维度频控 + 接口级配额，超限直接拒绝；② **缓存一致性**：Redis 预扣 → 异步落 DB → 对账；不一致时以 DB 为准回滚/回补 Redis；扣减事件幂等；③ **缓存雪崩**：活动期间避免热点库存自动失效，活动结束后按保留策略清理+ Redis 高可用（主从/哨兵/集群）+ 预热 + 降级开关（Redis 故障先暂停或严限流，验证状态与数据库余量后才切换）；④ **缓存击穿**：库存 key 是热点，Lua 保证单次扣减原子性，但 key 缺失/淘汰仍需预热、单航班重建和回源限速。

**风险与取舍：**超卖风险：Redis 扣减与 DB 兜底之间的窗口（用 DB 条件更新兜底 + 对账）；恶意刷单：接口幂等 + 频控 + 风控；MQ 积压：消费者水平扩展 + 监控；Redis 故障：降级预案 + 容量冗余。

**项目落地：**活动前：压测定容量、预热库存、灰度开关；活动中：监控 Redis 扣减 QPS、MQ 积压、订单成功率、超卖差异；活动后：对账、回补、复盘调参；发奖异步化 + 状态机管理订单生命周期。

**面试追问：**秒杀为什么不直接扣数据库（行锁串行化，QPS 上不去）；Redis 扣了 MySQL 没扣怎么办（对账 + 回补）；怎么防止一个人抢多个（Redis 用户维度标记 + 幂等）；库存预热失败怎么办（降级直连 DB + 限流）。

## 02 纠错 原子扣减不等于可靠整条链路

Lua 不能自动避免缓存击穿，也不能让 Redis 预留与 MQ 发布形成跨系统事务。扣完 Redis 后进程崩溃、消息未发出时，需要可靠预留记录或事务 outbox 才能发现并恢复。入口按钮置灰与隐藏地址只能改善交互或增加滥用成本，授权、限额与防重必须在服务端完成。

MySQL 扣库存、创建订单、唯一购买约束应在同一本地事务里；如果数据库条件更新失败，就不能把之前的 Redis 成功返回当作最终订单成功。受理和售罄状态的查询应有明确幂等键与终态。

## 03 故障恢复比正常扣减更难

恢复 Redis 前暂停入口或切换活动 epoch，收敛/核对在途任务，重建剩余额度与已预留记录，验证新旧消费者不会同时对同一批请求生效后再放量。取消订单释放库存用状态条件更新，避免迟到付款与重复释放互相覆盖。

压测应覆盖突然流量、热点商品、MQ 慢消费、Redis failover 和重建期间重试；验收同时看超卖数、少卖/卡单量、最老待处理时间和恢复耗时。口述：“缓存闸门降流量，数据库事务保最终不变量，可靠事件连接两者，故障时先保护正确性再恢复吞吐。”
