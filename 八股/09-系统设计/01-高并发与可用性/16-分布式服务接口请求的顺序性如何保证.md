# 16 分布式服务接口请求的顺序性如何保证？

## 01 核心回答

**前提：**尽量从业务设计上**避免强顺序依赖**——引入严格顺序保证会带来系统复杂度上升、吞吐下降、热点 key 压力变大、排障恢复更麻烦。

**三类解法：**① **Hash 分发到同一机器**——按业务 ID 一致性 hash 路由到同一台机器，机器内部同一 key 请求进内存队列串行处理（同一 key 有序、不同 key 并行）；② **MQ/内存队列串行化**——生产端按业务 key 发到同一 partition/队列，消费端对 key 做 hash 落到固定线程顺序消费；③ **锁与序列号控制**——锁保证互斥，序列号/版本校验才用于识别期望顺序，两者不能互相替代（更重、吞吐和热点问题更明显）。

**更新型请求加幂等：**使用业务幂等键与权威状态的原子约束；Redis 标记与外部副作用之间仍有故障窗口，避免重复执行。

**口述重点：**顺序性不是白拿的，核心思路是「同一 key 聚合到同一路径上串行处理」，常见手段是 hash 路由 + 队列串行 + 幂等兜底。

---

## 02 先定义要保证哪一种顺序

请求发出顺序、服务端到达顺序、存储追加顺序和业务生效顺序不同。两台客户端没有共享序列号，仅凭本地时间戳不能建立可靠全局顺序。多数业务只需同订单/会话的局部顺序，不需要所有用户串成一条全局队列。

锁只保证同一时刻一个执行者，后到请求可能先抢到锁，所以互斥不等于先来先执行。同 key 路由还要处理扩缩容与故障转移：旧节点有在途工作时，新节点不能同时接管且无版本约束；内存队列宕机也不能作为唯一持久顺序记录。

---

## 03 序列号如何处理重复与缺口

为实体保存 lastAppliedSeq。相同或更旧序号按幂等规则跳过；恰好为下一序号才能推进；出现缺口时选择等待、补拉或报错，不能无限缓存。状态更新和序号推进应在同一事务中，Worker 接管使用 epoch/fencing 防止旧实例迟到写入。

若业务可改为交换律更新或“仅接受较新版本”的状态覆盖，就可以放宽严格顺序，但这与“每条命令都必须执行”语义不同。口述：“先定顺序范围与序列来源，再做串行路由、持久化位点和幂等，尤其说明故障接管与缺口怎么处理。”
