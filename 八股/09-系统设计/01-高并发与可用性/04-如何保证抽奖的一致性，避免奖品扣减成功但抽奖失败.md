# 04 如何保证抽奖的一致性，避免奖品扣减成功但抽奖失败？

## 01 核心回答


**概念原理：**"奖品扣减成功但抽奖失败"的本质是**两个操作不在一个事务边界**——扣库存（写）和抽奖结果（写）分离导致部分成功。解决思路：要么同事务，要么用状态机 + 补偿保证最终一致。

**方案一（同事务强一致）：**抽奖动作和奖品扣减放**同一个数据库事务**：`BEGIN → 扣减奖品库存（条件更新）→ 写入中奖记录 → COMMIT`，任一步失败整体回滚，天然一致。适合能在单库短事务内完成的链路，吞吐上限应压测而非按“低频”一概排除。

**方案二（异步最终一致）：**先落受理记录（状态=进行中），可靠投递后异步确认或预留奖品库存，消费者幂等处理；失败重试进死信，补偿任务扫描未决记录，先核查预留和扣减结果再重试或终止。适合 Redis 扣减 + 异步落库的高并发场景。

**关键细节：**奖品库存扣减必须**幂等**（抽奖单号做唯一键）；用**状态机**管理抽奖单状态（待处理/已中奖/已发货/已回滚）；对账任务定期扫描状态不一致的单据；Redis 扣减成功但 DB 落库失败时，补偿要么补落库要么回补 Redis。

**风险与取舍：**强一致方案在高并发下锁竞争大；最终一致方案有等待窗口，库存确认前只能显示处理中，不能承诺已中奖；补偿任务本身可能失败——要设计重试上限和人工介入通道。

**项目落地：**抽奖单号贯穿全链路；受理记录持久化 + 库存确认后落中奖终态 + 死信告警 + 对账补偿；监控"中奖未扣减"和"扣减未中奖"两类差异单；发货状态机推进。

**面试追问：**为何不直接采用分布式事务（评估参与资源、锁持有、恢复复杂度与业务补偿能力）；最终一致怎么保证不丢（消息可靠投递 + 幂等消费 + 对账兜底）；回滚时 Redis 和 DB 的顺序（先恢复 DB 权威，再刷缓存）。

## 02 纠错 先承诺中奖再尝试扣库存并不安全

奖品稀缺时，“用户已中奖，稍后再扣库存”可能产生无法履约的成功结果。可以先给抽奖请求分配 drawId 并返回处理中；最终中奖只能在库存已可靠预留或同库事务扣减成功后确认。响应丢失也不等于抽奖失败，客户端重试同一 drawId 应查询或重用原结果，不能再抽一次。

单库方案用条件扣库存、唯一 drawId 结果和待发奖事件构成短事务，通知/发货移出事务；跨系统方案则持久化预留与状态迁移。随机结果、规则版本和库存选择应被记录，重试不能改变已经作出的抽奖决定。

## 03 补偿只修复确定的差异

消费失败可能发生在数据库提交前，也可能是提交后 ack 丢失。先查交易流水再判断是否回补；对未知结果立即返还库存可能让同一奖品被再次分配。取消和发奖都用状态条件转换，成功发奖后不能由迟到的取消消息释放库存。

口述：“同库优先短事务绑定扣库存与中奖记录；跨系统先受理并预留，库存确认后才宣布中奖。全链路同一个抽奖号，重试不重新抽、补偿不盲加库存，结果不明先查再对账。”
