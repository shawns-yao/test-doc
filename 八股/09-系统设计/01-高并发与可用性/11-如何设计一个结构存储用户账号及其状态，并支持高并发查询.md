# 11 如何设计一个结构存储用户账号及其状态，并支持高并发查询？

## 01 核心回答


**概念原理：**核心是"分场景选存储"：账号属性（稳定、低频）放 MySQL，在线状态（高频、短生命周期）放 Redis，两者通过账号 ID 关联。查询要支持点查（按 ID）和批量（按 ID 列表），避免大表全扫。

**实现流程（分层设计）：**① **MySQL 账号表**：账号 ID（主键）、昵称、头像等稳定属性；按账号 ID 哈希分库分表（`user_id % N`）；② **Redis 状态存储**：在线状态用 Bitmap（`SETBIT online user_id 1`，内存极省）或 Hash（要存设备/时间详情时）；③ **查询路径**：状态查询走 Redis（`GETBIT`/`HGET`），属性查询走 MySQL 主键索引；④ **缓存层**：账号属性热点数据 Redis 缓存（Cache Aside），写穿 DB 删缓存。

**关键细节：**状态更新要幂等和防乱序（带时间戳/版本，旧状态不覆盖新状态）；批量查询用 `pipeline`/`mget` 减少 RTT；热 key（明星账号）做本地缓存副本；Redis 只存实时态，历史审计落 DB。

**风险与取舍：**Bitmap 在账号 ID 稀疏时浪费空间（改用 Set/Hash）；在线展示可按需求容忍短暂误差并用心跳修复；封禁、权限等账号状态不能按同样标准处理，属性数据不能丢（DB 权威）；分库分表后跨片批量查询要并发拼装。

**项目落地：**在线状态：Redis 状态快照配合逐会话租约/最后心跳与超时清理，Bitmap 本身没有每一位 TTL；账号属性：MySQL 分表 + Redis 缓存 + 缓存失效重试；监控：状态查询 P99、缓存命中率、分片热点。

**面试追问：**为什么在线状态用 Bitmap 不用 MySQL（高频写 + 内存按位 + 天然去重）；分库分表键怎么选（按账号 ID 保证同账号同库）；热 key 怎么处理（本地缓存/副本/读扩散）。

## 02 首先拆开在线状态与账号安全状态

昵称、启用/封禁、认证权限和“当前在线”不是同一种状态。在线通常是带租约的估计，可在几次心跳周期后判离线；封禁或权限撤销可能要求立即影响请求，不能只查一个允许陈旧的在线 Bitmap。是否分库分表也应由实际数据规模与吞吐决定，普通主键索引可能已经够用。

Bitmap 以最大位偏移决定空间，直接用很大的 Snowflake ID 当 offset 不合适，可用稠密映射或分段。一个 bitmap key 的 EXPIRE 会过期整块位图，不能给每个用户位独立续约；在线租约应单独以会话键/截止时间索引管理，再生成便于批查的位图快照。

## 03 多设备和迟到事件如何处理

同一账号可能同时登录多设备，不能在一个连接断开时直接把账号设离线。保留 sessionId、连接 epoch 和最后心跳；旧会话的迟到断开只删除匹配会话，新会话仍有效时账号保持在线。时间戳来自不同机器时也可能偏斜，优先用服务端版本或可核验的会话身份。

口述：“账号持久属性和在线估计分开，安全状态单独制定一致性要求。在线用逐会话租约维护，Bitmap 只作紧凑查询视图，不能靠刷新整个位图 TTL 模拟每人心跳。”
