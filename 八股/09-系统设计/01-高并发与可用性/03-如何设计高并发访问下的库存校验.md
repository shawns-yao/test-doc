# 03 如何设计高并发访问下的库存校验？

## 01 核心回答


**概念原理：**高并发库存校验的核心矛盾：校验（读）和扣减（写）必须原子，且不能把全部流量压到数据库。经典分层：本地预检 → Redis 原子扣减 → MySQL 条件更新兜底。

**实现流程（分层方案）：**① **本地预检**：进程内缓存库存快照，先过滤明显无货请求（秒级粗筛）；② **Redis 原子扣减**：Lua 脚本一次完成"库存 > 0 判断 + 扣减 + 记录用户"，避免先读后写竞态；③ **MySQL 兜底**：`UPDATE stock SET stock = stock - 1 WHERE id = ? AND stock > 0` 条件更新，影响行数 0 即库存不足；④ 扣减成功才允许下单，失败回补。

**关键细节：**Redis 与 MySQL 库存要**对账**（定期比较差异，差异来自回补失败/超时重试）；库存扣减要**幂等**（同用户同单不能扣两次）；预扣（下单冻结）与实扣（支付成功）分离，超时自动释放。

**风险与取舍：**分布式锁粒度过大会串行化所有请求（不要全局锁，用 Lua/条件更新替代）；Redis 故障时优先暂停或严限流，只有数据库容量与状态切换已验证时才走直扣；本地缓存可能误放或误拒绝；最终是否超卖取决于权威扣减与订单事务。

**项目落地：**秒杀/抢购场景：本地预检 + Redis Lua + DB 条件更新 + 对账任务；普通商品：Redis 缓存读 + DB 扣减；监控库存差异、扣减失败率和回补任务执行情况。

**面试追问：**为什么 Lua 脚本能保证原子（单线程执行整段脚本）；条件更新为什么能防超卖（行锁 + 条件判断原子）；预扣和实扣为什么分离（表达待支付占用；还须超时释放与限额防恶意占用）。

---

## 02 先定义库存不变量与权威来源

库存校验用于展示时可以读快照；用于承诺售出时，必须把检查与扣减放在权威存储的同一原子操作中。若允许一次购买 q 件，条件应是可售库存至少 q，而非仅大于零；订单流水唯一约束与扣减放在同一事务，防止重复请求扣两次。

Redis 预扣是准入或预留，MySQL 条件更新是另一层最终约束，两套数量的含义必须明确：可售、已预留、已售和已释放不能混成一个 stock。Lua 的执行原子性只覆盖当前 Redis 执行域，不覆盖 MySQL、MQ 或故障切换后的持久性，也不意味着脚本出错自动回滚所有已执行写入。

---

## 03 失败与补偿的正确姿势

扣减超时先按 reservationId 查询结果，不能盲目再扣或直接加回；释放要从“已预留”条件转换为“已释放”，保证只释放一次，且不能释放已支付订单。Redis 重建要考虑在途预留，直接加载数据库剩余数再开放入口可能重卖已经承诺的份额。

口述：“读库存只是提示，防超卖靠权威条件扣减、订单事务和请求幂等。Redis 可以挡流量，但我会明确预留账本、超时状态与只执行一次的释放，故障时先停或限流再恢复。”
