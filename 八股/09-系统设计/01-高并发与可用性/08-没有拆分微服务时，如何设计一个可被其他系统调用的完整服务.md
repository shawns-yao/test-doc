# 08 没有拆分微服务时，如何设计一个可被其他系统调用的完整服务？

## 01 核心回答


**概念原理：**单体也按"可对外服务的完整闭环"设计：对外暴露稳定的 API 契约，对内分层清晰，把服务能力（接口、鉴权、限流、监控、数据）打包完整，让调用方只依赖契约不依赖实现。

**实现流程（设计要点）：**① **API 契约**：定义接口（REST/RPC）、参数校验、错误码规范、版本策略（`/v1` 兼容演进）；② **鉴权与安全**：调用方认证（签名/Token/ak-sk）、权限控制、敏感数据脱敏；③ **分层结构**：Controller → Service → DAO，事务边界在 Service，日志/异常统一处理；④ **稳定性**：限流（按调用方配额）、超时设置、幂等键（防重试重复）、熔断（保护自身与下游）；⑤ **可观测**：日志、Trace、指标、告警——调用方出问题能快速定位；⑥ **数据与部署**：独立 Schema 或表前缀隔离，独立配置，可独立发布。

**关键细节：**对外接口和内部实现解耦（接口不暴露表结构）；错误码要语义化且文档化；接口必须有超时和重试策略（调用方视角）；版本不兼容变更要灰度（新旧并存）。

**风险与取舍：**单体演进到微服务的边界要在接口层面先隔离（可减少后续拆分的契约变化，但仍需处理网络故障、数据归属和事务边界）；过度设计接口（过早抽象）增加维护成本；无独立部署单元时发布互相影响——用模块化 + 独立配置缓解。

**项目落地：**对外提供 OpenAPI 文档 + 签名鉴权 + 按调用方限流配额；接口幂等（幂等键表）；监控接口 P99、错误率、调用方维度报表；后续拆分时按"接口契约不变、实现搬移"演进。

**面试追问：**接口版本兼容怎么做（加版本号、字段可选、新老并存）；幂等怎么实现（幂等键 + 唯一索引）；调用方配额限流怎么做（按 ak 维度令牌桶）。

## 02 可调用能力不取决于部署是否微服务

先给模块定义稳定契约、数据归属和错误语义，再提供 HTTP/RPC 适配层。调用方不应直接读写模块的数据库，否则表结构、事务与业务约束都变成隐式公共 API。单体内部仍可用函数调用，没必要为“未来微服务”先制造网络开销。

接口需要明确幂等键作用域、重复请求返回什么、分页与版本兼容、鉴权后的租户隔离、超时后的结果查询。版本号只标记变化，不会自动解决兼容性；新增字段也可能影响严格校验客户端，应做消费者契约测试。

## 03 迁移边界与口述

“独立 schema”有助于治理但不是物理隔离保证；共享数据库和同进程仍可能相互拖慢。真正拆出服务时，本地事务可能变成跨系统最终一致，调用延迟与重试语义改变，所以不应承诺只搬代码。

口述：“先做模块化单体，业务模块有数据所有权和稳定 API，公共入口统一认证限流，业务内部做授权和幂等。接口可独立测试，部署先保持简单；真正需要拆分时再显式处理分布式失败与事务。”
