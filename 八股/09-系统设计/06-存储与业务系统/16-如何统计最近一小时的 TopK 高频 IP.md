# 16 如何统计最近一小时的 TopK 高频 IP？

## 01 核心回答

先问“一小时”是固定自然小时、处理时刻最近 60 分钟，还是事件发生时刻的滑动窗口；再问结果需要精确还是近似、刷新频率和允许迟到多久。静态日志 TopK 只需完整聚合后选前 K，持续滑动窗口还必须正确移除过期计数并处理乱序。

---

## 02 精确窗口怎样做

如果按处理时间且要求逐事件精确，保存窗口内事件或可精确到期的计数增量；新事件增加对应 IP 计数，过期事件扣减，零计数回收。计数变化后更新支持增减的排序结构，或周期性扫描活跃键维护小顶堆。小顶堆本身不能替代全部 IP 计数，也不能只在新增时更新而忘记过期导致排名下降。

高吞吐时可按一分钟等粒度分桶，保留各桶计数并滚动汇总。但按整桶删除只能得到约定粒度的窗口；若要求任意时刻精确最近 3600 秒，边界桶必须保留更细数据，否则最多会有一个桶宽度的边界误差。这个误差应明示，不能称为严格精确。

---

## 03 分布式汇总与迟到数据

先按规范化 IP 分区，使同一个 IP 的全部计数归同一分区。每分区得到完整窗口计数及局部 TopK 后，按相同窗口/水位汇总，可合并局部候选再选全局 TopK；并列名次使用固定规则。若先按机器或文件块分区，同 IP 分散在多处，直接合并各机器 TopK 可能漏掉全球高频项，必须先按 IP 汇总。

事件时间窗口使用时间戳和 watermark 判断进展；watermark 是对迟到的工程判断，不是保证未来绝无旧事件。定义允许迟到、迟到更新或侧输出规则，结果带窗口与版本，接收方能幂等更新。空闲分区可能拖住全局进度，需按流处理实现设置空闲策略与监控。

---

## 04 内存预算和近似方案

状态量与活跃 IP 数、窗口粒度和事件量有关。内存不足可用分区状态后端或外存；允许误差时评估 Count-Min Sketch、Space-Saving 等频次估计和候选维护方案，但还要处理窗口过期和误差界，不能简单对只增不减的数据结构设一个全局 TTL。HyperLogLog 估不同 IP 的数量，不提供每个 IP 的频次，不能用它直接算 TopK。

还需规范 IPv4/IPv6 表示、排除格式错误，并防重试日志重复计数。监控吞吐、积压、水位延迟、状态大小及与抽样精确结果的差异。口述：“先定窗口和误差语义，再按 IP 聚合、维护到期状态，最后做同水位 TopK；数据分区和候选截断顺序决定结果是否正确。”
