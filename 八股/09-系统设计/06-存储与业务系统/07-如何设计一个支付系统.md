# 07 如何设计一个支付系统？

## 01 核心回答

**边界：**电商支付后端，不存信用卡信息，接入第三方 PSP（Stripe 类）；支持买家付款（pay-in）和卖家结算（pay-out）；高可靠、可审计、可对账。

**核心模块：****Payment Service**（接收支付请求、维护支付状态机、协调流程）、**PSP Adapter**（对接外部渠道）、**Ledger**（账务记账）、**Wallet**（卖家余额）、**Webhook Handler**（PSP 异步回调）、**Reconciliation Service**（每日对账）。

**核心流程：**前端调 Payment Service → 创建 payment event 和 payment order → 调 PSP 注册支付（带全局唯一 payment_order_id 作幂等键）→ PSP 返回 token → 前端拉起 hosted payment page → PSP redirect 用于界面导航，后端根据已验签 webhook 或主动查单确认结果，再按状态机更新 order → 成功则更新 wallet 和 ledger。

**三大关键难点：**① **幂等性**——防重复扣款：同一次支付尝试复用同一 idempotency key；新尝试与退款使用各自明确的操作键，服务端唯一约束/幂等表只处理一次，调 PSP 时也传幂等键；② **一致性和失败恢复**——不假设天然强一致：支付状态设计成明确状态机（pending/success/failed/unknown）+ retry queue + dead letter queue，最终不一致靠 reconciliation（拿 PSP/银行结算结果与内部 ledger 逐笔对账）；③ **账务正确性**——用 **double-entry ledger 复式记账**：钱包余额是业务视图，ledger 才是财务真相来源，每笔资金流转有借贷对应关系。

**口述重点：**支付系统最关注的不是单纯高并发，而是 correctness——不能重复扣款、不能丢单、账必须对得上。回答结构：先需求边界 → 再高层架构和核心流程 → 重点展开幂等、失败恢复、对账和账务系统。

## 02 先区分支付订单与支付尝试

商户订单可能经历多次支付尝试，需分别记录内部 paymentId/attemptId、PSP 对象 ID、金额、币种、请求幂等键和当前状态。一次超时不能立即换新键重扣，应先查原 PSP 对象；用户主动更换支付方式或重新尝试也要防止旧尝试随后成功造成两次收款。

前端跳转页和客户端上报不具备支付成功权威性。Webhook 验签使用提供方要求的原始载荷，持久化事件后快速响应，再异步处理；重复和乱序回调都可能发生，唯一事件 ID、支付状态版本和主动查单共同防止状态回退。

## 03 账务与外部一致性的边界

在内部事务中绑定已确认支付状态与记账事件，账务分录用稳定业务流水防重。金额使用按币种规则的整数最小单位或精确十进制定点，不用二进制浮点，也不能假设所有币种都固定两位小数。借贷平衡是必要检查，不代表交易一定没重复或账户一定选对，还需完整流水和业务约束。

退款、拒付、手续费和结算各是新事件，不能只把原记录覆盖掉；钱包可用余额还可能与在途、冻结或已结算余额不同。对账区分商户交易、PSP 处理与结算时间水位，发现差异后按查单、补记或人工处理推进，不能自动把所有差异当退款。

## 04 口述与故障推演

“支付设计优先防重复扣款和保留未知结果。一次尝试有稳定键与外部流水，回调验签、去重且允许乱序，前端跳转不定成功；内部状态和账务可靠衔接，最后按交易与结算流水对账。”最应演练的是 PSP 已成功但本地超时、回调先于同步响应、回调重复和退款晚到。
