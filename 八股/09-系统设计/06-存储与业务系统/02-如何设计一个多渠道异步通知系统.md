# 02 如何设计一个多渠道异步通知系统？

## 01 核心回答

**回答（目标 → 架构 → 取舍 → 治理）：**

**① 目标：**多渠道异步通知平台（iOS/Android Push + SMS + Email），软实时、支持用户退订，量级日千万级——目标是受理记录可恢复、投递可追踪，明确不同渠道的可达性和时效边界。

**② 架构主干：**API 层 → 通知编排层 → 分渠道消息队列 → worker 层 → 第三方通道层（APNS/FCM/Twilio/SendGrid）。初版有单点瓶颈，改进版引入多通知服务器 + 缓存/DB 拆分 + 按渠道队列 + workers。

**③ 核心链路：**业务服务调通知 API → 通知服务做校验和模板渲染 → 写队列 → worker 消费 → 调第三方通道。核心价值是**解耦和隔离**——某渠道故障不拖垮全链路。

**④ 关键取舍：**MQ 削峰解耦；语义上**至少一次投递**（通知日志持久化 + 失败重试 + 事件 ID 去重），靠幂等控制重复，接受「至少一次」而非幻想「绝对恰好一次」；按渠道隔离防单通道故障扩散。

**⑤ 治理闭环：**模板管理、用户通知偏好、限频、认证安全、队列监控、打开/点击事件追踪、队列积压告警。

---

## 02 状态模型要区分受理 投递和阅读

持久化 notificationId、业务事件、接收对象、渠道、模板版本、有效期和幂等键；通知任务与待发布事件同事务保存，再按渠道分发。一次业务事件可产生多个 deliveryId，分别记录排队、发送中、渠道接受、失败/过期；不要用一个 success 同时代表提交渠道、设备收到和用户已读。

FCM 返回消息 ID 表示接受投递，不保证已到设备；设备离线、过期或折叠消息可能使最终不可达。短信/邮件同样有通道状态和回执边界，无法承诺任何通知都必然被人看到。

## 03 重试与多渠道回退的成本

临时限额和网络故障退避重试，失效地址/设备 token 需要停止无效重试并更新状态。超时后渠道可能已发送，重试和备用渠道会造成重复；优先使用提供方幂等键或状态查询，记录每次 attempt，不能把内部去重当作外部只发一次的证明。

用户偏好、免打扰和退订应在入队与实际发送时按业务规则核对，防止很久前排队的营销消息越过最新设置。过期验证码不应继续补发。若需要跨渠道升级，明确等待多久、何种状态才触发以及是否允许多渠道同时送达。

口述：“通知平台以可恢复受理、分渠道投递状态和有限重试为主，渠道接受、设备送达与已读分开。偏好和有效期在发送前复核，回退策略控制重复与成本，死信有处理闭环。”
