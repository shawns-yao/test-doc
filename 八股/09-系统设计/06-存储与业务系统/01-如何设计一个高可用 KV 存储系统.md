# 01 如何设计一个高可用 KV 存储系统？

## 01 核心回答

**① 分片（一致性哈希）：**哈希空间看成一个环（0 到 2^32-1），节点和 key 都映射到环上，key 顺时针找到第一个节点作为归属；扩缩容只迁移受影响区间数据。用**虚拟节点**（每台物理机映射多个点到环上）让键空间更均匀；单个热点 key 不会被虚拟节点自动拆散；可加**加权虚拟节点**（高配机器分配更多 vnode）。

**② 数据模型与复制：**key → value + version + timestamp；每个 key 按副本偏好列表选择 N 个存储副本；协调请求的节点不等于 Raft 的唯一写 Leader。

**③ 读写路径：**写——客户端到协调节点，并行写 N 副本，达到 **W 个成功即返回**；读——协调节点读 N 副本中的 **R 个**，按版本关系检测冲突并依据已定义合并规则返回结果。固定副本集合下 `R + W > N` 保证相应读写 quorum 相交，但单靠相交不能推出线性一致。

**④ 故障处理：**副本宕机时先写可用副本（**hinted handoff**），恢复后补数据；后台修复用 **anti-entropy**（如 Merkle tree）+ **read repair**。

**⑤ 可用性与一致性取舍：**追求强一致（偏 CP）——采用适当的共识复制与读协议，失去所需 quorum 时限制操作；单靠“多数派写”不充分；追求高可用（偏 AP）——优先接受读写、允许短暂不一致后续异步收敛。场景决策：交易、余额、库存扣减优先一致性；缓存、Feed、推荐、计数优先可用性和低延迟。

**口述重点：**一致性哈希分片 + N 副本复制（写 W 确认、读 R 合并）+ read repair 收敛；一致性与可用性按业务分级——核心是把取舍显式化，并用监控和修复机制兜底。

---

## 02 先选择语义路线 再选择复制实现

原回答更接近 Dynamo 风格的无主/可调 quorum 方案，不应同时不加区分地称为“主副本强一致”。如果要求单 key 的线性一致读写，可将每分片建成 Raft 等共识组，使用符合协议的读路径；若要求分区时尽量接受写入，则需要版本、冲突检测与业务合并。

R+W>N 是固定 N 个副本中集合相交的数学条件，并非提高一点概率。但并发写、未完成写、版本选择、成员变更和 sloppy quorum 都可能让“读到最新”的推论不成立；用物理时间戳选最大值也会受时钟偏斜影响，可能覆盖合法更新。

---

## 03 存储 恢复与扩容的完整链路

单节点需要 WAL、内存索引/表、持久数据文件与崩溃恢复；LSM 方案还要管理刷盘、compaction 和写放大。副本复制解决节点故障，快照与备份解决误删/逻辑损坏，两者不能互相替代。

扩容需更新路由版本、复制迁移范围、追平增量再切所有权，处理迁移中重复请求和旧路由；限速迁移防止挤占前台 I/O。虚拟节点改善分布但不解决明星 key，要用读缓存、拆业务粒度或限流。

删除不能只清本地值，否则旧副本修复可能复活数据；需墓碑与安全回收窗口。Hinted handoff 是临时恢复手段，反熵修复还要有预算、进度与告警，不能假设“最终”一定发生。

---

## 04 口述重点

“我先确定一致性、操作集合、数据量和 RPO/RTO。强一致分片用共识及正确读协议；高可用无主方案用明确冲突语义与修复。再补单机持久化、路由迁移、墓碑、备份和热点治理，R+W>N 只是一个条件，不是整个正确性证明。”
