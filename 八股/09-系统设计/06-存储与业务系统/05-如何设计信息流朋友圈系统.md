# 05 如何设计信息流/朋友圈系统？

## 01 核心回答

**目标：**用户发动态后粉丝较快看到、首页打开快、高峰期不崩、允许几秒内慢慢同步但不能乱。

**发帖流程（写扩散）：**发帖先落帖子库 → 生成分发任务入 MQ → 推送工人查粉丝列表 → 把帖子编号写进粉丝首页列表 → 粉丝打开首页直接看到。「首页列表只存编号」省内存速度快。

**读扩散与混合：**大 V 发一条要写几百万粉丝首页、写入压力太大——大 V 用读扩散（发帖不全量分发，粉丝打开首页时临时拉取合并）。最终**普通用户写扩散（读快）、大 V 读扩散（写稳）**混合模式。

**稳定性：**幂等（同一条分发任务重复执行只写一次）、重试、死信队列（多次失败先隔离）、监控（队列堆积、首页延迟、分发成功率）。

**权限控制：**「发布时控制可分发范围，读取时再做一次权限校验」双层控制——关系 + 可见范围 + 用户配置联合判断，客户端缓存仅作展示优化，服务端每次返回内容及媒体访问时仍须校验当前权限。

**点赞链路：**独立存储、缓存优先——Redis Set 可存点赞用户并计数；大集合避免直接 `SMEMBERS` 全量返回，列表需有界分页或单独索引；好友可见用好友集合与点赞集合做交集判断；幂等（DB 用 (user_id, post_id) 联合唯一键，Redis Set 天然去重）。

**口述重点：**朋友圈主链路是「发帖异步分发到时间线」，点赞链路是「独立存储、缓存优先、关系裁剪可见性、幂等防重」。

---

## 02 混合扩散由读写成本决定

写扩散成本约随发帖量乘目标粉丝数增长，读扩散成本随每次读取需要合并的作者数增长。是否将大 V 改读扩散，不应只看粉丝数，还要看粉丝活跃比例、发帖频率、允许分发延迟和缓存命中。长期不活跃用户可不预建完整时间线，登录时重建近期候选。

帖子正文与媒体存一份，时间线存 postId 和排序所需信息；帖子入库与分发任务通过 outbox/可靠事件衔接。分发按分片批次记录进度，重复写由 (userId, postId) 或等价结构幂等处理，Worker 失败可续跑，不必从百万粉丝头部重来。

### 发布受理、个人相册和红点如何衔接

客户端可先把草稿和上传任务存本地，展示“发布中”并允许断网续传；只有服务端持久化受理后才展示相应成功状态，本地缓存不是发布成功证明。图片/视频先进入上传与处理流程，帖子保存媒体对象引用，内容可见时再按权限通过 CDN 分发，不能把“直接上传 CDN”当完整存储链路。

好友时间线之外，个人相册或历史发布页还需要按作者查询的索引，例如 `(authorId, publishedAt, postId)`，先分页取作者的 postId，再批量读取正文和媒体引用，无须扫描所有人的发布表。它可以是同库组合索引，也可以是异步维护的独立视图；后一种必须用可靠事件更新，定义延迟、删除和重建策略，不能无恢复记录地顺序双写两张表。

红点只提示“有新的可见内容”，可保存用户上次确认的时间线水位，与最新可见内容水位比较；用户打开并确认后按产品规则推进。权限收窄、删除、重复分发和多端确认不能把红点当作精确未读条数，展示前仍要按服务端权限过滤。媒体的处理和访问控制见下方关联的独立存储题。

## 03 权限变更 删除与分页

仅发布时过滤不够，拉黑、好友解除、可见范围收窄和删除都会改变权限。读路径在服务端重新核验，缓存与媒体签名链接也要有撤销或短期失效策略；不能让客户端决定是否有权查看。删除用可传播的状态/墓碑，并处理迟到分发任务，避免内容复活。

时间线使用稳定排序字段和 tie-breaker 游标，排序模型更新可能使候选漂移，需要产品定义分页快照或去重规则。点赞计数可异步汇总，但用户自己的点赞状态和重复操作需明确幂等；大 Set 全量列举与跨槽大集合交集会形成热点。

口述：“我按作者写成本和用户读成本选择混合扩散，分发可重试可续跑；服务端读时复核权限，删除和关系变化能使缓存失效，时间线分页与点赞各自明确一致性窗口。”
