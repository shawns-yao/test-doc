# 09 分布式 ID：UUID、号段、Snowflake 怎么选？

## 01 核心回答

**UUID**

无中心、生成简单、全局唯一性好；通常为 128 位，可用二进制而非字符串存储；随机 v4 的局部性较差，v7 带时间排序结构，不能笼统说 UUID 都无序。适用：去中心化生成、跨系统标识等；是否适合高流量数据库主键取决于版本和存储布局。

**号段模式（Segment/Leaf）**

从 DB 一次批量申请一段 ID（如 10000 个），本地内存递增发放——趋势递增、性能高、实现简单；依赖号段服务和 DB，要处理预取和高可用。适用：业务主键、订单号等「希望有序且高性能」场景。

**Snowflake**

时间戳 + 机器 ID + 序列号（常见 41+10+12）——本地生成、趋势递增、吞吐高、长度固定；难点是时钟回拨、机器 ID 分配、跨机房部署。解法：持久化 lastTimestamp 服务重启时先校验，或把时间上报 ZK 校验管理。适用：高并发在线系统主流方案。

**口述重点：**要无依赖选 UUID；要数据库友好选号段；要高并发低延迟通常选 Snowflake，但要重点治理时钟回拨和机器号冲突。

---

## 02 唯一 趋势有序 全局单调是不同目标

UUID v4 用随机空间降低碰撞概率，不是数学上永不碰撞；RFC 9562 定义的 v7 把 Unix 毫秒时间放在高位，改善按时间的排序与索引局部性，但跨机器时钟、同毫秒生成仍不能自动得到业务全序。

号段内可递增，多台机器持有不同号段时，先产生的 ID 可能比后产生的大，因此通常不是全局按生成时刻单调。Snowflake 的时间戳+节点+序列同样主要提供可管理的唯一与趋势有序，不能用它替代聊天会话序号或事务提交顺序。

## 03 故障边界怎样验证

号段申请需原子分配，服务重启丢掉未用尾号可以接受，但不能重复发放；预取缓冲提升数据库短时故障耐受，故障时间超过可用号段仍须停止或切换有证明的方案。业务一般不该要求 ID 连续无缺口。

Snowflake 同一节点每时间片序列耗尽后要等待/拒绝，机器号需唯一租约或稳定分配；时钟回拨可拒绝、等待或采用受控逻辑时间，任何方式都要防机器号重用和旧实例复活。仅持久化 lastTimestamp 若写入频率、崩溃窗口和恢复规则没说明，不足以证明安全。

口述：“我先问唯一性范围、排序要求、可用性与存储成本。UUID v7、号段和 Snowflake 都可以评估，但都要解释故障和重复风险；可排序 ID 不是业务顺序证明，ID 可预测也不代表有访问权限。”
