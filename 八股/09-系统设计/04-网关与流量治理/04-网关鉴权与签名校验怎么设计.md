# 04 网关鉴权与签名校验怎么设计？

## 01 核心回答

先验证凭据与身份（如访问令牌/API Key；JWT 是格式、OAuth2 是授权框架，登录身份常结合 OIDC），再做**权限判定**（资源级 ACL/RBAC），最后校验**重放防护**（时间戳 + nonce + 签名）。敏感接口要有细粒度审计日志，确保「谁在何时访问了什么资源」可追踪。

**面试追问：**如果 token 被盗用，网关层有哪些快速止血手段？

---

## 02 从信任来源开始验证

JWT 不是简单 Base64 解码后信任 claims。验证时应限制允许算法与可信发行方，使用可信 key 来源验签，检查 issuer、audience、exp/nbf 等条件并采用有限时钟容差。不能由 token 自己的任意 URL 决定去哪里取 key，kid 也只是可信密钥集合里的索引。令牌必须通过 TLS 传输并避免进入访问日志。

OAuth2 规定授权令牌相关流程，本身不是“用户登录协议”；OIDC 才在其上定义身份层。API Key 常识别调用应用，并不总能识别最终用户。网关验完凭据后仍要确定主体、租户、scope，再让业务服务检查具体资源归属和动作权限。

---

## 03 请求签名解决完整性 重放要另管

先定义稳定的签名输入：方法、路径/查询的规范化、必要头、正文摘要和时间参数。双方必须对重复参数、大小写、编码、空白、代理改写和正文原始字节有一致约定，避免一个“看起来一样”的请求两端计算不同。不要自行用随意字符串拼接代替明确签名规范。

签名能证明签名覆盖的内容未被篡改，不天然阻止原请求再次提交。时间窗只能缩短重放范围，nonce 需按调用身份在窗口内原子判重；对合法网络重试，还要区分认证防重放和业务幂等，设计如何重新签名但复用同一业务请求 ID。

---

## 04 密钥轮换与被盗后的处置

保留 key ID 与有效期，在受控重叠窗口支持新旧密钥，定期轮换；撤销时明确缓存刷新时限。访问令牌短期有效、撤销名单或 introspection 是不同取舍，不能承诺纯离线 JWT 自动立刻撤销。未知发行方、校验失败或不可确认权限时按风险拒绝，不能默认放行。

日志只留必要身份、动作、对象标识、决策原因与 trace，避免写完整 token/secret。口述：“我先界定可信凭据和 key 来源，再做验签与 claims 检查，业务端保留对象授权；请求签名规范化、nonce 防重放和业务幂等分别实现，最后补轮换、撤销与审计。”
