# 05 引入 Mesh 后排障方式有什么变化？

## 01 核心回答

**三层联动：**先看应用的业务错误、线程池和下游耗时，再看 Sidecar 的访问日志、集群连接、路由命中、重试和熔断计数，最后确认控制面是否成功下发配置、证书和服务发现信息。很多问题不是代码 bug，而是治理配置或策略冲突。

**定位顺序：**用 TraceId 对齐客户端、代理和服务端时间线；在受控测试中比较路径差异，不以关闭生产鉴权或绕过安全策略作为常规排查手段；检查配置版本、目标子集、端口协议、mTLS 状态和资源水位。若只有部分实例异常，优先对比实例标签、代理版本和节点网络。

**工具与预防：**保留配置快照、代理 debug 日志和关键指标，避免长期打开高开销日志；配置发布使用校验、灰度和回滚，防止一条错误策略扩散到整个命名空间。

## 02 从一次失败请求查实际数据面

先定位请求在哪一跳失败：源应用、源代理、网络、目标代理、目标应用。代理生成的 503 与业务服务返回的 503 应区分，结合访问日志的响应细节、目标集群/实例、连接错误和重试次数。没有业务日志时，可能请求在目标代理鉴权阶段已被拒绝。

检查代理实际 listener、route、cluster、endpoint、证书和配置同步状态，而不只看控制面 YAML。控制面期望版本与部分代理加载版本不一致，可能解释“同一请求只有某些实例失败”；配置 NACK、错误 subset 标签、协议识别与 TLS 模式不匹配是常见候选。

## 03 把控制面故障与数据面故障分开

控制面暂时失联时已有代理可能继续用最后配置，但新服务发现、策略变更或证书轮换会受影响；数据面代理 CPU 限额、连接耗尽则可直接拖慢当前请求。Ambient 模式还应沿 ztunnel 与 waypoint 路径定位，不能套用所有 Sidecar 检查项。

保留小范围复现、时间线与配置快照，调高日志要限时且防敏感信息泄漏。口述：“引入 Mesh 后我多查代理实际状态与控制面下发，先确定响应由谁生成，再核对身份、路由和资源，不只盯应用栈。”
