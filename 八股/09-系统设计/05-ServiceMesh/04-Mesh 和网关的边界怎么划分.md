# 04 Mesh 和网关的边界怎么划分？

## 01 核心回答

**网关：**主要处理南北向流量，即外部客户端到内部服务，承担 TLS 终止、认证鉴权、WAF、API 配额、协议转换、路由聚合和开放接口审计。

**Mesh：**主要处理东西向流量，即服务之间的调用，关注服务发现、负载均衡、超时重试、熔断、mTLS、服务级授权和链路遥测。两者可以同时存在，但策略维度要明确，避免重复限流和重试放大。

**边界原则：**用户身份、外部协议和产品级聚合逻辑放网关；服务身份、内部通信策略和实例级治理放 Mesh；领域业务规则不能因为方便而下沉到代理层。

**面试追问：**同一条流量在网关和 Mesh 都限流会有什么问题？

---

## 02 不是两条互不相交的网络线

南北向和东西向是常见职责划分，不是产品能力硬边界：Istio 自身也有 ingress/egress gateway，API 网关也可用于内部 API。应按调用方身份、策略归属和故障域决定放置位置，而不是看到“网关”就认定在 Mesh 外面。

用户登录、应用 key、套餐配额和公开 API 文档适合入口治理；内部工作负载身份、服务连接策略适合 Mesh；订单归属、库存状态、账户权限等业务规则仍由领域服务判定。入口认证通过后传播的用户身份也必须可信，不能任由下游相信外部可伪造的 Header。

---

## 03 一条调用链只分配一份总预算

网关、服务 SDK、Sidecar 都可能配置超时、重试和限流。需要明确谁做重试、各阶段能用多少剩余时间，以及重试是否计入配额；否则三层各尝试三次可能放大到底层 27 次调用。业务返回的永久失败也不应被代理当成传输抖动重试。

外部 TLS 在入口终止后，内部仍可重新建立 mTLS；两段认证的主体和信任域不同。口述：“按用户/API治理与工作负载通信治理分工，但实际拓扑可组合。关键是身份能验证、预算不重复、领域规则留在业务层。”

---

## 04 双层限流怎样避免重复扣配额和误拒

如果网关与 Sidecar 为同一外部请求调用同一个全局配额服务，却没有区分计费点，可能重复扣除用户的一次额度。即使两个计数器彼此独立，窗口长度、时钟边界、租户识别或突发容量不同，也可能让入口已接纳的请求在下游被拒，形成额外排队和无效重试；这不是“配两个限流器就更安全”。

可以让网关按用户或 API 套餐控制业务请求预算，Mesh 按服务/实例的并发、连接和处理能力做资源保护。两层限制解决不同问题，计数范围与拒绝原因应可观测；若共享一份配额，明确唯一扣费点及受信的上下文传递。下游拒绝仍可能是正确保护，不应为了入口承诺而绕过。重试和内部 fan-out 是业务请求数还是实际 attempt 消耗，需要事先定义并限制总预算。
