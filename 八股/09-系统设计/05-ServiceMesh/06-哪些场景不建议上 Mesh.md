# 06 哪些场景不建议上 Mesh？

## 01 核心回答

**不建议场景：**服务规模小、调用关系简单、治理诉求弱、延迟预算极紧、资源预算有限，或团队没有控制面、证书、代理和配置治理能力时，不建议直接上 Mesh。它会增加代理资源、网络跳转、版本升级和排障成本。

**替代路径：**少量服务可以先使用成熟 RPC/HTTP 客户端的超时、重试、熔断和指标能力；外部流量统一交给网关；等多语言、多集群和统一安全治理成为刚需后，再按命名空间或核心链路渐进引入 Mesh。

**引入前门槛：**先完成容量压测、故障演练、证书轮换、配置回滚和观测接入，明确代理开销与收益，再决定是否全量部署。

**面试追问：**如果不引入 Mesh，如何先做「轻量治理」过渡？

## 02 用需求缺口而不是服务数量决策

没有统一证书身份、跨语言策略和细粒度流量治理需求时，成熟客户端加网关可能已经满足目标。极低延迟、特殊协议、资源非常紧张或已有成熟统一 SDK 的系统，应先验证新增代理的收益；“服务超过多少个就必须上 Mesh”没有通用阈值。

团队若不能负责证书信任、控制面升级、代理版本、配置冲突和应急恢复，Mesh 可能把分散小问题变成平台级事故。也不能因为 Sidecar 开销大就断定全部 Mesh 不适用，ambient 等模式改变资源分摊，但仍有节点级代理与 L7 waypoint 的成本和故障域。

## 03 轻量过渡和退出门槛

先统一 deadline、有限重试、连接池、幂等契约与 trace 上下文；入口做认证和配额，内部通过已有框架维护发现与健康。记录仍无法经济解决的缺口，再选择代表性服务做 Mesh 试点。

试点定义成功条件：安全覆盖、策略变更速度或排障能力确有提升，且 P99、资源和恢复时间在预算内。证书轮换、控制面失联、错误路由和代理重启演练失败时先停止扩大；移除 Mesh 也要确保替代认证、路由和监控已就绪。

口述：“我不上 Mesh 的理由是当前需求用较简单方案已满足，或平台能力和成本尚不支持。先补基础治理，等可量化缺口出现，再做有回退路径的试点。”
