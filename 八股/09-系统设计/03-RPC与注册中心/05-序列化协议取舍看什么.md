# 05 序列化协议取舍看什么？

## 01 核心回答

**评估维度：**看**编码解码性能、消息体大小、跨语言能力、Schema 演进、可调试性、安全边界**和生态支持。协议选型要结合网络带宽、CPU、延迟目标和灰度发布方式，不能只比较单次 benchmark。

**常见协议：**Protobuf 采用字段编号和二进制编码，体积小、性能高、跨语言强，适合稳定的内部 RPC；JSON 可读性和调试体验好，适合开放 API，但体积和解析成本更高；Hessian 或 Java 原生序列化接入简单，却要重点治理版本兼容、反序列化类型白名单和不可信输入风险。

**兼容演进：**对 Protobuf 等编号协议，新增字段用新编号并核对 presence/默认值语义；旧客户端如何保留或忽略未知字段取决于协议和转换路径；不要复用已删除的字段编号，必要时标记 reserved。枚举新增值、字段类型变化和必填语义都要评估旧客户端行为，灰度期间保证新旧版本可以互相读写。

**取舍：**可读性优先的管理接口可以使用 JSON，高吞吐内网链路更适合 Protobuf；涉及外部合作方时要提供版本、文档和兼容测试。无论选择何种协议，都要限制消息大小、解析深度和超时，避免恶意或异常消息耗尽资源。

**面试追问：**线上灰度升级时，如何做字段向前/向后兼容？为什么不能随意复用删除过的字段编号？

---

## 02 Schema 兼容不等于业务兼容

协议能解析并不意味着业务能接受。例如新增“退款中”枚举，旧代码可能把未知值当成功；数值默认 0 也可能混淆“未提供”和“真的为 0”。Proto3 的 presence、optional 和默认值需要按字段语义选择；删除字段保留 reserved 编号，不能因为名称换了就复用 wire tag。

Protobuf 到 JSON 再转回的网关可能改变未知字段、整数或枚举表现；JavaScript 对超过安全整数范围的数值也需明确字符串等表示。兼容测试应覆盖新客户端/旧服务端和旧客户端/新服务端，两方向都测。

---

## 03 性能与安全的共同边界

用真实数据测编码 CPU、分配、压缩后大小、P99 和网关转换成本。文本并不一定是主要开销，二进制也不会自动消除大消息或恶意嵌套；限制字节长度、递归深度、集合数量、解压后体积和允许的类型。

避免对不可信输入开放任意对象反序列化。口述：“我把 wire 兼容、业务兼容、语言表示和安全限制分开，性能测真实载荷；字段编号、未知枚举和缺省语义是灰度升级时重点验证项。”
