# 02 RPC 一次调用的完整链路是什么？

## 01 核心回答

**完整链路：**调用方先通过**代理拦截**本地接口，序列化请求并做**服务发现、负载均衡**，再经网络传输到服务端；服务端反序列化后执行业务逻辑并返回结果，客户端再做反序列化、超时控制和重试决策。

**Dubbo 调用底层（五层）：**① **动态代理**——面向接口编程，底层代理对象拦截方法调用；② **负载均衡**——random、consistent hash 等选一台机器；③ 协议层——按所用版本选择 dubbo、Triple 等，不混淆历史协议支持与当前能力；④ **网络通信**——常基于 Netty/Mina 做 NIO 异步通信；⑤ **序列化**——把请求编码成二进制发出。服务端先网络收包与协议帧解码，再反序列化、鉴权和调度到本地服务。

**Dubbo 集群容错策略：**`failover` 失败自动切换重试（读操作）；`failfast` 失败立刻返回（非幂等写）；`failsafe` 失败忽略（日志类）；`failback` 失败后台重发（消息通知）；`forking` 并行调用多个 provider 一个成功即返回（换时延耗资源）。

**如何设计一个 RPC 框架（最小闭环）：**动态代理（本地接口代理成远程调用）+ 注册中心（服务注册与发现）+ 负载均衡（从多个 provider 选路）+ 协议与序列化（请求格式与编解码）+ 网络通信框架（Netty 高并发连接）。

**面试追问：**链路里最常见的性能瓶颈在哪三处，如何快速定位？

---

## 02 按一次调用的时间线展开

调用开始先确定方法契约、deadline、认证和追踪上下文；客户端从已缓存/订阅的服务发现结果选择可用实例，取得连接，编码发送。注册中心通常不转发每个请求，不必在每次调用时同步查询它。

服务端经历接收缓冲、拆帧、长度/类型校验、反序列化、认证授权、工作队列与业务执行，再编码响应。客户端用请求/stream 身份匹配 Future，处理状态与响应。并非所有框架都必须动态代理，也可使用生成 stub 或显式客户端。

## 03 最危险的是结果不确定

连接断开或超时可能发生在发送前、服务执行中，或者服务已经提交但响应丢失。三者对重试安全性不同，传输错误不是业务回滚证明。RPC 最小实现还需解决帧边界、请求关联、大小限制、背压、连接生命周期、错误语义及兼容，而不只是“代理 + Netty”。

Failover/forking 可能增加重复执行，failsafe 忽略异常也不等于任务真的完成；应按方法语义选择容错策略。口述：“RPC 把本地调用样式映射到远程协议，但保留了网络失败和未知结果。我按发现、连接、编解码、排队、业务、响应逐层看，并把 deadline 和幂等贯穿始终。”

### SPI 扩展如何接入调用链

Dubbo SPI 把协议、负载均衡、过滤器等扩展点定义为接口，再按扩展名称与配置装配具体实现；自适应扩展可依据调用 URL 等参数选择实现。它解决可替换与组合，不意味着可以在生产随意加载未知代码。需要验证默认扩展、依赖注入、扩展顺序与所用 Dubbo 版本，防止替换后超时、鉴权或序列化语义变化。和 Java 原生 ServiceLoader 相比，不能只说“都是反射”，应解释 Dubbo 增加了命名选择、适配与包装等机制。

依据：[Dubbo SPI 定义与用法](https://dubbo.apache.org/en/overview/mannual/java-sdk/reference-manual/spi/description/)。

### 追问中怎样定位三类常见瓶颈

不把固定“三处”当作所有系统的定律，可先沿三个证据方向排查：编解码/计算看CPU采样、分配率、消息大小与压缩成本；排队/资源池看请求入队到开始执行的等待、线程活跃数、队列年龄与连接获取时间；网络/下游看建连、TLS、RTT/重传和服务端业务span。用同一次attempt的分段耗时对齐，才能区分“序列化慢”“在池里等”和“远端处理慢”，不要只从总耗时猜组件。
