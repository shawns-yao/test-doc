# 04 2PC、3PC、TCC、Saga 怎么选？

## 01 核心回答

**2PC / XA**

事务管理器先询问每个参与方能否执行；第一阶段预留资源，第二阶段统一提交或回滚。提供原子提交协议，但隔离性仍取决于参与者；准备阶段资源持有与故障恢复可能限制吞吐，需按负载评估。

**3PC**

引入额外阶段和超时，在其网络/故障假设下改善阻塞，不能无条件解决任意网络分区。

**TCC**

Try 检测资源并预留；Confirm 真正执行；Cancel 失败补偿回滚。通过业务预留与确认/取消协调结果，隔离和可见性需业务保证，侵入大、恢复逻辑复杂——适合资金类、强一致、每环节执行时间短的场景。

**Saga**

适合长流程**最终一致**，各步骤带补偿动作。

**本地消息表**

A 系统本地事务同时写业务数据和消息表，后台线程轮询再调 B 系统，B 必须幂等；缺点：高并发下消息表成为数据库压力点。

**可靠消息最终一致**

以 RocketMQ 事务消息为例，A 先发 half message，本地事务成功再发 confirm/commit；confirm 丢了 MQ 通过**回查**确认本地事务状态；B 消费需幂等、失败重试补偿。适合订单、库存、履约这类允许最终一致的链路。

可靠消息的故障顺序要讲完整：先发送暂不对消费者可见的 half message，收到 Broker 按所配持久化/复制语义返回的成功确认后，才启动本地业务事务。半消息发送明确失败或未拿到成功确认时，本轮不能先执行业务再假设消息以后一定补上；超时可能只是确认丢失，需要保留事务标识并处理后续回查。发送确认本身也不能替代对 Broker 刷盘、复制和故障模型的配置检查。

本地事务明确提交则发 commit，明确回滚则发 rollback；通知丢失、进程崩溃或结果暂不明时，由回查读取与业务事务同库提交的权威事务记录决定结果，未决返回 unknown，不能用进程内变量或“暂时查不到”就猜提交成功。业务执行、回查和重试应共用稳定事务标识并防并发竞态；回查受次数、时间等版本配置约束，超限仍需告警与对账。该协议协调的是本地事务与消息可见性，不自动提交下游消费事务。

**Seata 框架理解：**`TC` 协调器维护全局事务状态；`TM` 事务发起者，负责开始/提交/回滚全局事务；`RM` 资源管理器管理各分支事务并向 TC 汇报。流程：TM 向 TC 申请全局事务 ID → 各分支注册 → 成功统一提交，失败由 TC 驱动各分支回滚。

**选型：**核心链路先考虑缩小为本地事务；跨系统再按资源能力、隔离要求与补偿成本选择 TCC/XA 等；大部分互联网业务更常用「可靠消息 + 幂等 + 补偿 + 对账」这套最终一致方案。

**面试追问：**为什么很多互联网业务最终选 Saga/Outbox 而不是 2PC？

## 02 几种方案解决的层面并不相同

2PC 是原子提交协议：参与者准备后不能随意自行决定结局，需要协调器持久化决定和恢复路径；参与者的锁、日志与隔离实现决定实际效果。它不是所有故障下都立刻恢复可用，也不能替参与资源实现任意业务不变量。

TCC 把预留能力暴露为业务接口。Try 占资源，Confirm 确认，Cancel 释放；必须处理重复 Confirm/Cancel、Try 未成功却收到 Cancel（空回滚）、Cancel 已完成后迟到 Try（悬挂）。它并不自动等于全局可串行化，外界是否看到中间状态要自己约束。

Saga 将长流程分成已提交的本地事务与补偿，其他流程可能看到中间结果，通常不提供传统事务的全局隔离。补偿需要业务可行，若步骤不可逆，应推迟它或采用先预约、后确认的设计。

## 03 用四个问题做选择

先问能否同库短事务；再问每个资源是否支持 XA 或业务预留；再问中间态是否可见、操作是否可补偿；最后问最大事务时长、故障恢复与人工处理成本。Outbox/事务消息解决可靠事件，并不自动把消费端 DB 纳入发送端事务。

口述：“短事务能在一个库完成就不先分布式化；需要原子提交且资源支持时评估 XA，需要业务预留时评估 TCC；长流程且可补偿可用 Saga。选择依据是语义和故障模型，不是把 3PC 当 2PC 的无条件升级。”
