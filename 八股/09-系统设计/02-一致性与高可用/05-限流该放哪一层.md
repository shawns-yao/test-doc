# 05 限流该放哪一层？

## 01 核心回答

**核心原则：**限流应当分层设置。越靠近流量入口，越能以较低成本挡住无效流量；越靠近具体资源，越能按照真实容量精确保护。生产系统通常不是只在某一层限流，而是形成“边缘层粗筛、网关层统一控制、服务层精细保护、资源层兜底”的多级防线。

边缘层

CDN、WAF 或负载均衡器按 IP、地域和连接数做粗粒度限制，优先阻断攻击流量和异常爬虫，避免请求进入内部网络。

网关层

按用户、租户、应用、接口或令牌维度做全局限流，适合控制开放接口配额和系统总入口流量。网关知道身份与路由，但通常不了解服务内部线程池、数据库连接池等真实压力。

服务层

针对热点方法、核心业务和特定下游设置独立阈值。例如订单服务调用库存服务时，根据库存服务的承载能力限制并发，防止一个依赖变慢拖垮整个调用链。

资源层

线程池有界队列、数据库连接池、消息队列消费速率和信号量属于最后一道容量保护。即使上游规则失效，也不能允许请求无限堆积。

**算法选择：**固定窗口实现简单但存在窗口边界突刺；滑动窗口统计更准确但存储和计算成本较高；漏桶按固定速率流出，适合严格整形；令牌桶允许一定突发流量，是业务接口最常见的选择。单机限流可用 Guava RateLimiter、Sentinel 等，本地实例扩容后总阈值会随实例数变化；需要严格全局配额时，可用 Redis + Lua 或网关集中限流，但要考虑网络开销和 Redis 故障降级。

**被限流后的处理：**不是简单丢弃。可以返回 `429 Too Many Requests` 和 `Retry-After`，也可以根据业务选择排队、降级结果、异步受理或关闭非核心功能。写请求重试必须具备幂等性，并加入指数退避和随机抖动，防止客户端立即重试形成二次流量峰值。

**风险与治理：**阈值过低会误伤正常用户，过高则无法保护下游；仅按 IP 限流可能误伤 NAT 后的大量用户，仅按用户限流又挡不住匿名攻击。阈值应结合容量压测、历史峰值和下游 SLA 制定，并持续监控通过量、拒绝量、排队时间、P95/P99 延迟以及资源利用率。

**面试追问：**令牌桶与漏桶有什么区别；集群扩容后本地限流阈值如何调整；Redis 限流不可用时应该放行还是拒绝；为什么限流必须和降级、熔断一起设计？

## 02 把请求速率与并发量分开

QPS 限流控制进入频率，并发限制控制仍在占资源的请求数。相同 100 QPS，下游从 10ms 变成 10s，在途请求会大幅增加，单纯 QPS 限流未必能保护连接池；资源边界还需要并发配额、有界队列和 deadline。

全局 Redis Lua 限流只能保证一次计数更新在对应 Redis 执行域内原子，故障切换、跨地域复制和失败放行策略仍决定全局配额误差。请求执行成本差异大时，用“每请求一个令牌”也可能让重查询占满资源，可按成本等级分桶或使用加权配额。

## 03 拒绝策略也是接口契约

超出调用方配额可返回 429，服务自身临时不可用需按接口协议表达，不能把权限拒绝、限额与系统故障混成一个码。Retry-After 是建议，仍需客户端退避和随机抖动；保护支付等写操作时不能自动转成无可靠状态的后台任务。

口述：“入口挡无效流量，服务保护具体依赖，资源层限制在途和排队。每层有自己的配额对象，集中配额必须定义失联时策略，不追求所有层都重复计算同一件事。”
