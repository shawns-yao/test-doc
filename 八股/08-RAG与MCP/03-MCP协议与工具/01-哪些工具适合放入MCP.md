# 01 哪些工具适合放入MCP

## 01 核心回答

适合放进 MCP 的是边界清楚、输入输出可描述、多个客户端可能复用的业务能力，例如按权限搜索文档、读取工单、查询受控数据、创建已审批的任务。是否适合首先取决于能力设计，不能因为已有 API 就把所有接口原样公开。

## 02 怎样划分工具

工具粒度应表达一个可验收业务意图。过细会逼模型猜底层调用顺序，过宽的“执行任意命令/SQL/HTTP”又会扩大误用空间。参数要有明确类型、枚举与范围，结果要有稳定字段、来源及分页/大小限制。读取知识内容也可用 resource 表达，用户选择的提示模板可用 prompt；不是所有内容都必须包装成 tool。

可改编例子：暴露“按项目和状态查询工单”通常比“对工单库执行任意 SQL”更易鉴权与测试。写工具要单独声明副作用和幂等语义，审批与业务权限放在服务端执行。

## 03 哪些情况不急着 MCP 化

仅供单进程调用的纯函数，直接本地工具更简单；极高频低延迟路径可能不值得增加协议与运维层；尚无可信权限边界的管理员功能应先重构。MCP 不提供“装上就安全”的保证，readOnlyHint 等注释不能作为授权依据。

## 04 追问与口述

- “是否应该每个 REST endpoint 一个 tool？”不必。优先面向任务封装业务能力，并保留原 API 的错误与权限语义。
- “工具能返回无限长结果吗？”应分页、截断并给可继续读取的引用，避免上下文和内存失控。
- 口述：“可复用、契约清晰、权限可执行的能力适合 MCP。协议统一接法，业务边界、鉴权与幂等仍由应用负责。”
