# 02 从零搭建一个可用的 RAG 系统？完整流水线？

## 01 核心回答

**回答（离线 + 在线两段）：**

离线（数据准备/索引）：① 数据加载——PDF/Word/网页/数据库等源加载；② 文本切块——按语义完整切块；③ 嵌入——用适配检索任务的嵌入模型（如 BGE/M3E 等）把块转成向量，原始 BERT 不宜直接等同检索模型；④ 存储——存入向量存储并建索引；FAISS 是索引库，数据库系统还需提供权限、持久化等能力。

在线（查询/推理）：① 用户提问 → ② 用与文档向量兼容的嵌入体系及其 query 编码约定生成查询向量 → ③ 相似度检索 Top-K → ④（可选）重排序精细打分取 Top-N → ⑤ 增强与生成（按模板拼提示喂 LLM）。

**关键不在「跑通」在「可治理」：**切块要兼顾语义完整与召回粒度；嵌入模型要看领域适配和检索指标；索引要支持**增量更新和版本回切**。上线时保留数据版本、embedding 版本和索引版本，保证问题可复现、可回放。

索引全量重建成本高怎么办：① 增量索引——chunk_id + content_hash，只重算新增/变更/删除的分片；② 双索引版本化（蓝绿）——新索引验收后原子切换，失败一键回滚；③ 热冷分层——热数据实时小索引 + 冷数据大基线索引，夜间异步合并；④ 元数据与向量解耦——仅元数据变化可能无需重新嵌入，但索引与回填要求取决于引擎和映射配置。

---

## 02 上线前补齐数据契约

BERT 原始编码向量不一定适合直接做语义检索，应选择经过检索或句向量训练的模型及正确池化/前缀。FAISS 是向量索引库，不等于自带事务、权限和备份的完整数据库。

文档与查询通常使用同一兼容嵌入体系，但有的模型要求不同 query/document 前缀或编码方式，不能只强调“完全相同输入处理”。metadata 变化是否需要建索引取决于存储的索引和映射机制，不能一概说无需重建。

离线流水线要处理新增、修改、删除和 ACL 收紧；每次发布关联解析器、chunk、embedding 与索引版本，在线请求选定一个可追溯版本。更多存储约束见[[八股/08-RAG与MCP/01-RAG检索增强/20-RAG 向量库|向量库]]。
