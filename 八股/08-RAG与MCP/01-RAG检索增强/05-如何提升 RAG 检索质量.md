# 05 如何提升 RAG 检索质量？

## 01 核心回答

**优化路径：**按“数据质量 → 查询理解 → 召回 → 重排 → 上下文编排 → 生成约束”逐层定位，不把所有问题都归咎于向量库。

**数据与索引：**清理重复、过期和无权限文档，补齐标题、来源、版本、时间等元数据；采用 BM25 + 向量的混合搜索，关键词保证实体和错误码精确命中，向量召回覆盖同义表达，再用 RRF 或归一化分数融合。

**查询改写：**对省略主语、代词和多轮指代先做 query rewrite；复杂问题拆成子问题，多查询结果去重合并；HyDE 可用于语义表达差异大的场景，但要防止假设答案把检索方向带偏。

**两阶段排序：**先用低成本检索器召回 Top20-100，再用 Cross-Encoder 或轻量 reranker 对 query-document 联合编码，最终取 Top3-8；排序后按文档、章节和版本去重，避免上下文被同一来源占满。

**上下文与生成：**使用 Small-to-Large 返回父块，给每段附来源和证据范围；按 token 预算截断，提示模型只依据证据回答并在证据不足时拒答。对结构化字段可先查数据库，再把结果作为可信上下文。

**评估闭环：**分别测召回命中、排序位置、上下文有效率、答案正确性和引用准确性；线上按 query 类型、租户、版本和失败原因监控，采用离线回放 + 小流量 A/B，避免只看最终满意度。

**面试追问：**TopK 越大越好吗（召回覆盖与噪声、成本存在权衡）；为什么需要 rerank（向量相似度不等于答案相关性）；如何处理权限（检索前过滤或在索引中写入租户 ACL，不能只在生成后过滤）。

## 02 分层定位要能做对照实验

先判断标准证据是否存在且解析完整，再看初召回是否命中、rerank 是否保留、上下文是否截掉关键条件，最后检查生成引用。重排只能重排已有候选，救不回完全漏召回的证据。

BM25 与向量分数尺度不同，融合方法要固定并调参；RRF 按排名融合，不能把两个原始分数直接相加就当等权。Top20–100、Top3–8 是示例参数，应按召回覆盖、token 预算和时延选取。

服务端在材料进入重排、模型、缓存前检查权限；可信数据库也可能含用户提交的恶意文本，不能把整段结果都升级为指令。

## 05 直接追问：BM25 和 HyDE 实际怎样参与检索

BM25 先匹配查询词，再综合词频、逆文档频率与字段长度打分：词在当前文档出现较多通常增加贡献，但增长会饱和；在整个语料中很常见的词区分度较低；长度归一化避免长文档仅靠词多占优。常见实现用 `k1` 控制词频饱和、`b` 控制长度归一化强度，参数应在当前语料验证。它与向量召回互补，但不是普通 TF-IDF 换个名字。[Elastic 的 BM25 说明](https://www.elastic.co/guide/en/elasticsearch/reference/8.19/index-modules-similarity.html)

HyDE 的关键链路是：原始问题 → 生成一段可能回答问题的假设文档 → 用与语料兼容的编码器将该文档转为向量 → 检索真实语料 → 用真实证据回答。它尝试用“文档对文档”的语义匹配弥合问题与答案的表达差异，不只是把问题改写得更长。[HyDE 原论文](https://arxiv.org/abs/2212.10496)

假设文档可能包含虚构细节，不能写入事实库或当最终引用。工程上保留原始 query 的召回通路，比较加入 HyDE 前后的真实证据召回、错误引导比例、生成开销和时延；错误码、精确数值等查询可能更需要词法匹配。
