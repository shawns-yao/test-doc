# 03 线程池的拒绝策略是什么

## 01 核心回答

触发时机：`execute()` 提交任务时，若阻塞队列已满（入队失败）且当前工作线程数已达到 `maximumPoolSize`，线程池会调用 `RejectedExecutionHandler.rejectedExecution()` 处理该任务。JDK 内置四种策略：

**AbortPolicy（默认）**

**行为：**直接抛 `RejectedExecutionException`。

**注意：**默认策略，明确拒绝该任务，调用方需捕获异常或靠监控告警发现。

**CallerRunsPolicy**

**行为：**由提交任务的线程自己执行该任务；已 shutdown 时丢弃。

**注意：**天然限流——提交线程被任务占用，后续提交自然放慢；但慢任务会阻塞调用方。

**DiscardPolicy**

**行为：**静默丢弃新任务，不抛异常。

**注意：**丢弃无感知，适合允许丢消息的场景，需配合监控指标。

**DiscardOldestPolicy**

**行为：**丢弃队列中最老的任务，再重试提交新任务。

**注意：**配优先级队列时会丢弃优先级最高的任务，与直觉相反；被丢的可能是关键业务。

**生产实践：**核心链路常用 `AbortPolicy` + 监控告警（fail-fast，暴露问题）；能容忍延迟或丢消息的场景用 `CallerRunsPolicy` 或自定义策略；`DiscardPolicy`/`DiscardOldestPolicy` 用得少，因为静默丢任务难以发现。

**常见追问：**① 如何自定义策略？实现 `RejectedExecutionHandler` 接口，常见做法：降级返回兜底值、带上限重试入队、写入本地文件或消息队列补偿、延迟后重试；② `DiscardOldestPolicy` 的坑：配合 `PriorityBlockingQueue` 时丢的是最高优先级任务；③ `CallerRunsPolicy` 会阻塞提交线程，调用方不可接受阻塞的场景要慎用。

**口述重点：**拒绝策略的本质是“任务饱和时丢谁、怎么丢”：AbortPolicy 抛异常 fail-fast、CallerRunsPolicy 在运行中反压提交方，shutdown 时丢弃、两个 Discard 分别丢新/旧任务；生产常用 AbortPolicy + 告警，或自定义策略做降级补偿。

## 02 拒绝还会发生在关闭之后

拒绝不仅是“队列满加最大线程数满”；shutdown 后的新任务也被拒绝。CallerRunsPolicy、DiscardOldestPolicy 在已关闭时会丢弃，所以不能把 CallerRuns 当作绝不丢任务保证。

静默丢弃一个经 submit 包装的 FutureTask 时，返回的 Future 可能永远未完成，调用方 get 持续等待。自定义拒绝策略需明确抛错、取消 Future 或完成失败结果，并记指标。不要在事件循环/持锁调用线程中使用会执行长任务的 CallerRuns。

DiscardOldest 丢的是队头而非必然最老业务任务；标准 PriorityBlockingQueue 本身近似无界，通常不会因容量触发饱和拒绝，只有真正有界的优先队列等组合才出现“丢最高优先级”问题。
