# 02 Java 内存泄漏的常见原因有哪些？如何排查？

## 01 核心回答


内存泄漏是指对象已经不再需要，但仍然被 GC Roots 引用，导致垃圾回收器无法回收。常见原因包括：

静态集合长期持有对象

缓存没有淘汰策略

监听器或回调没有解绑

线程池中的 `ThreadLocal` 没有及时 `remove`

连接和流等资源没有关闭

类加载器泄漏

**常见追问：**为什么 `ThreadLocal` 会泄漏？`ThreadLocalMap` 的 Entry 对 key（ThreadLocal 对象）是弱引用，但对 value 是强引用；线程池线程长期存活时，key 被回收而 value 无人取出，value 可能经该活跃线程长期保留，直到 stale Entry 被清理或线程退出。规范做法是每次用完后 `remove()`，`set/get` 时也会顺带清理部分过期 Entry。

排查流程：

**① 判断是否真泄漏**
先确认是泄漏还是业务本身确实需要更多内存，通过监控观察堆使用量和 GC 后老年代是否持续上涨。

**② dump 定位持有者**
评估暂停和磁盘成本后，在可比负载阶段获取 heap dump，用 MAT、VisualVM 或 JProfiler 查看支配树、对象数量和 GC Roots 引用链；结合线程 dump、GC 日志和 JFR 确认创建与释放路径。

**③ 修复后验证**
通过重复场景和多轮 GC 验证对象数量能够回落。

---

## 02 怎样证明是泄漏而不是高峰

在相近请求量下比较多轮 GC 后的存活基线、同类对象数量和保留大小，找出随业务次数持续增长而不回落的持有者。Dominator Tree 的大 retained size 表示“这个对象支配多少可回收内存”，不等于它自己很大，也不自动证明业务不再需要它。

连接/文件句柄未关闭首先是资源泄漏；即使堆没有明显上涨，也可能耗尽连接、描述符或本地内存。堆外问题可借助堆中包装对象找持有链，但不能仅靠 heap dump 计算所有 native 占用。

## 03 安全取证与参考

heap dump 可造成暂停和大量磁盘 I/O，且可能包含请求和凭证等敏感数据，应控制访问与保留时间。修复必须对应所有权：缓存加界限、订阅注销、任务边界清理、类加载器解除静态/线程引用，再用同一负载复测。
