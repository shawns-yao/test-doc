# 12 GC 日志快速看什么？

## 01 核心回答

**回答（30 秒五看点）：**

**① GC 类型**
Young / Mixed / Full。

**② 停顿时长**
是否超过 SLA（如 >200ms）。

**③ 回收效果**
before → after 降了多少。

**④ 触发原因**
Allocation Failure / Humongous / Metadata / System.gc。

**⑤ 老年代趋势**
Old 是否持续上涨（晋升压力/泄漏风险）。

**正常 vs 故障示例：**① 正常 Young GC：`Pause Young ... 1536M->1180M 6.1ms`——类型 Young、6.1ms 是否可接受需对照本业务延迟预算、回收 356M；但 Old 210→228 说明有晋升，需观察。② 故障信号：`To-space exhausted` → `Pause Full 7.8G->6.9G 1.42s`——结合后续日志确认复制空间不足后发生 Full GC、1.42s 重停顿、回收后空间仍紧——加堆/提前并发标记/查大对象和泄漏。

**面试一句话：**"先看类型和时长，再看回收前后堆占用和触发原因，最后看老年代趋势；`To-space exhausted / Evacuation Failure / Pause Full` 是高风险信号。"

---

## 02 不要把并发周期总耗时当暂停

同一 GC ID 可有暂停和并发子阶段。分析时分别统计单次 pause、暂停频率、窗口内累计暂停占比和并发 GC CPU；一秒并发标记不等于所有线程停了一秒。应用延迟还包括进入安全点的等待，应结合 safepoint 日志、CPU 限流和 JFR。

堆 before→after 只说明该次回收结果；判断泄漏要看可比负载下多次回收后的存活基线。频繁 Young GC 可能只是分配率高，Old 上升可能是正常预热或缓存填充，必须联合趋势与业务验证。

---

## 03 Young GC 过频要不要立刻加大年轻代

先同时看分配速率、两次回收的间隔、单次暂停、累计暂停占比和回收后存活量。高吞吐服务频繁回收短命对象可能正常；只有请求尾延迟、GC CPU 或晋升压力恶化时，才有明确的优化目标。不能仅凭次数断言“回收跟不上分配”，更不能把它直接判成泄漏。

沿证据往下查：用分配采样定位临时集合、序列化中间对象和过大的批处理；看 Survivor、晋升量与 Old 基线区分短命对象多和对象活得久；核对堆大小、CPU 配额和最近发布。先减少无效分配、限制并发和批次，再验证参数调整的收益。

对 G1，年轻代大小是实现停顿目标的重要调节手段，不能照搬其他收集器经验直接用 `-Xmn` 或 `NewRatio` 固定它。调大年轻代可能降低次数，同时增加一次疏散的存活对象量与停顿；吞吐、尾延迟和内存余量必须一起复测。依据：[Oracle JDK 21 G1 调优](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-garbage-collector-tuning.html)。

## 04 版本与参考

JDK 9+ 使用统一日志体系，GC 与 safepoint 标签可分别配置；JDK 8 的 PrintGCDetails 等参数不要不加检查地原样带入升级环境。日志按时间轮转并保留重启前文件，避免故障现场被覆盖。
