# 07 标记-清除算法导致内存碎片化，要分配一块很大的内存怎么办？

## 01 核心回答


**概念原理：**标记-清除只清不整，留下碎片——连续大对象可能找不到足够大的连续空间。JVM 的应对策略：

**应对机制：**① **标记-整理（Compact）**：CMS 触发 Full GC 时做整理；G1 疏散普通 Region 的存活对象以回收整块空间，但 Humongous 对象仍可能因缺少连续 Region 分配失败；② **大对象直接进老年代**：某些传统收集器可使用 `-XX:PretenureSizeThreshold` 等策略，不能作为所有收集器的通用规则，避免在新生代反复复制——但老年代也可能碎片化；③ **TLAB 与大对象分配**：TLAB 放不下时可退到 TLAB 外的 Java 堆分配路径，不会自动变成 off-heap；④ **内存预留**：CMS 预留空间（`-XX:CMSInitiatingOccupancyFraction`）防碎片导致 promotion failure；⑤ 兜底：老年代空间不足且无法整理时抛 `OutOfMemoryError` 或触发 Full GC。

**关键细节：**碎片化严重时表现：老年代占用不高但频繁 Full GC（大对象找不到连续空间）——整理型收集器能缓解，仍需排查连续空间和活跃对象占用；大对象分配失败先看是不是碎片（`-XX:+PrintGCDetails` 看 promotion failed / concurrent mode failure）。

**面试追问：**大对象为什么直接进老年代（避免新生代复制开销）；promotion failure 是什么（可用容量或连续空间不足导致晋升失败）；G1 为什么仍可能有碎片（Humongous 连续 Region 与尾部空间）。

---

## 02 为什么总空闲足够仍可能分配失败

假设需要连续 20 MB，但空闲空间散在多个小洞里，总空闲大于 20 MB 也不一定成功。整理通过移动活对象合并空闲区域，代价是移动和引用修正；若真正存活集已占满，再整理也不能创造可用空间。

G1 的大对象需要连续 Region，普通 Region 疏散并不保证立刻得到任意大的连续区间。业务上优先减少单次大数组、分块流式处理、限制并发大请求；增大 Region 可减少部分 Humongous 分类，却可能增加内部浪费和回收粒度，需实测。

## 03 校正依据

TLAB 是堆内分配优化；CMS 参数只用于历史版本，JDK 21 不应照搬。判断根因需区分容量、分配速度、复制预留和碎片，不能见 Full GC 就认定碎片。
