# 01 HashMap 底层数据结构是什么？如何扩容？

## 01 核心回答


**底层结构：**JDK 8 为**数组 + 链表 + 红黑树**。key 的 `hashCode()` 经扰动（`h ^ (h >>> 16)`）后与 `(n - 1)` 做位与定位桶；哈希冲突时用链表存储（尾插法），链表长度 > 8 且数组长度 ≥ 64 时转红黑树（查询 O(n) → O(log n)），扩容拆分后的树桶节点数 ≤ 6 时退化为链表；普通删除还有树形状等判定，不是一条统一的“少于 6”规则。

**扩容流程：**默认容量 16、负载因子 0.75，元素数 > 容量 × 0.75 时扩容为**原来的 2 倍**（容量恒为 2 的幂，保证位运算定位）。JDK 8 扩容后元素**要么留在原位、要么移动到「原位置 + 旧容量」**（按新增 bit 是 0 还是 1 拆分），不需要重新计算 hash——这是 JDK 8 对 JDK 7 的重要优化。

**关键细节：**为什么用 2 的幂（`hash & (n-1)` 等价取模且更快）；扰动函数目的（让高位参与定位，减少冲突）；默认负载因子 0.75 是空间与时间的折中。

**风险与取舍：**HashMap 线程不安全（并发 put 可能覆盖丢失数据）；自定义对象做 key 必须同时正确实现 `hashCode` 和 `equals`（先比 hash 再比 equals）。

**面试追问：**HashMap 遍历有序还是随机（无序，插入顺序不保证）；JDK 7 头插法为什么有死循环（扩容时链表反转成环）；Java 17 插入/查找时间复杂度（散列良好时平均 O(1)；树桶常见可比较键为 O(log n)，恶意同 hash 且不可比较键不能无条件承诺最坏 O(log n)）。

## 02 扩容为什么只用检查一个 bit

旧容量为 16 时，桶索引只用 hash 的低四位；扩为 32 后增加第五位。新增位为 0 的节点留在旧桶，为 1 的节点去“旧索引 + 16”，所以无须再次调用 key.hashCode。链表相对次序被保留，与 JDK 7 并发迁移中链表反转的问题应分开讨论。

树化阈值 8、退化阈值 6 和最小树化容量 64 都是 OpenJDK 实现细节。碰撞多但数组还小时，优先扩容，希望利用更多 hash 位分散碰撞；树化是散列不佳时的兜底。不同插入 API 的触发细节不要仅凭“第八个”或“第九个”背结论，应限定 putVal 路径。

## 03 为什么不一开始全部使用红黑树

普通短桶使用链表更简单，树节点需要额外链接与树维护，插入删除还可能旋转和重平衡。OpenJDK 的实现注释以树节点约为普通节点两倍大小解释这一空间取舍；散列良好时绝大多数桶很短，因此树化用于异常长桶的兜底，不值得让所有桶一直承担树成本。

8 和 6 是该实现的工程阈值，不是数学证明的唯一最优数。源码用默认扩容条件下近似参数 0.5 的泊松模型说明长桶罕见，列出的长度 8 概率约为 6×10⁻⁸，并非“百万分之六”，也不代表任意用户 hashCode 都服从这一分布。树化和扩容拆分退化采用不同阈值，可留出缓冲、减少边界来回转换；实际删除退化仍要看树形状及操作路径。容量不足 64 时先扩容，尝试用更多 hash 位分散节点，不能仅凭桶长就断言立即树化。依据：[OpenJDK HashMap 实现注释和阈值](https://github.com/openjdk/jdk21u/blob/master/src/java.base/share/classes/java/util/HashMap.java)。

## 04 key 为什么应保持稳定

键放入后若修改了参与 equals/hashCode 的字段，查找会用新 hash 定位，可能找不到原来的节点。hash 相同只说明候选桶/节点可能匹配，最终仍需 equals。无序也不等于每次随机洗牌，而是 API 没有插入顺序保证。

## 05 校正与依据

校正统一退化阈值和最坏复杂度的过度承诺。预估容量应结合预计元素数与负载因子；指定初始容量不代表能容纳同数量元素而不扩容。
