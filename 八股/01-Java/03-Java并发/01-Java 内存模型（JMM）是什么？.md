# 01 Java 内存模型（JMM）是什么？

## 01 定义
JMM 是一套并发访问共享变量的规则，也就是 Java 为了规定多线程环境下，线程之间如何读写共享变量，以及如何保证，原子性，可见性，有序性，而定义的一套规范

## 02 想要解决的问题
一个线程修改了变量，另外一个线程什么时候能看到，代码执行的顺序能不能重排，多线程并发读写怎么样才算是正确的？
可以理解成每一个线程都有自己的工作内存，线程操作共享变量的时候 ，并不是直接抽象成每次都访问主内存，所以会导致一个线程修改了变量，而另外一个线程暂时看不到的问题

---
JVM 内存区域，堆，栈，方法区，程序计数器等 --> 解决的数据存在哪里
JMM 解决的是多线程情况下，数据怎么读写，什么时候可见，能不能重排序？

---

## 03 JMM 基本概念

主内存与工作内存是帮助入门的历史抽象；真正判断并发结果是否合法，要看共享读写之间是否建立规范定义的同步关系。

### 03.1 可见性问题
JMM 抽象出来了两个概念，其中主内存存放共享变量，每一个线程还存在自己的工作内存
线程不会保证每次操作都直接访问主内存，而可能操作自己的变量副本，如果没有建立正确的同步关系，这就有可能导致其中一个线程读取的是旧值

## 04 怎么解决这三个问题

先区分观察旧值、复合操作交错和可观察重排，再选择足够的同步边；三种风险可能出现在同一个业务操作中。

### 04.1 可见性-->一个线程修改共享变量后，其他线程能否及时的看到

使用 volatile 关键词

### 04.2 原子性-->一个操作能不能被看作不可分割的整个操作

比如 count++ 其实是三个操作。并不是原子操作，所以可以使用 synchronized 或者 Lock 等保证原子性

### 04.3 有序性-->为了提高 CPU 和编译器的效率，代码可能会发生指令重排序

从单线程来看的话，只要结果不受影响，编译器或者 CPU 在某些情况下可能对操作进行调整
但是在多线程环境下，重排序可能导致另外一个线程看到不是预期的行为，

因此 JMM 规定了，哪些操作允许重排序，哪些可观察的顺序不能被破坏，比如 Volatile ， Synchronized 就会建立起一定的内存顺序约束

## 05 JMM 的核心规则--> Happens-Before

比如 happens-before 规则就是 JMM 判断一个线程的修改是否应该对另外一个线程可见

比如操作 A happens-before 操作 B，那么保证 A 做的修改 B 一定能看到，并且也不是说在时间上 A 比 B 先执行，而是 A 和 B 之间建立了一个可靠的内存可见性关系

## 06 和其他并发问题的关系

JMM 是理解并发工具的基础模型：

- [[八股/01-Java/03-Java并发/03-Synchronized是什么|Synchronized是什么]] 通过同一把锁建立互斥和可见性关系。
- [[八股/01-Java/03-Java并发/04-ReentrantLock是什么|ReentrantLock是什么]] 通过显式锁和 AQS 管理线程之间的同步状态。

## 07 面试口述版

JMM 不是 JVM 的堆、栈、方法区等内存区域，而是 Java 对多线程读写共享变量建立的一套抽象规则。它主要解决可见性、有序性和原子性问题，并通过主内存、工作内存以及 happens-before 规则描述线程之间什么时候能够可靠地看到彼此的修改。volatile 和锁都是 JMM 规则在 Java 中的具体使用方式。

## 09 旧面经的详细补充


**概念原理：**JMM（Java 内存模型）描述线程与内存的抽象关系：**主内存**（所有线程共享的变量存储区）和**工作内存**（线程私有的变量副本，含寄存器/缓存）。主内存/工作内存是辅助理解的抽象，不要求每次读取实际访问物理内存；现代 JMM 用可观察读写、同步顺序和 happens-before 定义合法结果。

**历史教学模型（八种操作，不是现代 JLS 的实现指令要求）：**主内存 → 工作内存：`read`（主存读）→ `load`（载入工作内存）→ `use`（使用）；工作内存 → 主内存：`assign`（赋值）→ `store`（存）→ `write`（写回主存）；另有 `lock`（加锁）和 `unlock`（解锁）作用于主内存变量。这套历史教学术语不替代现代 JLS 的同步动作和 happens-before 定义。

**同步语义（不等于物理缓存清空）：**① **volatile**：写与同一变量后续读建立同步关系；② **锁（synchronized/Lock）**：释放与后续成功获取同一把锁建立可见性关系；③ **final**：正确构造且构造期间不逸出的对象具有特殊初始化安全保证，不代表所有普通字段都自动安全发布。

**风险与取舍：**没有同步机制时，线程 B 不能依赖何时观察到 A 的写入（可见性），编译器与处理器也可能进行规范允许的重排（有序性）——这就是 `volatile`/锁要解决的两件事；但 JMM 是**抽象模型**，实际由内存屏障 + 缓存一致性协议（MESI 等）在硬件层实现。

**面试追问：**JMM 和 JVM 内存区域的关系（抽象并发模型 vs 运行时区域，两者独立）；happens-before 规则是什么（先行发生原则，volatile/锁/线程启动等）；锁如何建立可见性（同一把锁的 release/acquire 语义）。

## 10 用 happens-before 推导发布关系

不要背“过一会儿总会刷新”。假设生产者先写普通字段 data，再写 volatile 标志 ready；消费者先读 ready，确认已发布，再读 data。程序顺序、volatile 同步边与传递性组成一条链，所以发布前的 data 写入对消费者可见。如果消费者绕过 ready 直接读 data，这条链就不存在。

常用规则包括：同线程程序顺序；同一监视器的解锁先于后续加锁；同一 volatile 变量的写先于后续读；start 先于新线程动作；线程动作先于另一线程成功 join 返回；以及传递性。这里的“先于”是规范约束，不要求机器指令完全按墙上时钟顺序执行。

## 11 三个容易混淆的边界

- 可见性不是实时通知。消费者必须执行相应的读取/同步操作；sleep 和 yield 不建立同步关系
- 无数据竞争不等于业务正确。每次 get、set 都线程安全，组合起来的“检查后更新”仍可能需要共同临界区
- 局部变量本身不共享，但它引用的对象可能共享；对象不因被局部引用而天然线程安全
