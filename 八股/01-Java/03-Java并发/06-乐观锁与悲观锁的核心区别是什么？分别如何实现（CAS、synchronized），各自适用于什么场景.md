# 06 乐观锁与悲观锁的核心区别是什么？分别如何实现（CAS、`synchronized`），各自适用于什么场景？

## 01 核心回答


**乐观锁**

**理念：**认为并发冲突发生的概率较低，读数据时不加锁，更新时再检查数据是否被修改过。

**实现：**CAS：线程带着期望值和新值执行比较并交换，只有当前值仍等于期望值时才更新；数据库中也常用版本号或更新时间字段实现。

**适用与权衡：**适合读多写少、冲突较少的场景，优点是不会因为加锁阻塞线程；但高并发冲突时会频繁重试，CAS 还要注意 ABA 问题。

**悲观锁**

**理念：**认为冲突概率较高，访问共享资源前先加锁，保证同一时间只有符合条件的线程能够操作。

**实现：**在 Java 中可以使用 `synchronized`、`ReentrantLock`，数据库中则可以使用行锁等。

**适用与权衡：**适合写多、临界区较长或冲突严重的场景，能够降低重试成本，但会带来线程阻塞、上下文切换以及死锁风险。

CAS 底层机制：原子类/VarHandle 按其 API 提供原子性及内存排序语义；HotSpot 映射到平台相关原子指令（如 x86 的 cmpxchg），不能只归因于 volatile：比较内存当前值与期望值，相等才写入新值，整个过程原子完成。

**ABA 问题**
值从 A 变 B 又变回 A，CAS 误判未修改；可用 `AtomicStampedReference` 加版本号解决。

**自旋开销**
冲突激烈时循环重试空转 CPU，高竞争下实际退化为类似锁的串行执行。

**单变量原子性**
只能保证一个共享变量的原子操作，多变量需加锁或封装成对象再整体 CAS。

**常见追问：**`synchronized` 锁可以升级：无锁 → 偏向锁 → 轻量级锁 → 重量级锁，这是旧版 HotSpot 教学路径，具体版本不保证逐级经过全部状态，避免一上来就依赖操作系统互斥量；`ReentrantLock` 则基于 AQS 队列实现，支持可中断、超时、公平锁等更细粒度控制。

**口述重点：**CAS 是一种无锁算法实现，不代表没有竞争；`synchronized` 是基于对象监视器的互斥锁，必要时会让线程阻塞。

## 02 CAS 成功不代表业务语义完整

CAS 比较的是当前状态是否等于期望值，不知道两次读取之间发生过多少次变化。若算法依赖“对象从未被移走/重用”，A→B→A 可能破坏假设，可把版本戳纳入状态；若只关心当前值，ABA 未必构成问题。

重试循环中的计算要可重复，不能每次失败重试都重复扣款、发消息。更新两个相关变量时，分别 CAS 并不能保证跨变量不变量；可以使用锁，或将状态组织成不可变快照并 CAS 引用，但要评估分配和冲突成本。

## 03 取舍与参考

冲突率、临界区成本和饥饿风险比“读多写少”四个字更重要。CAS 只保证一次操作的原子性，使用 CAS 的整体算法不自动获得无锁、无等待或公平性保证；锁内部也可以用 CAS 实现获取路径。
