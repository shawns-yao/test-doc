# 08 死锁如何排查？

## 01 核心回答

**先说定义：**死锁是多个线程互相持有对方需要的资源，并且永久等待。经典死锁同时满足**互斥、占有且等待、不可剥夺、循环等待**四个条件；排查时要先证明存在环路，再定位业务代码中的加锁顺序。

**线上排查流程：**
① 记录进程号、线程数、CPU 和接口延迟，确认是死锁而不是普通锁竞争或下游阻塞；
② 使用 `jstack <pid>`、`jcmd <pid> Thread.print -l` 连续采集两到三次线程转储，观察线程状态和锁等待是否持续；
③ 搜索 `Found one Java-level deadlock`、`BLOCKED`、`waiting to lock`，沿着“线程 A 持有锁 X 等锁 Y、线程 B 持有锁 Y 等锁 X”的关系还原环；
④ 回到代码核对锁对象是否一致、是否存在嵌套加锁和异常分支未释放资源。

**工具边界：**`jstack` 对 `synchronized` 和 JVM monitor 最直观；支持 ownable synchronizer 检测的工具也可识别 `ReentrantLock` 等锁；结合 `Thread.print -l`、ThreadMXBean、线程栈与 JFR 判断，getOwner 是受保护的监控方法，不能当通用外部 API；数据库锁、Redis 分布式锁还需要查看数据库锁表、Redis key 的持有者和租约信息，不能只看 JVM 线程转储。

**修复优先级：**
① 对多个资源规定全局一致的加锁顺序，例如按账户 ID 从小到大加锁；
② 尽量缩短临界区，锁内不做网络调用、磁盘 I/O、复杂计算和用户回调；
③ 对可中断场景使用 `tryLock(timeout)`，超时后释放已持有的锁并返回可重试结果；
④ 使用 `try/finally` 保证释放，避免锁对象被重新赋值。
⑤ 对跨进程锁设置租约、续期和持有者标识，防止客户端异常后永久占用。

**注意事项：**不要只通过重启进程掩盖问题；重启可以止血，但还要保留线程转储、请求链路和锁指标。预防上可监控锁等待时长、BLOCKED 线程数、接口超时率，并在压测和故障演练中覆盖嵌套锁、超时和异常路径。

**面试追问：**“为什么线程 dump 没发现死锁？”可能是锁在数据库或其他 JVM、采集时机已错过，或者只是长时间阻塞；“如何避免死锁又保证并发？”通常采用统一顺序、缩小临界区和分段锁，并用超时机制限制最坏等待时间。

## 02 用等待图区分真正死锁与卡顿

证据至少要说明每个线程持有什么、正在等待什么、资源由谁持有，最终能否闭合成环。BLOCKED 只表示进入监视器等待；
ReentrantLock 等待常见 WAITING/parking，不能只筛 BLOCKED。线程池所有工作线程等待本池队列中的子任务也会形成资源饥饿，但不一定被 Java 锁环检测自动报告。

ThreadMXBean.findDeadlockedThreads 支持检测平台线程的监视器和 ownable synchronizer 死锁；JDK 21 的这个管理接口不覆盖虚拟线程。工具未报告死锁，不能排除跨数据库、跨进程或线程池容量依赖。

## 03 修复验证与参考

超时只能让等待有界，必须同时释放已持资源、定义重试和幂等，才形成完整处理。验证统一锁顺序时，要覆盖正常、异常、回调和批处理路径，避免主流程修好了而补偿流程倒序拿锁。
