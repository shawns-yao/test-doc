# 20 Agent扩展新能力，会考虑那些问题

## 01 原有理解

比如动态能力发现

现在的工具通常是，系统启动，注册一批工具，模型从这些工具中选择

再进一步的话，比如模型判断当前任务需要什么能力，从工具注册表中查询，只加载相关的工具，可以做权限，信任等级检查，

但是比如用户需要 postgresql，假设原版本没有 DB 工具，发现有 postgresql MCP
，可以进行检查，判断来源是否可信，readonly 是否可信，schema 校验，需要用户授权等等，允许之后才加入工具集合

---

## 02 将动态发现落成受控能力接入

原有思路抓住了“按需加载”，还需把发现、安装、授权、执行拆成四个阶段。工具注册表返回的是候选元数据，不是可信代码或自动授权。只加载相关工具能节约上下文，也能缩小可误用的能力范围。

1. 需求与契约：定义能力要解决的问题、输入输出 Schema、前置条件、超时、幂等语义及失败类型。
2. 信任审查：验证发布者、来源和版本，审查依赖与网络访问；描述里的 readonly、idempotent 等标注只能作提示，不能充当安全证明。
3. 权限审批：最小范围授权，凭证保留在执行环境或凭证系统，不塞入模型上下文；数据库工具应从服务端限制只读角色、表范围和查询资源。
4. 接入验证：沙箱契约测试、恶意参数测试、权限负例、过长结果截断和小流量试用。
5. 生命周期：固定版本，记录能力变更，支持禁用、回滚、撤销授权和清理缓存；工具集合变化应同步到正在执行任务的策略层。

## 03 PostgreSQL 示例与追问

可改编示例：已有 Agent 缺少数据库查询能力，发现候选 PostgreSQL MCP Server 后，先检查它是否会执行任意 SQL，能否只暴露受控查询、是否带独立只读账户。工具声称“只读”而底层账户有写权限仍然不安全；只允许 SELECT 也不能完全替代数据库权限和资源限制。

“能力太多怎么选？”先按租户权限过滤，再按任务检索候选工具，最后让模型在有限集合中选择；加载失败要回到清晰的 blocked 状态，不能临时造一个不存在的工具。

口述：“扩展能力不仅是注册函数，还包括来源、权限、契约、资源和撤销。动态发现减少接入成本，但信任判断与实际授权必须在模型外执行。”
