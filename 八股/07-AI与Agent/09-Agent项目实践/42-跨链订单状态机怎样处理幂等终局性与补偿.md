# 42 跨链订单状态机怎样处理幂等终局性与补偿

## 01 一个订单关联两条链上的不同阶段

跨链不是一笔数据库事务。参考状态可拆为报价、等待授权、源链已提交、源链达到所需确认、跨链消息处理中、目标链执行中、成功，另设拒绝、可重试失败、待人工处理和退款处理中。具体状态必须对齐所用桥/消息协议，不能把源链交易成功当成目标操作完成。

保存业务订单 ID、报价版本与有效期、源/目标链、用户确认内容、源交易 ID、消息 ID、目标交易 ID和每阶段时间；这些标识不能互相替代。

## 02 为什么采用订单对象

订单对象把报价、授权、提交、跟踪和恢复绑定在同一业务意图上，便于查询及审计，比客户端串接多个独立 API 后只记最后响应可靠。它并不自动保证原子性，仍需状态机、供应商查询与幂等控制。

签名前校验报价是否失效、接收地址和金额是否变化；变化应重新确认，不能复用旧签名去表达新意图。签名、广播、上链、达到终局条件是不同事件。

## 03 重试与补偿

回调和轮询共同驱动条件更新，用业务幂等键去重，用版本号避免旧状态覆盖新状态。发送超时代表结果未知，先用已有订单或交易标识查询，不能重新生成一个新订单反复广播。

链重组、确认未完成、桥暂停和目标链失败分别处理。已终局执行通常无法技术回滚，所谓补偿可能是新的退款或反向操作，必须明确责任、费用与授权；没有可安全补偿的路径就进入待核查状态，不能伪装成功。

## 04 一手依据与验收

[Chainlink CCIP 消息生命周期](https://docs.chain.link/ccip/concepts/message-lifecycle) 展示源链、验证与目标链执行的不同阶段，仅作为跨链分阶段的实例，不代表全部协议。

参考验收覆盖：两次相同回调、消息迟到、目标执行失败、源链重组、查询超时和人工补偿。验证一个业务意图不会因重试生成多笔未经授权的执行，所有未知状态都可追踪。
