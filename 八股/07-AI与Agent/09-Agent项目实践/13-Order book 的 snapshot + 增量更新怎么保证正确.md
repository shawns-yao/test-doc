# 13 Order book 的 snapshot + 增量更新怎么保证正确？

## 01 核心回答

流程：先订阅并缓冲增量，再获取 snapshot，按协议序列号衔接后合并——价格档同价替换、数量为 0 删除、无同价则按 bid 降序/ask 升序插入。

正确性校验：持续校验序列连续性；平台若提供 checksum 则按其规则验证，发现缺口或不一致就重新同步。

---

## 02 正确同步的关键是序列衔接

不能只“先拿快照，再订阅增量”，否则两者之间有漏更新窗口。常见做法是先建立增量订阅并缓冲，再拉快照，按交易所定义的序列号丢弃已包含事件，找到能接上快照的第一条，然后连续应用。不同平台对起止序列、前序序列和快照标识定义不同，必须按具体协议实现。

以 Binance 的 diff-depth 为例，应根据快照的 lastUpdateId 与事件更新区间判断是否已过期、是否能衔接；出现缺口就丢弃本地状态并重新同步，而不是继续带错计算。只按事件时间排序无法证明更新完整，因为时间可能相同、乱序或粒度不足。

---

## 03 更新语义与失败边界

先确认数量字段表示绝对值还是差量；本题常见绝对数量语义下，同价替换、零数量删除。价格和数量使用十进制或整数刻度，避免浮点误差破坏档位键；买卖两侧分别保持正确排序。

CRC32 等 checksum 仅在平台提供且按其指定格式计算时才有意义，不是通用标准，也不能替代序列检查。还要检测快照深度限制、消费积压、数据过期，并在重建完成前停止向下游宣称订单簿有效。

口述：“先缓冲、后快照、按序列接上，持续查缺口；校验失败就重建，有效状态再开放给下游。”
