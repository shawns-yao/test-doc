# 35 如何设计一个抢红包系统？

## 01 核心回答

**需求：**规则同微信红包、可设置红包权限、考虑数据量和并发。

**架构：**Gateway → 红包服务（无状态）→ Redis Cluster（高并发原子扣减）→ MQ → 账务服务 → MySQL（主存）。

**分工：**Redis 负责「抢红包瞬时并发」（原子扣减）；MQ 解耦削峰避免直接打库；MySQL 负责「最终账务与审计」。

## 02 并发扣减与账务一致性是两件事

Redis 原子脚本可在一次执行中检查剩余数量/金额、用户是否已领取并完成预占，但它不与 MQ 和数据库天然形成分布式事务。抢成功后消息发送失败、重复投递、消费者落账后未确认，都需要显式处理。

---

## 03 可恢复流程

为红包和用户建立唯一领取键，领取结果有业务 ID。Redis 先原子预占并记录可恢复凭据，再可靠投递事件；消费端用唯一约束幂等落库，记录账务流水与领取状态。失败通过可重试消息、对账与补偿收敛，不能只靠“MQ 保证不丢”。具体采用事务消息、outbox 或持久日志应说明各自一致性边界。

金额用最小货币单位整数，不用二进制浮点；随机分配必须保证单份上下限和总额守恒。红包到期退回未领取余额时，与领取并发竞争需要统一状态检查，不能同时领取又退款。Redis Cluster 的多键原子脚本还涉及键在同一槽的约束。

---

## 04 追问与口述

“防超领就等于资金正确吗？”不，账务还需唯一流水、余额约束、授权和对账。“Redis 丢数据怎么办？”根据持久领取证据与账务记录恢复，不能继续把过期缓存当事实。

口述：“用原子预占抗瞬时并发，用幂等账务和对账保证最终资金正确；本页是设计讨论，不代表真实支付系统已验证。”

## 07 领取权限怎样在服务端落实

创建红包时就绑定发放者、可领取主体范围、有效期和规则版本。领取请求中的 user_id、群关系或“已获资格”标志不能由客户端自报后直接信任：服务端从认证身份得到实际领取者，再按红包当前规则校验指定用户、群成员或其他条件。查询领取记录与金额明细也要校验可见权限，不能只保护领取接口。

领取资格检查和金额/数量预占需要明确同一操作的授权时点。规则固定时可在创建后冻结该版本；规则可撤销时，要由权威策略判断当前资格，并让领取执行端检查受信的规则版本或有效租约。不能先通过权限检查，排队很久后仍用旧结果领取。若权限与余额跨系统，说明撤销何时生效、如何传播和如何在无法核验时拒绝领取，不能声称一次 Redis Lua 能同时保证外部权限数据最新。

在通过权限校验后，用红包ID与领取者组成幂等业务键并原子检查是否已领取，限制请求频率，拒绝越权与过期操作。回归场景包含伪造身份、非指定用户、退群后领取、过期令牌、规则更新与在途领取竞争、重复点击及越权查看记录。金额守恒和领取权限分别验证，防超领并不能替代授权。
