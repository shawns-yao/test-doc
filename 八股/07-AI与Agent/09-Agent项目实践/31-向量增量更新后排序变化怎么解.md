# 31 向量增量更新后排序变化怎么解？

## 01 核心回答

通常不用每次全量重建——向量检索排序是查询时实时算相似度，不是全库预排序。实践上用「Base 索引 + Delta 增量索引」，查询时合并结果；只在低峰期做周期性 merge/compact 提升检索效率；模型空间变化、索引质量退化、删除碎片或其他实现约束也可能需要重建，应通过基线定位。

---

## 02 先判断排序变化是否正常

新增更相关文档挤进 TopK 是合理变化，不应为了保持旧顺序而阻止新知识。异常包括向量模型/归一化变化、旧块未删、ANN 图变化带来召回波动、混合检索统计变化或缓存版本不一致。必须固定 query、过滤、距离与数据版本，才能比较原因。

---

## 03 定位和修复

1. 对受影响 query 同时跑精确近邻基线与 ANN：若精确结果也变，先看新增/修改内容；只有 ANN 明显波动再检查搜索参数与索引质量。
2. 检查 chunk_id、版本、去重和删除标记，避免旧新块同时出现。
3. 检查 embedding 模型、维度、输入前缀和归一化是否混用；模型空间变化通常需要重嵌入。
4. 如果采用 Base + Delta，查询分别召回后合并、去重、应用删除覆盖并统一重排，确保分数可比；这是一种架构选择，不是所有向量库必须采用。
5. 发布索引版本，验证召回/答案质量后切换，故障时回到兼容版本。

---

## 04 追问与口述

“什么时候重建？”取决于实现、删除碎片、索引质量、模型变化和性能，而非只有大规模分布变化才重建。并列分数可用稳定 ID 做展示 tie-break，但不能掩盖相关性变化。

口述：“先分正常新知识变化与异常检索波动，拿精确基线定位，再决定参数、增量治理还是重建。”相关：[[八股/08-RAG与MCP/01-RAG检索增强/16-向量检索算法有哪些|ANN 算法]]。
