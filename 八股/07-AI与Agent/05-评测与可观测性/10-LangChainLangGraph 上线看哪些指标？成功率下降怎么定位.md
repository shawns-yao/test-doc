# 10 LangChain/LangGraph 上线看哪些指标？成功率下降怎么定位？

## 01 核心回答

**回答（四类指标）：**

① **任务成功率**（业务结果）；② **链路稳定性**（错误率/重试率/中断率）；③ **性能与成本**（p95 时延、token 成本）；④ **质量指标**（幻觉率、格式通过率、人工接管率）。没有这套指标就无法判断是模型问题还是编排问题。

成功率下降漏斗定位（编排 → 工具 → 检索 → Prompt）：① 图编排层——看 loop_rate、step_count、p95 timeout、retry_rate：步数暴涨/回环增多/超时增多提示检查路由、工具与证据不足等原因；② 工具层——看 success_rate、5xx/429、schema 校验失败率、p95 延迟：调用失败或慢 = 工具可用性/契约问题；③ 检索层——看 hit@k/recall@k、空召回率、索引新鲜度：召回质量掉则答案成功率同步下降；④ Prompt 层——同一检索结果 + 同一工具返回下做 Prompt A/B：前面未发现异常时继续对照 Prompt、模型版本与输入分布。

症状速判：步数/超时突然上升 → 优先核查图编排及上游依赖；工具报错和慢调用上升 → 工具；空召回或错召回上升 → 检索；链路都健康但答案质量掉 → Prompt。

---

## 02 症状只能帮助提出假设

步数暴涨也可能是上游检索不到证据、模型版本变化或工具结果缺字段，不能直接断定是图路由错误。排查先看发布时间和依赖变更，再按同一任务对照基线 trace，找首次偏离的位置。

将任务、模型调用、检索和工具请求串成关联 trace；观察 p50/p95/p99 与错误分桶，不用均值掩盖长尾。回放历史样本时冻结输入和索引版本，含副作用的工具换成模拟或只读核验，不能在线重放真实发送/下单。

口述：“先证据定位再改配置，速判是线索，不是因果结论。”

## 05 直接追问：为什么还要看过滤后的检索命中

只看初始召回命中率，会漏掉候选在权限、租户或元数据过滤后丢失的情况。对同一问题、索引版本和授权范围，分别记录候选召回、过滤后和最终送入上下文三个阶段的命中情况；先固定 k 的取值与分母，明确测的是“包含至少一条相关且允许使用证据的请求比例”还是相关证据的召回率，避免把不同阶段的数字直接混比。

若初始候选包含正确且有权访问的材料，过滤后却消失，应检查租户标记、权限元数据、日期条件和过滤顺序；若本来就无权访问，正确过滤属于预期行为，不能为提高命中率绕过权限。按过滤原因分桶，并与空召回率、索引新鲜度和版本变更一起核验，才能区分检索召回不足与过滤规则误杀。
