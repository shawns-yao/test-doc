# 04 什么是上下文工程？和 Prompt Engineering 的边界？

## 01 核心回答

**定义：**上下文窗口不是「越大越好」，核心是**上下文工程**——如何挑选、组织、压缩、更新上下文。从聊天机器人走向可执行任务的 Agent 时，Prompt Engineering 不够用了，必须升级为 Context Engineering：Agent 的上下文是持续演化的状态系统（工具结果、网页观察、代码反馈、阶段结论、失败重试、长期记忆）。

与 Prompt 的边界：Prompt Engineering 侧重指令与示例设计，Context Engineering 更广地管理推理时可见信息及其生命周期；两者有重叠，不严格按单轮/多轮划界。前者解决「怎么说」，后者解决「基于什么说」，两者必须同时做。

**四件事：**上下文**采集、选择、压缩、治理**（预算/监控/回滚）。「状态优先于文本」——模型每一步读到可执行状态，而不是冗长叙述。

---

## 02 概念边界与可测指标

Prompt Engineering 不限于单轮，上下文工程也不限于多轮；前者侧重指令与示例的写法，后者更广地管理某次推理可见的信息及其生命周期，两者有重叠。原文的“怎么说/基于什么说”适合记忆，不是严格互斥定义。

可将上下文分成不可丢的目标和授权、当前状态、证据引用、可回取的大块材料。压缩前后测关键约束保留率、引用可追溯率和最终任务成功率，防止摘要看起来顺畅却丢失否定条件或数值。

口述：“管理的不只是 token 数，而是当前决策需要的信息，以及这些信息从哪里来、何时失效。”
