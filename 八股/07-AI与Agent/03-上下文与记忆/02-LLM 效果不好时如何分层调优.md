# 02 LLM 效果不好时如何分层调优？

## 01 核心回答

**回答（三层法）：**

L1 Prompt 调优（常见低成本手段，按实际瓶颈选择）：① 定义执行协议——角色、边界、输出格式、拒答策略；② 结构化输出——JSON Schema/函数调用；③ 少量高质量 few-shot（正例 + 反例）；④ 上下文工程——按 Gather-Select-Structure-Compress 组织；⑤ 建评测集——50-200 条真实样本，按准确率、格式通过率、幻觉率评估；⑥ 提示词版本化——A/B、灰度、可回滚。

**L2 检索与工具链路（第二层）：**① RAG 数据治理（清洗、去重、切块、元数据）；② 检索策略（hybrid + rerank）；③ 查询改写（multi-query、HyDE）；④ 工具编排（路由器决定直接答/检索/调工具，信心阈值 + 兜底）；⑤ 结果校验（schema 校验、失败重试或降级）；⑥ 观测闭环（检索命中率、工具成功率、端到端成功率、时延、成本）。

**L3 训练调优（最后做）：**① 触发条件——Prompt+RAG 已到瓶颈仍有稳定性/领域表达问题；② 先 SFT（真实任务轨迹数据）；③ 参数高效微调优先 LoRA/QLoRA；④ 再做偏好优化 DPO/RLHF；⑤ 训练数据覆盖高频失败样本、难例、边界例；⑥ 上线策略——影子流量 + 小流量灰度 + 回归评测，避免微调后退化。

原则：通常优先低成本干预，但顺序由错误归因与验证决定——先改低成本高收益环节。很多线上问题来自上下文构造和评估缺失，不是模型不够强。

**微调后变差的排查顺序：**先回滚模型流量止损（卸载新 LoRA adapter），再按**数据（标注噪声/分布漂移/样本冲突）、训练（学习率/epoch/过拟合/LoRA 参数）、评测（离线集不代表线上/口径错误）、系统（RAG/工具链路变了）**四层对照排查，最后小流量灰度重放上线。

---

## 02 调优顺序不是硬编码流水线

先固定业务基线并分类失败：缺知识、缺能力、输出格式错、权限阻断或工具不可用分别需要不同改法。明显的检索和数据错误不必先折腾 Prompt；没有评测基线就微调，则无法确认改善来自哪个变量。

50–200 条只能是启动样本量示例，长尾安全与复杂流程可能远远不够。训练、开发和最终测试集按任务或时间隔离，避免同源样本泄漏。每次改变一组可解释变量，用误差分桶和成本收益决定是否继续。

口述：“先定位瓶颈，再从可验证且成本较低的干预开始。Prompt、检索、工具、训练是不同杠杆，不是人人必须依次走完。”
