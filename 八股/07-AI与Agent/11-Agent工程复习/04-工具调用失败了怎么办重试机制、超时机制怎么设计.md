# 04 工具调用失败了怎么办?重试机制、超时机制怎么设计?

## 01 核心回答

**一句话结论:**核心原则是**区分可重试与不可重试错误,失败信息回灌给 Agent 决策,而不是无脑重试**。

可重试(指数退避):按服务契约确认可安全重试的网络/限流/服务端错误 → 指数退避 + 抖动(Exponential Backoff + Jitter),设置最大重试次数(如 3 次)与总超时上限。

通常需先修复原因:参数校验失败、鉴权失败、404 是否暂时不可见取决于契约，不能机械归类；参数与权限错误应先处理原因,直接把错误转成结构化反馈让 Agent 修正参数/换工具。

幂等设计:写操作必须带请求 ID/幂等键,并由服务端持久去重与业务回查控制重复副作用(避免重复下单/重复写库)。

超时机制:分连接超时、读取超时、总执行超时三层;超时后返回明确状态；写操作可能结果未知，应先回查，不保证下游已取消。

记忆要点:退避重试防抖 + 幂等防重复 + 错误分类防空转 + 反馈模型让它自己改;能说出"429 要退避、参数错要改参不是重试"就及格。

## 02 状态未知与不可重试并不相同

超时、5xx 和断线可能发生在业务已经提交之后。写操作先核验原业务 ID，只有确认未生效且安全才重试；生成幂等键还需要服务端持久去重。404 是否暂时可重试取决于资源可见性契约，不能仅凭状态码一刀切。

连接、读取、单次请求和整体任务的超时应有包含关系，并考虑 SDK 内部重试。遵守 Retry-After、指数退避加抖动以及全局预算；取消请求不保证下游执行被取消。
