# 03 Function Calling 底层模型是怎么"决定"该调哪个工具、传什么参数的?

## 01 核心回答

**一句话结论:**本质仍是**语言模型的自回归预测**:工具描述和参数 Schema 随请求提供，模型据输入生成工具选择与参数提议；结构合法性还取决于是否启用受支持的严格约束或校验。

决定依据:模型综合用户意图 + 对话历史 + 各工具的描述与参数说明做语义匹配;清晰描述可减少歧义，但选对率仍受模型、工具数量与任务分布影响(典型失败是工具描述含糊导致选错)。

参数生成:模型利用 Schema 的 required 字段、类型与枚举描述生成结构化参数，普通生成模式仍可能违背格式;部分模型可能产生推理摘要或内部推理，但不要求披露隐藏思维链，也不自动保证参数准确。

**工程侧兜底:**不能完全信任模型输出——调用前做 Schema 强校验、参数白名单/枚举校验、低温度、必要时加 few-shot 示例,校验失败让模型重生成而不是直接执行。

记忆要点:"选工具靠语义匹配,传参数靠 Schema 约束,可靠性靠工程校验"——模型负责决策,代码负责兜底。

## 02 模型生成和程序强制约束分开

模型根据输入和训练形成调用选择，不只是对工具说明做一个独立关键词匹配。Schema 放进提示并不必然保证合法 JSON，约束解码或严格模式支持范围依供应商而异；即使结构合法，参数也可能对应错误账户、时间或单位。

工具说明应准确区分用途、禁用条件和关键参数，工具太多或高度重叠会增加误选。调用前仍做业务语义与授权校验；缺关键参数时澄清，不能把默认值当万能补全。

推理说明不是必须向用户展示的真实内心过程，也不保证参数更准确。口述：“模型建议工具与参数，解码与校验守格式，执行层守业务和权限。”
