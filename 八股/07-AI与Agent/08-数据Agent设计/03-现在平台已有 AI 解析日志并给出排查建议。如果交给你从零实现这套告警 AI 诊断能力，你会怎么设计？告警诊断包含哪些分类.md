# 03 现在平台已有 AI 解析日志并给出排查建议。如果交给你从零实现这套告警 AI 诊断能力，你会怎么设计？告警诊断包含哪些分类？

## 01 核心回答


设计成**“告警接入、上下文补全、假设生成、分层取证、根因判断、处置建议、结果反馈”**七步链路：

1. **告警接入：**去重、聚合并关联服务、版本、部署和时间窗口，提取错误指纹、指标异常和最近变更。

2. **上下文补全：**聚合告警相关上下文，构建受限证据上下文（关联版本、变更、时间窗）。

3. **假设生成：**Agent 生成多个结构化竞争假设（根因候选/支持征兆/会否证它的证据）。

4. **分层取证：**按区分度和取证成本调用日志、Trace、Kubernetes、配置和发布记录等**只读工具**，逐轮验证和剪枝。

5. **根因判断与处置建议：**输出必须经过 Schema 校验、证据引用和置信度检查，涉及副作用的操作必须审批。

6. **结果反馈：**诊断结果回流，持续优化（正确/错误案例进评测集）。

**诊断分类：**应用异常、依赖服务异常、数据库与缓存、网络与 DNS、资源与容量、配置或发布变更、数据质量、权限与证书、基础设施故障。

**安全边界：**设计上可把 LLM 限制为**提交建议事件**，状态机负责确定性流转，避免模型直接改变生产状态。

**面试追问：**为什么取证工具只读（生产安全 + 可审计）；假设为什么要多个（竞争剪枝防一条路走到黑）；LLM 为什么不直接改状态（不可控 + 审计要求）。

---

## 02 从告警现象到可证伪假设

先定义事件时间、影响服务、发布版本和异常基线，将重复告警归并为一次事件。证据分为指标趋势、Trace 异常路径、相关日志、配置/发布变更和依赖状态；相同时间出现的现象不自动构成因果。

每个假设带支持证据、反证条件和下一步查询。例如数据库延迟升高可能是连接池耗尽、锁等待、慢 SQL 或上游请求放大，应选能区分这些情况的只读检查。若证据不足，输出“待验证假设”而非确定根因，置信度需校准而非模型自报百分数。

---

## 03 处置与评价

将建议、审批、执行和效果验证分开。故障时先根据预定规则止血，Agent 的诊断不能阻塞已有应急流程；处置后核查错误率、时延和业务指标是否恢复，防止“命令成功”但事故仍在。日志需脱敏和限制时间窗口，不全量外发。

评价看根因命中、证据支持、误报、诊断时长与人工采纳后的实际结果。本页是可改编设计，原文“项目中”不代表本人已上线该系统。

口述：“让模型提出竞争假设，工具提供可验证证据，状态机控制处置与验收。”
