# 02 假设要开发一个需求开发 Agent，输入需求可能是加工数据表、制作 BI 看板或对接数据产品应用。如果由你设计这个 Agent 的整体工作流程，你会怎么做？

## 01 核心回答


**① 意图识别与拆解：**对自然语言需求做意图识别和结构化拆解，提取业务目标、数据范围、指标口径、产出类型和验收条件。

**② 检索与方案确认：**检索数据目录、指标字典、表血缘和历史案例，生成候选方案并让用户确认关键口径。

**③ 分类型计划：**确认后进入计划阶段——加工数据表：生成数据模型、SQL 和调度依赖；制作 BI 看板：生成指标、维度、图表和权限配置；对接数据产品：生成接口、字段映射和联调计划。

**④ 安全执行：**工具白名单、参数校验、沙箱或测试环境和人工审批。

**⑤ 自动验证与交付：**完成后自动运行数据质量校验、接口测试和看板验收，最终输出变更记录和可回滚方案。

**面试追问：**为什么关键口径要人工确认（LLM 理解歧义，一次确认省返工）；沙箱执行的意义（防误改生产）；回滚方案为什么必须（AI 产物不可控，留退路）。

---

## 02 把三个交付分支接到同一验收状态机

共同状态保存目标、已确认口径、数据权限、依赖、计划版本、产物引用和验收条件。数据表分支检查唯一键、分区、增量语义与回填范围；BI 分支检查指标口径、聚合粒度、维度过滤和可见权限；接口分支检查契约、错误码、限流和幂等。

先在测试环境产出可审阅方案与变更，再执行对应验证。开发完成不等于发布授权，尤其表结构迁移、看板共享和接口开放会改变其他人的访问或业务行为，需按治理规则审批。长任务持久化状态，失败时保留已验证产物并明确哪些未执行。

---

## 03 直接追问

“如何避免需求改变后继续按旧计划执行？”计划有版本，关键口径变化使下游产物和审批失效；重新验证受影响的分支。“怎么回滚？”代码和配置可切旧版，但数据变更要有备份、兼容迁移或补偿，不承诺任意 SQL 都能一键撤销。

口述：“共用需求与状态底座，按产出类型拆执行器；每个阶段都能验收、恢复和追溯，发布与数据权限独立控制。”
