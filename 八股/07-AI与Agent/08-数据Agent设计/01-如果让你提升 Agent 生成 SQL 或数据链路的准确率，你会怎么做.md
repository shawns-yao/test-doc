# 01 如果让你提升 Agent 生成 SQL 或数据链路的准确率，你会怎么做？

## 01 核心回答


把问题拆成**“理解需求、检索知识、生成 SQL、执行校验、结果解释”**五个环节，逐环加约束和反馈：

1. **元数据与约束：**先建立统一的指标、表、字段和血缘元数据，使用结构化 Schema 约束模型输出。

2. **知识检索：**生成 SQL 前检索相关表结构、字段含义、样例值和历史正确 SQL，减少幻觉。

3. 执行前校验：SQL Parser 检查语法与语句结构，数据库身份与行列策略校验真实权限，再通过 EXPLAIN、成本限制和只读连接做安全检查。

4. **结果校验与修正：**执行后进行行数、空值、时间范围和指标口径校验，失败则把错误信息反馈给 Agent 进行**有限次数修正**。

5. **评测闭环：**用固定评测集衡量 SQL 执行成功率、结果正确率、关键链路召回率和 Token 成本。

**面试追问：**为什么生成前要检索知识（减少幻觉、对齐口径）；校验失败让 Agent 自纠几次（有限次数，防死循环）；评测指标怎么定（执行率 + 正确率 + 成本）。

---

## 02 准确率提升的执行细节

先抽取指标、维度、时间范围、粒度和过滤条件。存在歧义时澄清，例如“活跃用户”是去重登录还是产生事件，不能让 SQL 语法正确掩盖口径错误。Schema 检索保留表间连接键、基数、分区和字段单位，并优先提供已验证 SQL 模板。

SQL Parser 能识别语法与语句结构，但真实权限必须由数据库角色/行列策略执行；仅检查 SELECT 也可能遇到高成本查询或有副作用的函数。EXPLAIN 的估算不是实际运行成本保证，EXPLAIN ANALYZE 会真正执行，应放在受控环境并配置超时与资源限制。

结果验收至少有三层：能执行、业务结果正确、符合授权与资源预算。用已知小数据集验证 JOIN 放大、NULL、时区、去重和聚合粒度，再在代表性数据上测性能；不同 SQL 文本可能同样正确，不应只靠字符串精确匹配评分。

---

## 03 追问与口述

“错了让模型改几次？”按错误类型有限纠正，权限拒绝不能当成改写绕过理由；结果未知先核验。“如何减少幻觉字段？”优先 schema linking、约束解码和执行前解析，仍需回到数据库元数据确认。

口述：“我先保证业务口径和表结构正确，再加执行前权限与成本控制，最后用结果语义评测，而不是把能跑当成答对。”
