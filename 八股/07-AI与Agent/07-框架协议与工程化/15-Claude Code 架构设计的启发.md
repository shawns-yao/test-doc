# 15 Claude Code 架构设计的启发？

## 01 核心回答

**回答（六课）：**

① Agent 工程特别重要——模型调用之外，还需设计权限、上下文管理、错误恢复和任务协调，不引用未经核验的代码比例；② 提示词分层管理——静态层走缓存节省费用、动态层注入实时环境信息，每个工具配一份给 AI 看的使用手册；③ 安全的重视——根据真实行为与权限评估工具风险，不能仅相信工具自身声明；④ 上下文管理是生命线——上下文窗口是策略不是开关，区分哪些内容可丢、哪些必须保留；⑤ 记忆系统要「精确」不「贪多」——宁可漏掉可能有用的记忆，也不把不相关记忆塞进上下文污染判断；⑥ 多 Agent 协作给每个 Agent 明确「身份」——协调者只协调、执行者只执行，职责边界在设计阶段写死。

工程细节补充：工程细节应按官方所述版本核验。可借鉴的原则是权限边界、按需工具使用、上下文压缩及明确子任务职责；原稿内部代码规模、文件数、审查层数、固定压缩阈值和提示语缺少可靠依据，已移除事实性断言。

## 02 未经证实数字的勘误

原文中“模型调用占比不到 5%”“51 万行代码”“18 个安全文件、9 层审查”“87% 自动压缩”和具体子代理提示语，没有可核对的官方版本依据，不能作为面试事实引用；以下以公开文档支持的原则为准。

Claude Code 官方架构说明强调围绕模型的工具执行、权限与上下文管理。可以借鉴任务—工具—反馈循环、在权限边界内执行以及长上下文压缩，但具体实现可能随版本改变。工具自称安全不等于执行许可；自动摘要也可能丢失条件，需要保留可回查的产物和目标。

可改编口述：“我关注的是它如何让模型在工具与反馈闭环中工作，而不会用未核验的代码行数或内部阈值证明架构优劣。”

## 05 补充子任务扩散的限制

工程设计还应限制递归派生子任务：同时约束派生深度、总子任务数、全局 token/时间预算和在途并发。子任务不能绕过父任务权限和预算，终止时要回收仍在执行的后代任务。这是避免无界扩散的治理要求，不把未公开的产品内部限制写成既定事实。

## 07 补充上下文整理的顺序

官方说明的上下文整理包含先清理旧工具输出，必要时再摘要对话。这个顺序有助于先减少较容易重取的冗余，再压缩语义信息；不据此宣称固定 87% 阈值或未公开的内部文件结构。
