# 14 什么是 Harness Engineering？

## 01 核心回答

**概念：**Harness（驾驭工程）的核心是**系统性地设计约束、反馈链路和持续改进机制**，使 AI Agent 在规模化、长周期的软件开发中可靠运行——包含系统提示词、工具、文件系统、沙箱、编排逻辑和检查机制，本质上回答三个问题：AI 在哪干活？用什么干活？怎么知道干得对不对？

**本质：**把工作方法和判断标准转化为 AI 能理解和执行的环境——AI 出错时反问「我的环境里缺了什么」；工程师角色从「写代码」转向「设计环境/标准、建立反馈」。

实践细节：除了开发 Agent，并行起一个测试 Agent打通反馈链路——测试 Agent 在授权范围内读取所需工具链的脱敏日志、端到端模仿人在浏览器验证每个功能、收集报错信息给开发修正。Linter 错误信息面向 AI 重写——每条报错包含 AI 决策所需完整信息：规则意图（这条规则防什么问题）、具体修复方向（不是「你错了」而是「你应该这样改」）、上下文约束（依赖方向等架构规则违反时说明是哪条链路）。

---

## 02 Harness 的验收闭环

Harness 是模型外围的运行环境与控制体系，包含工具契约、状态恢复、权限、测试和反馈。它不只适用于编程，也不是统一协议或某个框架名；“工程师角色转向”是趋势描述，不代表人无需评审代码与承担设计责任。

长任务可保存进度、已验证产物和下一步，让新一轮在已知状态继续；独立测试器检查外部结果而非相信生成报告。测试 Agent 读取日志仍需最小权限和脱敏，“能读所有日志”不应成为设计默认。

口述：“我把模型放进能获取真实反馈、可恢复且有安全边界的系统里，并用任务验收证明改动有效。”

## 05 直接追问：如何组织 Agent 可查找的工程知识

可以把仓库说明入口做成简短地图，指向架构约束、任务计划、接口契约、测试方式和关键设计决策；详细材料分层组织，Agent 按当前任务加载。渐进披露的目的，是让需要的信息可发现，同时避免把全部规则重复塞进每一轮上下文。

OpenAI 的 Harness 工程案例明确采用简短的 AGENTS.md 入口和结构化 docs，并用检查维护文档链接与时效。可迁移的设计是“可定位、可校验、随代码更新”，不要求照抄某个行数或目录。项目自身仍需决定知识负责人、可信来源及访问权限。[官方工程案例](https://openai.com/index/harness-engineering/)
