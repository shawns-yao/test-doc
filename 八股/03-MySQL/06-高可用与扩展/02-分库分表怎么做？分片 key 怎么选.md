# 02 分库分表怎么做？分片 key 怎么选？

## 01 核心回答


**概念原理（什么时候才分）：**通常先确认**容量、写入吞吐、隔离或维护目标**的实际瓶颈，再评估分片，不能按两千万行一刀切；分库 = 分布到多个库，分表 = 分布到多张物理表；均可结合垂直或水平策略；常见拆分：垂直拆分（按业务模块/字段冷热）→ 水平拆分（按分片键数据分散）。

**分片 key 选择原则：**

① 选**高频等值查询条件**（如 user_id/order_id）——保证同一实体的数据在同一分片，单分片内完成大部分查询。
② 分片键要**分布均匀**（避免热点）。
③ 分片方式包括：**哈希取模**（`user_id % N`，均匀但扩容要迁移）、**范围分片**（按时间/ID 区间，扩容简单但可能热点）和**一致性哈希**（迁移量小）。
④ 关联查询多按同 key 分片；跨分片查询使用冗余表或汇总。

**分库分表的缺陷与补偿：**跨分片事务（尽量收敛单分片，必要时 2PC/TCC/最终一致）、全局唯一 ID（雪花/号段）、跨分片 JOIN（冗余/应用层组装/大宽表）、扩容迁移（双写 + 影子迁移）、分片路由（中间件 ShardingSphere/MyCat）。

全局 ID 的时钟回拨与唯一性单独见雪花算法问题；分片路由不能替代全局 ID 和业务幂等设计。

**面试追问：**取模分片扩容怎么迁（2 倍扩容法：N → 2N 只迁移一半数据）；分片后怎么按非分片键查询（索引表/基因法）；全局 ID 详见关联的雪花算法笔记。

---

## 02 理解机制与追问

分库、分表描述部署和逻辑划分位置；垂直、水平描述拆分维度，二者不能一一对应。水平分片常以逻辑槽或路由表间接映射物理分片，降低扩容时全面修改业务取模规则的成本。共分片能保留本地事务，但全局唯一约束仍需要单独设计。

---

## 03 易错点与适用边界

分片后局部唯一键不一定能保证全局唯一；分片键缺失的查询可能广播。分片数量、数据量与访问流量均匀性都应分别验证，不能只用取模公式证明热点消失。全局 ID 的生成、业务幂等与分片定位是三个不同问题。

---

## 04 面试口述

先选择能让核心事务落单分片的稳定键，再解决扩容、全局约束与跨片查询；只有收益超过路由、迁移、运维和一致性成本才值得拆分。
