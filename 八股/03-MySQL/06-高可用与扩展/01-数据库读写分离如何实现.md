# 01 数据库读写分离如何实现？

## 01 核心回答


**概念原理：**读写分离 = 主库负责写，从库（只读副本）负责读，主库通过 binlog 把变更复制到从库；应用或代理按 SQL 类型路由（写走主、读走从），分摊读压力。

**实现流程（三层路由）：**① **应用层**：ORM/数据源切分（ShardingSphere-JDBC、Spring 多数据源路由）自动路由；② **代理层**：数据库中间件（ProxySQL、MyCat）解析 SQL 路由，应用无感；③ **驱动层**：JDBC 驱动级（ReplicationDriver）。复制链路：主库 binlog → 从库 I/O 线程拉取 → relay log → SQL 线程重放。

**关键细节（写后读一致）：**主从延迟是核心问题——刚写入就读的数据要路由到主库、会话粘滞或等待副本追平；**写事务和需要写后读一致的事务应固定走主库；纯只读事务可整体路由副本**；GTID 便于断点续传；监控延迟秒级告警。

**风险与取舍：**延迟导致读到旧数据（可接受最终一致才路由从库）；从库故障要摘除自动切换；复制中断要报警；读写分离不解决写瓶颈（写瓶颈需另行优化或评估分片）；不会自动提升所有查询性能——复杂 Join、报表和大事务仍可能压垮副本，热点数据配合缓存。

**面试追问：**主从延迟怎么处理（读主/等待应用位点；半同步不等于已应用）；写事务为何固定读主（同连接事务与写后读语义；纯只读事务可固定副本）；主库故障切换怎么防脑裂（唯一写主控制 + 隔离旧主；半同步不能单独保证）。

## 02 理解机制与追问

路由应按一致性需求，不应仅靠 SQL 是否以 SELECT 开头。写事务内读、锁定读通常固定在主库同一连接；允许滞后的只读事务可整体固定到一个副本。写后读可走主，或记录提交 GTID 并在目标副本等待该事务应用到位，再读取。等待必须有超时和回主策略。

## 03 易错点与适用边界

修正“事务内读必须主库”：需与写操作一致的事务应读主，纯只读事务可在副本内保持所选隔离级别的快照。半同步仅确认接收持久化，不解决应用延迟；选主还需隔离旧主、防止两个可写入口，半同步本身不防脑裂。固定延迟几秒读从不是严格一致性证明。

## 04 面试口述

读写分离扩展读吞吐，核心风险是副本滞后。我按请求一致性路由，写后读主或等具体提交位点，故障切换还要保证唯一写主。
