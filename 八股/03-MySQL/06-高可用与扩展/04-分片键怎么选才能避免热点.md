# 04 分片键怎么选才能避免热点？

## 01 核心回答

**基本原则：**分片键同时要满足**高基数、分布均匀、长期稳定、查询常携带**四点。高频等值查询优先选择 `user_id`、`order_id` 等业务键，使请求能路由到单个分片；不能只追求均匀而牺牲查询命中。

**热点识别：**先按分片统计 QPS、写入量、锁等待、磁盘和缓存命中率，识别“少数 key 占大多数流量”的情况。时间范围分片易集中最新数据，单个大租户易形成请求热点；递增 ID 是否热点还取决于范围或哈希路由方式。

**降热点手段：**可对天然热点业务键增加**哈希扰动或多桶**，例如 `bucket = hash(order_id) % K`；读请求再并行聚合多个桶。对超大租户可单独分片或租户内二次分片，但要同步修改路由、唯一约束和数据迁移策略。

**不能盲目随机：**随机分片虽然均匀，却会让按用户查询广播到所有分片；因此应根据主要访问路径在“单分片命中”和“写入均匀”之间取平衡，并为非分片键查询准备索引表、冗余字段或搜索索引。

**面试追问：**如果业务天然按商户聚集，热点商户怎么做专项治理？分片键变更时如何迁移历史数据？

## 02 理解机制与追问

均匀的是数据量还是请求量要分开看。哈希可把多个不同键分散，却不能把一个超级商户的单键写入自动拆开。热点租户可独立分片隔离；若仍超过单片能力，按订单或时间桶二次拆分，但这会增加按商户查询和事务的扇出。

## 03 易错点与适用边界

递增 ID 不必然形成分片热点：按范围分片常集中最新段，按合理哈希分片可分散不同 ID。给同一热点键加盐后，读、更新与幂等判定必须能定位所有桶；临时随机写、事后广播查通常只是把写热点换成读放大。唯一性不能只依赖各片局部唯一索引。

## 04 面试口述

我同时看键基数、查询携带率、数据倾斜和请求倾斜。均匀哈希解决多键分布，单键热点还要隔离或二次拆分，并接受相应查询代价。
