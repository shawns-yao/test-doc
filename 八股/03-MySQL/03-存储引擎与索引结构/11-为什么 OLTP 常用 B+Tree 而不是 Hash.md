# 11 为什么 OLTP 常用 B+Tree 而不是 Hash？

## 01 核心回答

**场景：**OLTP 典型查询不只是 `=`，还有范围查询（`between`）、排序分页（`order by limit`）、联合索引前缀查询（`where a=? and b>?`）。

**B+Tree 为什么适合**

① 支持**范围和排序**（叶子有序 + 链表）；② 支持**最左前缀**，联合索引复用性高；③ **磁盘友好**：扇出高、通常层数较少，实际 I/O 还受缓存和行宽影响；④ 一套索引覆盖点查/范围/排序/分页。

**Hash 为什么不作主索引**

只擅长等值查找，不支持范围/排序；无法利用最左前缀；查询能力单一，不匹配 OLTP 复杂多样的 SQL 形态。

**一句话：**OLTP 要的是"一套索引覆盖多种查询"——B+Tree 既支持等值也支持范围/排序且 I/O 稳定；Hash 点查快但能力太窄。

**追问：**Hash 索引在哪用（内存表/精确匹配场景）；为什么不直接用 Hash + 链表（范围查询无解）。

## 02 理解机制与追问

Hash 把键映射到桶，完整键等值查找可很高效，但桶顺序不是业务键顺序。B+ 树保留排序关系，因此一次索引可兼顾点查、范围、前缀和排序。联合 Hash 键通常需要完整键值，不能像字典序树一样自然复用左前缀。

## 03 易错点与适用边界

两者复杂度不能直接换算性能：Hash 有碰撞、扩容和缓存局部性成本，B+ 树有比较和页访问成本。InnoDB 可能用自适应哈希作为已有索引上的内部优化，不意味着用户把主索引换成 Hash；是否启用受版本配置约束。给 Hash 加无序链表也不会产生可高效定位的有序范围。

## 04 面试口述

OLTP 的访问模式通常不止等值查询。B+ 树以一个有序结构兼顾多种访问方式，Hash 更适合完整键等值这一窄场景。
