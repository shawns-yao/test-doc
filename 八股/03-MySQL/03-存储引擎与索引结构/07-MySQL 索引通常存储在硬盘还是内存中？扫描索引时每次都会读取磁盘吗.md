# 07 MySQL 索引通常存储在硬盘还是内存中？扫描索引时每次都会读取磁盘吗？

## 01 核心回答


**概念原理：**索引首先**持久化在磁盘/SSD 表空间**中，重启后仍然存在；运行时 InnoDB 把索引页和数据页加载到 **Buffer Pool**，最近访问的页留在内存。查询是否产生磁盘 I/O 取决于目标页是否在 Buffer Pool、操作系统缓存、预读策略和扫描范围——不是“每次使用索引都读一次磁盘”。

**关键细节：**冷启动或内存不足时，索引页不在缓存，需要从存储设备读入；连续范围扫描可能触发**预读**，减少单页随机读取；即使使用索引，如果需要回表且访问记录分散，也可能产生大量数据页 I/O；覆盖索引只扫描索引页，通常更省 I/O，但索引本身也占用缓存空间。

**风险与取舍：**Buffer Pool 太小 → 命中率低 → 频繁磁盘读；索引太多 → 缓存空间被索引占满 → 数据页被挤出。排查时结合 `EXPLAIN`、`EXPLAIN ANALYZE`、Buffer Pool 命中率、磁盘 I/O、读取请求和查询延迟判断，不能因为执行计划显示 `ref` 或 `range` 就断言一定很快——还要看扫描页数、回表比例、缓存冷热和并发竞争。

**面试追问：**Buffer Pool 命中率怎么查（`SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%'`）；预读是什么（顺序扫描时提前读下一批页）；索引和数据都放内存会怎样（内存不够，缓存竞争）。

---

## 02 理解机制与追问

InnoDB Buffer Pool 统一缓存表页与索引页。查询的逻辑页访问数和存储设备读取数应分别看：一次逻辑读命中内存即可返回，未命中才需要读入；不同 I/O 配置下操作系统页缓存参与程度不同。脏页意味着内存版本比磁盘新，淘汰前需要满足 WAL 并完成刷盘。

---

## 03 易错点与适用边界

全局命中率高也可能掩盖少数冷查询的尾延迟。应取一段时间内计数器增量，结合单条 SQL 实际扫描行数、物理 I/O 与延迟；不要把实例启动以来累计值当成当前负载。大扫描还可能污染缓存，影响热点请求。

---

## 04 面试口述

索引持久化在存储上，热点页缓存在 Buffer Pool；用索引不等于每次读盘。排查要把逻辑读取、物理读取和回表分别量化。
