# 02 B+ 树索引是怎么更新的？

## 01 核心回答


**插入流程：**InnoDB 从根页开始，根据索引键在内部节点中查找子页，直到定位到目标叶子页。叶子页有足够空间就直接插入合适位置；空间不足触发**页分裂**——把部分记录移动到新页，并把新的分隔键写入父节点；父节点也满时继续向上分裂，极端情况生成新的根页（树增高一层）。

**删除与更新：**删除记录通常先做**删除标记**，后续由后台清理；页面利用率过低时发生页合并或重新组织。更新主键 = 删除旧索引记录 + 插入新记录，因此主键应尽量稳定；更新普通列时，如果该列出现在二级索引中，需要同步修改对应二级索引。

**关键细节（写入路径）：**这些操作不是每次都直接同步写入磁盘。目标页通常先加载到 **Buffer Pool**，在内存中修改为脏页；**WAL** 要求刷脏页前相关 `redo log` 有恢复保障；提交持久化强度取决于刷盘配置，脏页再由后台线程刷盘。`undo log` 用于事务回滚和 MVCC；部分符合条件的二级索引页不在内存时，可在启用且符合条件时通过 **Change Buffer** 延迟合并（8.4 默认关闭），减少随机读盘。随机主键容易让插入位置分散并频繁分裂，**递增主键更容易在叶子链表尾部顺序写入**，但分布式系统还要考虑热点和 ID 生成方式。

**面试追问：**页分裂会带来什么问题（写放大 + 空间碎片）；为什么递增主键写入快（尾部顺序写，少分裂）；Change Buffer 缓存什么（二级索引的变更）；WAL 为什么先写日志再刷页（崩溃恢复）。

---

## 02 理解机制与追问

修改页的短期并发保护使用 latch，事务锁保护逻辑记录与隔离性，两者不是同一种锁。删除先标记是为了让仍需旧版本的事务继续读；purge 确认不再需要后才清理。页分裂、二级索引维护和后续刷盘共同形成写入成本。

---

## 03 易错点与适用边界

版本修正：MySQL 8.4 的 innodb_change_buffering 默认值为 none，不能把 Change Buffer 当作默认启用的必经流程。它只适用于符合条件的二级索引修改，不用于聚簇索引，也受唯一性检查等限制。WAL 要求刷脏页前相关 redo 可恢复；提交是否逐次持久化还受刷盘配置影响。

---

## 04 面试口述

先定位叶子页，在 Buffer Pool 修改；空间不足会分裂并影响父节点。删除还要考虑 MVCC 清理。redo 保证恢复顺序，Change Buffer 是有条件且受版本配置影响的优化。
