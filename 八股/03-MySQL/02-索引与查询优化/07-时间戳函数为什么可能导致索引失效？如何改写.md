# 07 时间戳函数为什么可能导致索引失效？如何改写？

## 01 核心回答


**概念原理：**普通 B+ 树索引保存的是**原始列值**。如果在索引列上使用函数，例如 `DATE(create_time) = '2026-09-07'`，数据库通常需要先对每行的 `create_time` 计算 `DATE()` 后再比较，无法直接根据原始有序值确定连续范围，因此可能放弃普通索引或扫描大量索引项。

**改写方式：**把函数计算转移到**常量侧**，改写为左闭右开的范围条件（既能用索引，也避免时间精度边界遗漏）：

```sql
-- 普通列索引通常难以直接定位：列上套 DATE 函数
SELECT * FROM t WHERE DATE(create_time) = '2026-09-07';

-- 等价时间语义下改为半开范围，提高普通索引可检索性
SELECT * FROM t
WHERE create_time >= '2026-09-07 00:00:00'
  AND create_time <  '2026-09-08 00:00:00';
```

**关键细节：**注意字段类型和参数类型一致，防止隐式转换；确实需要按表达式高频查询时，可评估**生成列**或函数索引（MySQL 8），但会增加存储和写入维护成本，仍需执行计划验证。

**面试追问：**为什么右开（避免包含次日 00:00:00）；函数索引是什么（索引存函数结果）；隐式转换为什么失效（字符串列被转成数字比较）。

---

## 02 理解机制与追问

范围改写成立的前提是保留同一时间语义。TIMESTAMP 会受会话时区转换影响，DATETIME 通常表示无时区的日期时间；“某地一天”在夏令时切换日未必等于固定 24 小时。应先按业务时区计算当天起止时刻，再转换为存储列对应的边界。

---

## 03 易错点与适用边界

原示例“错误/正确”只指普通索引的可检索性，并不代表前者 SQL 结果错误，也不能保证后者一定选索引。若索引建在匹配的函数表达式或生成列上，函数条件也可利用该索引。半开区间避免小数秒精度变化带来的末秒遗漏。

---

## 04 面试口述

先把业务日期转成同一时区下的起止边界，保留原列不套函数，用大于等于起点、小于终点表达一天，再验证执行计划。
