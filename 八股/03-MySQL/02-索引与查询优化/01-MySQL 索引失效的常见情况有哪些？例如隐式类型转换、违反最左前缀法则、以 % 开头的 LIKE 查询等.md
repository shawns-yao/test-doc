# 01 MySQL 索引失效的常见情况有哪些？例如隐式类型转换、违反最左前缀法则、以 `%` 开头的 `LIKE` 查询等。

## 01 核心回答


常见情况包括：

**函数/表达式/计算**
对索引列做函数或计算，例如 `DATE(create_time)`，无法利用原始有序值。

**隐式类型转换**
字符串列用数字条件比较，导致索引列被转换。

**违反最左前缀**
跳过最左列或中间缺列，通常限制连续范围定位，但不等于完全无法使用索引。

**左模糊 LIKE**
`LIKE '%abc'` 无法按前缀定位；`'abc%'` 可以。

**OR 一侧无索引**
`OR` 时其中一侧没有索引，优化器可能放弃索引，具体看成本估算。

**!= / NOT IN / 大范围**
选择性变差，优化器可能选择全表扫描。

**数据量/统计信息**
数据量很小、返回比例高或统计信息不准确时，全表扫描可能更便宜。

排查时使用 `EXPLAIN` 查看 `key`、`type`、`rows` 和 `Extra`，再结合实际数据分布判断，不应把“执行计划没有使用索引”简单等同于数据库出错。

**面试追问：**为什么函数会让索引失效（B+ 树存的是原始列值，无法按函数结果定位）；`%abc%` 怎么优化（覆盖扫描/倒排检索；普通前缀索引不能直接解决包含匹配）；范围条件后索引失效的边界（通常停止扩展后续范围键，仍可能索引层过滤）。

## 02 理解机制与追问

先区分三种现象：不能用条件构造索引查找范围、仍能做索引扫描或覆盖过滤、优化器认为全表扫描更便宜。“索引失效”把这三种情况混在一起会误判。字符串列与数字比较可能需要转换列值；数字列与可转换的字符串常量比较则不能一概判定失效。

## 03 易错点与适用边界

修正：缺最左列不等于索引完全不可用，MySQL 8 的 Skip Scan 在满足单表、覆盖等限制时可能枚举前缀后扫描；也可能全索引扫描。范围后的列仍可参与 ICP/覆盖。普通前缀索引不能解决任意包含搜索；倒排检索需按分词与业务语义选择。函数索引匹配表达式时也可能可用。

## 04 面试口述

我先问是不能定位、不能覆盖，还是成本模型没选它；用访问范围、实际行数和回表量验证。修改 SQL 后保持结果语义一致，再比较整体读写成本。
