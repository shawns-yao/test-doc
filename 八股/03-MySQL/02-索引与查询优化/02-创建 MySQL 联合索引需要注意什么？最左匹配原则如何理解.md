# 02 创建 MySQL 联合索引需要注意什么？最左匹配原则如何理解？

## 01 核心回答


**概念原理（最左匹配）：**联合索引按索引列从左到右的顺序组织 B+ 树，例如索引 `(a, b, c)` 首先按 `a` 排序，`a` 相同时再按 `b` 排序，`a、b` 都相同时再按 `c` 排序。因此查询通常要从最左列开始连续使用：条件只有 `b` 或 `c` 时通常不能按普通最左前缀定位，但可能覆盖扫描或 Skip Scan；条件包含 `a`，或 `a、b`，才符合最左前缀。

**设计注意：**① 结合真实查询设计，而不是机械地把区分度最高的字段放最前；② 优先覆盖高频等值过滤、租户或业务范围、排序和分组字段，再考虑范围条件和需要覆盖的返回列；③ **范围条件之后的列通常不能继续缩小扫描区间**，但有时仍可通过 Index Condition Pushdown 在索引层过滤；④ 避免与现有索引前缀重复的冗余索引——已有 `(a, b)` 时，单列索引 `(a)` 可能没必要。

**风险与取舍：**索引列不是越多越好——联合索引增加磁盘占用、Buffer Pool 压力和插入更新成本；字段过长降低单页容纳的索引项数量。最终用 `EXPLAIN`、实际数据分布和线上慢查询验证，关注是否减少扫描行数、排序、临时表和回表，不能只看 `key` 字段是否出现索引名。

**面试追问：**范围条件后的列为什么通常不再缩小连续范围（排序只保证同 a、b 内 c 有序）；ICP 是什么（索引条件下推，索引层过滤减少回表）；`(a,b)` 索引能覆盖仅返回 `a` 的查询吗（能；是否覆盖取决于全部所需列）。

## 02 理解机制与追问

把联合索引理解为字典排序。WHERE 中 a、b、c 的书写顺序不必等于索引顺序；优化器可重排等值条件。真正决定可用前缀的是有哪些条件以及比较方式。等值列在前、范围列在后只是常见方案，若 ORDER BY、LIMIT、覆盖需求更重要，列顺序可能不同。

## 03 易错点与适用边界

“覆盖”取决于全部查询列，不是只看过滤列。(a,b) 可支持 a 的查找，但 SELECT 其他未覆盖列仍需回表。等值范围如 IN 可能形成多个小范围，不应把所有“范围条件”简单视为同一种截断。去掉冗余前缀索引前要验证其唯一约束、长度和排序方向是否相同。

## 04 面试口述

我会把主要查询列成访问模式，平衡过滤、排序、覆盖和写入开销；最左前缀解释的是字典序定位能力，不能机械等同于 SQL 条件书写顺序。
