# 04 两千万数据量的 MySQL 表应该如何设计和优化？

## 01 核心回答


**概念原理：**两千万行本身并不意味着必须分库分表，首先要看单行大小、访问模式、并发量、增长速度和延迟目标。优化顺序：表结构 → 查询 → 架构，逐层看瓶颈。

**表结构层：**选择合适的数据类型，避免无意义的大字段和过长主键；主键尽量短小、稳定；常用过滤和排序条件建立合理索引；大文本、低频字段按访问模式拆到扩展表，但不能为了“看起来规范”盲目拆表。

**查询优化层：**从慢日志和执行计划出发，减少全表扫描、深分页、返回大字段和无效回表。列表查询用覆盖索引和基于主键或时间的**游标分页**；历史数据归档到历史表或冷存储；按时间范围访问且有明确生命周期时考虑**分区**——高频查询若能约束分区键，更有机会获得分区裁剪收益，分区也不能替代索引。

**架构层：**Redis 缓存热点数据、只读副本分担查询、异步化非核心操作、搜索引擎承接复杂检索。只有单实例容量、写入吞吐或维护窗口确实成为瓶颈时，才考虑**分库分表**，并提前设计分片键、全局 ID、跨分片查询、扩容和数据迁移。

**风险与取舍：**分库分表引入的复杂度（跨片查询、全局 ID、扩容）远大于收益时不要提前做；拆表/分区要评估查询模式变化；优化后必须用真实 SQL 和数据量验证 P95/P99 延迟、扫描行数、Buffer Pool 命中率、磁盘 I/O 和主从延迟。

**面试追问：**什么时候才必须分库分表（容量/写入吞吐/维护窗口是硬瓶颈）；分区和分表的区别（单机内 vs 跨实例）；深分页怎么优化（游标分页/延迟关联）。

## 02 理解机制与追问

容量估算先看“行数 × 平均行宽 + 每个二级索引 + 预留空间”，工作集大小决定 Buffer Pool 能否容纳热点。再看高峰读写、锁冲突、每小时增量以及备份恢复和 DDL 所需时间。两千万条窄行和两千万条大文本记录可能是完全不同的问题。

## 03 易错点与适用边界

分区主要帮助分区裁剪和生命周期管理，不会自动提供跨机器扩容。MySQL 分区表要求分区表达式涉及的列包含在每个唯一键中，可能改变业务唯一约束设计。分区键是否出现在查询中是裁剪效果的常见前提，不是创建分区的语法要求。

## 04 面试口述

我不会先按行数决定分库。先用容量、延迟和维护窗口确认瓶颈，优先优化索引与访问路径，再评估归档、分区、只读副本，最后才承担分片复杂度。
