# 08 SQL 分页怎么写？深分页有什么问题？

## 01 核心回答


**概念原理（深分页问题）：**普通分页 `LIMIT offset, size`（如 `LIMIT 20, 10`）在偏移量很大时，MySQL 仍需要找到并扫描前面的记录再丢弃绝大部分；如果还要回表或排序，深分页的 I/O 和 CPU 成本明显增加，而且并发插入、删除可能导致翻页重复或遗漏。

**游标分页（Seek Method，推荐）：**记录上一页最后一条数据的有序键，下一页用 `WHERE id > last_id ORDER BY id LIMIT 10`。按时间和主键联合排序时，用 `(create_time, id)` 作为稳定游标，条件同时比较时间和 ID。不适合直接跳到任意页，但适合连续向后翻页和滚动加载。

**深分页的其他方案：**

① **延迟关联**：先通过覆盖索引只查询目标主键，再与原表关联获取完整数据。
② 限制最大页数，或提供条件筛选。
③ 由搜索引擎承接。

无论哪种方式，**排序字段必须稳定且最好唯一**，否则分页结果可能不确定。

**面试追问：**为什么 LIMIT 100000, 10 慢（扫描 100010 行再丢 100000 行）；游标分页为什么不能跳页（没有偏移概念）；排序字段不稳定会怎样（翻页重复/漏数据）。

---

## 02 理解机制与追问

游标要包含完整且唯一的排序元组。例如按时间降序、ID 降序，下一页必须同时处理“时间更小”以及“时间相同但 ID 更小”，不能只比较时间。游标还应绑定原查询筛选条件，否则换条件后继续翻页没有意义。延迟关联只减少回表次数，offset 对应的索引项仍要扫描和跳过。

---

## 03 易错点与适用边界

游标分页减少偏移成本，但不自动提供跨请求固定快照。排序字段被更新、数据删除或筛选字段变化仍会影响后续页面；严格导出应使用合适的一致性快照或固定版本。原“扫描 100010 行”是最理想的有序访问示意，遇到过滤、排序或 JOIN 可能扫描更多。

---

## 04 面试口述

连续翻页优先稳定唯一排序加游标；任意跳页要接受偏移成本或改交互。延迟关联主要省回表，严格一致的导出还需单独设计快照。
