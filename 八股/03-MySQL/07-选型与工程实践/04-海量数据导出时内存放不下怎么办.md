# 04 海量数据导出时内存放不下怎么办？

## 01 核心回答

把“全量查询到 List，再一次生成文件”改为有界管线：按稳定顺序读取一批，转换一批，流式写出并释放一批。长耗时导出用持久化异步任务生成文件，完成后再提供有权限控制的下载；不能只把 HTTP 请求搬到线程池，却仍在后台全量加载。

先明确数据量、平均/最大行宽、输出格式、完成时限以及一致性要求。目标是让客户端内存主要随批次和并发数增长，而不是随总行数增长；数据库执行、驱动缓冲、应用对象、编码器、上传队列都要检查。

---

## 02 分批读取与驱动流式不是一回事

连续翻页优先使用唯一稳定排序加 keyset 游标，例如按不可变主键升序，以 `id > lastId ORDER BY id LIMIT batchSize` 读取下一批；复杂排序需保存完整排序元组，避免同时间记录漏读。深 `OFFSET` 会重复扫描前面的记录，不适合长批量导出。

即使业务一行一行遍历 `ResultSet`，驱动也可能已把整个结果装入内存。MySQL Connector/J 文档区分两条路径：

- 前向只读结果集配合 `setFetchSize(Integer.MIN_VALUE)` 是其逐行流式读取约定，属于驱动特有行为
- `useCursorFetch=true` 配合正数 fetch size 启用游标分批抓取，服务端预处理相关行为按驱动版本核对

流式结果未读完或关闭前，同一连接通常不能随意发其他查询。必须及时关闭 ResultSet、Statement 和连接；ORM 若不断把实体放进一级缓存，也会重新变成全量保留。应用内存降低不等于数据库排序、临时表或服务端游标零成本。依据：[Connector/J 结果集实现](https://dev.mysql.com/doc/connector-j/en/connector-j-reference-implementation-notes.html)、[useCursorFetch 条件](https://dev.mysql.com/doc/connector-j/en/connector-j-connp-props-performance-extensions.html)。

---

## 03 游标不能代替一致性快照

仅保存 lastId 和导出开始时的最大 ID，至多在相应键单调规则成立时限制后续新增，不能阻止已有行被更新、删除，也不能把所有分页固定到同一版本。

允许近似实时结果时，说明导出期间可能变化的语义；要求严格时点一致时，可在合适的 RR 一致性快照内读取，或从已固定版本的快照/离线数据集导出。长事务会占用连接并使旧版本保留更久，需评估 undo、清理压力和数据库负载；对超长任务可考虑专用副本或离线管道，并明确数据新鲜度。RR 与 RC 的快照差异见 [InnoDB 一致性读](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)。

进程重启后新建事务不能自动恢复原事务的 Read View。严格快照任务若没有可重新读取的固定源版本，应重新生成，不能拼接旧快照前半段和新快照后半段并宣称一致。

---

## 04 输出端和背压同样要有界

CSV/JSONL 可以逐行编码到缓冲输出流；需要 Excel 时评估 SXSSF 等流式写入方式，按格式容量拆文件或工作表。SXSSF 会将窗口外行写入临时文件，但共享字符串、批注、合并区域等仍可能大量占内存，临时磁盘也必须有上限，结束及异常路径都要清理。依据：[Apache POI SXSSF](https://poi.apache.org/components/spreadsheet/how-to.html#sxssf)。

写盘或上传变慢时，读取端要随之减速：单线程读写天然形成顺序背压，多阶段并行则使用有界队列和有限在途批次。不要把每批数据都放进异步 Future 列表再统一等待，也不要把文件先写进无上限 ByteArrayOutputStream。

估算每个任务的批数据、对象与字符串放大、编码/压缩缓冲、在途上传分片和临时文件开销，再乘并发任务数；最大行宽比平均值更容易打破预算。限制每租户和全局导出并发、读取速率与连接占用，避免报表任务挤占在线交易。

## 05 持久任务与失败续传如何设计

以下是工程设计方案：任务表记录请求者、筛选条件、字段/格式版本、一致性模式、源版本、状态、进度和输出引用。工作进程领取任务后，分批生成临时产物；校验行数、字节数和校验和，确认产物完整可读，才把任务发布为 SUCCEEDED。对象上传成功但状态更新失败时，可按任务及产物标识幂等核对，而不是再次生成并暴露两个结果。

需要重试续传时，可按稳定区间生成独立分片，持久化“任务版本、区间、最后游标、分片标识、行数、校验和”。只有分片持久化完成后才推进检查点；进程在两步间退出时，重试应识别已完成分片，避免追加重复行。最终 manifest 只引用已校验的完整分片。

恢复能力同时取决于输出格式与源版本：不能对任意损坏的 XLSX/压缩文件直接接着追加；可选择重做当前分片后重新组装，或者重做整个文件。取消时停止后续读取、协作取消在途操作、关闭数据库资源并回收临时产物。下载时再次校验权限和有效期，导出文件不能仅凭可猜测任务 ID 公开访问。

## 06 追问与验收

- **加大堆能解决吗？**只能提高一次性装载上限，数据继续增长或多个导出并发仍会失败，先消除全量保留
- **分页就一定不 OOM 吗？**不一定，批次行很宽、ORM 缓存、工作簿结构或无限异步队列仍可积累全量数据
- **为什么不一直持有 HTTP 连接？**小任务可以直接流式返回；长任务受客户端断连、代理超时和重试语义影响，持久异步任务通常更便于恢复
- **怎么证明修好？**在总行数增加、输出端变慢、超大单行、并发导出、中途退出/重试和数据变更场景下，验证内存峰值有界、业务不漏不重、快照语义成立，在线接口延迟不被拖垮

面试口述：“我先确定一致性和格式，再用稳定游标或驱动流式读取、有界转换和流式输出控制内存。大任务持久化，分片成功后才记检查点；快照、断点续传、连接预算和慢写背压一起设计，不只是把 List 换成 Stream。”
