# 05 MySQL 隔离级别中的读未提交和读已提交有什么特点？

## 01 核心回答


**读未提交（RU）**

允许事务读取其他事务**尚未提交**的修改，可能发生脏读、不可重复读和幻读。

**适用：**不能保证比 RC/RR 更高并发，但读到的数据可能随后回滚——只有对短暂不一致完全不敏感的统计或监控场景才可能考虑，核心交易不使用。

**读已提交（RC）**

只读取已经提交的数据，避免脏读；但同一事务中两次普通查询可能创建**不同的 Read View**，仍可能出现不可重复读和幻读。

**特点：**比 RR 更容易看到最新提交结果，锁定范围可能更小；业务需要跨多条语句稳定快照时，要评估额外的锁、版本或应用层一致性方案。

在 InnoDB 中，普通一致性读主要通过 MVCC 实现，更新、删除和 `SELECT ... FOR UPDATE` 等当前读仍会加锁。隔离级别选择要结合业务语义、长事务、锁等待和副本延迟，不能只按照“隔离级别越低性能越高”做判断。

**面试追问：**RC 和 RR 哪个锁范围小（RC 通常更小，但外键和重复键检查等仍可能用间隙锁）；为什么 RC 还有不可重复读（每次读新建 Read View）；哪些场景用 RU（几乎不用，统计可容忍脏读）。

## 02 理解机制与追问

RC 每条一致性读建立较新的视图，一次 SELECT 内部仍按其视图读取，而不是每处理一行就刷新快照。RU 容许读到未提交版本，可能把随后回滚的数据用于业务决策。读写是否阻塞不能仅用级别排序，InnoDB 的 RC/RR 普通快照读本来就通常不依赖记录共享锁。

## 03 易错点与适用边界

修正：RC 不是绝对没有间隙锁，外键约束检查与重复键检查仍可能需要。RU 也没有普遍“并发更高”的保证，脏读风险通常不值得；统计需求往往可用 RC、快照或专门分析系统解决。RC 的更小锁范围并不免除死锁处理。

## 04 面试口述

RU 允许脏读；RC 避免脏读但两条查询可看到不同提交版本。选 RC 常为减少范围锁冲突，仍要考虑写冲突、外键检查和业务一致性。
