# 07 为什么有 `binlog` 还需要 `redo log`？两者分别解决什么问题？

## 01 核心回答


**redo log**

InnoDB 存储引擎层，面向**数据页修改**，循环写入。

**职责：**WAL 和崩溃恢复——事务提交时脏页没刷回表空间也没关系，在相应刷盘保障下 redo log 已持久化，重启后把修改重新应用到数据页。

**binlog**

MySQL Server 层，记录已提交的**逻辑变更事件**。

**职责：**主从复制、增量备份、按时间点恢复和 CDC；需要支持不同存储引擎和下游订阅者，不能承担 InnoDB 页面恢复的职责。

单独依赖 `binlog` 做崩溃恢复，无法替代存储引擎对脏页和页结构的恢复机制。事务提交时通过**两阶段提交**协调两种日志：先准备 `redo log` → 写入并刷 `binlog` → 提交 `redo log`，这样宕机恢复时可以根据日志状态判断事务是否应该完成，避免主库数据与复制日志不一致。

**面试追问：**两阶段提交哪一步失败怎么恢复（按日志状态判断回滚或补齐）；redo 为什么不用 binlog 替代（层次不同：物理页 vs 逻辑事件）；binlog 什么时候刷盘（提交时，sync_binlog 控制）。

## 02 理解机制与追问

假设页在内存已改、磁盘页仍旧，redo 提供把页恢复到一致状态所需的变更信息；binlog 关注可供复制的事件，不能替代页面级恢复。相反，redo 空间会循环复用且依赖引擎页结构，也不是可长期回放到任意备份的业务增量日志。

## 03 易错点与适用边界

两阶段提交不是要求每个事务独占三次物理 fsync，group commit 可合并多个事务刷盘。常用“prepare → binlog → commit”是逻辑顺序；实际落盘保证必须结合两种刷盘参数。恢复发现完整可判定的 binlog 提交记录后可处理 prepared 事务；文件里出现一截事件不等于已安全提交。

## 04 面试口述

两者分别对齐存储页恢复和逻辑复制，各自不能替代。内部两阶段提交把两种日志的事务决定协调起来，刷盘与组提交决定具体持久化代价。
