# 03 MySQL 默认隔离级别是什么？可重复读解决幻读了吗？

## 01 核心回答


**默认隔离级别：**MySQL InnoDB 默认是**可重复读（Repeatable Read，RR）**。在一个事务第一次执行普通 `SELECT` 时会形成 Read View，后续普通快照读按同一视图判断记录可见性，因此即使其他事务提交了更新，当前事务仍能看到一致的历史版本。

**幻读问题（分场景）：**不能用一句“解决了”概括。

① **普通快照读**：依靠 MVCC 读取同一快照，结果集通常保持一致，传统意义上的幻读不会出现。
② **当前读**（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`）：需要看到最新已提交数据，范围查询通过**记录锁、间隙锁或临键锁**阻止其他事务插入符合条件的新记录。
③ 没有合适索引时，加锁范围和扫描范围可能扩大，锁竞争更严重。

**隔离级别选择：**业务只需要较高并发的已提交数据时评估**读已提交（RC）**；需要跨语句稳定快照用 RR。选择时结合读写比例、锁等待、长事务、主从延迟和业务对一致性的要求，不能只追求最高隔离级别。

**面试追问：**RR 和 RC 的 Read View 创建时机（事务第一次读 vs 每次读）；为什么 MySQL 选 RR 做默认（历史原因 + binlog 复制兼容）；临键锁是什么（记录锁 + 间隙锁组合）。

---

## 02 理解机制与追问

RR 普通一致性读通常在第一次一致性读时建立快照，而不是 BEGIN 一执行就必然创建；WITH CONSISTENT SNAPSHOT 可显式建立相应快照。当前读读取并锁住当前记录，不能把它看成“同一历史快照上加锁”。若先做快照读、再更新其他事务刚插入的行，后续快照读还会看见本事务自己的修改。

---

## 03 易错点与适用边界

关键限定：同一快照、无本事务相关修改的重复普通读可以稳定；带范围锁的当前读阻止相关并发插入。但混用快照读、当前读以及本事务写入时，不能宣称 RR 下观察结果永不变化，更不能等同 SERIALIZABLE。普通 SELECT 在 SERIALIZABLE 和不同事务设置下也可能转为锁定读。

---

## 04 面试口述

InnoDB 默认 RR。重复快照读靠同一 Read View，锁定范围读靠 next-key lock；两条路径的观察时点不同，所以我不会用“RR 完全解决一切幻读”概括。
