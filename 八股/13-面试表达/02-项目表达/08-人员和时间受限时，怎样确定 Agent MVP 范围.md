# 08 人员和时间受限时，怎样确定 Agent MVP 范围

## 01 先选可验收的最小闭环

以两名工程师六周为假设，先确认目标用户、一个高频任务、数据授权和可用依赖，再定验收指标与停止条件。MVP 的“小”是任务边界小，不是省略身份校验、日志、恢复或风险控制。排期是估算，不能仅按人数和周数保证交付。

## 02 交易平台参考场景

可把只读行情/公告检索与证据化解释作为候选：用户提问、检索已授权数据、带时间与来源输出、证据不足时拒绝作确定判断、记录质量与延迟。它是否值得做仍要靠需求验证；查询持仓也涉及敏感账户数据，不能默认获取。

真实下单、自动签名、跨链执行、杠杆及自主付费需要额外的授权、风险评估和恢复设计，不为了展示“Agent 自主性”塞进第一版。原题中的高风险投机或收益导向方案不作为默认 MVP，也不承诺赚钱。

## 03 把排期写成决策检查点

先验证需求与数据接口；接着打通一个可运行的只读纵向切片；然后补固定评测集、权限隔离、故障注入和观察；最后由验收结果决定试用、缩减范围或停止。每一阶段应有可检查产物，并预留依赖失败和安全问题的缓冲。

效果看任务完成与证据支持，效率看单位成功任务成本和时延，风险看越权、错误执行和人工介入。若核心数据不合法可用、指标不达标或团队无法维护，就停止扩功能。
