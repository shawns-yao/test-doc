# 07 灰度发布的风险控制关键点是什么？

## 01 核心回答

**核心四步：**「**分批、观测、门禁、回滚**」。先按用户、租户、地域或实例分批放量，确保灰度组具有代表性；每一批都要有稳定观察窗口，不能刚发布就继续扩大比例。

**指标门禁：**同时看技术指标和业务指标，例如错误率、P95/P99、超时率、CPU/内存、线程池队列、数据库连接，以及支付成功率、下单转化率等。阈值要和基线、流量规模、时间窗口绑定，并设置自动暂停和人工确认。

**一致性控制：**灰度策略、代码版本、配置版本和数据库兼容性要绑定，避免同一用户在新旧版本之间来回漂移。涉及缓存、消息和状态机时，优先保证新旧版本都能读写，切换完成后再清理旧逻辑。

**回滚边界：**应用版本通常可以快速回切，但数据库字段删除、数据格式变更和不可逆消息发送不能简单回滚。发布前要准备反向兼容脚本、流量开关、数据修复方案，并记录每批次的版本和时间。

**面试追问：**灰度看板里你最看重哪 3 个核心指标？灰度流量没有覆盖到真实长尾用户怎么办？为什么发布成功但业务指标下降？

---

### 01.1 如果只能先看三个指标，怎么选

以交易 API 灰度为例，我先看业务完成率（订单/支付最终成功，防止 HTTP 成功但业务没完成）、请求错误率（区分业务拒绝与系统异常）、P99 延迟（覆盖排队与慢依赖）。三者分别检查业务结果、技术失败和慢请求影响；资源饱和度用于解释原因，不能替代结果指标。新旧版本要在相同接口、租户和流量条件下对照，绑定最小样本与持续窗口；流量不足时不能靠暂时零错误宣布通过。离线任务则可把请求 P99 换成任务完成时效，三项选择取决于业务 SLO。

## 02 理解补充与边界校订

小流量可能没有统计能力发现低频错误，也可能因只选内部用户而遗漏真实负载。除了整体成功率，要按接口、租户、地域和新旧版本分组对比。停止条件应提前写清：触发时冻结放量、保留现场、回切可逆部分，并对数据副作用单独处理；不要让自动回滚与自动扩容相互反复触发。
