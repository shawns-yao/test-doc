# 02 Linux CPU 过载时如何排查和优化？

## 01 核心回答


**概念原理：**CPU 过载指计算需求超过可用处理能力；高 load、CPU 利用率和响应延迟需分别观察，不能直接画等号。排查思路"由粗到细"：**谁在消耗 → 在干什么 → 为什么**。

**排查流程（命令链）：**

1. `top`：看负载、CPU 使用率，按 `P` 排序找出最耗 CPU 的进程和线程。

2. `top -Hp <pid>`：定位进程内哪个线程忙。

3. `pidstat -t -p <pid> 1`：确认线程 CPU 占用。

4. 线程 ID 转十六进制（`printf "%x" tid`），`jstack` 匹配线程栈——Java 场景直接看业务代码/GC。

5. `perf top`/火焰图：采样看热点函数。

6. **结合 `vmstat`** 看上下文切换（cs 列）和运行队列。

**常见原因与优化：**① **业务代码热点**：循环/序列化/正则回溯——优化算法、加缓存、减少无谓计算；② **GC 频繁**：Full GC 是 CPU 大户——调堆、查内存泄漏；③ **线程风暴**：线程数过多导致上下文切换爆炸（cs 高）——线程池收敛；④ **自旋/忙等**：锁竞争自旋空转——优化锁粒度；⑤ **日志刷屏**：大量日志序列化+刷盘——降日志级别/批量；⑥ **资源不足**：容器 CPU 配额过小——扩容。

**关键细节：**区分 **用户态 CPU（us）**、**内核态（sy）**、**等待 I/O（wa）**——us 高是计算问题、sy 高是系统调用/锁、wa 高是磁盘瓶颈；load average 高但 CPU 低可能是 D 状态（不可中断 I/O）进程堆积；先看趋势（是否持续）再动手。

**风险与取舍：**不要凭 top 一屏就下结论——要持续采样（`top -d 1`、sar）确认持续性；优化前先量化（占比、时长），优化后复测；紧急时先扩容/重启止血，再定位根因。

**项目落地：**监控 CPU 使用率 + load + GC 次数告警；压测基线明确正常水位；大促前容量评估；Java 服务排查标配：top → jstack → 火焰图 → 代码优化。

**面试追问：**load average 高但 CPU 不高可能是什么（I/O 等待/不可中断进程）；Full GC 为什么耗 CPU（标记整理算法 + STW 处理）；上下文切换高怎么降（减少线程数/协程/无锁）。

## 02 理解补充与边界校订

原文第一句把高 load 与 CPU 饱和直接等同，后文其实已指出 D 状态例外。还要检查容器 CPU quota 的 throttling：宿主 CPU 不满也可能是本容器受限。先保存时间窗口、线程栈和热点证据，再做最小风险止血；重启会销毁现场。pidstat 需要线程视角参数才看得到线程，iowait 本身也不是某个磁盘故障的直接证明。

## 03 热点线程抓到 WAITING 为什么进程 CPU 仍然高

`top`/`pidstat` 展示某个采样区间的 CPU 消耗，而一次线程转储展示采集瞬间的状态。线程可能刚完成一轮忙计算就进入等待，因此两个结果不矛盾；也可能是热点线程 ID 对错、容器 PID 命名空间不一致，或真正消耗 CPU 的是其他线程、GC/JIT 或 native 代码。

先把 PID、线程 ID、时间戳和采样区间对齐，Linux TID 通常先以十进制得到，再转十六进制匹配传统平台线程转储中的 `nid`。连续采样线程 CPU，并结合 JFR 方法采样、线程 CPU/GC 事件；涉及 native 或内核时间时再使用支持相应栈的分析工具。JDK 21 的虚拟线程不能简单按一个固定 OS TID 去追踪业务任务，需结合虚拟线程感知的诊断手段。

真正处于 WAITING 的线程不会因为“等待状态本身”持续烧满 CPU。若多次同窗口证据仍对不上，就扩大到全进程线程、native 栈和容器配额，不能仅凭一张 WAITING 栈断言是锁竞争或死循环。依据：[Oracle JFR 性能诊断](https://docs.oracle.com/en/java/javase/21/troubleshoot/troubleshoot-performance-issues-using-jfr.html)。
