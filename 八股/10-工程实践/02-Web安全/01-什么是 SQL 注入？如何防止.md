# 01 什么是 SQL 注入？如何防止？

## 01 核心回答


**概念原理：**SQL 注入是应用把用户可控输入直接拼接进 SQL，导致输入被数据库解析为额外的语法或条件。攻击者可能绕过登录、读取不应访问的数据、修改数据，严重时还可能利用数据库能力影响文件或系统。根因不是“输入里出现了某个特殊字符”，而是代码把数据和 SQL 结构混在了一起。

**实现流程（攻击链）：**① 应用把参数直接拼进 SQL 字符串；② 输入中的特殊字符（引号、注释符）闭合原语句结构；③ 注入片段被当作 SQL 执行；④ 数据泄露或篡改。注入点常见于登录、搜索、排序、分页和批量接口。

**防止手段：**首选参数化查询或 ORM 的绑定参数，让 SQL 模板和参数分开，由驱动负责正确编码；动态表名、排序字段和列名不能直接接收任意输入，应使用白名单映射。还要对输入做长度、类型和业务范围校验，但不能把黑名单过滤当成主要防线。数据库账号遵循最小权限，读写分离，禁止应用账号拥有不必要的管理权限，并通过日志、告警和审计发现异常查询。

**关键细节：**测试时覆盖登录、搜索、排序、分页、批量接口和二次拼接路径，检查是否仍存在字符串拼接；错误响应不要暴露 SQL、表结构和堆栈；上线前配合代码扫描、依赖升级和定向安全测试验证。

**风险与取舍：**必须用 `${}` 的动态表名/排序字段是天然高风险点，只能白名单映射；黑名单转义可被编码变体绕过，只能当辅助；安全方案不能只依赖单一手段。

**项目落地：**DAO 层强制 `PreparedStatement`/MyBatis `#{}`；排序字段走枚举白名单；错误统一脱敏返回；数据库账号按服务隔离最小权限；上线前 sqlmap 扫描 + 代码审计。

**面试追问：**为什么预编译能防注入（结构解析先于参数绑定，数据不再参与语法解析）；MyBatis `#{}` 和 `${}` 的区别；哪些场景必须用 `${}` 如何保证安全（白名单）；盲注和报错注入是什么。

---

## 02 理解补充与边界校订

参数绑定保护的是数据位置，不能拿一个占位符替代 SQL 关键字或任意表名；动态结构需要由服务端允许列表映射产生。ORM 仍可提供拼接 SQL 的逃生接口，所以「使用 ORM」不等于已防注入。安全验证应在授权测试环境检查入口和二次拼接路径，不对生产服务随意执行攻击扫描。
