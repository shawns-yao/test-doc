# 02 如何设计高可用的 RabbitMQ？镜像队列有什么作用？

## 01 核心回答


**概念原理：**RabbitMQ 高可用需要区分集群元数据与队列数据复制。RabbitMQ 4.x 的 classic queue 不复制消息；关键任务队列通常使用 **quorum queue（仲裁队列）**。经典镜像队列是历史方案，已在 4.0 移除，故障切换不能无条件承诺消息不丢。

**实现流程：**① 部署跨故障域的多节点集群；节点间 Erlang cookie 必须匹配且妥善保护，它不同于 AMQP 客户端用户名密码，也不替代传输加密；② 声明 `x-queue-type=quorum` 并规划实际副本成员；③ 队列 Leader 通过 Raft 复制；④ 在保有多数派时选举新 Leader。旧 `ha-mode` policy 仅用于已移除镜像方案，不应作为 4.x 部署步骤。

**关键细节：**历史镜像的 `ha-sync-mode` 控制新/重入副本如何补齐存量，并不是可切换的“同步写 vs 异步写”确认模式；仲裁队列确认依赖多数副本。客户端需**重连、发布确认和幂等重试**，重连本身不会补发全部未确认消息。

**风险与取舍：**副本数增加带来写放大；仲裁队列丢失多数派时宁可暂停服务，不能用少数派强行继续写来兼得一致性与可用性；高可用不等于不丢消息——生产端确认 + 队列持久化 + 消费端 ack 三层都要配置。

**项目落地：**生产环境 3 节点集群 + 仲裁队列；队列和消息都声明持久化；生产者确认（publisher confirm）；消费者手动 ack；监控队列副本同步状态和节点健康。

**面试追问：**镜像队列和仲裁队列的区别（已移除的旧复制机制 vs Raft 多数派）；普通集群为什么不复制消息（只有元数据）；网络分区怎么处理（区分队列多数派与集群分区策略，不能绕过数据安全条件）。

## 02 版本订正与多数派边界

经典镜像队列自 3.9 弃用，4.0 完全移除；classic queue 本身仍受支持，只是不再带镜像复制。本题保留旧方案是为了理解历史系统，新部署不能照抄 ha-mode 配置。仲裁队列不是“给现有 classic queue 加一条 policy”即可原地转换，迁移需要规划新队列、绑定、生产消费切换和存量处理。

假设一条 quorum queue 有 3 个成员，至少 2 个可互通才能取得多数派；5 个成员通常可容忍 2 个成员不可用。这里数的是该队列的成员，不是集群节点总数。集群新增节点也不应被想当然地理解为所有现有队列已经自动取得新副本。

依据：[仲裁队列及成员管理](https://www.rabbitmq.com/docs/quorum-queues)、[3.13 镜像队列历史说明](https://www.rabbitmq.com/docs/3.13/ha)。

## 03 一次故障切换怎么推演

1. Producer 发布后等待 confirm；Leader 确认到客户端之前宕机，客户端可能不知道消息是否已接受
2. 仍有多数派时选出新 Leader，客户端恢复连接与通道，再处理未确认发布；重发可能造成重复，必须保留稳定业务 ID
3. Consumer 业务已提交但 ack 尚未到达 Broker，也会造成重投；数据库唯一约束或幂等状态机负责兜底
4. 如果多数副本或所在故障域同时损坏，就不能承诺继续服务或恢复全部数据。复制不是备份，仍需灾备、容量预警和演练

队列持久化、可靠发布、可靠复制和消费成功确认回答的是四个不同问题。负载均衡地址只能改善客户端接入，不能把单副本队列变成高可用队列。

## 04 面试口述与核对项

“我会先问 RabbitMQ 版本。4.x 的关键业务任务用 quorum queue，以 3 个跨故障域成员为常见起点；保留多数派才可故障切换。生产端跟踪 confirm 和不可路由返回，消费端业务成功后 ack，并接受不确定结果带来的重复。旧镜像队列只能作为迁移背景，不能作为当前部署方案。”

上线演练至少覆盖：杀 Leader、丢失一个节点、网络分区、磁盘接近水位、确认超时与消费者提交后宕机。看可用性、未确认消息、重投、最老消息年龄和恢复耗时，而不只看节点是否存活。

依据：[发布确认的意义](https://www.rabbitmq.com/docs/confirms)、[官方镜像迁移说明](https://www.rabbitmq.com/blog/2025/07/29/latest-benefits-of-rmq-and-migrating-to-qq-along-the-way)。
