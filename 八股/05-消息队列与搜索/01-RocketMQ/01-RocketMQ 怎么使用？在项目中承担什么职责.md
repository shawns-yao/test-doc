# 01 RocketMQ 怎么使用？在项目中承担什么职责？

## 01 核心回答


**概念原理：**RocketMQ 是分布式消息中间件，核心模型：Producer → Topic → ConsumerGroup，Broker 存储消息、NameServer 负责路由。使用方式：创建 Topic → 生产者 send → 消费者订阅消费（push/pull），支持延迟消息、顺序消息、事务消息和重试/死信。

**项目中承担的职责：**

**① 异步解耦：**下单后异步发通知/扣积分/更新搜索，主流程不等下游；

**② 削峰填谷：**秒杀/大促请求先入队，消费者按能力消费，保护数据库；

**③ 事件驱动：**订单状态变更事件广播给多个系统（库存、物流、风控）；

**④ 数据同步：**业务数据变更异步同步到 ES/数仓（配合 binlog CDC 或业务事件）。

**关键细节：**使用要确认消息语义：至少一次（默认，消费需幂等）、顺序消息（按所用版本配置同队列或同消息组，并串行发送、按序处理）、事务消息（半消息 + 本地事务 + 回查，协调本地事务结果与消息可见性）；消费失败进重试队列，超过次数进死信队列。

**风险与取舍：**引入 MQ 后链路变复杂：消息丢失（发送/存储/消费三阶段都要确认）、重复消费（必须幂等）、积压（消费能力不足）、消息乱序。生产要监控积压量、消费延迟、重试率和死信数量。

**项目落地：**发送端：同步发送关键消息 + 重试 + 本地事务内写 outbox 后可靠投递，或使用事务消息；未确认发送保留补偿记录；消费端：业务幂等（唯一键/去重表）、消费失败重试 + 死信告警；监控积压和延迟，限流保护下游。

**面试追问：**如何降低丢失风险（发送确认、适合版本的刷盘与复制配置、业务完成后返回消费成功或 ack）；如何保证不重复消费（幂等）；顺序消息怎么实现（业务维度消息组/路由 + 串行发送 + 顺序消费）；事务消息原理（半消息 + 回查）。

## 02 事务消息解决的是哪段一致性

以“订单已支付后发送发货事件”为例，先写订单再发送消息有一个宕机窗口：数据库已提交，消息尚未发出。仅在发送失败后补一张表覆盖不了“还没来得及执行失败处理就宕机”的情况。

- 事务消息路径：先发送暂不可消费的半消息，确认成功后执行本地事务，再根据事务结果提交或回滚消息；二次确认丢失时，Broker 回查生产者
- 回查要读取持久化的业务状态或事务记录，不能靠进程内变量猜测；事务结果暂不明确时按协议返回未知，受超时与回查上限约束
- 事务消息不能把发货服务的数据库事务也纳入订单事务，更不保证消费者只执行一次。下游仍需幂等、重试和对账
- 替代方案是 outbox：订单更新与待发送事件写在同一个数据库事务中，再由可靠任务或 CDC 转发。投递可能重复，因此 eventId 在重试中保持不变

依据：[RocketMQ 事务消息机制与限制](https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/)。

## 03 顺序与消费确认的实际边界

RocketMQ 5.x FIFO 以 message group 表达局部顺序，例如每个 orderId 一个组；旧版客户端常通过选择同一 MessageQueue 实现。消息的 keys 属性主要用于检索，并不等价于配置了 FIFO 消息组。生产端多线程同时发送、跨生产者提交，不能仅凭“同 key”推导业务时间顺序。

消费者也必须完成当前业务再处理后续事件。先把消息扔进无序线程池、立即返回成功，会同时破坏可靠性和处理顺序。严格顺序链路遇到毒消息时，需要明确选择阻塞该实体、修复重试，还是记录缺口后继续；直接跳过会改变业务语义。

同一消费组用于共同分担一份订阅，不同下游职责应使用不同消费组，避免通知服务与搜索同步服务互相“抢走”消息。PushConsumer 一般通过监听器返回消费结果，SimpleConsumer 则有显式确认和不可见时间，不宜把所有 SDK 都说成“手动 ack”。

依据：[FIFO 消息](https://rocketmq.apache.org/docs/featureBehavior/03fifomessage/)、[消费组](https://rocketmq.apache.org/docs/domainModel/08consumergroup/)、[消费重试](https://rocketmq.apache.org/docs/featureBehavior/10consumerretrypolicy/)。

## 04 项目口述与追问

可按“具体事件 → 为什么异步 → 一致性方案 → 失败处理 → 指标”介绍项目，避免把支持的特性说成实际全都用过。示例口述：“订单事务完成后通过可靠事件触发搜索同步和通知，各服务独立消费组；重复投递由业务流水唯一键处理，失败有限重试并告警。对订单状态更新按订单维度保序，监控最老未消费消息年龄，而不只看总积压。”

- 回查发现业务已成功但提交消息超时怎么办？以持久化事务结果决定提交，后续允许重复投递，不能重新执行原业务
- 超时关单为什么还要查订单？延迟消息只是触发检查，消费时订单可能已付款，要做带状态条件的更新
- 发货事件最终没消费怎么办？把投递、消费失败和业务状态对账串起来，不能把 Broker 接收成功当作业务闭环
