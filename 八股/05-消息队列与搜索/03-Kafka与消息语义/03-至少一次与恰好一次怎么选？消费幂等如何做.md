# 03 至少一次与恰好一次怎么选？消费幂等如何做？

## 01 核心回答

**怎么选：** **恰好一次**语义实现复杂、成本高，跨系统链路很难端到端保证。多数业务采用**"至少一次投递 + 消费端幂等"**——在可控复杂度下获得足够的可靠性。

**消费幂等三层：**核心是为每条业务事件定义**唯一幂等键**（订单号、业务流水号等），通过原子约束判重，不能只做先查后写。

① **数据库唯一键/去重表**：与业务变更放进同一本地事务。
② **条件状态更新**：重复操作不再改变结果。
③ **Redis SET NX** 可减轻重复请求压力，但和数据库不原子，不能单独充当正确性兜底。

**追问：**为什么恰好一次难（分布式事务 + 多系统）；SETNX 幂等键过期了怎么办（DB 兜底）；幂等键怎么生成（业务 ID + 操作类型）。

---

## 02 先说清楚“恰好一次”针对什么

至少一次允许一条记录被交付多次；恰好一次应指在规定的处理边界内，最终可观察的效果只生效一次，不代表网络只发送一次或业务函数只被调用一次。选择时先问输出落在哪：Kafka 输出 Topic、同一数据库，还是第三方支付接口。

Kafka 事务能够把一组输出记录与输入消费位点一起提交，下游使用 read_committed 隔离未提交和中止事务。这对 Kafka 到 Kafka 的处理链路有效；调用短信、支付或外部数据库不会自动被 Kafka 事务回滚。依据：[KafkaProducer 事务及消费位点 API](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/producer/KafkaProducer.html)。

## 03 用故障窗口检验幂等方案

假设事件 E 为订单发券：在同一数据库事务内插入唯一的 (consumer_scope, eventId) 处理记录，并新增优惠券，提交后才确认消息。若事务提交前宕机，两项一起回滚，重投可重新执行；若提交后、ack 前宕机，重复插入被唯一约束拒绝，不会再发第二张券。检查唯一冲突后仍要区分“已成功处理”与其他错误，不能把所有数据库异常都当作重复。

Redis 先 SET NX 成功再写数据库，若中间宕机，会出现“标记已处理但业务没做”；反过来先写业务再标记，则可能重复执行。TTL 到期、主从故障和旧消息重放又会引入额外窗口。因此 Redis 可以作为前置减压，但最终正确性应落在与业务结果原子的约束，或外部服务提供的幂等协议上。

幂等键也不能只写 orderId：同一订单的支付、退款、发券是不同操作；同一操作如果允许多次分批执行，还需要操作流水号或版本。去重记录保留时间至少覆盖允许的重试、重放和补偿窗口，清理前要明确旧事件是否仍可能回来。

---

## 04 选择和口述

普通业务通常优先“至少一次 + 业务幂等”，但代价并非零：需要存储去重记录、管理并发和对账。Kafka 内部流处理可评估事务或 Streams 的恰好一次模式；外部副作用则按目标系统能力设计，而不是套一个全局 exactly-once 标签。

口述：“先明确一次的边界。消息重复交付可以接受，重复扣款不行。我把幂等键和业务变更放进同一事务；对外部调用使用对方的幂等键并在超时后查询结果。Kafka 事务只覆盖它能原子提交的记录和位点，不替外部数据库兜底。”

延伸依据：[Kafka 消费位置与外部存储协调](https://kafka.apache.org/41/javadoc/org/apache/kafka/clients/consumer/KafkaConsumer.html)。
