### 1. 消息投递语义

核心考察：Redis Streams 如何投递、接管和确认消息。

- 为什么选择 Redis Streams，而不是 Kafka、RabbitMQ 或普通 Redis List？
- Consumer Group、Pending Entries List、ACK 分别解决什么问题？
- 消费者处理到一半崩溃，消息如何被其他实例发现并接管？
- 为什么不能看到消息空闲就立即执行 `XCLAIM`？
- 消息在业务处理完成但 ACK 前崩溃，会发生什么？
- 这条链路是 at-least-once、at-most-once，还是 exactly-once？
- 如何处理乱序消息和同一业务链路上的并发消费？

这些问题本质上都在问：

> Redis Streams 如何做到消息可恢复，但为什么仍然可能重复投递？

### 2. PostgreSQL Outbox

核心考察：如何解决“数据库写成功，但事件发布失败”的双写一致性问题。

- PostgreSQL Outbox 解决了什么问题？
- 为什么不能先更新业务状态，再直接向 Redis 发布事件？
- 业务状态和 Outbox 记录如何保证在同一个事务中提交？
- 如果事务提交成功，但进程还没发布消息就崩溃，怎么办？
- Outbox Worker 如何找到需要重放的记录？
- 如果事件已发布，但更新 Outbox 状态前进程崩溃，会不会重复发布？
- Outbox 重试达到上限后如何处理？
- 多个 Outbox Worker 同时运行时，如何避免重复扫描和并发发布？

这些问题本质上都在问：

> 如何保证业务状态变化后，事件最终一定有机会发布？

### 3. 处理租约与故障接管

核心考察：如何区分“消费者已经死亡”和“消费者只是处理得比较慢”。

- Redis Pending 消息长时间没有 ACK，是否就代表消费者崩溃？
- 为什么还需要单独的处理租约？
- 处理租约的 TTL 如何确定？
- 为什么按照 TTL 的一部分定期续约？
- 租约续约失败后，正在执行的任务如何停止？
- 如果发生长时间 GC、网络抖动或模型调用超时，会不会被错误接管？
- 新消费者接管前为什么还要检查旧消费者的活动租约？
- 分区租约和单条消息处理租约分别解决什么问题？

这些问题本质上都在问：

> 如何安全接管故障消费者，同时避免两个消费者并行处理同一条消息？

### 4. Fencing Token

这是这条简历最容易被深挖、也最能拉开差距的部分。

- 已经有租约了，为什么还需要 Fencing Token？
- 什么是“旧实例的陈旧写入”？
- 租约过期后，旧实例为什么可能仍然继续运行？
- Fencing Token 如何生成，为什么必须单调递增？
- 新旧消费者同时提交时，数据库如何判断谁有资格写入？
- Token 应该在哪一层校验：Redis、应用代码还是 PostgreSQL？
- 只在任务开始时校验 Token 是否足够？
- 为什么最终提交前还需要再次检查租约和执行代次？
- 如果旧实例已经调用了不可回滚的外部接口，Fencing Token 还能阻止吗？
- Fencing Token 和乐观锁版本号有什么区别？

这些问法都在验证同一个关键点：

> 租约只能表示当前所有权，Fencing Token 才能阻止曾经持有租约的旧实例产生迟到写入。

### 5. 幂等与外部副作用

核心考察：如何让重复投递不演化为重复业务结果。

- 幂等键根据事件编号、业务对象还是消费者生成？
- 为什么不同消费者不能简单共用同一个幂等键？
- 幂等状态为什么要区分处理中、已完成和失败？
- 失败记录是否允许重新处理？如何避免永久阻塞？
- 幂等记录的 TTL 到期后，历史事件重新到达怎么办？
- 数据库状态变更可以通过唯一约束和事务保护，飞书通知、HTTP 调用等外部副作用如何幂等？
- 如果业务操作成功但幂等状态更新失败，会发生什么？
- 如果消息重复投递十次，系统在哪几层进行拦截？
- Outbox 本身会重复发布，为什么下游仍然需要幂等？
- 你们实现的是 exactly-once 消费，还是 effectively-once 的业务效果？

### 面试官最可能采用的连续追问

1. Redis Streams 为什么还会重复投递？
2. 重复投递如何避免重复状态变更？
3. 消费者处理中崩溃，其他实例如何接管？
4. 长任务没有 ACK，怎么避免被误接管？
5. 已经有处理租约，为什么还需要 Fencing Token？
6. 旧实例恢复运行后，数据库如何拒绝它的提交？
7. 业务提交成功但事件发布失败，Outbox 如何恢复？
8. Outbox 重放产生重复事件怎么办？
9. 外部通知已经发送但本地状态没有更新，如何处理？
10. 为什么这套方案仍然不能宣称严格 exactly-once？

准备时可以压缩成 5 份核心答案：

1. Redis Streams 的 at-least-once 投递与 Pending 接管。
2. PostgreSQL Outbox 解决双写一致性。
3. 可续约处理租约防止长任务被误接管。
4. Fencing Token 拦截失去所有权后的陈旧提交。
5. 幂等将重复投递限制为无重复业务副作用。
