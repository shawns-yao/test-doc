- 参与建设基于 **Redis Streams** 与 **PostgreSQL Outbox** 的可靠事件链路，引入幂等提交、处理租约和 Fencing Token，支持消费者故障接管并拦截旧实例的陈旧写入，避免重复消费进一步产生重复状态变更和外部副作用。

### 1. 为什么抽象统一状态迁移契约

- Pipeline 和 Collaboration 的业务完全不同，为什么可以复用同一套状态迁移契约？
- 公共契约抽象了哪些内容，哪些规则仍由业务模块自己定义？
- 为什么不直接在每个事件处理器中写状态判断？
- 如何避免把公共状态机抽象得过于复杂？
- 新业务接入这套契约时，需要提供哪些内容？
- 状态迁移契约和普通状态枚举有什么区别？

本质是在问：

> 你抽象的是通用并发语义，还是强行统一不同业务的状态模型？

### 2. Pipeline 与 Collaboration 状态机

- Pipeline 的状态和交付阶段为什么是两个维度？
- 构建失败、GitOps 冲突、Argo CD 同步失败分别如何流转？
- Pipeline 失败后为什么允许重试，而某些成功或终止状态又允许重新进入处理？
- Collaboration 从未读、已确认、处理中到已修复、已复核、已关闭如何迁移？
- 为什么未读状态不能直接变成已修复？
- 为什么无效回复后必须重新进入调查或升级？
- 哪些状态是终态？终态是否允许恢复？
- 为什么有些相同状态之间的重复迁移被允许？
- 延迟到达的旧事件如何避免把状态从已修复退回处理中？

本质是在问：

> 两套业务状态图是怎样根据真实流程设计的，而不是随意罗列状态？

### 3. 实体锁与版本校验

这是最容易被深入追问的部分。

- 实体锁锁定的“实体”是什么？Pipeline 和 Collaboration 分别用什么标识确定锁粒度？
- 为什么已经有实体锁，还需要版本校验？
- 两个实例同时读取版本 3，并分别尝试写入版本 4，会发生什么？
- 状态版本属于乐观锁还是悲观锁？
- 实体锁属于数据库行锁、咨询锁，还是应用级锁？
- 锁需要覆盖读取、校验和写入的哪些阶段？
- 锁粒度过大会有什么问题？过小又会有什么问题？
- 多个实体需要同时更新时，如何避免死锁？
- 版本冲突后应该直接失败、自动重试，还是重新读取后重新执行业务判断？
- 本地文件存储和 PostgreSQL 是否具有相同的并发保证？

这部分本质上在问：

> 实体锁负责串行化临界区，版本校验负责识别调用方依据的状态是否已经过期，两者为什么不能互相替代？

### 4. 非法迁移与迁移审计

- 非法状态迁移是在业务层、公共契约层还是数据库层拒绝的？
- 如何区分“迁移路径非法”和“状态版本过期”？
- 一条迁移审计记录包含哪些信息？
- 为什么需要记录迁移前状态、迁移后状态、触发来源、操作者、原因和时间？
- 如何证明某次状态变化来自用户操作、超时调度还是系统事件？
- 审计记录是覆盖更新还是追加保存？
- 能否通过审计记录完整重建实体的状态变化过程？
- 同一迁移事件重复到达时，会不会产生多条重复审计记录？
- 状态更新成功但审计记录写入失败怎么办？
- 审计记录和下游事件是否在同一事务中提交？

本质是在问：

> 系统不仅要知道“当前是什么状态”，还要解释“为什么以及由谁变成这个状态”。

### 5. “状态一致性”的真实边界

- 你所说的状态一致性具体指什么？
- 这是单个业务实体的一致性，还是跨 Pipeline、Diagnosis 和 Collaboration 的分布式强一致性？
- 状态机能否解决消息重复投递问题？
- 状态写入成功但后续事件发布失败时，状态机会怎么处理？
- 如果 Collaboration 收到旧版本的诊断结果，如何判断是否应该更新？
- 状态版本、事件顺序和 Fencing Token 分别解决什么问题？
- 为什么合法的状态迁移仍然可能因为版本冲突被拒绝？
- 如果两个并发操作都符合状态图，系统如何决定接受哪一个？
- 状态迁移失败后，调用方如何得到明确、可重试的错误？
- 如何测试所有合法路径、非法路径和并发冲突？

### 最可能出现的连续追问

1. Pipeline 和 Collaboration 差异很大，为什么能共用一个契约？
2. 公共契约究竟统一了什么？
3. 实体锁和版本校验为什么要同时存在？
4. 两个实例同时更新一个实体会发生什么？
5. 如何防止旧事件造成状态回退？
6. 非法迁移与版本冲突有什么区别？
7. 迁移审计记录了什么？
8. 状态修改和下游事件如何保持一致？
9. 这是否属于分布式强一致性？
10. 其中哪些部分是你实际参与设计和实现的？

准备时可以归并成 5 份核心答案：

1. 公共契约与业务状态图的分层。
2. Pipeline 和 Collaboration 各自的状态设计。
3. 实体锁与乐观版本校验的组合。
4. 非法迁移拒绝与迁移审计。
5. 状态一致性的适用范围和系统边界。
