# 图数据库与时态拓扑

图数据库的重点不是“关系查询快”这句口号，而是：关系来自哪里、属于哪个时刻、查询能发现什么，以及不能证明什么。

## 41. 为什么引入 Neo4j？原来的日志查询和关系数据库不够吗？

**口述回答：** 日志解决“发生了什么”，但故障调查还需要“哪个实例、哪次发布、哪个依赖、哪份证据相互关联”。这些联系跨多个层次，Neo4j 让我们沿关系组织调查，而不是每次由模型从散落材料里重新猜关联。

例如服务异常后，需要从 Service 找到受影响 Pod，再沿归属找到 ReplicaSet、Deployment 和变更，同时定位日志及 Trace 证据。当前图谱还提供封存的必要关系条件：控制器可以排除与可靠观测矛盾的候选，而关系满足只支持机制，不直接确认根因。

关系数据库也能通过关联查询实现这些能力，图数据库不是唯一正确答案。项目选择图模型，是因为多跳关系导航和事故证据网络适合这种表达；代价是增加派生数据的一致性、权限、历史重放与运维负担。

项目默认用 Neo4j 持久化诊断与安全图谱。本地开发由 Docker 提供图库及本机端口，生产清单也包含 Neo4j；开发可以显式选择内存实现，生产禁止关闭。图库初始化失败阻止启动，运行中单次取证失败保留降级。这是仓库配置与代码行为，不能据此声称服务已经启动或生产已经部署。

**追问：为什么不是向量库？** 向量检索适合找相似文本，不能仅凭相似度确认资源归属、实例身份或事故时间。相似案例与结构关系服务不同问题，不能相互替代。

## 42. 项目有哪两类图？为什么不能混成一个“知识图谱”？

**口述回答：** 一类是资源与依赖关系，另一类是事故调查关系。它们可以连接，但可信度和生命周期不同。

资源图组织 Service、Deployment、ReplicaSet、Pod 等资源，以及构建、变更和观测到的依赖。事故图组织本次 Incident、证据、候选假设、评估、根因、修复建议与验证结果。

为什么拆清楚：资源归属来自外部系统观测，假设是模型提出的解释，根因是受控制器约束的结论。不能让“模型认为 A 导致 B”覆盖真实资源关系，也不能把候选与已确认结论画成同等事实。

**追问：镜像也是独立节点吗？** 当前没有专门的 Image 类型，镜像通过 `Resource` 节点及 `container_image` 属性表达，并关联构建或工作负载。裁剪需要可识别的稳定镜像身份；只有可变标签时不能按唯一镜像据此裁决。

## 43. 图中的节点和边从哪里来？会不会是模型随意生成的？

**口述回答：** 资源关系应来自事件、资源观测和封存上下文，诊断关系则来自结构化候选与控制器处理后的报告。不同来源必须保留区别。

例如 Pod 的所有者和资源 UID 来自 Kubernetes 材料，调用依赖可来自 Trace 观测；诊断完成后再把假设、证据评估和结论投影入图。图投影读取保存的产物，不应重新向模型询问并改写旧结果。

事故上下文构建会先登记当前源事件的资源观测，再登记实际查询到的 Trace 调用边，随后按事故时间与获知截止时间读取、封存拓扑。查询没有取得调用或结果截断，不生成“调用不存在”的关系。

一条“依赖”边说明存在相应观测，不说明这个依赖必然是故障来源；一条支持边说明评估认为某证据支持候选，也不免除原始证据核对。

**边界：** 图谱不是天然权威。它可能来自不完整或错误的上游观测，所以必须结合来源、时间、范围和覆盖解读，不能只因进入 Neo4j 就提高证据等级。

## 44. 为什么不能用现在的拓扑解释过去的事故？两个时间分别是什么？

**口述回答：** 发布和修复会改变实例与依赖。如果事故之后再查当前图，可能拿新版本的正常现场解释旧版本的故障，因此要恢复事故时刻可知的关系。

这里区分两个时间：关系在现场何时被观测到，以及系统何时收到并记录它。恢复时同时限制事故时间和系统当时已获知的信息。

例如 10:00 的资源关系直到 10:05 才到达。按 10:02 已知信息重放时，不应该使用这条后来才收到的观测；按更晚的已知范围重新分析时，可以纳入，但必须承认分析材料发生了变化。

当前构建事故上下文时，会读取有时间约束的历史拓扑并封存结果。已保存的上下文是一次调查的材料版本，后来到达的事件不应悄悄修改它。

**边界：** 这是时态观测重建，不是对集群真实状态的全知记录。没有采到的变化仍然可能缺失。

## 45. 同名资源、删除事件和全量快照为什么重要？

**口述回答：** 同名不等于同一实例，未出现在某份材料里也不一定意味着已删除。历史还原必须同时处理身份与观测语义。

Pod 删除重建后 UID 不同，旧实例的终止状态不能移到新实例。删除观测表示某个具体对象或关系不再有效；全量快照在已声明的完整范围内，可以帮助关闭此前存在而此次已消失的关系。

例如一次只返回部分 Pod 的查询不能当全量快照，否则会错误地删除其他实例的边。相反，确实完整且范围一致的快照，才可能用于更新该范围的历史状态。

**边界：** 当前历史建模依赖上游提供 UID、删除和快照范围等信息。上游缺失时应降级，不能仅凭资源名称声称已经实现可靠历史重建。

## 46. 图查询怎样限定范围？为什么没有找到路径不等于没有关系？

**口述回答：** 查询必须关联当前事故和授权资源范围，并限制遍历深度、节点、边、邻居和证据引用数量，避免跨环境泄露和高连接节点引发查询爆炸。

当前诊断图查询是受控、有界的查询，不允许模型提交任意全库遍历。结果还会过滤为本次允许读取的证据入口。

初始假设可见的拓扑视图最多包含 48 个节点与 48 条直接关系，提供有限身份属性，并标注是否截断；它是声明具体关系条件的材料，不代表全库完整图。控制器裁剪使用封存上下文，另检查身份、来源、时态和覆盖。

有界意味着返回的是被允许看到的局部图。例如深度不足、结果上限、投影延迟或历史观测不完整，都可能让某条路径没有出现在结果里。所以空结果只能说明“本次查询未取得这条路径”，不能排除真实依赖。

**追问：为什么限制会损失召回？** 因为安全和成本有代价。结果应带覆盖或退化说明，让后续调查知道是否需要合法补查，而不是假装局部图代表全局。

## 47. 图工具返回证据地址和下一步工具，为什么还要再读取？

**口述回答：** 地址证明存在一个入口，不证明模型已经读过、材料完整或内容支持候选。图工具在当前设计中是引用型检索，不产生直接诊断证据。

正确流程是图中找到关联资源或产物，再通过允许的读取工具取得内容，记录实际读取范围，检查事故归属、完整性和引用，最后才用于候选评估。

后续工具提示也是按节点类型和已开放能力映射出来的，不是图数据库自主理解故障。工具仍须经过本次授权。

**追问：图中已有根因，为什么不直接返回？** 因为可能属于另一事故、旧版本或尚未确认的评估。即使是历史已审核案例，也只能作为线索，当前事故仍要重新取证。

### 图谱现在怎样参与候选裁剪？

引用型图工具与封存拓扑裁决是两条不同路径。图工具返回资源、证据地址和后续读取线索；控制器的拓扑检查则比较模型事先冻结的必要关系条件与本次事故的可靠观测。

条件通过 `service_topology` 预测声明：明确关系起点、终点、类型、预期存在或不存在及时间范围。当前检查 `DEPENDS_ON`、`SELECTS`、`MANAGES`、`DEPLOYED_FROM`、`USES_CONFIG`，只处理这些直接关系；多跳路径要拆成必要的单条关系，目前没有实现任意多跳因果推理。

| 检查结果 | 控制器处理 | 判断边界 |
| --- | --- | --- |
| 满足 | 保留候选原有评估 | 只支持关系机制，不自动确认根因 |
| 矛盾 | 排除候选、置信度归零，保存原因和来源事件 | 条件必须是该假设在指定范围的必要条件 |
| 未知 | 原本得到支持的候选降为证据不足，记录缺口 | 缺少 UID、来源、可靠时态或完整覆盖时不能强行判断 |

例如候选要求某个 Pod 的资源 spec 引用配置 X。只有固定同一 Pod UID 和配置身份、取得事故快照时刻的完整 spec，才能用未引用 X 反驳这项条件。当前缺边反证仅覆盖完整 spec 可枚举的镜像来源和配置引用出边；没有服务调用边，不能证明整个事故期间没有调用。

控制器在每轮与最终裁决中执行检查。报告保留条件、来源事件、封存 Context、事故时刻和获知时间，并明确 `root_cause_correctness_verified=false`。这项裁剪已写入 `260bcf3`，尚未经过真实 Neo4j 与诊断链路验证。

## 48. 图投影失败、重复事件或处理顺序颠倒，怎么办？

**口述回答：** 先把证据和报告作为可追溯产物保存，再让图成为可重试的派生视图。诊断不应因为一次图写入失败就丢掉全部调查材料，也不能因为图暂时落后就用旧节点覆盖新结论。

当前上下文流程保留了即时投影尝试，也增加了独立事件消费者处理上下文、诊断完成和修复验证完成事件。它读取已保存产物，校验归属及相关完整性，失败可重试并进入失败处理；实现还加入范围级并发保护与投影时间检查。

重复处理应指向稳定的事故和产物身份，而不是每次生成另一套同义节点。处理顺序保护的目标是避免旧投影回写覆盖较新状态。

**边界：** 这是最终一致性的设计，不是跨证据仓储、业务存储和 Neo4j 的一个强一致事务。本次未运行重复事件、并发或故障恢复验证，不能承诺所有竞争场景已经验收。

## 49. 历史拓扑检查点怎样工作？晚到事件为什么可能要重新重放？

**口述回答：** 如果每次查询都从第一条观测重建，历史越长成本越高。检查点保存某个边界上的已派生状态，后续可以从这个状态继续应用观测。

但检查点必须符合查询的事故时间与获知时间范围。若检查点之后才收到一条影响它之前历史的晚到观测，旧检查点可能不再代表正确起点；当前逻辑会识别相应情况，回到历史物化路径，而不是无条件套用检查点。

例如先记录 10:05 的快照，后来补到 10:03 的删除事件。如果该删除影响检查点中的资源关系，直接增量续算可能保留错误关系，需要重新处理受影响历史。

**边界：** 检查点是派生加速材料，不是删掉原始历史的理由。当前历史读取和图返回仍有边界，也尚不能声称完成无限历史规模、自动冷归档清理和生产并发验收。
