# 高概率开场问题

先学会从业务问题讲到设计选择，再讲具体实现。以下示例用于说明推理过程，不是本次运行得到的真实事故结果。

## 1. 请用两分钟讲清楚从故障进入系统到输出诊断的完整流程

### 可以直接口述的回答

这个项目解决的是构建、发布和运行故障发生后，证据分散、排查依赖个人经验的问题。比如服务发布后持续报错，原因可能在发布配置、容器状态或下游依赖，只看某一段日志容易把症状当成根因。

我们先把相关事件归并成一次事故，确定服务、环境、资源和时间窗口。显式事故或交付标识优先；缺少这些标识的运行时事件，可以在同集群、命名空间、服务、环境和时间桶内弱关联。然后采集构建及运行证据、日志错误组、指标和 Trace，并保存事故时刻的资源关系。Neo4j 组织这些关系，也为控制器检查假设的必要拓扑条件提供材料。

如果故障命中可确定的已知规则，就先走规则分流；复杂情况进入模型调查。模型先提出可证伪的候选假设，写清楚每个假设预期看到什么、什么证据能推翻它。控制器再把这些需求编译成带权限、范围和预算的调查计划。

调查时，图查询帮助找到相关资源和证据入口，具体工具读取或补查真实观测。控制器同时检查封存拓扑：可靠关系与假设必要条件矛盾时排除该候选；关系满足只支持机制；数据不足保持未知。最后检查引用、已知信号一致性、覆盖、竞争解释和因果支持，输出候选、建议和复核要求。未知根因信号不会仅因引用真实而自动通过语义门禁。

另外，经过批准的修复可以进入独立观察流程，用同范围的日志、指标和 Trace 比较前后变化，把验证结果保存并关联回图谱。但“观察到改善”和“根因已经严格确认”是两个层次，不能混着说。

### 被追问时，按这六步展开

1. **界定事故。** 输入是构建失败、部署异常、Kubernetes 事件或告警；输出是明确的事故范围。先确定范围，是为了避免把另一个环境的报错当作当前证据。
2. **整理材料。** 按范围采集并封存证据，标注来源、时间、完整性；日志聚类减少重复阅读，时态拓扑避免查询到修复后的关系。输出的是可以检查的调查上下文，不是根因。
3. **提出假设。** 输入是当前症状与有限上下文；输出是候选解释、机制和检验条件。盲生成阶段不调用检索工具，也不让历史相似答案主导第一轮判断。
4. **安排并执行调查。** 控制器把“检查发布”转成具体资源与时间范围内的动作。图查询提供导航，工具取得观测；封存拓扑还用于检查候选的必要关系条件。白名单和预算控制实际执行。
5. **形成受约束的结论。** 用真实证据评估每个候选，排除与可靠拓扑矛盾的候选；对互斥解释做区分，检查引用、信号与覆盖。无法区分或根因信号未知时保留复核。
6. **验证修复效果。** 修复需要经过既有审批与交付流程；观察模块比较前后遥测，排除数据缺失、流量不足等干扰，输出有效、恶化或无法判定的结果。

### 一个能贯穿全流程的例子

发布后出现大量数据库连接超时。候选一是下游数据库异常，候选二是这次发布引入了错误连接配置。

先利用事故时刻拓扑找到实际受影响的 Pod 和所属发布，而不是查询已经被替换的新 Pod。再比较新旧版本、发布变更、对应 Pod 的日志以及 Trace 中失败的调用环节。如果只有新版本异常、变更涉及连接地址，而且原始日志和调用证据一致，就增强配置错误候选；如果新旧版本都失败，则需要认真调查共享下游。

这仍是示例。能否确定单一根因，取决于证据覆盖和替代解释是否解决，不取决于故事是否讲得通。

## 2. 面试官问“你具体负责什么”，怎样回答才能经得住追问？

**口述回答框架：** 我的工作集中在【本人实际承担的环节】，解决的具体问题是【原有缺陷】。我采用【设计选择】，与【已有平台能力】衔接，最后通过【实际完成的验证】检查结果。其他模块由团队已有能力提供，我负责的是接入或协同，不会把它们都算作个人独立开发。

为什么要这样回答：仓库能证明模块存在，但不能证明个人分工。仅凭项目结构不能替你确认谁实现了哪些提交。

准备时为自己的每一项贡献补齐四件事：改动前哪里容易出错；为什么选择这个方案；替代方案有什么代价；实际验证过哪些边界。比如确实参与证据治理，可以讲“防止模型引用其他事故的证据”，再展开范围校验与引用校验，而不是声称独立完成整个 Agent。

**追问：图数据库是不是你做的？** 按事实回答建模、查询约束、接入、测试分别承担了什么。没有负责的内容可以解释架构，但不能冒充个人实现。

## 3. 为什么设计成 Agent，而不是一次 LLM 日志分析调用？

**口述回答：** 一次调用适合对给定材料做摘要，但复杂故障往往缺少决定性证据。我们需要根据假设决定下一步查什么，拿到结果后再更新候选并决定是否继续，这就是受控调查型 Agent 的价值。

具体做法不是让模型随意循环：先把解释变成能检验的假设，控制器安排合法工具动作，工具返回可追溯观测，再做候选评估。如果仍有关键问题、剩余预算和可执行动作，才继续调查。

例如“连接超时”不能直接区分地址配置错误和数据库不可用，下一步需要查发布变更、资源分布和实际调用。一次日志摘要可能只重复“请检查数据库”，调查流程则要求说明哪项观测能够区分两个解释。

**边界：** Agent 不代表自主改生产配置。自主性主要体现在受约束的调查决策；执行修复仍要遵守审批和交付边界。

## 4. 各阶段的输入、输出和职责分别是什么？

| 阶段 | 输入 | 输出 | 必须守住的边界 |
| --- | --- | --- | --- |
| 事故上下文 | 事件、资源身份、时间范围、可取得的观测 | 封存证据、完整性说明、事故拓扑、错误组 | 不混入其他环境或后来的现场 |
| 假设生成 | 故障症状及限定上下文 | 可证伪的候选解释、机制和预测 | 不把猜测写成事实 |
| 调查规划 | 候选的证据需求、合法工具、预算 | 范围明确的调查动作和优先顺序 | 不让模型自行授予权限 |
| 图导航与取证 | 当前事故范围与具体调查动作 | 图中的引用线索、实际工具观测和执行记录 | 图线索与直接证据分开 |
| 评估与继续调查 | 新观测、原假设、剩余预算 | 候选状态、未解决问题、补查或停止决定 | 不能移动原来的证伪标准 |
| 根因裁决 | 候选评估、真实证据、覆盖与引用校验 | 候选或结论、解释、建议、复核要求 | 结论不能超过证据强度 |
| 修复观察 | 已批准变更、基线、修复后的新观测 | 有效、恶化或无法判定的验证产物 | 不能将改善直接等同于因果证明 |

为什么要拆开：让“提出解释”“执行查询”“批准结论”由不同层承担，便于审计，也能防止模型用自信的语言绕过证据要求。

**追问：Neo4j 属于哪一步？** 它横跨上下文、调查、候选筛选和结果组织。先提供事故时态关系，再导航证据；控制器用封存关系检查假设必要条件，最后保存诊断关系。Neo4j 提供关系数据，裁决代码决定候选状态，关系存在不能自动确认根因。

## 5. Diagnosis、Pipeline 和 Collaboration 如何分工？

**口述回答：** Pipeline 主要推进构建、发布等既定状态和流程；Diagnosis 主要在故障后做证据驱动的调查；Collaboration 主要把结果、审批和人工反馈送到协作渠道。这是职责区别，不应该简单说“只有 Diagnosis 才算 Agent”。

为什么拆开：流水线要处理流程一致性和交付约束，诊断要处理不确定性，协作要处理人机交互与反馈。如果把三者揉在一起，模型一次错误推断可能直接变成生产操作。

例如诊断提出“可能需要回退发布”，并不表示它可以自行提交回退。建议要进入相应治理与审批流程，交付完成后才有条件观察修复效果。

**追问：事件驱动有什么价值？** 各环节可以分别重试、保留产物、关联同一次业务流程，不必让一次模型请求承担从故障到修复的全部生命周期；同时也必须处理重复、延迟和部分失败，不能把异步等同于天然可靠。

## 6. 这个项目真正难在哪里？怎样讲清设计取舍？

**可选回答，须按实际个人经历使用：** 最难的不是让模型生成一段看起来合理的根因解释，而是保证它调查的是正确现场，引用的是当前证据，并且知道什么时候不能下结论。

可以选择一条你确实参与的难点深讲：

- **现场漂移：** Pod 会替换，关系会变化。按事故时间恢复拓扑，保留系统获知时间并封存上下文，避免复盘时读到修复后的现场。
- **证据强度：** 图和日志聚类提供入口，但原始证据才能支撑诊断。将检索线索、实际观测、引用校验和结论等级分开。
- **异步一致性：** 诊断与图投影、修复观察并非一次事务。利用稳定身份、重试、租约和封存产物减少重复与错配，失败时明确降级。

不要三项只报名称。选一项讲“旧方式如何失败 → 为什么这样设计 → 如何执行 → 还剩什么限制”。例如时态拓扑还依赖历史观测覆盖，不可能凭 Neo4j 凭空还原从未采集的资源关系。
