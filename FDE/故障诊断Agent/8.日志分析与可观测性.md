# 日志分析与可观测性

日志聚类减少重复阅读，指标描述变化趋势，Trace 描述调用路径；它们一起提供调查材料，但没有哪个组件能够独立保证根因正确。

## 50. 加入日志分析后，和“把几段日志发给模型”有什么不同？

**口述回答：** 先按事故范围检索日志，再把重复错误整理成可定位的错误组，保留模式、频次、时间、受影响资源和样本入口，最后交给受控调查流程使用。

这样做是因为真实日志重复多、规模大，模型直接阅读大量相同超时文本会浪费上下文，也容易忽略关键变化。错误组让模型先看到主要现象，再按具体假设回到相关原始材料。

例如同一种连接拒绝在多个 Pod 反复出现，先看发生时间、影响资源和代表样本，再判断是否与某次发布相关；不能仅因这个组数量最多，就认定它是根因。

**边界：** 聚类输出是摘要和引用型线索，不是可直接裁决的完整原始证据。模型后续仍需要合法读取、范围检查和引用验证。

## 51. 当前日志聚类具体怎样做？是不是模型自己总结？

**口述回答：** 当前日志后端使用 OpenSearch PPL，在应用、环境、资源和时间过滤之后取得有界样本，用模式提取归并相似日志，再由项目整理错误组；不是每条日志都让大模型分类。

查询主要选取错误级别或带异常类型的日志，按时间排序并设样本上限，随后使用 PPL 的 brain 模式提取日志模板。项目结合模式、异常类型和服务形成稳定指纹，统计组内出现次数、首末时间、影响资源和少量代表样本，并做敏感内容与长度处理。

例如不同请求标识的同类连接拒绝，可以归到一个模式下，让调查聚焦错误结构而不是随机变量。

**追问：准确率是否有保证？** 没有。模板可能过度合并，也可能把同类错误拆开；仍需查看原始样本。本次未运行真实日志后端，不能把调用能力说成聚类效果已经验证。

## 52. 错误组里的次数是否就是事故期间全部错误？怎样解释采样偏差？

**口述回答：** 不是。当前次数来自实际返回并归组的样本，查询有上限、时间排序和过滤条件，不能直接称为全量事故计数。

例如最近的高频错误占满样本上限，会挤掉较早的少量首发异常。某个组出现最多，可以指导先读哪些材料，但不保证它是最早原因或最重要故障。

当前查询结果会标注样本数量、范围和截断等信息。用于负面判断时尤其要检查：没有出现在错误组，不代表没有发生；用于修复比较时也不能直接用两个样本组的绝对次数当作真实错误率。

**追问：那统计还有什么用？** 用于有边界的模式导航和粗略分布观察。若要做效果比较，应核对采集完整性、窗口长度和请求负载，不能忽略这些条件。

## 53. OpenTelemetry、OpenSearch、Prometheus、Neo4j 分别承担什么？

| 组件 | 当前主要职责 | 不能替代什么 |
| --- | --- | --- |
| OpenTelemetry 与 Collector | 接收、处理、批量转发日志、指标和 Trace；配置也包含文件日志采集 | 不是最终长期存储，也不直接诊断根因 |
| OpenSearch | 保存与查询日志、Trace，提供有界日志检索和模式分析 | 不代替资源与事故关系的图导航 |
| Prometheus | 保存与查询时间序列指标，支持异常及前后窗口比较 | 不替代原始日志和单次调用细节 |
| Neo4j | 保存资源与事故时态关系，提供导航与候选必要条件，组织诊断和验证关系 | 关系存在不等于根因正确，不替代原始遥测 |
| 证据产物存储 | 保存本次查询结果、范围、完整性及校验信息 | 不等于上游系统永远正确 |

**口述解释：** 采集系统把材料送到适合它的后端；事故采集器按范围查询并封存日志、指标和 Trace；实际调用关系登记图库并形成事故拓扑。图查询组织证据入口，控制器另用封存关系检查候选必要条件；原始材料继续承担根因取证。

**边界：** 当前配置能力不代表所有目标服务都已接入。范围标签、数据保留和采集链完整性都需要实际环境提供，缺失就会导致降级。

### 本地开发与 K8s 现在怎样配置？

生产配置以 `apps/fde-workstation/overlays/prod` 为准；`docker-compose.yml` 提供开发 Redis 与 Neo4j，完整单机编排只用于演示。模型、Neo4j 开关、索引和归并窗口共用 `Config/runtime-defaults.env`；当前默认模型为 `gpt-5.6-sol`，实际请求允许环境覆盖，历史评测模型不代表当前默认值。

| 数据 | 上报或写入路径 | 项目读取 |
| --- | --- | --- |
| 日志 | 业务 OTLP → Collector → OpenSearch `fde-logs-*` | 按事故范围执行 PPL 查询 |
| 指标 | 业务 OTLP → Collector `:9464` → Prometheus | 使用服务、环境等标签执行 PromQL |
| Trace | 业务 OTLP → Collector → OpenSearch `fde-traces-*` | 读取事故 Span 与调用关系 |
| 图谱 | Kubernetes 资源观测、实际 Trace 调用边 → Neo4j | 按事故时刻和获知截止时间封存 |

K8s 已声明日志、指标和 Trace 三类诊断 Provider 及后端地址，补充 Collector、OpenSearch、Prometheus 和 Neo4j 的服务与存储；这只是仓库清单，还未应用到集群。本地 Browser 端口为 `7474`，Bolt 为 `7687`，只映射本机；本地 OpenSearch REST 使用 HTTP 与认证，K8s 使用 HTTPS 与受信 CA，不能用关闭 Node.js TLS 校验替代证书配置。

字段与索引也要匹配：日志使用 OTel 的 `severity.number`，Trace 解析对应的时间、时长和状态字段；默认 PromQL 需要 `service_name`、`deployment_environment` 标签，由 Collector 显式映射。Trace 在未单独配置凭证时复用日志凭证，不在笔记保存真实密码。

开启 FDE 的 OTel 只采集 FDE；被诊断业务仍须插桩并接入 Collector，提供与事件一致的服务、环境、命名空间和集群属性。filelog 只读取 FDE 日志卷，不自动收集所有 Pod 标准输出；默认 Pod 重启查询还需要 kube-state-metrics 或明确的自定义查询。凭证、TLS 证书、存储权限、业务接入和完整查询链均未验证，操作说明见 [[0.核心问题汇总]] 的部署入口。

## 54. 日志、指标和 Trace 怎样互相补充？为什么不能拿到三种就下结论？

**口述回答：** 日志告诉我们错误内容，指标告诉我们频率、负载和持续变化，Trace 帮助定位哪段调用失败。它们应该围绕同一资源与时间范围比较，而不是把三个独立截图拼成一个故事。

例如发布后接口超时：日志显示连接错误，指标显示失败率变化，Trace 指向数据库调用。它们共同增强下游连接问题，但仍不能单独区分错误地址、数据库故障或网络阻断；需要变更和针对性观测。

同时，多个产物可能来自同一请求，不具备统计独立性。重复表达同一事实，不等于多份独立支持。

**边界：** Trace 只反映已采集调用，不能凭没有 Span 排除某个依赖；指标缺少样本或标签不匹配，也不能用平稳曲线证明事故不存在。

## 55. 为什么事故遥测要单独封存？什么时候采集，缺失怎么处理？

**口述回答：** 实时后端会继续变化，按事故范围保存查询结果，才能让后续诊断与修复比较知道自己用了什么材料。

当前事故处理在应用、环境、集群、命名空间、受影响资源和时间范围内分别采集日志、指标与 Trace，将结果保存为证据产物。事故窗口根据来源事件界定并向前留出调查范围，不是无限制拉取所有历史。

每类来源记录可用、缺失或退化原因，查询截断、后端失败、指标无有效信号都不能被抹成“采集成功”。这些状态进入上下文质量与结论约束。

**边界：** 封存让内容可追溯，不自动保证采集全量、来源独立或语义正确。尤其日志组本身仍然是摘要，不能因为被保存为产物就提升为直接根因证明。

## 56. 怎样避免日志与图谱把模型引向一个听起来合理但错误的解释？

**口述回答：** 用固定检验命题、当前证据和竞争解释来约束导航。图负责找关联对象，日志组负责定位现象，两者都不能替模型预先宣布答案。

例如图中某 Pod 属于最近的发布，日志组中连接超时很多，只能提出“是否与这次发布相关”的调查。还要比较旧版本、实际变更及下游状态；若旧版本也失败，发布配置候选就不能因为“最近有变更”继续占优。

操作上，将图线索与原始证据分开记录，针对候选读取材料，检查身份、时间、完整性和引用；对冻结的必要关系检查可信矛盾，缺失保持未知。已知信号一致性门禁只匹配根因文本，摘要中的 OOM 等已知症状不能替未知根因通过检查，最后由控制器限制结论等级。

**追问：图中关联越多是不是越可信？** 不是。一个高连接节点可能只是常见依赖，重复投影也不是独立观测。关系数量与因果强度没有自动等价关系。

## 57. Kafka、Fluentd、MongoDB、ClickHouse、Flink 是当前项目必需的吗？

**口述回答：** 就当前项目的诊断主链路和已核对配置而言，这几项不是必需组件，不能把招聘要求中的名单全部写成项目已使用技术。

当前事件消息链路使用 Redis Streams；可观测性采集使用 OpenTelemetry Collector，日志和 Trace 进入 OpenSearch，指标使用 Prometheus；Neo4j 提供关系导航与拓扑裁剪材料，PostgreSQL 保存业务记录。这些分工按仓库实现解释，实际部署状态另行验证。

Kafka 可承担不同规模的事件消息需求，Fluentd 属于日志采集方案，MongoDB 是文档存储，ClickHouse 偏分析型存储，Flink 用于流处理；有相邻能力不代表本项目已采用，也不代表必须把现有组件换掉。

**追问：岗位要求这些，你不需要学吗？** 要区分岗位能力与项目依赖。可以说明理解消息消费、日志采集、查询分析等通用原理，再如实说本项目采用什么；没有实践的组件不要声称有生产经验。是否迁移应由真实负载和需求驱动，不由技术名词数量决定。
